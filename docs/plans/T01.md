## 0 一页总览

T01 是地基：T02–T08 五条线要并行开工，靠的是 T01 定下来的三样东西——crate 边界、协议、领域类型。本方案的关键决定：

| 决定 | 内容 | 依据 |
| --- | --- | --- |
| 17 个 crate，放 `crates/` 与 `client/src-tauri/` | 设计第 2 节的 13 个 + 卡上要求的 `iwork-claude-hook`、`iwork-bench`、`iwork-fake-agent` + Tauri 壳 `iwork-client`（第 2 节） | 设计 2；卡「范围 1」 |
| 依赖方向写成数据文件 `scripts/deps-policy.toml`，`check-deps.sh` 读它检查传递闭包 | 加一个 crate = 加一行；策略与检查分离，自测用注入了违规的 `cargo metadata` 快照 | 设计 2「依赖只向下」；good-code「登记表」 |
| Protobuf 一个包 `iwork.v1`，8 个文件；事件只定义一次，存储与推送共用 | 持久事件的载荷和推给客户端的事件是同一个 proto 消息（第 3 节） | 设计 3.4、5.2 |
| 协议兼容靠两样：只增不减的 `FileDescriptorSet` 契约双向比对 + 二进制金样本跨语言解码 | 已登记字段的编号、类型、名字任何一个变了 CI 就红；新加字段不登记也红；破坏性变更只能升主版本，数据库门、握手门、契约目录共用这一个号；Rust 与 TS 解同一批样本，保证两边线格式一致 | 设计 3.3「字段只增不改号」、10.2 |

| ID 一律 ULID，按实体生成强类型 newtype | 时间有序、26 字符、`domain` 不做 I/O（生成走端口） | 卡「范围 3」；设计 5.3 |
| 状态机写成「转换表 + 纯函数」，表外转换返回错误 | 回合、审批、亲手执行卡片、对话、消息、项目路径六张表（第 4 节）；测试分正向逐条、反向逐对、手写场景、不变量、对桩实现的对照五类，空实现过不了 | 需求 12；设计 6.4、7.3 |
| 端口用原生 `async fn`/RPITIT 加 `Send`，静态分发 | 不引 tokio、不引 `async-trait`；core/app 对端口类型泛型，daemon 组合时落实（第 5 节） | 设计 2「ports 不依赖任何框架」 |
| 事件编解码与投影是端口 | store 收 domain 事件，编码经注入的 `EventCodec`，在线提交与历史重建走同一个 `Projector`；store 不依赖 proto（5.2） | 设计 2 的依赖表、5.2 |

## 1 现状与约束

**现状**：仓库只有文档和团队配置，没有代码、没有根 `.gitignore`、没有 `docs/plans/`。本机开发环境：Homebrew 的 rustc 1.83（没装 rustup）、node 26.5、protoc 29.2；没装 pnpm 与 cargo-deny。Rust 2024 edition 需要 rustc ≥ 1.85（edition guide），所以实施前要先装 rustup 并按 `rust-toolchain.toml` 拉工具链；这是环境准备，不是设计问题，写进第 11 节第 0 步。

**约束**（都来自 `AGENTS.md` 与设计第 2 节，T01 是第一次把它们落成可执行检查）：

- 依赖只向下：`domain`、`ports` 不依赖框架与 I/O（含 tokio）；`core` 不知道 SQLite、git、ACP；只有 `daemon` 知道全部实现。违反即 `important`。
- 后台服务只通过 AgentPort 说 ACP，厂商差异在适配器；版本控制差异在 VcsProvider。`iwork-domain` 里不出现厂商名与 git 字样（卡「注意」）。
- 状态变化一律经事件；命令只返回受理结果与 `seq`。
- 网页层只渲染；Rust 侧 16ms 合并一次 `ViewPatch`。
- 协议：Protobuf，Rust 用 prost、TS 用 protobuf-es；生成代码不入库；包名带主版本；字段只增不改号。
- 状态机与审批求值是纯函数，有属性测试。
- 安全不变量（`AGENTS.md`）在 T01 的体现：错误码里不能出现任何会携带凭据的字段；`claude auth status` 的登录信息在领域类型里只留 4 个字段；审批结果固定五种，不得新增。

**两问的答案**（good-code「动手前」）：

- 再加一种东西要动几处？加 crate：`Cargo.toml` members 一行 + `deps-policy.toml` 一行。加命令/查询/事件：proto 对应 `oneof` 一个字段 + 领域枚举一个变体 + `iwork-app` 一处映射 + 对拍测试自动覆盖（枚举穷举）。加状态转换：转换表一行。加端口：`iwork-ports` 一个 trait，由需要它的卡加，T01 不预留。
- 改这里牵动谁？proto 牵动全部 crate 与 TS；domain 牵动 core/app/store/agent-acp/vcs-git/host；ports 牵动全部实现 crate。所以 T01 之后改 proto 与 domain 的规则写在第 8 节「出事场景」S1、S2。

### 2.3 `scripts/check-deps.sh`

**目的**：让「依赖只向下」从一句约定变成 CI 红绿（出事场景 S4）。

**手段**：

1. 真值在 `scripts/deps-policy.toml`。两类检查分开定义，别混在一起：**直接依赖许可**只看 crate 自己 `Cargo.toml` 里写的依赖（白名单，精确到 crate 名）；**传递禁用**看会被链接进该 crate 的全部依赖闭包（黑名单，只列 I/O 与框架类 crate）。这样 `thiserror` 背后的 `syn`、`proc-macro2` 不用写进任何白名单，`ulid` 经 `domain` 进到 `ports` 闭包也不会误报。

   ```toml
   [workspace]
   # 传递禁用：出现在闭包里就违规，除非该 crate 的 transitive_exempt 列了它
   io_and_framework = ["tokio", "async-std", "smol", "mio", "rusqlite", "sqlx", "gix", "git2",
                       "agent-client-protocol", "tauri", "hyper", "reqwest", "keyring", "notify-rust"]

   # 工作区 crate 之间的依赖：按闭包检查，列的是「允许出现在闭包里的全部工作区 crate」
   [crates.iwork-domain]
   internal = []
   direct = ["ulid", "thiserror"]           # 直接依赖白名单（normal + build）
   direct_dev = ["proptest"]                # dev 直接依赖白名单；不写这一行表示 dev 不限
   deny_transitive = "normal_build_dev"     # 传递禁用查到哪一层：dev 闭包也不许出现 tokio 等

   [crates.iwork-ports]
   internal = ["iwork-domain"]
   direct = ["thiserror"]
   direct_dev = ["pollster"]                # 跑 future 用的最小执行器，测试 5.2 的假实现
   deny_transitive = "normal_build_dev"

   [crates.iwork-core]
   internal = ["iwork-domain", "iwork-ports"]
   direct = ["thiserror"]                   # T07 加 shell 解析器时改这一行
   deny_transitive = "normal_build"         # 默认值：只查会链接进产物的闭包

   [crates.iwork-app]
   internal = ["iwork-core", "iwork-ports", "iwork-proto", "iwork-domain"]
   # 没有 direct 一行 = 直接依赖不限，只受传递禁用约束
   deny_transitive = "normal_build"

   [crates.iwork-client]
   internal = ["iwork-client-core", "iwork-ipc", "iwork-proto"]   # 闭包完整：client-core 带进来的 ipc 也要列
   transitive_exempt = ["tokio", "tauri"]                           # 这个 crate 本来就该有的框架
   # ……其余 crate 按 2.2 表；daemon 的 transitive_exempt 是整张 io_and_framework
   ```

2. 三条规则逐条说清楚算法（都用 `cargo metadata --format-version 1 --locked` 的 `resolve` 图，或 `--metadata <json>` 读文件）：
   - **工作区内部**：对 crate A 求 normal + build 依赖的传递闭包（`resolve.nodes[].deps`，按 `dep_kinds.kind` 过滤，dev 不算），闭包里的工作区 crate 必须 ⊆ `internal`。查闭包是为了 `ports` 错引 `store` 时 `core` 也红。
   - **直接依赖许可**：只在写了 `direct` 的 crate 上生效。读 `packages[A].dependencies`，`kind` 为 normal 或 build 的外部 crate 必须 ⊆ `direct`，`kind` 为 dev 的必须 ⊆ `direct_dev`（写了才查）。不看闭包，所以宏依赖链不用登记。
   - **传递禁用**：按 `deny_transitive` 决定闭包范围（`normal_build` 或 `normal_build_dev`），闭包里命中 `io_and_framework` 且不在 `transitive_exempt` 的，违规。`domain`、`ports` 用 `normal_build_dev`：它们的测试也必须是纯的。
   - 任一违规打印「crate A 经 B → C 依赖了 X（规则：直接许可 / 传递禁用 / 工作区内部），策略 `scripts/deps-policy.toml [crates.A]`」，退出码 1。
3. `jq` 三平台 GitHub 托管 runner 都自带；本机没有时脚本报「缺 jq」退出 2，不静默跳过。
4. 自测（卡验收 2）：`scripts/check-deps.sh --selftest`，先跑一次真实 `cargo metadata` 存成 JSON，之后全部用 jq 改这份 JSON 喂 `--metadata`，不碰 `Cargo.toml`、不联网。必须覆盖的情况与期望：

   | 用例 | 做法 | 期望 |
   | --- | --- | --- |
   | 合法依赖图 | 原样快照 | 退出 0（真实工作区里 thiserror 的宏链、domain 的 proptest、ports 经 domain 的 ulid、client 经 client-core 的 ipc 都在） |
   | 间接违规（外部） | 在 `ulid` 节点的 deps 里注入 `tokio` | 退出 1，输出含「iwork-domain 经 ulid → tokio」 |
   | 间接违规（内部） | 在 `iwork-ports` 节点的 deps 里注入 `iwork-store` | 退出 1，`iwork-ports` 与 `iwork-core` 两处都报 |
   | dev 依赖违规 | 把 `tokio` 作为 `kind = "dev"` 注入 `iwork-domain` 的 dependencies 与 deps | 退出 1（`normal_build_dev` 生效） |
   | 直接依赖越白名单 | 往 `iwork-core` 的 dependencies 加一个 normal 的 `rand` | 退出 1，规则名为「直接许可」 |

   任一用例结果不符，自测失败。自测在 CI 里是独立一步。
5. 卡上提到的 `deny.toml` 管许可与来源；依赖方向不放 cargo-deny（它的 `bans` 不按 crate 分组，表达不了「只有 daemon 能依赖 rusqlite」）。

### 3.2 帧与握手

帧 = `u32 长度（小端，= 类型字节 + 载荷的字节数）| u8 类型 | Protobuf 载荷`，单帧上限 4MB，`Chunk` 载荷 ≤ 1MB（设计 3.3）。类型字节：

| 值 | 类型 | 方向 | 载荷 |
| --- | --- | --- | --- |
| 1 | `Hello` | 客户端 → 后台 | `Hello{ uint32 protocol_major=1; uint32 protocol_minor=2; ClientKind client_kind=3; string client_version=4; optional bytes resume_token=5 }` |
| 2 | `Welcome` | 后台 → 客户端 | `Welcome{ string session_id=1; string server_version=2; repeated string capabilities=3; uint64 head_seq=4; uint32 protocol_major=5; uint32 protocol_minor=6 }` |
| 3 | `Request` | 客户端 → 后台 | `Request{ uint64 request_id=1; oneof body { Command command=10; Query query=11; Subscribe subscribe=12; Unsubscribe unsubscribe=13 } }` |
| 4 | `Response` | 后台 → 客户端 | `Response{ uint64 request_id=1; oneof body { CommandAccepted accepted=10; QueryResult result=11; Subscribed subscribed=12; Error error=13 } }` |
| 5 | `Event` | 后台 → 客户端 | `Event{ repeated uint32 subscription_ids=1; oneof body { PersistedEvent persisted=10; TransientEvent transient=11 } }`；`PersistedEvent{ uint64 seq=1; google.protobuf.Timestamp at=2; string actor=3; DomainEvent event=4 }` |
| 6 | `Chunk` | 客户端 → 后台 | `Chunk{ string upload_id=1; uint64 offset=2; bytes data=3; bool last=4 }` |

- 主版本不同：后台回 `Response{request_id=0, error{PROTOCOL_VERSION_MISMATCH, details{client_major, server_major}}}` 后断开；客户端显示「正在切换版本」（设计 4）。判断是 `iwork_proto::handshake::check_hello` 纯函数，两个方向（旧客户端 × 新后台、新客户端 × 旧后台）都在 T01 单测里，见 3.7「握手门」；主版本就是包名，所以升主版本后两边的消息类型本身就不同，握手必须先拦。
- 主版本号的真值是 `common.proto` 里的常量注释 + Rust `iwork_proto::PROTOCOL_MAJOR`（从生成的 `FileDescriptorSet` 包名 `iwork.v1` 解析出来，不手抄第二份）。
- `ClientKind`：`DESKTOP`、`DEV_TOOL`。桥接与 hook 在 M1 不接 IPC（ACP 走 stdio），所以 7.2a「只接受来自客户端连接的请求」在 M1 等价于「来自通过了对端校验的 IPC 连接」；T03 实现校验，T10 在 `ExecuteUserAction` 受理时断言连接类型。
- `CommandAccepted{ uint64 first_seq=1; uint64 last_seq=2; bool replayed=3 }`：`replayed` 表示这是幂等重发命中的旧结果（设计 5.2）。命令不返回状态。
- `Subscribe{ uint32 subscription_id=1; SubscriptionScope scope=2; uint64 from_seq=3 }`；`Subscribed{ uint32 subscription_id=1; optional Snapshot snapshot=2; uint64 snapshot_seq=3 }`（`from_seq` 太旧时带快照，设计 3.5）。`SubscriptionScope` 是 `oneof { Sidebar; Conversation{id}; Pending; Quota; RuntimeStatus; Settings }`。
- 流式增量 `TransientEvent{ oneof { MessageDelta{ message_id, offset, text }; ToolOutputDelta{ tool_call_id, offset, text }; CloneProgress{ job_id, phase, percent, text }; SubscriptionLagging{ subscription_id, last_seq } } }`，不落盘、不带 `seq`（设计 3.5）。

prost 配置：`bytes` 字段生成 `bytes::Bytes`（零拷贝，事件推送是热路径）；输出 `FileDescriptorSet` 到 `OUT_DIR` 并以 `include_bytes!` 暴露为 `iwork_proto::FILE_DESCRIPTOR_SET`，供 3.7 的兼容测试使用。

`ReadArtifact` 的规则（T01 定协议与端口，T02 实现存储，T10 实现受理）：

- `ArtifactRef{ string sha256 = 1; ArtifactArea area = 2; uint64 size = 3 }` 定义在 `common.proto`；`ArtifactArea` 只开放 `ARTIFACTS` 与 `ATTACHMENTS`，`PRIVATE`（凭据附件存档）经此查询一律返回 `PERMISSION_DENIED`。
- 身份：只接受通过了对端校验的 IPC 连接（3.2 的 `ClientKind`），与 `ExecuteUserAction` 同一条判断；T10 受理时断言。
- 范围：引用必须被当前数据库里的某条消息、工具调用、附件或亲手执行卡片引用（`ReadModelPort::artifact_is_referenced`），否则 `ARTIFACT_NOT_FOUND`——客户端拿不到的引用就读不到，制品存储里的孤儿对象也读不到。
- 分段：`limit` 上限 1MB（与 `Chunk` 一致，保证一帧远在 4MB 以下）；`offset > total_size` 返回 `ARTIFACT_RANGE_INVALID`；`offset == total_size` 返回空 `data` 且 `eof = true`；`offset + len(data) == total_size` 时 `eof = true`。客户端按 `eof` 判断读完，不靠猜大小。
- 查询结果不带 `seq`（制品不可变），`QueryResult.seq` 填当前 `head_seq` 即可。

### 3.4 关键消息的字段与编号

只列会被多张卡同时依赖、改起来最疼的几个；其余消息在实施时按同样风格定义，编号从 1 起连续分配。

```protobuf
// common.proto
message Error {
  ErrorCode code = 1;
  string message = 2;            // 给人看的中文说明；不含路径以外的用户数据，不含凭据
  bool retryable = 3;
  map<string, string> details = 4;  // 机器可读的补充，如 "path", "expected_version"；禁止放凭据
}

enum ErrorCode {
  ERROR_CODE_UNSPECIFIED = 0;
  // 通用 1–19
  INVALID_ARGUMENT = 1; NOT_FOUND = 2; ALREADY_EXISTS = 3; CONFLICT = 4;      // CONFLICT：expected_version 不符
  PRECONDITION_FAILED = 5; PERMISSION_DENIED = 6; UNAVAILABLE = 7; INTERNAL = 8;
  CANCELLED = 9; TIMEOUT = 10; PAYLOAD_TOO_LARGE = 11;
  // 协议与连接 20–29
  PROTOCOL_VERSION_MISMATCH = 20; PEER_REJECTED = 21; MALFORMED_FRAME = 22; SUBSCRIPTION_TOO_OLD = 23;
  // 存储 30–39
  STORAGE_FAILURE = 30; MIGRATION_FAILED = 31;
  // 运行时与模型 40–59（设计 9.6 第 7 条要求三种模型不可用原因可区分）
  RUNTIME_NOT_FOUND = 40; RUNTIME_INCOMPATIBLE = 41; RUNTIME_NOT_LOGGED_IN = 42; RUNTIME_CHANGE_FORBIDDEN = 43;
  MODEL_NO_PERMISSION = 44; MODEL_RETIRED = 45; MODEL_OVERLOADED = 46; MODEL_UNKNOWN = 47;
  // 对话与回合 60–69

### 3.6 领域事件 ↔ proto 的单一真值

事件在 proto 里只定义一次；`iwork-domain` 有对应的 Rust 枚举 `DomainEvent`（domain 不能依赖 proto，见 2.2）。两份靠一条对拍测试绑在一起（good-code「抄不了的配对拍测试」）：

- 转换写成普通函数，放在 `iwork_app::convert`：`pub fn event_to_proto(&domain::DomainEvent) -> proto::DomainEvent` 与 `pub fn event_from_proto(proto::DomainEvent) -> Result<domain::DomainEvent, ConvertError>`。不写 `impl From<domain::DomainEvent> for proto::DomainEvent`：两个类型对 `iwork-app` 都是外部类型，孤儿规则不允许。命令、查询、模型类型的 domain ↔ proto 转换照同样写法，全部是 `convert` 模块里的函数（或 app 自己定义的本地 trait），不用 `From`/`TryFrom`。
- 这对函数同时就是 `EventCodec` 端口（5.2）的实现 `ProtoEventCodec`：`encode` = `event_to_proto` + prost 编码，`decode` = prost 解码 + `event_from_proto`。存储层（T02）通过这个端口编解码事件，自己不依赖 proto（见 F-1 的接缝说明，5.2「事件编解码与投影」）。
- proptest `domain_event_proto_roundtrip`：任意 `domain::DomainEvent` → `event_to_proto` → `event_from_proto`，等于原值；`domain_event_kinds_match_proto_oneof`：用 `FILE_DESCRIPTOR_SET` 枚举 proto `DomainEvent` 的全部 oneof 字段名，与 `domain::DomainEvent::KINDS`（`&'static [&str]`，也是 `events.type` 列的取值）逐一对应，少一个多一个都红。
- `ConvertError` 带 `kind` 与字段名，解不出来时点名；它映射到 `ErrorCode::INTERNAL`，因为同一程序写进去的事件解不回来只可能是代码缺陷。

### 3.7 `proto/compat/`：兼容样本怎么组织

```
proto/compat/
  README.md                       # 本节规则
  v1/contract.binpb               # 主版本 1 的兼容契约：承诺不变的全部字段，只增不减（见下）
  v1/samples/<Message>.<n>.binpb  # 二进制金样本，用当时的类型编码；只增不改
  v1/samples/<Message>.<n>.txtpb  # 同一样本的 text format，人读、也作期望值
```

**目的**：任何一个已经进过契约的字段，之后改号、改类型、改名、删掉，CI 都要红；新加的字段一进仓库就自动受同样的保护，而不是只保护 T01 那一刻的字段。

**身份只有一个：协议主版本。** 契约目录、proto 包名（`iwork.v1`）、握手里的 `protocol_major`、数据库 `meta.protocol_major`、`EventCodec::protocol_major()` 都是同一个数，真值是 proto 包名，Rust 侧 `iwork_proto::PROTOCOL_MAJOR` 从 `FILE_DESCRIPTOR_SET` 的包名解析出来，不手抄。不另设「谱系号」这类第二套身份（AGENTS.md 安全设计原则：不为堵一个缺口引入一串新机制）。

**两种操作分开**：

- **契约随新增单调扩充**（日常开发唯一允许的操作）：`cargo run -p iwork-proto --example update-contract -- --additive`。它把当前 `FILE_DESCRIPTOR_SET` 里契约还没有的消息、字段、枚举值追加进 `v<N>/contract.binpb`；对契约里已有的任何条目，只要当前描述符与它不一致（编号、类型、label、名字、oneof 归属）或当前已没有这个条目，工具拒绝写入并逐条列出差异，退出码 1。
- **破坏性变更 = 升主版本**：把包名改成 `iwork.v2`，新建 `proto/compat/v2/`，旧的 `v1/` 目录原样保留（旧程序的契约仍在仓库里可查）。没有「在 v1 里重置」这个操作；`update-contract` 不提供 `--reset`。允许升主版本的条件：产品负责人书面同意，且按下文「旧库与旧客户端怎么办」把门槛走完。M1 开发期也一样——与其让 dev 库被错读，不如改个包名。

**两条 CI 测试**（`iwork-proto/tests/compat.rs`）：

1. **契约比对**，双向：
   - 契约 → 当前：契约里每个字段「同名、同编号、同类型、同 label、同 oneof 归属」，每个枚举值「同名、同值」；契约里有、当前没有的字段一律报错——同一主版本内不准删，只能标 `deprecated = true` 留着；删字段是升主版本的事。
   - 当前 → 契约：当前描述符里每个字段、枚举值都必须在契约里。新加字段忘了跑 `update-contract --additive` 就红，错误信息直接给出要跑的命令。这样「新增进契约」不靠自觉。
   - `view.proto` 排除在外（只在客户端进程内传，不落盘，见 S8），排除清单写在测试里并注明理由。
2. **样本解码**：每个 `.binpb` 用当前类型解码，再编成 text format 与 `.txtpb` 比对（卡验收 4「旧版本消息样本解码新版本类型通过」）。

**两步测试**（契约比对函数的单元测试，构造合成的 `FileDescriptorProto`，不依赖仓库文件）：

1. 契约 C0 含消息 `M{a=1}`；描述符 D1 = `M{a=1, b=2}`；`additive_update(C0, D1)` 得 C1，断言 C1 含 `b=2`；`check(D1, C1)` 通过。
2. 描述符 D2 = `M{a=1, b=3}`（把刚进契约的 b 改号）；`check(D2, C1)` 必须失败，错误里点名 `M.b 2 → 3`；`additive_update(C1, D2)` 也必须拒绝。
3. 对照：D3 = `M{a=1, b=2, c=3}` 用 C1 检查，报「c 不在契约里」；跑 `additive_update` 后通过。

TS 侧 `client/src/gen.test.ts` 对同一批 `.binpb` 用 protobuf-es 的 `fromBinary` 解码并与 `.txtpb` 对应的 JSON 期望比对，证明 Rust（protox）与 TS（buf）两条生成链路产出同一线格式。

样本由 `cargo run -p iwork-proto --example dump-compat -- proto/compat/v1/samples` 生成，内容是手写的构造函数（每个关键消息至少一条，字段尽量填满）。样本只增不改：加了新字段想保护它的取值，就再加一个带新编号的样本文件，旧样本不动。

**旧库与旧客户端怎么办（升主版本的门与恢复）**

技术设计 5.5 的迁移只向前，schema 版本 +1 不会让旧库被拒绝，它会试着迁移，然后用新类型去解旧编码的事件——这正是要防的。所以门不走 schema 版本，走协议主版本，三处用同一个数：

1. **数据库门**：`meta` 表记 `protocol_major`（T02 建表时加这一列，值取 `iwork_proto::PROTOCOL_MAJOR`）。后台服务启动时比对：库里的主版本 ≠ 程序的主版本 → 先 `VACUUM INTO backups/<时间>-v<旧>.db`（复用 5.5 的备份机制，备份失败照样拒绝并说明）→ **拒绝启动**，日志与客户端诊断页写明「数据库是协议 v1，程序是协议 v2，不能读取；数据库未改动，备份在 …」。不迁移、不删除、不自动做任何写入。
2. **握手门**（设计 3.3 已有，这里把两个方向都写死）：`Hello.protocol_major ≠ 服务端 PROTOCOL_MAJOR` → 服务端回 `Response{request_id = 0, error{PROTOCOL_VERSION_MISMATCH, details{client_major, server_major}}}` 后断开；客户端收到这个错误码显示「正在切换版本」（设计 4）。因为主版本就是包名，v1 客户端的 `Command` 与 v2 后台的 `Command` 根本不是同一个消息类型，连上也只能解出垃圾，所以握手必须先拦。这个判断是纯函数 `iwork_proto::handshake::check_hello(&Hello, server_major) -> Result<(), Error>`，T01 实现并测两个方向：旧客户端（major 1）× 新后台（major 2）→ 错误；新客户端（major 2）× 旧后台（major 1）→ 错误（旧后台跑的也是这个函数，所以行为一致）；同主版本、不同次版本 → 通过。T03 把它接进真实连接后，再在集成测试里跑一遍两个方向（交接用例 A）。
3. **契约门**：`proto/compat/v<N>/` 与包名一致；`compat.rs` 断言「契约目录名里的 N == PROTOCOL_MAJOR」，改了包名忘建新目录就红。

**数据怎么前进**——只承诺一件事：**旧库原样保留 + 回退旧程序即可用**。不承诺「旧数据带进新主版本」。原因：字段改名、改类型、拆消息时，通用的「导出 JSON 再导入」走不通，而且事件不只是载荷，还有信封（`seq`、`at`、`actor`、`command_id`）、`commands` 幂等表、`outbox`、制品引用计数，泛泛的导出导入漏掉任何一样都是数据损坏。所以把它写成**门槛**而不是机制：真要发生某一次 v<N> → v<N+1> 的升级、又要带数据，升级前必须为这两个具体版本写一个显式转换程序，范围覆盖事件信封、幂等记录、outbox、制品引用，并做一次无损演练（旧库 → 转换 → 新库 → 重建投影 → 与旧程序的投影逐表比对），演练通过才允许改包名合入。没做这件事就只能回退。现在不写任何导出导入代码。

4. 演练（第 11 节第 9 步，交接用例 A）：造一个 `meta.protocol_major = 1` 的库 → 用把 `PROTOCOL_MAJOR` 编译成 2 的测试构建启动 → 断言拒绝启动、备份文件存在、原库哈希不变；用正常构建（major 1）启动 → 正常。数据库门归 T02，诊断页归 T04，需要加进它们的卡并补技术设计 5.5、3.3，见第 10 节 Q5。

这整节写进 `proto/compat/README.md`，审查时按它判。

## 4 领域模型

全部在 `iwork-domain`，无 I/O、无时间读取、无随机数。模块：`id`、`project`、`assistant`、`conversation`、`message`、`turn`、`approval`、`user_action`、`rule`、`security_list`、`attachment`、`runtime`、`settings`、`event`、`error`。

### 4.1 ID：ULID，强类型 newtype

**目的**：ID 混用（把 `ProjectId` 传进要 `ConversationId` 的地方）在编译期就报错；ID 按时间有序，消息与事件按 ID 排序即按创建顺序，SQLite 索引局部性好；一种 ID 全仓一个格式。

**手段**：

- `ulid` crate `default-features = false`（不拉 `rand`、不拉 std 时间），domain 只用它的 128 位值、Crockford base32 编码与解析。
- 宏 `define_id!(ProjectId, "project")` 生成 `pub struct ProjectId(Ulid)`，实现 `Display`（26 字符）、`FromStr`（校验长度与字符集，失败返回 `IdParseError{ kind, input }`，点名）、`Ord`、`Hash`、`Copy`。
- 生成走端口：`iwork-ports::IdGenerator::next(&self) -> RawUlid`，domain 提供 `ProjectId::from_raw(RawUlid)`。实现（daemon）用单调 ULID 生成器（同一毫秒内递增随机部分），保证同毫秒内仍有序。
- 一共 13 个：`ProjectId`、`AssistantId`、`ConversationId`、`MessageId`、`TurnId`、`ApprovalId`、`UserActionId`、`RuleId`、`SecurityEntryId`、`AttachmentId`、`RuntimeId`、`CommandId`、`JobId`（克隆、草稿等后台作业）。另有 `ReviewId`：包住 `TurnId` 的 newtype，值就是那次 AI 审查系统回合（`TurnKind::SystemAiReview`，设计 7.2b）的 `TurnId`，proto 侧仍是 string（主管 2026-11-09 裁定）。`Seq` 是 `u64` newtype，不是 ULID。
- 为什么不用 UUID v4：无序，十万条消息的键集分页要靠额外的 `created_at` 索引；UUID v7 有序但 36 字符；ULID 26 字符、生态成熟（设计 5.3 的分页需求）。与设计 8.2「项目 UUID」措辞的关系见第 10 节 Q1。

### 4.3 状态转换表

**目的**：状态机漏一条转换时，是在表里看出来、在 proptest 里红出来，而不是在用户的回合里卡死（出事场景 S2）。

**手段**：每个状态机一个 `const TRANSITIONS: &[(State, Trigger, State)]`，一个纯函数 `fn next(state, trigger) -> Result<State, IllegalTransition{ state, trigger }>`，表外转换返回错误并点名；实体的 `apply` 只调它。触发器就是领域事件或命令的名字，不另造一套词。

**测试怎么写**（回合、审批、亲手执行卡片三张表都照这套，防「永远返回 `IllegalTransition` 的空实现也能全绿」）：

1. **正向逐条断言**：遍历 `TRANSITIONS` 的每一行 `(s, t, s')`，断言 `next(s, t) == Ok(s')`。这是表驱动的，表有多少行就有多少条断言。
2. **反向逐对断言**：对 `State × Trigger` 的全部组合，不在表里的断言 `next(s, t) == Err(IllegalTransition{s, t})`。状态与触发器都实现 `strum::IntoEnumIterator`（或手写 `ALL` 常量）保证穷举。
3. **手写场景**（期望值不从表推，防表本身写错）：每张表至少三条完整序列，例如回合 `Queued → Started → PermissionAsked → PermissionDecided → Completed`、`Running → Cancel → ProcessEnded`、`WaitingApproval → WaitLimitReached → Resume → Completed`，断言每一步的状态。
4. **不变量 proptest**：随机触发序列下只发生表内转换；终态之后任何触发都是 `IllegalTransition`；`Denied` 永不变 `Approved`；每个非终态可达终态（穷举图搜索）。
5. **对照用例**：把 1–4 包成 `fn verify_machine<S, T>(next: fn(S, T) -> Result<S, _>, table: &[(S, T, S)]) -> Result<(), Vec<Mismatch>>`，再写一条测试：对 `always_illegal`（任何输入都返回 `IllegalTransition`）和 `always_identity`（任何输入都返回 `Ok(s)`）两个桩调用 `verify_machine`，断言它们**都返回 `Err`**。这条红了，说明验证函数本身失效。

| `InProgress{id}` | `ModeSwitchAllows`（切到全开） | 主状态 → `Approved{ModeSwitch}`，子状态保持 `InProgress`，之后的结果一律 `Stale` |

子状态的每一次变化都是持久事件 `ApprovalReviewUpdated{ approval_id, review_id, review, reason }`（3.3 事件 111），`review_id` 与 `ABANDONED` 都在里面；查询模型 `Approval.review_id` 同步落盘。重建投影后的审批带着和在线一样的 `review_id` 与子状态，迟到结果的判定在重建后和重建前一样。

**AI 审查「通过」的生效条件**（三条同时满足，缺一即丢弃）：① 触发里的 `review_id` 等于当前 `InProgress{review_id}`——对应的是这一次审查，不是上一轮或别的审批的；② 主状态仍是 `Pending` 且子状态仍是 `InProgress`——没有超时转交用户、没有被用户决定、没有被模式切换放行；③ 调用方传入的当前有效档位是 `Auto`——用户已经切回手动的话，AI 审查不算数。为此审批的 `apply` 签名是 `fn apply(&mut self, trigger: ApprovalTrigger, ctx: &ApprovalContext{ mode_now: ApprovalMode }) -> Result<Applied, ApprovalApplyError>`，其中 `ApprovalApplyError::Stale{ trigger, why }` 与 `IllegalTransition` 区分：`Stale` 是预料之中的乱序结果，不是程序缺陷；`IllegalTransition` 才是缺陷。迟到的 `AiReviewFailed`/`TimedOut` 用同一套条件，过期同样丢弃。

**`Stale` 的落盘规则**：`Stale` **不**产生 `ApprovalReviewUpdated`，不改 `approvals` 投影的任何列，只写一条 audit 流的 `ApprovalStaleResultDropped{ approval_id, review_id, result, why }`（3.3 事件 111a）；`Projector` 对它只追加审计表，不碰审批表。所以「Stale 前后审批状态完全不变」在事件层面就成立：审批流里根本没有多出事件。

`Pending && review == InProgress` 不计入「待你处理」（用户还没被问到）；一旦进入 `Failed/Errored/TimedOut/Abandoned`，就计入。

乱序用例（T01 交付，单测）：
1. `InProgress{r1}` → `AiReviewTimedOut{r1}`（→ 问用户）→ 迟到的 `AiReviewPassed{r1}`：结果 `Stale`，主状态仍 `Pending`，用户随后 `UserAllow` 才 `Approved{User}`。
2. `InProgress{r1}` → `ModeChanged{Manual}`（→ `Abandoned`）→ `AiReviewPassed{r1}` 且 `mode_now = Manual`：`Stale`，仍 `Pending`。
3. `InProgress{r1}` → `UserDeny`（用户在超时前直接拒了）→ `AiReviewPassed{r1}`：`Stale`，仍 `Denied`，`Denied` 永不变 `Approved` 在这里也成立。
4. 对照：`InProgress{r1}` → `AiReviewPassed{r1}` 且 `mode_now = Auto`：`Approved{AiReview}`。
5. 错 id：`InProgress{r2}` → `AiReviewPassed{r1}`：`Stale`。
6. **重建后仍能判**（`iwork-app` 测试 `approval_review_identity_survives_rebuild`，用 `ProtoEventCodec` + `ports/tests/fakes.rs` 的内存 store）：`ApprovalRequested` → `AiReviewStarted{r1}` 两条事件经 codec 编码提交 → 清投影、`rebuild_projections` 解码重建 → 取出审批，断言 `review == InProgress{r1}`；对它 `apply(AiReviewPassed{r2})` → `Stale`，深比较审批前后完全相同，事件日志只多一条 audit 流的 `ApprovalStaleResultDropped`、审批流无新事件；再 `apply(AiReviewPassed{r1}, Auto)` → `Approved{AiReview}`。

`Void` 的原因枚举 `VoidReason`（需求 12 与设计 7.3 第 5 条、9.0、9.1a 逐条对应）：`TurnCancelled`、`ConversationDeleted`、`TurnAbandonedAfterInterrupt`、`AssistantDeleted`。**没有** `ApprovalWaitLimit` 这个原因——hook 超时防护引起的中断不作废，类型上就写不出来。

测试按上文五类写；本表特有的不变量：`Denied` 永不变 `Approved`；三个终态不再转换；`Voided` 只能由上面四个原因之一触发；`Stale` 永不改变主状态。

**亲手执行卡片 `UserActionState`**（设计 7.2a）

| --- | --- | --- | --- |
| `Pending` | `Execute{hash 校验通过}` | `Starting` | app 校验哈希后进入；此时还没起进程 |
| `Pending` | `Dismiss` | `Dismissed` | 回给 Agent「用户未在 iWork 中执行」 |
| `Pending` | `Void{reason}` | `Voided` | 原因同审批 |
| `Starting` | `Spawned` | `Executing` | 进程起来了，后台服务持有 `ExecutionHandle`（只在内存里，不落盘） |
| `Starting` | `SpawnFailed{error}` | `Failed{error}` | **明确知道没起来**（`spawn` 系统调用返回错误：找不到程序、权限不够）；终态。卡片显示原因与「复制命令」，Agent 收到「用户执行失败：<error>」。不自动重试 |

| `Starting` / `Executing` / `Stopping` | `ProcessLost` | `Unknown{error: "后台服务中断"}` | **崩溃恢复（做法 A，产品负责人 2026-11-09）**：三个状态一律转结果未知。`Starting` 的进程可能已起来并产生了副作用（`Spawned` 没来得及提交）；`Executing`/`Stopping` 的进程已不是子进程。iWork 不判断它是否还活着、不去停它 |

终态：`Done`、`Ended`、`Failed`、`Dismissed`、`Voided`。**`Unknown` 不是终态**：它表示「结果未知、iWork 已不再跟踪」，用户确认前不算结束。`Ended` 没有载荷：它只由用户确认产生（正常流程的结束都走 `Done{exit}`，没有别的取值要区分）。

- **结果不确定时的策略**（需求 12「结果不确定时先对账再决定」「不静默重放」）：进入 `Unknown` 的卡片程序**绝不**自动重跑，也**绝不**自动判为结束；Agent 收到「用户已执行，结果未知」。卡片显示「执行结果未知，iWork 无法核对，请自行确认」、命令、已收到的输出，和「我已核对」按钮（发 `ConfirmUserActionEnded`）。
- **不记进程身份**：事件与查询模型里没有 pid。崩溃后 iWork 停不了崩溃前起的那条命令、也不知道它跑完没有，由用户自己处理——登记为已知限制（第 8 节末尾）。不为这个缺口加 pid 对账、进程启动时间比对这一串机制（AGENTS.md 安全设计原则）。
- `Executing`/`Stopping`/`Unknown` 不接受 `Void`：进程是用户本人起的。**删除对话或助手碰上这些卡片**：`DeleteConversation` 的 `Deleting` 阶段对持有句柄的 `Executing` 卡片发 `Stop`；所有卡片到终态才 `AllSettled → Deleted`；`Unknown` 的卡片程序确认不了，对话就停在 `Deleting`，界面显示「有一张卡片的执行结果无法核对，请确认后继续删除」，卡片保持可操作（看输出、复制命令、「我已核对」）；用户确认后删除自动完成。`Deleting` 期间仍受理的命令见对话表。
- 档位切换对卡片无影响（7.3 第 6 条），表里没有这种触发。`proposal_hash` 校验在 `Execute` 触发之前由 app 做，不符返回 `USER_ACTION_HASH_MISMATCH`。
- 恢复演练（`ProcessLost` 一行、`Unknown` 下的删除）排进第 11 节第 9 步与附录 B；归 T04 验收 3（产品负责人 2026-11-09 已按默认定，见 Q6）。

    ProjectConversation { member_override: Option<ApprovalMode>, conversation_setting: Option<ApprovalMode>, project_default: ProjectDefaultMode },
    /// 助手私聊：不跟随 iWork 对话；有自己的覆盖值；按所选项目的默认档位；未选项目时手动（FR11）
    AssistantDm { own_setting: Option<ApprovalMode>, selected_project_default: Option<ProjectDefaultMode> },
}
pub fn effective_mode(inputs: &ModeInputs) -> ApprovalMode
```

规则：
- 项目对话：`member_override` > `conversation_setting` > `project_default`。
- 私聊：`own_setting` > `selected_project_default`；没选项目时 `selected_project_default = None` → `Manual`。私聊在自己的对话里切到全开，立即生效（`own_setting = Some(FullAccess)`）；iWork 对话里的 `conversation_setting` 根本不在私聊的输入里，所以不可能「跟随」。
- `DmProjectSwitched` 事件把该私聊的 `own_setting` 清成 `None`（FR11「切换项目时全开失效，回到该项目的默认档位」；这里把 Auto 覆盖一并清掉，是对「回到该项目的默认档位」的直读；若产品负责人想保留 Auto 覆盖，只改这一行）。
- `project_default` 的类型是 `ProjectDefaultMode{ Manual | Auto }`，所以「项目默认全开」在类型上写不出来（FR11「不能设为项目默认」）。

用例（`effective_mode_table`，FR11 原文逐句一行，期望值手写不从实现推）：
1. 项目对话，无任何设置 → 项目默认（Manual / Auto 各一例）。
2. 项目对话，iWork 切到 Auto，某成员单独设置 Manual → 该成员 Manual，其他成员 Auto。
3. 项目对话，切到全开 → 全开（即时生效）；该成员单独设置 Manual 的仍为 Manual。
4. 私聊，选了项目 P（默认 Auto），无自己的设置 → Auto；iWork 在 P 的对话里切到全开，对私聊**无影响**，仍 Auto。
5. 私聊，自己切到全开 → 全开，立即生效。
6. 私聊，全开状态下切换到项目 Q（默认 Manual）→ `DmProjectSwitched` 清空 → Manual。
7. 私聊，未选项目 → Manual；未选项目时自己切到 Auto → Auto（覆盖仍可用）。

## 5 端口（`iwork-ports`）

### 5.1 异步写法

**目的**：`ports` 不依赖 tokio，也不引 `async-trait` 这类宏 crate；实现放进 tokio 多线程运行时要能 `spawn`。

**手段**：原生 `async fn` 的返回类型没法加 `Send`，所以统一写 RPITIT 形式：

```rust
fn open_session(&self, spec: SessionSpec) -> impl Future<Output = Result<Self::Session, AgentError>> + Send;
```

所有 trait `: Send + Sync`。代价是不能 `dyn`；`core`/`app` 对端口类型泛型（`App<P: Ports>` 聚合 trait，关联类型指向各端口），`daemon` 组合时落实具体类型，测试用假实现。如果某处确实需要动态分发（M2 多运行时同时在线），在 `daemon` 加一个 `Boxed` 适配层，不改 `ports`。这条写进 ADR（第 12 节）。

同步的端口（`Clock`、`IdGenerator`）就是普通方法。

## 7 每条规则的「目的 + 手段」汇总

| 规则 | 目的（防什么） | 手段 |
| --- | --- | --- |
| 依赖只向下 | `core` 里混进 SQLite/git/ACP 后，换实现与纯函数测试都做不到；安全判定被 I/O 细节污染 | `deps-policy.toml` + `check-deps.sh` 查传递闭包，CI 必跑，自测证明它会红 |
| 字段只增不改号 | 老事件、老客户端用新类型解出错值而不报错；新加的字段没人保护 | 兼容契约只增不减、双向比对（忘登记也红）+ 金样本解码；破坏性变更只能升主版本，数据库门、握手门、契约目录用同一个主版本号 |
| 旧数据不被错读 | 升主版本后旧库被迁移吃掉再用新类型解；旧客户端连上新后台解出垃圾 | 数据库门先备份再拒绝启动；握手两个方向都拦；带数据前进不是机制而是门槛（写显式转换 + 无损演练才许合入） |
| 事件只定义一次 | 存储格式与推送格式分叉，回放重建出的视图和实时视图不一致 | 存储载荷就是 `DomainEvent` proto；编解码经 `EventCodec` 端口注入 store；在线与重建走同一个 `Projector` |
| 状态机表驱动 | 漏转换在用户回合里表现为卡死；加一个状态要改一堆 `match`；空实现全绿 | 转换表是 const 数据，`next()` 唯一入口；正向逐条 + 反向逐对 + 手写场景 + 不变量 + 对两个桩实现的对照 |
| AI 审查结果只在本次、进行中、自动档下生效 | 迟到的「通过」放行已经交给用户、已切回手动或用户已决定的审批 | `review_id` + 子状态 `InProgress` + `mode_now = Auto` 三条件；过期结果 `Stale` 丢弃并审计 |
| 亲手执行结果不确定就停 | 崩溃后重跑一条用户只想跑一次的命令，或把没跑完的命令当成已结束 | `Unknown` 非终态，没有任何自动出口，不重跑、不自动判结束；唯一出口是用户点「我已核对」；删除对话等它确认。崩溃后停不了那条命令是已知限制 |
| 五种结果、规则即数据 | 有人加第六种结果或在求值流程里塞特例，底线被绕 | `Verdict` 五变体；`RuleEffect` 没有能把底线变放行的值；T07 只加条目 |
| `LoginInfo` 四字段 | 邮箱等个人信息落盘、进日志 | 结构体只有四字段，proto 注释禁止新增，审查对照 |
| 密钥不进事件 | 密钥随事件日志永久留存、随诊断包导出 | `SetMcpSecret.value` 直通 SecretStore；事件只带 `key_name`；`SecretValue` 不可 Debug/Serialize |
| domain 无厂商名与 git | 核心长出厂商特例，M2 接第二家时要改核心 | 不透明 `RuntimeKind`/`VcsKind`；`check-domain-terms.sh` 进 CI |
| 原生 async + Send，静态分发 | 引入 tokio 或宏 crate 破坏「ports 无框架」；或者没有 Send 导致 daemon 无法 spawn | RPITIT + `Send`；需要 dyn 时在 daemon 包一层 |
| ID 强类型 ULID | ID 串位；分页要额外索引 | newtype 宏；生成走端口；单调生成器 |
| 生成代码不入库 | 手改生成代码后与 `.proto` 脱节 | `OUT_DIR` 与 gitignore 的 `client/src/gen/`；CI 从零生成 |

## 8 出事场景

每条写：会出什么事 / 怎么止血和回退 / 由什么保证。

**S1 协议字段编号定错或被改号**（卡点名的典型场景）
- 会出什么事：T02 已把事件按旧编号写进 `iwork.db`，T09 客户端按新编号解码，字段错位——最坏是 `Approval.state` 解成别的枚举值，待审批显示成已批准。
- 止血和回退：永远不改号。发现编号分配不合理（比如想把字段移到别的消息），做法是新加字段、旧字段标 `deprecated = true` 并在 `iwork-app` 映射里兼容读两份；旧编号只在升主版本时进 `reserved`。已经改了号且 CI 红了：revert 那次提交。确有必要重排（大面积设计错误）：升主版本——PO 书面同意、包名改 `iwork.v2`、新建 `proto/compat/v2/`；新程序遇到 `meta.protocol_major = 1` 的库先 `VACUUM INTO` 备份再拒绝启动、库文件不动；旧客户端连新后台、新客户端连旧后台都在握手处被拦；用户要么装回旧程序继续用旧数据，要么（dev 阶段）自己删库；想带数据过去，先按 3.7 的门槛写显式转换并做无损演练。不用 schema 版本做门：设计 5.5 的迁移是向前的，版本 +1 会被迁移吃掉，然后用新类型错读旧事件。
- 由什么保证：`tests/compat.rs` 双向契约比对 + 两步测试 + 「契约目录号 == PROTOCOL_MAJOR」（T01 交付）；`update-contract --additive` 对已有条目拒绝写入（T01 交付）；`check_hello` 两个方向的单测（T01 交付）；数据库门与备份、握手两方向的集成演练（第 11 节第 9 步，归 T02/T03/T04 验收，Q5 已定）。

**S2 状态机漏了转换**（卡点名）
- 会出什么事：T05/T06 实现时碰到表里没有的 `(state, trigger)`，`next()` 返回 `IllegalTransition`，回合停在非终态，对话上一直转圈，取消也走不通。
- 止血和回退：`IllegalTransition` 是带状态与触发器名的错误，日志里一眼看到；修复 = 在转换表加一行 + 加一条用例。线上止血：daemon 重启走崩溃恢复，`Running/WaitingApproval` 且进程不在的回合标 `Interrupted`，用户可「放弃」到 `Cancelled`；`Cancelling` 的直接 `Cancelled`。所以任何卡死态都能被「重启 + 放弃」清掉，前提是表里保证 `Interrupted → Cancelled` 与 `Cancelling → Cancelled` 两行存在。
- 由什么保证：4.3「测试怎么写」的五类测试（正向逐条、反向逐对、手写场景、不变量、对桩实现的对照）+ 「每个非终态可达终态」+ 「`ProcessLost` 在所有非终态都有定义」（T01 交付）；T04 验收 3 证明回合的恢复路径真能走；亲手执行卡片的 `Starting`/`Executing`/`Stopping` 中断恢复见 S2a 与第 11 节第 9 步（做法 A，Q6 已定）。

**S2a 亲手执行卡片执行到一半 daemon 崩溃**
- 会出什么事：用户点了「执行」，`iwork-host` 起了进程，daemon 随即崩溃。重启后如果把卡片当成没执行过再跑一遍，一条本来只该跑一次的命令（如 `git push --force`、往 `~/.ssh/config` 追加一行）跑了两次。
- 止血和回退（做法 A，产品负责人 2026-11-09）：恢复时停在 `Starting`/`Executing`/`Stopping` 的卡片一律 → `Unknown`，iWork 不判断进程是否还活着、不去停它，卡片显示「结果未知，请自行确认」与「我已核对」；绝不重跑，绝不自动判为结束；Agent 收到「结果未知」。删除对话碰上它：停在 `Deleting` 等用户确认。用户自己看输出或系统状态处理那条命令（还在跑就自己结束它）；想再来一次是点「复制命令」自己跑，不经卡片。
- 由什么保证：4.3 卡片表的 `ProcessLost` 一行、`Unknown` 唯一出口与它们的单测（含 `user_action_unknown_only_user_confirms`，T01）；恢复演练「`Spawned` 提交前的窗口注入 → 副作用只一次、卡片 `Unknown`、删除停在 `Deleting`、确认后删完」（第 11 节第 9 步，附录 B，归 T04 验收 3）。
- 已知限制：见第 8 节末尾「已知限制（T01 登记）」。

**S2b AI 审查结果迟到**
- 会出什么事：自动档下 AI 审查 60 秒超时，审批已经交给用户显示在卡片上；用户还没点，审查结果「通过」这时回来，若直接应用就放行了一个用户正在看的请求。切回手动或用户已拒绝时同理。
- 止血和回退：三条生效条件（4.3）不满足即 `Stale` 丢弃；已经错放的情况不存在，因为 `Stale` 不改主状态。如果真发现放行了，审计里有 `ApprovalEvaluated` 与 `ApprovalReviewUpdated` 两条可追溯，修法是补条件，不是加新机制。
- 由什么保证：4.3 的五条乱序用例（T01 交付）；T07 把 `review_id` 真正接到 AI 审查回合上时沿用这些用例。

**已知限制（T01 登记；按需求第 9 章「新增安全规则时同时登记其覆盖不到的风险」的做法，实施时抄进需求文档的已知限制清单由产品负责人决定）**

- **后台服务崩溃后，iWork 停不了崩溃前亲手执行卡片起的那条命令，也不知道它跑完没有。** 卡片转「结果未知」，只由用户核对后确认；进程还在跑的话由用户自己结束。原因：恢复后它不再是子进程，可靠地核对与停止需要持久化进程身份并处理 pid 复用，产品负责人 2026-11-09 决定不为这个缺口加这一串机制（做法 A）。没崩溃时，后台服务经句柄停止与等待自己的子进程，不受此限。

**S3 两套 proto 生成链路（protox / buf）解出不同结果**
- 会出什么事：某个 `.proto` 写法一边接受一边拒绝，或 `optional`/`proto3` 语义解释不同，TS 收到的字段为空。
- 止血和回退：金样本跨语言解码测试会红；回退是改 `.proto` 写法到两边一致的子集（不用 `proto2`、不用 extensions、不用 `Any`）。若 protox 跟不上某语法，退回 `prost-build` + 系统 `protoc`（CI 装 protoc），`build.rs` 留 feature 开关，不改任何 `.proto`。
- 由什么保证：`client/src/gen.test.ts` 与 `tests/compat.rs` 解同一批样本（T01 交付）。

**S4 依赖方向被绕过**
- 会出什么事：有人在 `iwork-core` 的 `Cargo.toml` 加 `rusqlite` 做个「临时查询」，审批求值不再是纯函数，proptest 失真。
- 止血和回退：CI `check-deps.sh` 红，提交进不去。绕过方式只剩改 `deps-policy.toml`，而那是个明显的 diff，审查规则按 `important` 报。
- 由什么保证：`--selftest` 证明脚本会红（卡验收 2）；策略文件由 architect/审查看守。

**S5 `check-deps.sh` 本身误判（jq 缺失、Windows bash 差异）**
- 会出什么事：CI 在某平台上静默跳过或把 0 当通过。
- 止血和回退：脚本缺工具退出码 2，CI 当失败；三平台都跑自测，自测要求「注入违规必红、原样必绿」两方向成立。
- 由什么保证：CI 矩阵三平台跑 `--selftest`。

**S6 原生 async trait 的 `Send` 限制让某实现写不出来**
- 会出什么事：T02 的 rusqlite 连接不是 `Send`，`StoragePort` 实现编译不过。
- 止血和回退：这是 T02 内部结构问题（单写者线程 + channel 把请求送进去，future 本身 `Send`），不需要改端口；真到要 `?Send`，在 `ports` 给该 trait 加 `+ Send` 之外的 `Local` 变体是最后手段，需过方案审查。
- 由什么保证：T01 在 `iwork-ports` 里放一个 `tests/fakes.rs`：每个端口一个最小假实现 + 一个 `fn assert_send<T: Send>()` 的编译期测试，证明按签名写实现并能被 `spawn`（不引 tokio，用 std 的 `Send` 断言）。

**S7 CI Linux 装不上 Tauri 依赖 / Windows 路径问题**
- 会出什么事：`cargo test --workspace` 因 `iwork-client` 编不过而全红，挡住与客户端无关的卡。
- 止血和回退：把 `iwork-client` 的检查单独成 job（`cargo clippy -p iwork-client`），主 job 用 `--workspace --exclude iwork-client`；依赖清单照 Tauri v2 官方页面装。
- 由什么保证：CI 首次全绿是验收 1；拆 job 的做法写在 `ci.yml` 注释里。

**S8 `ViewPatch` 壳定得不够，T09 要改结构**
- 会出什么事：T09 把 `ConversationPatch` 拆成两个消息，老的 patch 字段作废。
- 止血和回退：只加 `optional` 字段与新 `ViewChange` 变体，老字段 `deprecated`；`ViewPatch` 不落盘、只在客户端进程内传，所以不进 `proto/compat/` 基线比对（在 `compat.rs` 里排除 `view.proto`），改起来没有数据风险。
- 由什么保证：`compat.rs` 的排除清单写明理由。

**S9 ULID 同毫秒无序 / 时钟回拨**
- 会出什么事：同一毫秒生成的两条消息顺序颠倒；系统时间回拨后新 ID 比旧 ID 小，分页漏条。
- 止血和回退：生成器单调（同毫秒递增随机位；时间回拨时沿用上一次的毫秒数继续递增），这是 daemon 里的实现；domain 的 `from_raw` 不做假设。
- 由什么保证：T01 在 daemon 空壳里不实现生成器（T02/T04 用到时实现），但把「单调」写成 `IdGenerator` 的文档契约，并在 `ports/tests/fakes.rs` 给一个单调假实现与它的测试，作为真实现的参照用例。

**S10 领域事件枚举与 proto 事件漏对**
- 会出什么事：T10 加了一个事件只加在 proto，没加 domain 变体，存进去的事件回放时 `TryFrom` 失败，投影重建中断。
- 止血和回退：对拍测试红；修法是补变体与映射。
- 由什么保证：3.6 的穷举对拍（T01 交付）。

## 12 ADR（由 developer 随实现写入 `docs/adr/`，每条一个文件）

**ADR-0001 ID 用 ULID 的强类型 newtype**
- 背景：需要跨进程、跨语言稳定的 ID；消息与事件要按创建顺序分页；多种实体 ID 容易串位。
- 决定：全部实体 ID 为 ULID，按实体生成 newtype；生成通过 `IdGenerator` 端口，domain 不读时钟与随机源。
- 备选：UUID v4（无序，分页需额外索引）；UUID v7（有序但 36 字符，Rust 生态里 ULID 更常用）；自增整数（跨设备/远程接入时冲突，D05 预留）。
- 影响：`.iwork/project.toml` 的 `id` 字段为 ULID 文本（见方案 Q1）；SQLite 主键为 26 字符文本。

**ADR-0002 端口用原生 async（RPITIT + Send）与静态分发**
- 背景：`ports` 不得依赖框架；daemon 用 tokio 多线程，需要 `Send` future。
- 决定：trait 方法写 `fn f(&self) -> impl Future<Output = T> + Send`；core/app 对端口泛型；daemon 组合。
- 备选：`async-trait` crate（Box 分配、可 dyn，但引入宏 crate 且每次调用堆分配）；`trait_variant`（同样是宏 crate）；只用 `async fn`（无法加 Send，daemon 无法 spawn）。
- 影响：端口不可 `dyn`；需要动态分发时在 daemon 包适配层；单元测试用泛型假实现。

**ADR-0003 领域事件在 proto 里定义一次，存储与推送共用**
- 背景：事件日志载荷与推给客户端的事件若分开定义，回放重建的视图和实时视图会分叉。
- 决定：`events.proto` 的 `DomainEvent` 既是 `events.payload` 的编码，也是 `Event` 帧的载荷；domain 的 Rust 枚举与它靠穷举对拍绑定；存储层通过 `EventCodec` 端口拿到编解码能力（实现在 `iwork-app`，由 daemon 注入），投影在线与重建共用 `Projector`。
- 备选：存储用自定义序列化（多一份格式）；domain 直接依赖 proto（违反依赖方向）；store 直接依赖 proto（违反设计 2 的表，且 proto 一变 store 就重编）。
- 影响：加事件要同时改 proto、domain、app 转换函数，对拍测试会提示遗漏；store 对 codec 泛型。

**ADR-0004 Rust 侧用 protox 编译 proto，TS 侧用 buf；兼容靠描述符快照与跨语言金样本**
- 背景：三平台 CI 装 protoc 增加环境差异；两条生成链路要证明线格式一致；「字段只增不改号」要有机器检查。
- 决定：如题；`proto/compat/v<N>/contract.binpb` 只增不减，新增字段必须登记（双向比对）；破坏性变更只能升主版本，包名、契约目录、握手、数据库 `meta.protocol_major` 共用这一个号；数据库门先备份再拒绝启动；带数据升主版本是门槛（显式转换 + 无损演练）不是机制。
- 备选：只用系统 protoc（环境依赖）；用 `buf breaking`（需要 buf 二进制进 Rust CI，且不覆盖 Rust 生成结果）；用 schema 版本做门（迁移向前，拦不住）；另设契约谱系号（与主版本两套身份，握手比不到它，已否决）；通用导出导入（改名改类型时走不通、漏信封与幂等记录，已否决）。
- 影响：`.proto` 只用 protox 与 buf 都支持的 proto3 子集；每次加字段多跑一条命令；破坏性变更的成本是改包名并重新生成，这是有意为之。

**ADR-0005 依赖方向以数据文件描述，脚本检查传递闭包**
- 背景：`AGENTS.md` 规定依赖只向下，cargo-deny 的 `bans` 表达不了按 crate 的允许集。
- 决定：`scripts/deps-policy.toml` 为唯一真值；`check-deps.sh` 读 `cargo metadata` 查闭包；自测注入违规。
- 备选：每个 crate 手写 `#![deny]` 注释约定（不可执行）；cargo-deny（粒度不够）；白名单也按闭包查（合法的宏依赖链与 dev 依赖会误报，已否决）。
- 影响：加 crate 或放开某个外部依赖都要改策略文件，diff 可审；直接依赖许可与传递禁用分两类规则维护。

## 附录 交接用例（第 11 节第 9 步；由 supervisor 按 Q5、Q6 的决定搬进对应卡的验收）

**A. 协议主版本门（候选：T02 数据库门一条、T03 握手两条、T04 诊断页一条）**

1. 造库：用当前程序正常启动一次生成 `iwork.db`，关闭后把 `meta.protocol_major` 改成 `1 + 当前值`（模拟「这是更新版本写的库」）或 `当前值 - 1`，两种各跑一遍；记录库文件 sha256。
2. 启动当前程序。断言：进程退出码非 0；日志含「数据库是协议 v<X>，程序是协议 v<Y>」两个数；`backups/` 下出现一个文件名含 `v<X>` 的 `.db`；原库 sha256 与第 1 步相同；没有发生迁移（`PRAGMA user_version` 不变）。
3. 把 `meta.protocol_major` 改回当前值再启动。断言：正常启动，`head_seq` 与第 1 步结束时一致（证明第 2 步真的没动库）。
4. 握手（T03，用参数化主版本的测试构建）：旧客户端（`Hello.protocol_major = 1`）× 新后台（2）→ 收到 `PROTOCOL_VERSION_MISMATCH`，`details` 含 `client_major = 1`、`server_major = 2`，连接被关闭，后续帧不被处理；新客户端（2）× 旧后台（1）→ 同样被拒。同主版本、次版本不同 → `Welcome`。
5. 客户端侧（T04）：第 2 步拒绝启动期间，客户端诊断页显示两个主版本号与备份路径；第 4 步被拒时显示「正在切换版本」。

**B. 亲手执行卡片的崩溃恢复（做法 A；归 T04 验收 3，产品负责人 2026-11-09 已定）**

1. 用假运行时触发一条命中底线的单个简单命令（如往 `~/.ssh/config` 的测试替身路径追加一行），得到卡片。
2. **`Spawned` 提交前的窗口**：用户点「执行」，命令是 `echo line >> <临时文件> && sleep 30`。`iwork-host` 在测试构建里提供注入点 `IWORK_TEST_CRASH_AFTER_SPAWN=1`：`spawn` 返回后、`Spawned` 事件提交前，先等子进程把文件写出来（轮询到文件有一行），再 `abort()` daemon。重启 daemon。断言：卡片 `Unknown`；临时文件**只有一行**（副作用只发生一次，没有重跑）；审计里有 `RecoveryCompleted`，没有新的 `Starting`/`Spawned` 事件，也没有任何把卡片转到 `Ended`/`Done` 的事件（不自动判结束）；客户端卡片显示「执行结果未知，iWork 无法核对，请自行确认」与「我已核对」按钮，没有「停止」按钮；假运行时收到的拒绝原因为「用户已执行，结果未知」。
3. **`Executing` 时崩溃**：同样的命令，等到 `UserActionStateChanged{Executing}` 提交后 `kill -9` daemon（此时 `sleep 30` 还在跑）。重启。断言与第 2 步相同：卡片 `Unknown`，文件一行，无自动结束事件；等 30 秒后再刷新，卡片**仍是** `Unknown`（iWork 不探测进程）。
4. **`Unknown` 时删除**：在第 2 或 3 步的状态下发 `DeleteConversation`。断言：对话进入 `Deleting` 并停住；界面提示「有一张卡片的执行结果无法核对，请确认后继续删除」；卡片仍可操作；`SendMessage` 返回 `CONVERSATION_DELETING`；`ConfirmUserActionEnded` 受理成功，卡片 `Ended`，对话随即 `Deleted`。
5. **正常删除（没崩溃）**：卡片 `Executing` 时发 `DeleteConversation`。断言：对话 `Deleting`，卡片经句柄 `stop()` 先到 `Done{Signal}`（3 秒内），然后 `Deleted`。
