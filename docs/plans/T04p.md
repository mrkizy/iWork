# T04p 发布包：后台程序与安装清单进包：方案

> 任务卡 `docs/tasks/M1/T04p.md`（承接 T04 组 3 审查 `2026-11-12-m1-t04-g3/1/F-7`）。依据：T04 方案 2.9（完成依据与两种包形态）、2.12（自启 plist 的 `Program`）；T03 方案 2.4、2.4a；`docs/design/t0-findings.md` 7.1（N5：真实包上的实测）、7.2（N1）；M1 技术设计第 4 节；AGENTS.md「客户端」命令一条与「本机通信」安全不变量。
> 对照的代码：main `1097558`；Tauri CLI 2.12.4、`tauri-build` 2.7.4（`Cargo.lock`、`client/package.json`）。
> 状态：第 1 版，待审。

## 0 一页总览

现在 `pnpm -C client tauri build` 打出来的 `iWork.app` 里只有客户端，没有后台程序 `iwork-daemon`，也没有安装清单。装上之后客户端拉不起后台，T04 的「装齐了没有」对它永远答「没有」。

**推荐办法 b**：`tauri build` 只负责把客户端打成 `.app`；后面接一个**装配步骤**，把后台放进包、按形态写清单或签名、再用后台自己的判定核一遍。整件事仍然只有 `pnpm -C client tauri build` 一个入口，装配是包装脚本里的后半段。

| | 形态 A：无证书 | 形态 B：有证书（M1 用自签证书） |
| --- | --- | --- |
| 怎么选 | 默认 | 环境变量 `IWORK_SIGN_IDENTITY=<钥匙串里的签名身份>` |
| 包里有什么 | `Contents/MacOS/` 下 `iwork-client`、`iwork-daemon`、`iwork-manifest.json` | `Contents/MacOS/` 下 `iwork-client`、`iwork-daemon`；`Contents/_CodeSignature/`；**没有清单** |
| 最后一步 | 写清单 | 整包签名 |
| T04 2.9 的哪一行判「装齐」 | 带清单那一行 | 整包签名那一行 |
| 成品在哪 | `target/release/dist/unsigned/iWork.app` | `target/release/dist/signed/iWork.app` |

选 b 不选 a（`bundle.externalBin`）的理由一句话：b 的每一步都是 T04 的 N5 在真实包上量过的；a 要靠好几条 Tauri 打包器的行为，这些只在文档和源码里看过，没量过，按项目约定不能拿来定做法。比较见第 3 节。

M1 的代价：macOS 只出 `.app`，不出 `.dmg`；Linux 只出一个目录（两个程序加清单），不出 deb、AppImage（PD-1）。

## 1 要守住的六条（正文逐条兑现）

| # | 要守住的 | 依据的事实 | 谁保证 |
| --- | --- | --- | --- |
| I1 | 包里后台、客户端、清单在**同一个目录**，文件名固定 | 客户端按「自己的目录 + `iwork-daemon`」找后台（`launcher.rs:486`）；清单按「自己的目录 + `iwork-manifest.json`」读；两种形态的判定都从后台自己的目录出发（`install/manifest_form.rs`、`signed_bundle_form.rs`） | 装配脚本只往 `Contents/MacOS/` 放；R1 |

| I3 | 清单登记的是**成品里那两个文件**的身份 | 无证书时 `tauri build` 不签名、不改主程序（N5 第 0 项：包里的主程序与 `target/release/iwork-client` 逐字节相同） | 形态 A 里写清单是最后一步，对着成品目录里的文件算；之后不再动任何文件；R3 |
| I4 | 形态 B 封印之后**不再往包里放任何东西** | 多放一个文件、少一个、改一字节，整包验签都不过（N5 B2） | 形态 B 里整包签名是最后一步；R4 |
| I5 | 签名**只在装配步骤一处**做，Tauri 自己不签 | Tauri 先封印、装配再放后台，就破了 I4 | 包装脚本拒绝会让 Tauri 签名的环境变量；装配脚本见到 Tauri 的产物已有封印就停；R5 |
| I6 | **不留下缺后台的安装包**当成品 | `.dmg` 是打包器从它自己的 `.app` 做的，那时后台还没放进去 | macOS 只让 Tauri 出 `.app`、Linux 不让它打包；成品放在 `dist/`，和 Tauri 的中间产物分开；R6 |

## 2 现状与约束

### 2.1 已经有的（main `1097558`）

- `client/scripts/tauri.ts` 与 `tauri-layers.ts`：`pnpm tauri` 只放行 `dev`、`build`，按层清单叠配置，拒绝自带的 `-c/--config` 与 `TAURI_CONFIG`。别的参数原样放行（`tests/tauri-wrapper.test.ts`「`--ci`、`--target` 等其他参数照常放行」）。
- `client/src-tauri/tauri.conf.json`：`bundle.targets` 是 `"all"`；没有 `externalBin`，没有签名配置。
- `scripts/write-install-manifest.sh <目录>`：对目录里的 `iwork-daemon`、`iwork-client` 算 `sha256:`，macOS 再取 `cdhash:`，写 `iwork-manifest.json`。
- 后台的安装判定：`iwork_daemon::install::{forms, installed_complete}` 是公开的，返回每一行的结论（`install/mod.rs:99-115`）。
- 客户端找后台：`own.exe_dir.join("iwork-daemon")`（`iwork-client-core/src/launcher.rs:486`）。
- CI：`release-check` 只对裸的 release 二进制跑 `scripts/check-no-dev-trust.sh --artifacts`，注释写着「打包步骤还没进 CI」（`.github/workflows/ci.yml:131-159`）。
- N5 的实测脚本 `tools/t0/iwork-t04-bundle-probe.sh` 里已经有两种形态的拼法（132–150 行）：把后台复制进 `Contents/MacOS/`，形态 A 跑清单脚本，形态 B 先签后台、再签整包。
- `scripts/drill-upgrade.sh`（T04 方案 7.3）：升级演练，用的是临时拼出来的目录和开了开发开关的后台（检查周期除以 10）。它不是真包，也不是发布构建；本卡的验收 3 补的正是这一块。

### 2.2 还没有的

- 打包流程里没有任何一步放后台、写清单、签名。
- **真实的桌面客户端还不会拉起后台**：`client/src-tauri/src/effects.rs:13` 用的是 `DirectDialer`（只连、不拉）。换成 `Launcher` 是 T09 方案的步 10，还没做。验收 2「客户端经 Launcher 拉起后台」要等它（第 13 节第 1 条）。
- 发布构建的后台没有改数据目录的参数（`args.rs` 只认 `--service`）：在本机演练用的就是当前用户真实的数据目录与端点。

### 2.3 约束

- 打包只经 `pnpm -C client tauri build` 一个入口；裸跑 `tauri build`、`tauri bundle` 被拒；`src-tauri/` 下不许有层清单之外的 Tauri 配置文件，平台配置文件一律不许出现（AGENTS.md「客户端」）。
- 有证书的包里不放清单；无证书的包不做整包签名（T04 方案 2.9、T03 方案 2.4a）。
- 发布构建里没有 `--dev-trust`（安全不变量）。
- 厂商工具（这里是 Tauri 打包器）的行为，只在文档或源码里看到、没实测的，只能拿来设计实测，不能拿来定做法（`.cao/project-prompts/architect.md`）。
- 重的构建套 `lockf /tmp/iwork-heavy-test.lock`。

## 3 两个办法怎么比

| 卡片问的 | a：`bundle.externalBin` | b：`tauri build` 之后装配（推荐） |
| --- | --- | --- |
| 清单里的哈希是不是成品的 | 清单得在打包**之前**算好、再让打包器放进 `Contents/MacOS`。它等不等于成品里的文件，取决于打包器会不会动后台程序（给它签名、改它）。没量过 | 是。清单是装配的最后一步，对着成品目录里的两个文件现算；之后不再动（I3）。依据 N5 第 0 项与 A2 |
| 证书包的整包签名会不会被后放进去的文件破坏 | 交给打包器：它要先签后台、再封整包，而且不能把清单也放进去。次序对不对、无证书和有证书两种配置怎么分开，没量过 | 不会。装配自己定次序：放后台 → 签后台 → 签整包，签完不再放东西（I4）。依据 N5 B1–B3、B5 |
| 包内路径和 plist `Program`、对端校验的路径一致吗 | 打包器把它放在哪、叫什么名（去不去三元组后缀），文档说在 `Contents/MacOS/`，没量过 | 一致。装配脚本写死 `Contents/MacOS/iwork-daemon`（I1；第 4.5 节） |
| 入口 | 一个；配置层要按形态再分（有证书时不能带「放清单」的那段配置） | 一个；形态只是装配脚本的一条分支 |
| 对平时开发的影响 | `externalBin` 一旦被编译期看到，编客户端之前就得先有后台的文件（2.4）。只放进发布层能避开，这一点同样没量过。后台和客户端共用一个 `target/`，打包器会把后台复制回 `target/release/iwork-daemon`，正好是 cargo 自己的产物路径 | 没有：平时的 `cargo build`、`tauri dev` 一行不变 |
| `.dmg`、deb、AppImage | 打包器出的每种包里都带后台，这是 a 实打实的好处 | 只能出 `.app` 与一个目录；别的格式要自己做（M1 不做，PD-1） |
| 自己要写多少 | 少：一段配置、一个算清单的脚本 | 多一个装配脚本，约百来行 bash，拼法在 N5 脚本里已经有 |
| 建立在什么上 | 五六条没实测的打包器行为 | N5 在真实包上量过的事实 |

**推荐 b。** a 的好处是真的（各种安装包格式自动带上后台），但 M1 只有产品负责人一个人用，装法就是把 `.app` 拷进「应用程序」。为了现在用不上的 `.dmg`，要先把一串打包器行为量一遍，量完还可能发现配置层得按形态再拆。b 今天就能照着 N5 的结论写。

**什么时候回头看 a**：要出 `.dmg` 或 Linux 安装包的时候。那时先跑第 8.2 节列的实测，都成立再换；装配脚本里「核对」那一段（4.4）原样留着，换办法不换判据。

## 4 设计（办法 b）

### 4.1 入口与次序（`client/scripts/tauri.ts`，只动 `build` 这一支）

`pnpm -C client tauri build` 依次做五件事，哪一步失败都以非零退出，后面的不做：

| 步 | 做什么 | 说明 |
| --- | --- | --- |
| 1 | 查参数与环境 | 见下面「拒绝的」 |
| 2 | `cargo build --release --locked -p iwork-daemon` | 后台与客户端同一个工作区、同一个 `target/` |
| 3 | 交给 tauri CLI：`build` + 层清单的 `--config` + 平台参数 | macOS 加 `--bundles app`；Linux、Windows 加 `--no-bundle` |
| 4 | `scripts/assemble-release.sh`（4.2） | Windows 跳过，打印「M1 不出 Windows 包」 |
| 5 | 核对（4.4） | 不过 → 删掉 `dist/` 里这次的成品，退出码非零 |

**`build` 多拒绝的参数与环境变量**（现在都是原样放行的；拒绝时错误信息写明原因）：

| 拒绝什么 | 为什么 |
| --- | --- |
| `--bundles` / `-b`、`--no-bundle` | 出哪种包由第 3 步按平台定。让调用方选 `dmg`，得到的是缺后台的安装包（I6） |
| `--target` / `-t`、`--debug` / `-d` | 产物目录会变成 `target/<三元组>/…` 或 `target/debug/…`，装配只认 `target/release/`。M1 只出本机架构的发布包 |
| `--features` / `-f` | 调用方能用它给客户端开 `dev`，打出带 `--dev-trust` 的「发布包」 |
| 环境变量 `APPLE_SIGNING_IDENTITY`、`APPLE_CERTIFICATE` | Tauri 文档里它们会让打包器自己签名。签名只许在装配步骤做（I5）。这里不依赖文档说得对不对：设了就拒；真被签了，装配脚本还有一道（4.2 第 2 步） |

`dev` 子命令不变。现有测试「`--ci`、`--target` 等其他参数照常放行」里的 `--target` 改成只对 `dev` 成立，`build` 另加拒绝的用例。

配置层不加文件：出哪种包用命令行参数给，不写进配置，所以不需要平台配置文件，层清单还是两行。

### 4.2 装配脚本（`scripts/assemble-release.sh`，新）

用法：`scripts/assemble-release.sh`，不带参数；形态由环境变量 `IWORK_SIGN_IDENTITY` 定（可另给 `IWORK_SIGN_KEYCHAIN=<钥匙串文件>`，原样传给 `codesign --keychain`）。脚本不建证书、不碰钥匙串的设置。

macOS：

| 步 | 形态 A（没设 `IWORK_SIGN_IDENTITY`） | 形态 B（设了） |
| --- | --- | --- |
| 1 | 把 `target/release/bundle/macos/iWork.app` 整个复制到一个临时目录（`ditto`，和成品同一个文件系统） | 同左 |
| 2 | 复制出来的包里有 `Contents/_CodeSignature` → 停，报「Tauri 给包签了名，装配不接着做」（I5） | 同左 |
| 3 | `Contents/MacOS/iwork-client` 与 `target/release/iwork-client` 逐字节相同，不同 → 停（I3 的前提，每次打包都核，不只靠 N5 那一次） | 同左 |
| 4 | 把 `target/release/iwork-daemon` 复制成 `Contents/MacOS/iwork-daemon` | 同左 |
| 5 | `scripts/write-install-manifest.sh <包>/Contents/MacOS` | `codesign -f -s "$IWORK_SIGN_IDENTITY" -i dev.iwork.daemon <包>/Contents/MacOS/iwork-daemon` |
| 6 | — | `codesign -f -s "$IWORK_SIGN_IDENTITY" <包>`（封整包；主程序随它一起签） |
| 7 | 把临时目录里的包改名成 `target/release/dist/unsigned/iWork.app`（先删旧的） | 改名成 `target/release/dist/signed/iWork.app` |

- 第 5、6 步的签法和 N5 脚本 149–150 行一样，那是 B1–B3 量过的。
- 形态 B 不写清单，也不许包里有清单：第 4 步之后查一遍 `Contents/MacOS/iwork-manifest.json` 不存在（I2）。
- 在临时目录里装配、最后才改名：装到一半失败，`dist/` 里不会留半个包。

Linux：建临时目录，放 `target/release/iwork-client`、`target/release/iwork-daemon`，跑 `write-install-manifest.sh`，改名成 `target/release/dist/linux/iwork/`。Linux 只有带清单这一种形态；设了 `IWORK_SIGN_IDENTITY` → 停，报「这个平台没有签名的形态」。

### 4.3 为什么成品另放 `dist/`

`target/release/bundle/macos/iWork.app` 是 Tauri 的产物，里面没有后台。把后台直接放进去，它就成了「有时齐、有时不齐」的东西：`tauri build` 重跑到一半、装配失败，留在原地的都是缺后台的包，路径却和成品一样。成品单独放，`bundle/` 下的永远是中间产物，`dist/` 下的永远是核对过的（I6）。

### 4.4 出包前的核对：用后台自己的判定

新加一个示例程序 `crates/iwork-daemon/examples/check-install.rs`：参数是一个目录，调 `install::forms()` 里的每一行 `check(目录)`，每行打一条结论；**恰好一行 `Complete`、别的都是 `NotThisForm`** → 退出 0，否则 1。包装脚本第 5 步跑：

```sh
cargo run --release --locked -p iwork-daemon --example check-install -- <成品>/Contents/MacOS
```

- 用的是后台运行时判「装齐了没有」的同一段代码（T04 方案 2.9 第二问），不另写一遍判据。N5 当时是照定义用 shell 重写的，这里换成正式函数。
- 它比「有一行 `Complete`」更严：另一行是 `Incomplete` 也不放过。成品不许是「带清单的形态齐了，同时又像一个没封好的签名包」这种两可的东西（I2）。
- 做成示例程序、不做成后台的命令行参数：发布的后台只认 `--service`，不为打包多开一个口子。
- 形态 B 另跑一次 `codesign --verify --deep --strict <包>`，和判定函数互为对照（T04 方案第 5 节 S7b 要的）。

### 4.5 路径对一遍（卡片范围 1 的第三问）

| 谁 | 用的路径 | 出处 | 成品里对应的 |
| --- | --- | --- | --- |
| 客户端找后台 | 客户端自己的目录 + `iwork-daemon` | `launcher.rs:486` | `iWork.app/Contents/MacOS/iwork-daemon` |
| 后台、客户端读清单 | 自己的目录 + `iwork-manifest.json` | T03 方案 2.4a；`peer/mod.rs` | `…/Contents/MacOS/iwork-manifest.json`（只有形态 A 有） |
| 带清单那一行 | 后台的目录下：清单，与清单里每个名字的文件 | `install/manifest_form.rs:24-43` | 同一个目录 |
| 整包签名那一行 | 后台的目录是 `X.app/Contents/MacOS`；封印在 `X.app/Contents/_CodeSignature/CodeResources` | `install/signed_bundle_form.rs` | `iWork.app` |
| 自启 plist 的 `Program` | 后台自己的可执行文件路径（绝对路径） | T04 方案 2.12 | `<装到哪>/iWork.app/Contents/MacOS/iwork-daemon`；app 挪了位置由对齐任务重写 |
| 对端校验 | **不看路径**：按连接对端的进程取运行映像的身份（cdhash 或证书），和内存里的清单或自己的证书比 | T03 方案 2.4 | 两个程序是谁就是谁，放哪都一样；清单要读得到，靠的是上面第二行 |

六处落在同一个目录、同样的三个文件名上，没有哪一处要改代码。

### 4.6 CI（`.github/workflows/ci.yml` 的 `release-check`）

- macOS：`pnpm -C client tauri build`（形态 A）→ `scripts/check-no-dev-trust.sh --artifacts` 的参数从裸二进制换成成品里的两个程序。形态 B：job 里现建一个临时钥匙串和自签证书（做法照 N5 脚本 26–28、155–172 行，`windows-n2` job 也是现建现删），设 `IWORK_SIGN_IDENTITY` 再打一次，结束时删钥匙串。进不进 CI 见 PD-2。
- Linux：`pnpm -C client tauri build` → 对 `dist/linux/iwork/` 下两个程序跑同一条检查。
- Windows：不变（仍然只编 `iwork-client`、查裸二进制）。
- 第 5 步的核对已经在打包命令里，CI 不另跑；CI 上打包命令返回 0 就说明「恰好一种形态成立」。

## 6 出事场景

每条写三件事：会出什么事 / 怎么止血和回退 / 由什么保证。

**S1 包里的后台或清单和判定对不上**
- 出什么事：装上之后客户端拉不起后台，或者后台起来了、两端互不相认；升级时旧后台一直停在「安装中」。
- 止血：这样的包过不了第 5 步的核对，打包命令是非零退出，`dist/` 里没有它。要是真流出去了：删掉装上的 `iWork.app`，换回上一个包；数据目录不用动（升级走的是「磁盘上换了一版」，换回去同样触发，T04 方案 2.9「降级同样触发」）。
- 保证：R1、R2、R3；第 9 节验收 1。

**S2 Tauri 换了版本，无证书时也开始给包签名或改主程序**
- 出什么事：形态 A 的前提没了：包有了封印，清单放不进去；或者主程序变了，清单算的不是成品。
- 止血：装配第 2、3 步当场停，打包失败，出不了包。回退办法是把 Tauri 版本换回去（`client/package.json` 与 `Cargo.lock` 固定着版本）；要跟新版本就回 architect 重看 N5 第 0 项。
- 保证：R3 的 `assemble_stops_when_bundled_client_differs`、R5 的 `assemble_stops_on_presealed_bundle`；这两步每次打包都跑。

**S3 签名身份不对或钥匙串锁着**
- 出什么事：形态 B 的 `codesign` 失败，或者卡在弹框等密码。
- 止血：装配失败，`dist/signed/` 不变（上一次的成品还在，这次的没生成）。不设 `IWORK_SIGN_IDENTITY` 可以照常出形态 A。
- 保证：`failed_assembly_leaves_no_dist`；CI 上钥匙串是现建的、关了自动上锁（做法照 N5 脚本 26 行的说明）。

**S4 有人绕过装配，直接把 Tauri 的 `.app` 拿去用**
- 出什么事：`target/release/bundle/macos/iWork.app` 能双击打开，但里面没有后台。
- 止血：装上之后的表现是客户端一直连不上（诊断页会写后台程序不在）。换成 `dist/` 里的包。
- 保证：没有技术手段挡住人去拿中间产物；靠 AGENTS.md 命令节写明成品在哪（第 10 节），和 S1 的诊断。记为 L2。

**S5 装到一半的包被启动**
- 出什么事：用户拖进「应用程序」的过程中就双击了；或者升级时新包拷了一半。
- 止血：这是 T04 管的（方案 2.9 的判据、2.2 的退出码 14）：没装齐时后台不重启、起不来的由拉起方过一会儿再拉，装齐后自动继续。本卡不加东西。
- 保证：T04 的 `process::` 用例；第 9 节验收 3 在真包上走一遍。

**回退整件事**：本卡只动打包脚本、一个示例程序和 CI，不动任何运行时代码与数据。发现办法 b 本身有问题时，把包装脚本的 `build` 一支恢复成原样即可，T04 已合入的代码不受影响。

## 7 性能（需求第 14 章）

不碰任何运行时路径。打包多出来的时间：后台的 release 构建（和客户端共用依赖，增量）、一次 `ditto`、形态 B 的两次 `codesign`、一次 `check-install`（形态 B 的整包验签 N5 量过，20–84 毫秒）。CI 的 `release-check` 现在约 6 分钟（只编客户端），加上后台与前端构建、打包，macOS 上预计多几分钟；步 4 验收时把实际时长记进完成记录，接近 30 分钟上限就拆 job。

## 9 验收与本机复现步骤（macOS）

演练用的是当前用户真实的数据目录和端点（发布构建没有改它们的参数）。**开始前**：确认没有 iWork 的后台在跑（`pgrep -fl iwork-daemon` 为空）；把 `~/Library/Application Support/iWork` 改名留底，结束后换回。每一步的输出存进 `tools/t0/out/t04p-accept/`，结论写进任务卡的完成记录。

**准备两版包**（验收 3 要用）。A 版在原工作区打；B 版在临时验证副本里打，只把根 `Cargo.toml` 的 `[workspace.package] version` 改成另一个值，让两版后台的 cdhash 不同：

```sh
export PATH=$HOME/.cargo/bin:$PATH
lockf /tmp/iwork-heavy-test.lock pnpm -C client tauri build                               # 形态 A
IWORK_SIGN_IDENTITY="<自签身份>" lockf /tmp/iwork-heavy-test.lock pnpm -C client tauri build   # 形态 B
```

自签身份的建法照 N5 脚本 155–172 行（`openssl` 出一张用途是代码签名的证书、`security import` 进一个钥匙串）；演练用自己的登录钥匙串或单独建一个都行，建完在「钥匙串访问」里看得到这张证书。

**验收 1：恰好一种形态成立**

```sh
A=target/release/dist/unsigned/iWork.app; B=target/release/dist/signed/iWork.app
cargo run --release -p iwork-daemon --example check-install -- "$A/Contents/MacOS"   # 期望：manifest=Complete signed-bundle=NotThisForm，退出 0
cargo run --release -p iwork-daemon --example check-install -- "$B/Contents/MacOS"   # 期望：manifest=NotThisForm signed-bundle=Complete，退出 0
codesign --verify --deep --strict --verbose=2 "$B"                                    # 期望：valid on disk
ls "$B/Contents/MacOS"                                                                # 期望：没有 iwork-manifest.json
jq . "$A/Contents/MacOS/iwork-manifest.json"                                          # 两个程序各有 sha256 与 cdhash
```

`self_listed` 是后台运行时自己说的，在验收 2 里看。

**验收 2：装上后客户端拉起后台、两端互认**（要 T09 步 10 先合入，第 13 节第 1 条）

```sh
ditto "$A" "$HOME/Applications/iWork.app" && open "$HOME/Applications/iWork.app"
pgrep -fl iwork-daemon            # 期望：一个进程，路径是 ~/Applications/iWork.app/Contents/MacOS/iwork-daemon，参数里没有 --dev-trust
```

再看后台日志（`~/Library/Application Support/iWork/logs/`）里 `iwork.ipc.audit` 的记录：有 `manifest_loaded` 且 `self_listed=true`；没有 `peer_rejected`；没有 `peer_accepted_without_signature_check`（那是 `--dev-trust` 才有的）。客户端窗口进到首页，不是「连接不上」的诊断页。形态 B 重做一遍：没有 `manifest_loaded`（有证书的构建不读清单），别的相同。

**验收 3：升级不停在「安装中」**

A 版装着、后台在跑（验收 2 做完的样子），记下后台的 pid 和运行映像：

```sh
P=$(pgrep -f 'iWork.app/Contents/MacOS/iwork-daemon'); codesign -dvvv "$P" 2>&1 | grep CDHash
ditto <B 版的形态 A 包> "$HOME/Applications/iWork.app"      # 覆盖安装
```

期望（T04 方案 2.9）：75 秒内，后台日志出现「磁盘上装齐了另一版，自行重启」；同一个 pid 的运行映像 cdhash 变成 B 版包里后台的（`codesign -dvvv <B 包>/Contents/MacOS/iwork-daemon` 的值）；日志里「安装中」的记录至多出现在拷贝的那几秒，之后有「离开『安装中』」或直接重启，没有每 30 秒一条地持续下去。然后关掉客户端再打开：连得上（新客户端和新后台互认）。

同样的步骤再做两遍：形态 B 的 A 版 → 形态 B 的 B 版；形态 A → 形态 B（换形态）。三遍的日志片段都存下来。

**Linux**（卡片：只要求构建通过）：`pnpm -C client tauri build` 退出 0；`check-install` 对 `target/release/dist/linux/iwork` 报带清单那一行 `Complete`。CI 上跑，不在本机演练。

## 11 已知限制

- **L1** M1 不出 `.dmg`、deb、AppImage，Windows 不出包（PD-1）。
- **L2** `target/release/bundle/` 下 Tauri 的中间产物能被人直接拿走，那里面没有后台（S4）。
- **L3** 只出本机架构的包，不出通用二进制，不支持交叉打包。
- **L4** 形态 B 在 M1 是自签证书：不公证，Gatekeeper 不认。换成正式的开发者证书时要重看签名参数（强化运行时、时间戳）与 T04 方案 2.12 里 `SMAppService` 那条结论。
- **L5** 形态 A 的包经 `codesign --verify --deep --strict` 与 `spctl` 会报「没有资源封印」（N5 A4），这是它的正常样子，不是坏包；判它齐不齐只看 `check-install`。

## 15 ADR（developer 随实现写入 `docs/adr/`，编号合入时定）

### ADR-T04p-a 发布包由「打包之后装配」做成，不用打包器的 sidecar

- **背景**：发布包里要有后台程序；无证书的包要带一份登记两个程序身份的清单，有证书的包要整包签名且不能有清单。清单必须在所有会改文件的步骤之后写，封印必须在所有放文件的步骤之后做。T04 的 N5 在真实包上把这两条次序量过，是手工拼的。
- **决定**：`pnpm -C client tauri build` 里，Tauri 只把客户端打成 `.app`（Linux 不打包）；之后由仓库自己的装配脚本放后台、写清单或签名，成品单独放在 `target/release/dist/`，出包前用后台运行时的同一个判定函数核「恰好一种形态成立」。签名只在装配步骤做。
- **备选与放弃原因**：`bundle.externalBin`：各种安装包格式能自动带上后台，但清单与成品是否一致、签名次序、两种形态怎么分配置、对平时编译的影响，都落在打包器没实测过的行为上；M1 用不上那些格式。让 Tauri 签名、装配后再重签：同一件事做两遍，先签的那一遍只会碍事。把后台直接放进 Tauri 的输出目录：中间产物和成品同一条路径，失败时分不清。
- **影响**：M1 不出 `.dmg` 与 Linux 安装包；`tauri build` 少接受四个参数；以后要出别的格式时照方案 8.2 先实测再换办法，核对那一段不变。
