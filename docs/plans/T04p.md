## 0 一页总览

现在 `pnpm -C client tauri build` 打出来的 `iWork.app` 里只有客户端，没有后台程序 `iwork-daemon`，也没有安装清单。装上之后客户端拉不起后台，T04 的「装齐了没有」对它永远答「没有」。

**推荐办法 b**：`tauri build` 只负责把客户端打成 `.app`；后面接一个**装配步骤**，把后台放进包、按形态写清单或签名，在暂存目录里核对过，才发布成成品。整件事仍然只有 `pnpm -C client tauri build` 一个入口，装配是包装脚本里的后半段。

| | 形态 A：无证书 | 形态 B：有证书（M1 用自签证书） |
| --- | --- | --- |
| 怎么选 | 默认 | 环境变量 `IWORK_SIGN_IDENTITY=<钥匙串里的证书名>`；`-`（ad-hoc）与空值被拒 |
| 包里有什么 | `Contents/MacOS/` 下 `iwork-client`、`iwork-daemon`、`iwork-manifest.json` | `Contents/MacOS/` 下 `iwork-client`、`iwork-daemon`；`Contents/_CodeSignature/`；**没有清单** |
| 最后一步 | 写清单 | 整包签名 |
| T04 2.9 的哪一行判「装齐」 | 带清单那一行 | 整包签名那一行 |
| 成品在哪 | `<输出根>/release/dist/unsigned/iWork.app` | `<输出根>/release/dist/signed/iWork.app` |

`<输出根>` 是 cargo 自己报的目标目录，平时就是仓库的 `target/`。

**出包前核三件事**（4.4），三件都过才发布：这个包恰好是一种形态；包里的两个程序按运行时的信任规则能互认；有证书时两个程序是预期的那张证书签的。装配读的每个文件都来自这一次构建，位置由 cargo 报出来，不靠写死的路径（4.1）。

选 b 不选 a（`bundle.externalBin`）的理由一句话：b 的每一步都是 T04 的 N5 在真实包上量过的；a 要靠好几条 Tauri 打包器的行为，这些只在文档和源码里看过，没量过，按项目约定不能拿来定做法。比较见第 3 节。

M1 的代价：macOS 只出 `.app`，不出 `.dmg`；Linux 只出一个目录（两个程序加清单），不出 deb、AppImage（PD-1）。

另外两件并进本卡的事：真实客户端换成会拉起后台的拨号器（T09 方案步 10，supervisor 2026-11-13 定并入，4.7）；真包演练的脚本与环境（第 9 节、PD-3）。

## 1 要守住的九条（正文逐条兑现）

| # | 要守住的 | 依据的事实 | 谁保证 |
| --- | --- | --- | --- |
| I1 | 包里后台、客户端、清单在**同一个目录**，文件名固定 | 客户端按「自己的目录 + `iwork-daemon`」找后台（`launcher.rs:486`）；清单按「自己的目录 + `iwork-manifest.json`」读；两种形态的判定都从后台自己的目录出发（`install/manifest_form.rs`、`signed_bundle_form.rs`） | 装配脚本只往 `Contents/MacOS/` 放；R1 |
| I2 | 一个成品**恰好是一种形态**：A 有清单、没有封印；B 有封印、没有清单 | 签名后加清单验签不过；清单放进 `Contents/MacOS` 再签，`codesign` 直接失败（N5 B5）；旧清单残留在签名包里两行都判不齐（N5 E2） | 装配脚本两条分支互斥；核对要求恰好一行 `Complete`；R2 |
| I3 | 清单登记的是**成品里那两个文件**的身份 | 无证书时 `tauri build` 不签名、不改主程序（N5 第 0 项：包里的主程序与 `target/release/iwork-client` 逐字节相同） | 形态 A 里写清单是最后一步，对着暂存包里的文件算；之后不再动任何文件；R3 |
| I4 | 形态 B 封印之后**不再往包里放任何东西** | 多放一个文件、少一个、改一字节，整包验签都不过（N5 B2） | 形态 B 里整包签名是最后一步；R4 |
| I5 | 签名**只在装配步骤一处**做，Tauri 自己不签 | Tauri 先封印、装配再放后台，就破了 I4 | 包装脚本拒绝会让 Tauri 签名的环境变量；装配脚本见到 Tauri 的产物已有封印就停；R5 |
| I6 | 成品路径上**只有核对过的包**；新包没验过之前，旧成品不动 | `.dmg` 是打包器从它自己的 `.app` 做的，那时后台还没放进去；核对可能失败，也可能被中断 | macOS 只让 Tauri 出 `.app`、Linux 不让它打包；装配与核对都在暂存目录里做，过了才改名进 `dist/`；R6 |
| I7 | 装进包的两个程序**是这一次构建出来的** | cargo 的输出目录能被环境变量、配置、转给 cargo 的参数改掉；写死的 `target/release/` 里可能躺着上一次的产物 | 位置取 cargo 自己报的；上一次的打包产物先删；会让 Tauri 那一次构建去别处的入口全部拒绝；R9 |
| I8 | 成品里的两个程序**装上之后能互认** | 运行时的信任规则（`judge_peer`，T03 方案 2.4）：有证书的只认同一张叶证书；没证书的要有清单且对方在清单里。「形态齐」不等于「能互认」：ad-hoc 签的整包形态齐、验签过，却没有证书也没有清单 | 核对时用同一个 `judge_peer` 对包里的两个程序双向判一遍；装配脚本拒绝 ad-hoc 身份；R10 |
| I9 | 真包演练**不改动产品负责人本机在用的东西**：真实的数据目录、已装的应用、登录自启注册项 | 发布构建的后台没有改数据目录的参数（`args.rs` 只认 `--service`）；自启的标签 `com.iwork.daemon` 是固定的，注册在当前用户的 `gui/<uid>` 域（`autostart/macos.rs:21、112`）；空库的后台见到「意图是关、系统里注册着」会去注销（T04 方案 2.12 对齐表） | 演练脚本有前置检查与收尾；演练全程不开自启；环境隔离的做法由产品负责人选（PD-3）；R11 |

## 2 现状与约束

### 2.1 已经有的（main `1097558`）

- `client/scripts/tauri.ts` 与 `tauri-layers.ts`：`pnpm tauri` 只放行 `dev`、`build`，按层清单叠配置，拒绝自带的 `-c/--config` 与 `TAURI_CONFIG`。别的参数原样放行（`tests/tauri-wrapper.test.ts`「`--ci`、`--target` 等其他参数照常放行」）。
- `client/src-tauri/tauri.conf.json`：`bundle.targets` 是 `"all"`；没有 `externalBin`，没有签名配置。
- `scripts/write-install-manifest.sh <目录>`：对目录里的 `iwork-daemon`、`iwork-client` 算 `sha256:`，macOS 再取 `cdhash:`，写 `iwork-manifest.json`。
- 后台的安装判定：`iwork_daemon::install::{forms, installed_complete}` 是公开的，返回每一行的结论（`install/mod.rs:99-115`）。
- 运行时的信任判定：`iwork_ipc::peer::judge_peer(own, peer, policy)` 是只看传进来的值的函数，`SelfIdentity`、`PeerIdentity` 的字段都是公开的（`peer/mod.rs:113-135、369`）。
- 客户端找后台：`own.exe_dir.join("iwork-daemon")`（`iwork-client-core/src/launcher.rs:486`）。`Launcher` 已经实现了 `Dialer`（`launcher.rs:550`）。
- 后台程序的名字有三处各写了一遍：`iwork_daemon::install::DAEMON_NAME`、`iwork_client_core::launcher::DAEMON_FILE`（Windows 带 `.exe`）、`write-install-manifest.sh` 的 `BINARIES`。
- CI：`release-check` 只对裸的 release 二进制跑 `scripts/check-no-dev-trust.sh --artifacts`，注释写着「打包步骤还没进 CI」（`.github/workflows/ci.yml:131-159`）。
- N5 的实测脚本 `tools/t0/iwork-t04-bundle-probe.sh` 里已经有两种形态的拼法（132–150 行）：把后台复制进 `Contents/MacOS/`，形态 A 跑清单脚本，形态 B 先签后台、再签整包。
- `scripts/drill-upgrade.sh`（T04 方案 7.3）：升级演练，用的是临时拼出来的目录和开了开发开关的后台（检查周期除以 10）。它不是真包，也不是发布构建；本卡的验收 3 补的正是这一块。

### 2.2 还没有的

- 打包流程里没有任何一步放后台、写清单、签名。
- **真实的桌面客户端还不会拉起后台**：`client/src-tauri/src/effects.rs:13` 用的是 `DirectDialer`（只连、不拉）；`main.rs:78` 拿不到拨号器就 `panic`。
- 没有「磁盘上一个程序文件是谁签的」这个取法：`peer` 现在只能取运行中进程的签名者（`SelfIdentity::detect`）和文件的映像身份（`file_image_ids`）。

### 2.3 约束

- 打包只经 `pnpm -C client tauri build` 一个入口；裸跑 `tauri build`、`tauri bundle` 被拒；`src-tauri/` 下不许有层清单之外的 Tauri 配置文件，平台配置文件一律不许出现（AGENTS.md「客户端」）。
- 有证书的包里不放清单；无证书的包不做整包签名（T04 方案 2.9、T03 方案 2.4a）。
- 发布构建里没有 `--dev-trust`（安全不变量）。
- 厂商工具（这里是 Tauri 打包器）的行为，只在文档或源码里看到、没实测的，只能拿来设计实测，不能拿来定做法（`.cao/project-prompts/architect.md`）。
- 开发用的两个脚本要靠 `CARGO_TARGET_DIR` 换输出目录（`client/scripts/dev-fake.ts:12`、`client/tests/e2e/webview.ts:14`），这个变量不能一拒了之。
- 不在产品负责人的机器上抢焦点、替他点界面；要手点的列给他。
- 重的构建套 `lockf /tmp/iwork-heavy-test.lock`。

### 2.5 两问（good-code）

- **再加一种要动几处？** 加一种包的形态（比如以后要公证的开发者证书）：装配脚本加一条分支，T04 的形态登记表加一行；核对不用动（它问的是「恰好一种」「能互认」）。加一个要进包的程序：装配脚本的程序清单与 `write-install-manifest.sh` 的 `BINARIES` 各加一个名字（R1 的测试对拍）。
- **改这里牵动谁？** 包装脚本多拒几个参数：`tests/tauri-wrapper.test.ts`。成品挪到 `dist/`：CI 的产物路径、AGENTS.md 命令节、T04 的演练脚本。`peer` 加一个只读函数：没有现有调用方受影响。客户端换拨号器：`client/src-tauri/src/{effects,main}.rs`、`iwork-client-core/src/session/dial.rs`，这两处 T09 组 2b 也在动，所以排在它合入之后。

## 3 两个办法怎么比

| 卡片问的 | a：`bundle.externalBin` | b：`tauri build` 之后装配（推荐） |
| --- | --- | --- |
| 清单里的哈希是不是成品的 | 清单得在打包**之前**算好、再让打包器放进 `Contents/MacOS`。它等不等于成品里的文件，取决于打包器会不会动后台程序（给它签名、改它）。没量过 | 是。清单是装配的最后一步，对着暂存包里的两个文件现算；之后不再动（I3）。依据 N5 第 0 项与 A2 |
| 证书包的整包签名会不会被后放进去的文件破坏 | 交给打包器：它要先签后台、再封整包，而且不能把清单也放进去。次序对不对、无证书和有证书两种配置怎么分开，没量过 | 不会。装配自己定次序：放后台 → 签后台 → 签整包，签完不再放东西（I4）。依据 N5 B1–B3、B5 |
| 包内路径和 plist `Program`、对端校验的路径一致吗 | 打包器把它放在哪、叫什么名（去不去三元组后缀），文档说在 `Contents/MacOS/`，没量过 | 一致。装配脚本写死 `Contents/MacOS/iwork-daemon`（I1；4.5） |
| 入口 | 一个；配置层要按形态再分（有证书时不能带「放清单」的那段配置） | 一个；形态只是装配脚本的一条分支 |
| 对平时开发的影响 | `externalBin` 一旦被编译期看到，编客户端之前就得先有后台的文件（2.4）。只放进发布层能避开，这一点同样没量过。后台和客户端共用一个 `target/`，打包器会把后台复制回 `target/release/iwork-daemon`，正好是 cargo 自己的产物路径 | 没有：平时的 `cargo build`、`tauri dev` 一行不变 |
| `.dmg`、deb、AppImage | 打包器出的每种包里都带后台，这是 a 实打实的好处 | 只能出 `.app` 与一个目录；别的格式要自己做（M1 不做，PD-1） |
| 自己要写多少 | 少：一段配置、一个算清单的脚本 | 多一个装配脚本，约百来行 bash，拼法在 N5 脚本里已经有 |
| 建立在什么上 | 五六条没实测的打包器行为 | N5 在真实包上量过的事实 |

**推荐 b。** a 的好处是真的（各种安装包格式自动带上后台），但 M1 只有产品负责人一个人用，装法就是把 `.app` 放进「应用程序」。为了现在用不上的 `.dmg`，要先把一串打包器行为量一遍，量完还可能发现配置层得按形态再拆。b 今天就能照着 N5 的结论写。

**什么时候回头看 a**：要出 `.dmg` 或 Linux 安装包的时候。那时先跑 8.3 列的实测，都成立再换；核对那一段（4.4）原样留着，换办法不换判据。

## 4 设计（办法 b）

### 4.1 入口与次序（`client/scripts/tauri.ts`，只动 `build` 这一支）

参数里有 `-h`、`--help`、`-V`、`--version` 时，原样交给 tauri CLI 就返回，下面的步骤一步都不做（`dev`、`build` 都一样）。

否则 `pnpm -C client tauri build` 依次做下面几步，哪一步失败都以非零退出，后面的不做：

| 步 | 做什么 | 说明 |
| --- | --- | --- |
| 1 | 查参数与环境 | 见下面「拒绝的」 |
| 2 | 问 cargo 输出根在哪：`cargo metadata --format-version 1 --no-deps` 的 `target_directory`，记作 T | 设了 `CARGO_TARGET_DIR` 时它报的就是那个目录。后面每一步用的路径都从 T 来 |
| 3 | 删掉 `T/release/bundle/` | 上一次打包器留下的 `.app`。删了之后，这个位置上再出现的包只可能是这一次做的 |
| 4 | `cargo build --release --locked -p iwork-daemon --bin iwork-daemon --example check-install --message-format=json`，从输出里取两个可执行文件的路径 | 路径是 cargo 报的，不是拼的。后台的路径必须恰好是 `T/release/iwork-daemon`；不是（环境变量或 cargo 配置把构建目标改了）→ 停，报「发布包只出本机默认目标」 |
| 5 | 交给 tauri CLI：`build` + 层清单的 `--config` + 平台参数 | macOS 加 `--bundles app`；Linux、Windows 加 `--no-bundle` |
| 6 | `scripts/assemble-release.sh`，把第 2、4 步得到的路径**逐个传进去** | 暂存、核对、发布都在这个脚本里（4.2–4.4）。Windows 跳过，打印「M1 不出 Windows 包」 |

**`build` 多拒绝的参数与环境变量**（现在都是原样放行的；拒绝时错误信息写明原因）：

| 拒绝什么 | 为什么 |
| --- | --- |
| `--bundles` / `-b`、`--no-bundle` | 出哪种包由第 5 步按平台定。让调用方选 `dmg`，得到的是缺后台的安装包（I6） |
| `--target` / `-t`、`--debug` / `-d`、`--runner` / `-r`、`--` 以及它后面的一切 | 它们让 Tauri 的那一次构建去别的目录、别的 profile，或者换一个构建程序。装配只认第 2、4 步定下来的位置（I7） |
| `--features` / `-f` | 调用方能用它给客户端开 `dev`，打出带 `--dev-trust` 的「发布包」 |
| 环境变量 `APPLE_SIGNING_IDENTITY`、`APPLE_CERTIFICATE` | Tauri 文档里它们会让打包器自己签名。签名只许在装配步骤做（I5）。这里不依赖文档说得对不对：设了就拒；真被签了，装配脚本还有一道（4.2 第 2 步） |

**为什么不拒 `CARGO_TARGET_DIR`、`CARGO_BUILD_TARGET`**：不用拒。前者第 2 步照着它走，两次构建和装配用的是同一个 T；开发脚本用它换目录不受影响（它们不跑 `build`）。后者（以及写在 cargo 配置文件里的同一个设置，环境变量看不到）会让后台落到 `T/<三元组>/release/`，第 4 步的路径核对当场停。按「事实对不对」拦，比按「哪个变量设没设」拦得全。

`dev` 子命令不变。现有测试「`--ci`、`--target` 等其他参数照常放行」里的 `--target` 改成只对 `dev` 成立，`build` 另加拒绝的用例。配置层不加文件：出哪种包用命令行参数给，不写进配置，层清单还是两行。

包装脚本里「拿到参数、环境、cargo 报的东西之后，算出每一步的命令行」写成一个纯函数（放 `tauri-layers.ts`，和 `withConfigLayers` 一处），真正起进程的只有薄薄一层。R9 的反例测试对这个函数测，不用真编。

### 4.2 装配脚本（`scripts/assemble-release.sh`，新）

用法（macOS）：`scripts/assemble-release.sh --app <Tauri 的 .app> --client <裸的客户端程序> --daemon <后台程序> --check <check-install 程序> --dist <成品目录>`。Linux 没有 `--app`。**没有默认值，缺一个就报用法错**：脚本自己不知道 `target/` 在哪，也就读不到「默认位置上的旧东西」。形态由环境变量 `IWORK_SIGN_IDENTITY` 定（可另给 `IWORK_SIGN_KEYCHAIN=<钥匙串文件>`，原样传给 `codesign --keychain`）。脚本不建证书、不碰钥匙串的设置。

**先处理上一次留下的**：`<dist>/.staging-*` 一律删掉（没验完的半成品）；某个形态目录下有 `.old-*` 而没有 `iWork.app`（上一次发布到一半断了）→ 把 `.old-*` 改名回 `iWork.app`。

**暂存**（都在 `<dist>/.staging-<进程号>/` 里做，和成品同一个文件系统）：

| 步 | 形态 A（没设 `IWORK_SIGN_IDENTITY`） | 形态 B（设了） |
| --- | --- | --- |
| 0 | — | 身份是空串或 `-` → 停，报「`-` 是 ad-hoc 签名，这样的包没有证书也没有清单，两端互不相认」。再从钥匙串里按这个名字找证书，取它的 SHA-256 作为「预期的叶证书」；找不到或找到不止一张 → 停 |
| 1 | 把 `--app` 整个复制进暂存目录，仍叫 `iWork.app`（`ditto`） | 同左 |
| 2 | 复制出来的包里有 `Contents/_CodeSignature` → 停，报「Tauri 给包签了名，装配不接着做」（I5） | 同左 |
| 3 | `Contents/MacOS/iwork-client` 与 `--client` 逐字节相同，不同 → 停（I3 的前提，每次打包都核，不只靠 N5 那一次） | 同左 |
| 4 | 把 `--daemon` 复制成 `Contents/MacOS/iwork-daemon` | 同左 |
| 5 | `scripts/write-install-manifest.sh <暂存包>/Contents/MacOS` | 查 `Contents/MacOS/iwork-manifest.json` 不存在（I2）；`codesign -f -s "$IWORK_SIGN_IDENTITY" -i dev.iwork.daemon <暂存包>/Contents/MacOS/iwork-daemon` |
| 6 | — | `codesign -f -s "$IWORK_SIGN_IDENTITY" <暂存包>`（封整包；主程序随它一起签） |

第 5、6 步的签法和 N5 脚本 149–150 行一样，那是 B1–B3 量过的。

Linux：暂存目录里放 `--client`、`--daemon` 两个程序，跑 `write-install-manifest.sh`。Linux 只有带清单这一种形态；设了 `IWORK_SIGN_IDENTITY` → 停，报「这个平台没有签名的形态」。

**核对**：对暂存包跑 4.4 的三件事。不过 → 删暂存目录，退出码非零；`dist/` 里原来的成品**一个字节都没动**。

**发布**（核对过了才做；`F` 是 `unsigned`、`signed` 或 `linux`）：

1. `<dist>/F/iWork.app` 在 → 改名成 `<dist>/F/.old-<进程号>`。
2. 把暂存包改名成 `<dist>/F/iWork.app`。
3. 删 `.old-<进程号>` 与暂存目录。

| 断在哪 | 盘上是什么样 | 怎么恢复 |
| --- | --- | --- |
| 暂存或核对当中（失败、被中断、断电） | 成品没动；留下一个 `.staging-*` | 下一次打包开头删掉它。成品路径上没有出现过没验的包 |
| 第 1 步之后、第 2 步之前 | 成品路径上暂时没有包；旧的在 `.old-*` 里 | 下一次打包开头把它改名回去。人要手动恢复也是这一条 `mv` |
| 第 2 步之后 | 新包已经在成品路径上，它是验过的；多一个 `.old-*` | 下一次打包开头看到「有 `iWork.app` 也有 `.old-*`」，删 `.old-*` |

### 4.3 为什么成品另放 `dist/`

`T/release/bundle/macos/iWork.app` 是 Tauri 的产物，里面没有后台。把后台直接放进去，它就成了「有时齐、有时不齐」的东西，路径却和成品一样。成品单独放，`bundle/` 下的永远是中间产物（而且每次打包开头先删），`dist/` 下的永远是核对过的（I6）。

### 4.4 出包前的核对：三件事，都用运行时的同一段代码

新加一个示例程序 `crates/iwork-daemon/examples/check-install.rs`，用法 `check-install <目录> [--expect-leaf <叶证书 SHA-256>]`。每件事打一行结论，三件都过退出 0，否则 1：

| # | 问的是 | 怎么判 | 用的是哪段现成的代码 |
| --- | --- | --- | --- |
| 1 | 这个包恰好是一种形态吗 | `install::forms()` 的每一行 `check(目录)`：**恰好一行 `Complete`、别的都是 `NotThisForm`**。另一行是 `Incomplete` 也不放过 | 后台运行时判「装齐了没有」的那一段（T04 方案 2.9 第二问） |
| 2 | 装上之后两个程序能互认吗 | 对包里的后台与客户端各取「它是谁签的」，再把清单（有的话）读进来，拼成 `SelfIdentity` 与 `PeerIdentity`，用 `judge_peer(…, RequireSigner)` **两个方向各判一次**：后台看客户端、客户端看后台，都要是「接受、验过签名」 | 握手时判对端的那一段（T03 方案 2.4） |
| 3 | 是预期的那张证书签的吗（只在给了 `--expect-leaf` 时问） | 两个程序的签名者都是证书，叶证书的 SHA-256 都等于给的值 | 同上取到的签名者 |

- 第 1 件不改 `PackageForm` 的职责：它仍然只回答「磁盘上的包齐不齐」。能不能互认是另一个问题，由第 2 件用信任规则本身回答。
- 第 2 件要一个新的只读取法，放 `iwork-ipc::peer`，只加不改：

  ```rust
  /// 磁盘上一个程序文件是谁签的：有证书 → Certificate{叶证书的 SHA-256}；没有 → Image(映像身份)；验不过 → Unavailable。
  /// 和 SelfIdentity::detect 判「有没有证书、叶证书是谁」是同一段代码，只是对象从运行中的映像换成磁盘上的文件。
  pub fn file_signer(path: &Path) -> SignerIdentity;
  ```

  「磁盘上取到的」等不等于「运行起来之后的」：映像身份这一半 N5 量过（B3、D1–D4：静态 cdhash 等于运行中的）；证书这一半（磁盘文件的叶证书等于它运行起来后握手时用的那张）没单独量过，列在 8.1 的 P3，由真包上握手成功来证。
- 拿 `IWORK_SIGN_IDENTITY=-` 走一遍：整包是 ad-hoc 签的，第 1 件过（整包签名那一行 `Complete`）；第 2 件里两个程序的签名者都是 `Image`，又没有清单，`judge_peer` 回 `NoManifest` → 不过，不发布。装配脚本第 0 步先拦一道只是为了报错说得清，真正的保证在第 2 件：以后有别的办法做出「形态齐、认不上」的包，它一样拦。
- 做成示例程序、不做成后台的命令行参数：发布的后台只认 `--service`，不为打包多开一个口子。
- 形态 B 另跑一次 `codesign --verify --deep --strict <暂存包>`，和第 1 件互为对照（T04 方案第 5 节 S7b 要的）。

### 4.7 真实客户端换成会拉起后台的拨号器（T09 方案步 10，并入本卡）

supervisor 2026-11-13 定：这一步并给本卡的实施者一起做；T09 的卡片与方案里步 10 那一行由 supervisor 标「已并入 T04p」。没有它，验收 2 做不了。

**改什么**

- `iwork-client-core/src/session/dial.rs` 加一个小枚举，把两种拨号器包起来并实现 `Dialer`：`Launch(Launcher<…>)` 与 `Direct(DirectDialer)`。原因：两种类型不同，而 `Dialer` 的方法返回 `impl Future`，做不成 `dyn`。`Direct` 这个变体只在 `dev` feature 下存在；发布构建里枚举只有 `Launch` 一种。
- `client/src-tauri/src/effects.rs` 的 `dialer()`：
  - `dev` feature 下设了 `IWORK_DEV_ENDPOINT` → 照旧 `DirectDialer` 连那个端点、走开发信任。`pnpm -C client dev:fake`、录场景、webview 的端到端测试都靠这条路，不能坏。
  - 别的情况 → `launcher::local(&own, desktop_config(版本))`。
- `client/src-tauri/src/main.rs:78`：现在拿不到拨号器就 `panic`。`launcher::local` 在端点目录不安全时回 `Environment(原因)`，自己的身份取不到时 `SelfIdentity::detect` 也会报错。这两种都不许让客户端起不来：窗口照常开，进诊断页，显示原因。做法是给枚举再加一个变体 `Broken(String)`，它的 `dial()` 每次都回 `DialError::Environment(原因)`；诊断页本来就认这个错（T09 方案 2.3 的表）。

**和 T09 的交接**

- T09 步 10 写的第二件事「诊断页接真的 `Diagnostics`」：`Launcher` 的 `Dialer` 实现里已经把 `NotReady(d)` 转成视图用的形状（`launcher.rs:550` 附近），不用再写；剩下的是页面在真后台下走一遍，并进验收 2（第 9 节）。
- T09 步 10 的验收「S14 第 1、2 条随 T04 演练走一遍」是回退演练，要两版包，和验收 3 用同一对包、同一个脚本（第 9 节）。

**测试**

- `release_dialer_is_launcher`（发布构建：`dialer()` 给的是 `Launch`；枚举在没开 `dev` 时没有 `Direct` 这个变体，编译期就定了）。
- `dev_endpoint_uses_direct_dialer`（`dev` 构建、设了 `IWORK_DEV_ENDPOINT`：给的是 `Direct`，连得上假后台）。
- `unsafe_endpoint_dir_shows_diagnostics`（端点目录权限不对：`dialer()` 不 `panic`，给的是 `Broken`；`dial()` 回 `Environment`，视图是诊断页，带原因）。
- 现有的 webview 端到端与场景录制照常通过（它们走 `dev` 的那条路）。
- 真包上的证据是验收 2。

| R10 | 包的形态是齐的，装上之后两端却认不上（I8） | 核对第 2 件：用 `judge_peer` 对包里的两个程序双向判；第 3 件：有证书时两个程序都是预期的那张；装配第 0 步拒 ad-hoc | **`adhoc_identity_fails_before_publish`**（`IWORK_SIGN_IDENTITY=-`：装配第 0 步就停；绕过第 0 步、手工做一个 ad-hoc 整包签名的包交给 `check-install`：第 1 件过、第 2 件报 `NoManifest`、退出 1，`dist/` 里没有它）；`check_install_trust_table`（完整的 A：双向接受；A 的清单里少登记客户端：后台不认客户端；B 的后台与客户端用两张不同的证书签：`SignerMismatch`；B 两个程序同一张证书：接受）；`expected_leaf_mismatch_fails`（B 是用另一张证书签的，`--expect-leaf` 给的是预期那张：第 3 件不过）；`file_signer_table`（证书签的、ad-hoc 签的、没签的、被改坏的文件各一例） |
| R11 | 真包演练动了产品负责人本机在用的东西（I9） | 演练脚本的前置检查与收尾（第 9 节）；全程不开自启；环境隔离（PD-3） | `drill_refuses_when_label_registered`、`drill_refuses_when_daemon_running`（假的 `launchctl` 与 `pgrep`：两种情况脚本都在动任何东西之前停）；`drill_cleanup_runs_on_failure`（演练中途故意失败：收尾照样执行，它起的进程都退出了，装的包删了）；每次真演练的记录里有开始与结束两次 `launchctl print` 的输出 |

## 6 出事场景

每条写三件事：会出什么事 / 怎么止血和回退 / 由什么保证。

**S1 包里的后台或清单和判定对不上**
- 出什么事：装上之后客户端拉不起后台，或者后台起来了、两端互不相认；升级时旧后台一直停在「安装中」。
- 止血：这样的包过不了核对，打包命令是非零退出，`dist/` 里还是上一次的好包。要是真流出去了：把装上的 `iWork.app` 整包换回上一个（第 9 节「装包的唯一做法」），数据目录不用动（T04 方案 2.9「降级同样触发」）。
- 保证：R1、R2、R3、R10；验收 1。

**S2 Tauri 换了版本，无证书时也开始给包签名或改主程序**
- 出什么事：形态 A 的前提没了：包有了封印，清单放不进去；或者主程序变了，清单算的不是成品。
- 止血：暂存第 2、3 步当场停，打包失败，出不了包，原来的成品不动。回退办法是把 Tauri 版本换回去（`client/package.json` 与 `Cargo.lock` 固定着版本）；要跟新版本就回 architect 重看 N5 第 0 项。
- 保证：R3 的 `assemble_stops_when_bundled_client_differs`、R5 的 `assemble_stops_on_presealed_bundle`；这两步每次打包都跑。

**S3 签名身份不对或钥匙串锁着**
- 出什么事：形态 B 的 `codesign` 失败，或者卡在弹框等密码；或者有人把 `IWORK_SIGN_IDENTITY` 设成了 `-`，想「随便签一下」。
- 止血：装配失败，`dist/signed/` 里上一次的成品还在。不设 `IWORK_SIGN_IDENTITY` 可以照常出形态 A。
- 保证：R6 的 `failed_check_keeps_previous_artifact`；R10 的 `adhoc_identity_fails_before_publish`；CI 上钥匙串是现建的、关了自动上锁（做法照 N5 脚本 26 行的说明）。

**S4 有人绕过装配，直接把 Tauri 的 `.app` 拿去用**
- 出什么事：`T/release/bundle/macos/iWork.app` 能双击打开，但里面没有后台。
- 止血：装上之后客户端一直连不上，诊断页会写后台程序不在。换成 `dist/` 里的包。
- 保证：没有技术手段挡住人去拿中间产物；靠 AGENTS.md 命令节写明成品在哪（第 10 节），和诊断页。记为 L2。

**S5 装到一半的包被启动，或者新包是合并着盖上去的**
- 出什么事：① 用户把包放进「应用程序」的过程中就双击了。② 升级时没有整包替换，而是把新包合并拷进旧目录：从无证书换成有证书时旧清单留了下来，两种形态都判不齐，后台永远停在「安装中」（N5 E2）。
- 止血：①：T04 管的（方案 2.9 的判据、2.2 的退出码 14），装齐后自动继续。②：把装上的包整包换成新包（先把现在这个改名留底），后台下一次检查就判「装齐」并重启；想回到旧版，把留底的那个改名回来。
- 保证：①：T04 的 `process::` 用例。②：第 9 节的装法只有整包替换一种；演练里另有一格专门做合并覆盖并照上面的步骤恢复（8.2 的 U4）；已知限制 L6 写明装法。

**S6 交付了旧代码**
- 出什么事：有人为了不动平时的 `target/`，设了 `CARGO_TARGET_DIR` 再打包；或者机器的 cargo 配置里指定了构建目标。两次构建去了新地方，装配却从老地方拿了上一次的客户端包与后台。老包里的主程序和老的裸程序当然相等，重新写一份清单，形态也是齐的，命令成功，包里是旧代码。
- 止血：真流出去了：这个包能用，只是不是要发的那一版；重新打一次、整包替换。
- 保证：R9。位置是 cargo 报的，老位置根本不在装配的输入里。

**S7 核对失败，把原来的好包也弄丢了；或者没验过的包出现在成品路径上**
- 出什么事：打新包之前先删了旧的，新包核对不过又被删，手里一个包都没有了。或者核对跑到一半被中断，没验的包留在成品路径上，下一个人拿去装。
- 止血：照 4.2 的表：成品要么没动，要么在 `.old-*` 里，一条 `mv` 找回来；下一次打包开头会自动恢复。
- 保证：R6 的两条。

**S8 演练把本机真实的 iWork 弄坏了**
- 出什么事：① 演练开始前有一个后台被 `launchd` 管着，`pgrep` 那一下正好没在跑，数据目录改名之后它又被拉起来，在空目录里建了新库。② 演练里有人在客户端点开了「登录自启」，真实的 `gui/<uid>` 域里注册了 `com.iwork.daemon`，指向演练的包。③ 演练的后台是空库，自启的意图是关；机器上本来注册着自启的话，它会照对齐表把原来的注册项注销。④ 演练失败退出，演练的后台还活着，这时把真实的数据目录换回去，两边交叉着用。
- 止血：②：`launchctl bootout gui/$(id -u)/com.iwork.daemon`，删 `~/Library/LaunchAgents/com.iwork.daemon.plist`，再 `launchctl print` 核一遍。④：先停掉所有演练进程并等它们退出，再动数据目录。③ 没有补救办法（注销已经发生），只能重新去开一次；所以要挡在前面。
- 保证：R11。演练脚本在动任何东西之前查「标签没注册」「没有后台在跑（隔 15 秒查两次，盖过 `launchd` 10 秒的重拉间隔）」，不满足就停、不自己处理；全程不开自启；收尾先停进程、等退出、再核一遍标签。环境隔离到什么程度见 PD-3。

**回退整件事**：本卡动的是打包脚本、一个示例程序、`peer` 的一个只读函数、客户端的拨号器和 CI，不动后台的运行时代码与数据。打包这一半有问题时，把包装脚本的 `build` 一支恢复成原样即可。拨号器这一半有问题时，客户端换回上一版；后台不受影响。

## 7 性能（需求第 14 章）

不碰后台的任何运行时路径。客户端换拨号器之后，启动时多一次「连不上就拉起后台」，预算是 T04 方案 2.7 定的 1 秒，不是本卡新加的。打包多出来的时间：后台与示例程序的 release 构建（和客户端共用依赖，增量）、一次 `ditto`、形态 B 的两次 `codesign`、一次核对（形态 B 的整包验签 N5 量过，20–84 毫秒）。CI 的 `release-check` 现在约 6 分钟（只编客户端），加上后台与前端构建、打包，macOS 上预计多几分钟；步 5 验收时把实际时长记进完成记录，接近 30 分钟上限就拆 job。

每格只记 PASS / FAIL / INCONCLUSIVE。

### 8.1 办法 b 换了入口之后的复核（步 4 做完后，在本机经新的打包命令跑）

| 项 | 做什么 | PASS 的判据 |
| --- | --- | --- |
| P1 | 各打一次形态 A、B | 打包命令退出 0；`check-install` 对两种包三件事都过；`codesign --verify --deep --strict` 对 B 通过、对 A 报没有资源封印（N5 A4 记过，是形态 A 的正常样子） |
| P2 | 仓库默认的 `target/` 里留着上一版的成品（版本号不同）；设 `CARGO_TARGET_DIR=<新目录>` 再打包 | 成品出在新目录的 `release/dist/` 下；清单里的 `app_version` 与两个 cdhash 是新版的；老目录里的东西一个都没变 |
| P3 | 磁盘上取的签名者等不等于运行起来之后的 | 验收 2 里形态 B 握手成功，且后台审计日志里没有 `SignerMismatch`。不成立 → 核对的第 2 件在证书这一半不可信，回 architect |

### 8.2 装新版的做法（验收 3 之前先量；要两版真包，不花订阅额度）

T04 的真进程测试换程序一直是「写临时文件、再改名」，换的是目录项，旧进程握着的是旧文件。真实的装法没量过：把新包盖到一个后台正在运行的 `.app` 上，后台程序那个文件是被原地改写、还是被换成了新文件，决定了旧后台是自己体面地重启、还是被系统当场结束。

每格都记：后台程序文件的 inode 前后变没变；旧后台是自己走完停机再 `exec` 成新版的（pid 不变、日志里有「磁盘上装齐了另一版，自行重启」），还是被系统结束的（退出状态或信号；系统日志里有没有代码签名失效一类的记录）；从动手到新后台就绪隔了多久；`check-install` 对装好的包三件事过不过。

| 格 | 装法 | 怎么算 PASS | 结果怎么用 |
| --- | --- | --- | --- |
| U1 | **留底后的整包替换**（第 9 节「装包的唯一做法」）：新包先复制到旁边，旧包改名留底，新包改名到位 | 旧后台自己重启成新版，pid 不变，75 秒内就绪；留底的旧包还在 | 这是验收 3、回退、换形态都用的做法。FAIL → 验收 3 不做，回 architect；同时告知 T04：2.9 的自行重启在真包的这种装法下不成立 |
| U2 | `ditto` 直接盖到正在运行的包上，同一种形态 | 只记录，不设 PASS 的门槛 | 写进 L6：这样装会怎样。后台被系统结束而客户端随后把新后台拉起来，功能上能恢复，但在跑的回合是被打断的，不算「交接」 |
| U3 | 在 Finder 里把新包拖进同一个位置、选「替换」（要人手点，请产品负责人做；不做就记 INCONCLUSIVE） | 只记录 | 同上；这是用户最可能用的装法，L6 要写它的实际表现 |
| U4 | 合并覆盖着换形态：`ditto` 把形态 B 盖到形态 A 上（旧清单会留下） | 预期是坏的：两种形态都判不齐，后台停在「安装中」（N5 E2）。然后照 S5 ② 的步骤恢复：整包替换成 B | 恢复之后后台重启成 B → PASS。它证的是「装坏了怎么救」这条路走得通 |

### 8.3 办法 a 要先量的（M1 不做；要换 a 时照这张表跑，都是 PASS 才换）

脚本草案 `tools/t0/iwork-t04p-sidecar.sh`，格局同 `iwork-t04-bundle-probe.sh`：在临时验证副本里给发布层加 `bundle.externalBin`，各打一次包，结果写 `tools/t0/out/t04p-sidecar/`。

## 9 验收与本机复现步骤（macOS）

演练由一个脚本带着做：`scripts/drill-release-bundle.sh`（新，步 6 交付）。它不打包，只拿两版已经打好的包做装、起、换、查、收尾；每一步的输出存进 `<输出目录>/`，结论写进任务卡的完成记录。**在哪种环境里跑由产品负责人选（PD-3）**；下面的步骤两种环境共用。

### 9.1 三条硬规定

1. **全程不开登录自启**。不在客户端的设置里点它，脚本也不发这个命令。发布构建的自启走的是真的 `launchctl`，一开就在当前用户的 `gui/<uid>` 域里注册 `com.iwork.daemon`、指向演练的包。
2. **开始前、结束后各核一次自启没注册**：`launchctl print gui/$(id -u)/com.iwork.daemon` 要报找不到这个服务，`~/Library/LaunchAgents/com.iwork.daemon.plist` 不存在。**开始前就注册着** → 脚本停，什么都不动，请产品负责人处理（那不是演练留下的，不替他注销）。**结束时发现注册了** → 照下面注销，并记进演练记录：

   ```sh
   launchctl bootout gui/$(id -u)/com.iwork.daemon
   rm -f ~/Library/LaunchAgents/com.iwork.daemon.plist
   launchctl print gui/$(id -u)/com.iwork.daemon    # 期望：找不到这个服务
   ```
3. **装包只有一种做法：留底后的整包替换**（下面 9.3）。安装、升级、换形态、回退都用它。不用 `ditto` 往已有的包上盖：那是合并，旧包里新包没有的文件会留下（N5 E2）。

### 9.2 前置检查与收尾（脚本做；任何一条不满足就停，不自己处理）

前置：

1. 9.1 第 2 条的自启核对。
2. 没有 iWork 的后台或客户端在跑：`pgrep -fl 'iwork-daemon|iwork-client'` 为空；**隔 15 秒再查一次**（`launchd` 管着的后台退出后约 10 秒会被重拉，只查一次会漏）。
3. 演练要用的位置是空的：数据目录不存在或为空；要装到的位置上没有 `iWork.app`。在专用账号里这两条天然成立；用临时家目录时它们指向临时目录，同样成立。**脚本不替人挪走真实的数据目录或已装的应用。**
4. 两版包都过 `check-install`。

收尾（成功、失败、被中断都执行，写在脚本的退出处理里）：

1. 关客户端（给它发终止信号），等它退出。
2. 让后台停：给它发 `SIGTERM`（走停机流程，报 0），循环查到它退出为止，上限 60 秒；到点还在 → `SIGKILL` 并记进记录。
3. 再查一遍没有任何 `iwork-daemon`、`iwork-client` 进程，隔 15 秒查第二次。
4. 9.1 第 2 条的自启核对；注册了就注销并记录。
5. 删掉装上的包与留底的包。数据目录改名成 `<原名>.drill-<时间>` 留作证据，不删。
6. 最后打印一份「动过什么、现在是什么样」的清单。

### 9.3 装包的唯一做法

```sh
# NEW 是要装的包，DEST 是装到哪（如 <应用目录>/iWork.app），两者在同一个文件系统
ditto "$NEW" "${DEST%.app}.incoming.app"                 # 先完整复制到旁边；目标是新位置，不是合并
[ -e "$DEST" ] && mv "$DEST" "${DEST%.app}.prev.app"      # 旧包整个改名留底（先删更早的留底）
mv "${DEST%.app}.incoming.app" "$DEST"                   # 新包整个改名到位
```

- 旧后台要是正在跑：它握着的文件跟着旧包一起改了名，文件本身没被动，进程不受影响；它按原来的路径去看磁盘，看到的是一个完整的新包，判「装齐了另一版」后自己重启（这一点由 8.2 的 U1 实测确认）。
- 回退：`mv "$DEST" "${DEST%.app}.failed.app" && mv "${DEST%.app}.prev.app" "$DEST"`。
- 新包里没有的文件（比如旧清单）不会留下：到位的是整个新目录。

### 9.4 准备两版包

A 版在原工作区打；B 版在临时验证副本里打，只把根 `Cargo.toml` 的 `[workspace.package] version` 改成另一个值，让两版后台的 cdhash 不同。每版各打形态 A、形态 B，一共四个包：

```sh
export PATH=$HOME/.cargo/bin:$PATH
lockf /tmp/iwork-heavy-test.lock pnpm -C client tauri build                                   # 形态 A
IWORK_SIGN_IDENTITY="<自签证书的名字>" lockf /tmp/iwork-heavy-test.lock pnpm -C client tauri build   # 形态 B
```

自签证书的建法照 N5 脚本 155–172 行（`openssl` 出一张用途是代码签名的证书、`security import` 进一个钥匙串）。打包在产品负责人平时的账号里做；演练在专用账号里做时，把四个包复制到 `/Users/Shared/iwork-drill/`。

### 9.5 验收 1：恰好一种形态成立，而且能互认

```sh
CHK=<输出根>/release/examples/check-install
A=<输出根>/release/dist/unsigned/iWork.app; B=<输出根>/release/dist/signed/iWork.app
"$CHK" "$A/Contents/MacOS"     # 期望：形态 manifest=Complete signed-bundle=NotThisForm；互认 双向接受；退出 0
"$CHK" "$B/Contents/MacOS"     # 期望：形态 manifest=NotThisForm signed-bundle=Complete；互认 双向接受；退出 0
codesign --verify --deep --strict --verbose=2 "$B"     # 期望：valid on disk
ls "$B/Contents/MacOS"                                 # 期望：没有 iwork-manifest.json
jq . "$A/Contents/MacOS/iwork-manifest.json"           # 两个程序各有 sha256 与 cdhash
```

这一条不起任何进程，不依赖演练环境，打完包就能做。`self_listed` 是后台运行时自己说的，在验收 2 里看。

### 9.6 验收 2：装上后客户端拉起后台、两端互认；连接类页面走一遍

脚本照 9.3 装形态 A 的 A 版，起客户端，然后查：

- `pgrep -fl iwork-daemon`：一个进程，路径是装上的包里的 `Contents/MacOS/iwork-daemon`，参数里没有 `--dev-trust`。
- 后台日志（`<数据目录>/logs/`）里 `iwork.ipc.audit` 的记录：有 `manifest_loaded` 且 `self_listed=true`；没有 `peer_rejected`；没有 `peer_accepted_without_signature_check`（那是 `--dev-trust` 才有的）。
- 客户端窗口进到首页，不是诊断页。（窗口里是什么要人看一眼；脚本这时停下等确认。）

形态 B 重做一遍（照 9.3 整包替换成 B）：没有 `manifest_loaded`（有证书的构建不读清单），别的相同。

### 9.7 验收 3：升级不停在「安装中」；回退走得通

先做 8.2 的 U1–U4，U1 是 PASS 才往下。

A 版装着、后台在跑（验收 2 做完的样子），先关客户端（后台留着），记下后台的 pid 和运行映像，然后照 9.3 把 B 版的同形态包整包替换上去：

```sh
P=$(pgrep -f 'iWork.app/Contents/MacOS/iwork-daemon'); codesign -dvvv "$P" 2>&1 | grep CDHash
```

期望（T04 方案 2.9）：75 秒内，后台日志出现「磁盘上装齐了另一版，自行重启」；同一个 pid 的运行映像 cdhash 变成 B 版包里后台的；日志里「安装中」的记录至多出现在两次改名之间的那一下，没有每 30 秒一条地持续下去。再起客户端：连得上（新客户端和新后台互认）。

  - 隔离到什么程度：那个账号有自己的家目录、数据目录、「应用程序」位置、`gui/<uid>` 的 `launchd` 域和钥匙串。演练里哪怕误开了自启，注册的也是它那个域里的标签，和你的账号没有关系。你的数据目录、已装的应用、自启注册项从头到尾不会被读到。
  - 代价：要你建一次账号；演练时要你人在、切过去操作（看窗口那几下本来也得你来）；agent 进不了那个账号的图形会话，命令得你在那边的终端里敲（就一条）。
- **做法乙：就在你的账号里，用临时的家目录**
  - 步骤：脚本建一个临时目录当家目录，从终端直接起包里的客户端程序并把环境变量 `HOME` 指过去（不是双击、不是 `open`：那两种起法带不上这个变量）。数据目录、端点、装包的位置都落在临时目录里。
  - 隔离到什么程度：数据和应用是隔开的（数据目录与端点跟 `HOME` 走，2.4 核过）。**隔不开的有两样**：一是 `launchd` 域和自启的标签，它们跟的是真实的用户，不跟 `HOME`；演练不开自启，并且开始前后各核一遍标签没注册，开始前注册着就不做。二是 WebView 自己的缓存，它不认 `HOME`，会在你真实的 `~/Library/WebKit/`、`~/Library/Caches/` 下留下 `dev.iwork.client` 的目录，收尾时删。
  - 另要你知道：开始前你的账号里要是装着、跑着真的 iWork，这个做法就不能用（同一个用户、同一个标签，分不开）；现在你机器上没装，所以眼下可行，以后你日常用上 iWork 就只剩做法甲。窗口会开在你当前的桌面上，起的时候会抢一下焦点，所以要挑你在场、同意的时候跑。从终端直接起程序和双击打开不完全一样（没有经过系统的启动服务），「双击能不能打开」这一点这个做法证不了。
  - 代价：不用建账号、不用切换；隔离差一层，证据少一样。
- 没列的第三种（把你真实的数据目录改名留底、装到真实的「应用程序」里）是第 1 版写的做法，不推荐：要停掉、挪开、再恢复你在用的东西，中途失败时恢复步骤最长，出错的后果也最大。
- 推荐甲：隔离是系统给的，不靠脚本每一步都做对；账号建一次以后都能用。

## 15 ADR（developer 随实现写入 `docs/adr/`，编号合入时定）

### ADR-T04p-a 发布包由「打包之后装配」做成，不用打包器的 sidecar；验过才发布

- **背景**：发布包里要有后台程序；无证书的包要带一份登记两个程序身份的清单，有证书的包要整包签名且不能有清单。清单必须在所有会改文件的步骤之后写，封印必须在所有放文件的步骤之后做。T04 的 N5 在真实包上把这两条次序量过，是手工拼的。另外三件事同样要紧：装进包的得是这一次构建出来的程序；包的形态齐不等于装上能互认；没验过的包不能出现在成品路径上。
- **决定**：`pnpm -C client tauri build` 里，Tauri 只把客户端打成 `.app`（Linux 不打包）；之后由仓库自己的装配脚本放后台、写清单或签名。装配读的每个文件的位置由 cargo 报出来、由包装脚本逐个传进去，脚本没有默认路径。装配与核对都在暂存目录里做；核对问三件事（恰好一种形态、按运行时的信任规则双向互认、有证书时是预期的那张），用的是后台与握手运行时的同一段代码；过了才用两次改名发布到 `dist/`。签名只在装配步骤做。
- **备选与放弃原因**：`bundle.externalBin`：各种安装包格式能自动带上后台，但清单与成品是否一致、签名次序、两种形态怎么分配置、对平时编译的影响，都落在打包器没实测过的行为上；M1 用不上那些格式。让 Tauri 签名、装配后再重签：同一件事做两遍，先签的那一遍只会碍事。把后台直接放进 Tauri 的输出目录：中间产物和成品同一条路径，失败时分不清。装配从固定的 `target/release/` 读：构建一旦去了别处，读到的就是旧的。把「能不能互认」塞进 `PackageForm`：它回答的是磁盘上的包齐不齐，信任是另一条规则，各问各的。逐个环境变量地拒（`CARGO_TARGET_DIR` 等）：开发脚本要用，而且拒不全（cargo 配置文件里也能设）。
- **影响**：M1 不出 `.dmg` 与 Linux 安装包；`tauri build` 少接受几个参数；`peer` 多一个只读函数；装新版只支持整包替换；以后要出别的格式时照方案 8.3 先实测再换办法，核对那一段不变。
