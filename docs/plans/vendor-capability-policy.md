# 提案：厂商能力的去留规则（交 supervisor 转产品负责人）

> 2026-11-12，产品负责人在会话里要求评估「为保持各厂商行为一致、统一安全与审批边界，要不要去掉很多厂商特色能力」，评估后同意写成提案。按 AGENTS.md「欢迎质疑需求和方案」的格式：问题、建议、依据。讨论出结论之前，仍按现有文档执行。

## 一句话

不按「统一」去掉厂商能力。统一的是**结果**（底线、沙箱边界、有副作用的动作要审批、拒绝不可绕过、审计），不统一**过程**（怎么规划、怎么拆子代理、用什么技能、有哪些模式）。现有禁用清单大多站得住，因为它们本来就不是为统一而关；要改的是两处：统一的范围定得太满，用户自己的配置一刀切隔离。

## 1 问题

### 1.1 去掉的东西其实是四类，理由各不相同，文档里混在一起

| 类 | 例子 | 为什么关 | 判断 |
|---|---|---|---|
| ① 动作离开本机或离开 iWork 视野 | RemoteTrigger、`/schedule` 云端任务、PushNotification、SendMessage、DesignSync | 不经本机 hook，iWork 对目标没有规则（技术设计 7.1） | 该关，与统一无关 |
| ② 与 iWork 的回合、团队模型冲突 | 后台任务、Monitor、CronCreate/ScheduleWakeup、Workflow、EnterWorktree/ExitWorktree、厂商原生团队（需求 8.4） | iWork 还没有承载它们的模型 | 该暂缓，不该永久关；D5 已写「方向是尽量保留厂商原本的做法」 |
| ③ 隔离用户全局配置 | 用户的插件、技能、MCP、hook、全局指令（需求 8.4） | 怕放宽审批、跨项目泄漏 | 代价最大，见 1.3 |
| ④ iWork 审批做全部工具调用的唯一权威 | 用 PreToolUse hook 接管一切调用 | 三家行为一致 | 做不到，也最贵，见 1.2 |

没有一条明文规则说「什么情况下关」，所以每遇到一个新的厂商能力，都要单独走一遍实测 + 方案审查 + 产品负责人决定。

### 1.2 「唯一权威」实际做不到，已经一条条退成了「有副作用的动作受控」

T06 只接 Claude Code 一家：方案 2619 行、7 轮审查、二十多个产品负责人决定（P1–P17、D1–D5、PD-x），2026-11-10 到 11-12 三天约 131 个提交，R2 一次实测约 673 万 token（STATUS）。其中大半在追堵厂商自带能力开的口子：P13（六个工具）、P14（环境变量带进插件）、P15（自动记忆）、P16（仓库内容；最后做成 iWork 自己读 CLAUDE.md、把技能复制成插件再送进会话，等于重写厂商的加载逻辑）、P17（技能 `allowed-tools`）、PD-5（技能内联命令）、D2（进程组）、D5（后台任务）。

堵完仍留下已接受的例外：hook 不表态时读照常执行（3.4 选 A）、技能 `!命令` 不经审批（PD-5）、`allowed-tools` 放宽 CLI 自己的规则（P17）、环境变量带进插件（P14）。也就是说，保证面已经事实上收窄成「有副作用的动作 + 底线」，只是没写成原则，而是靠例外累积出来的。M2 接 Codex、agy 时如果没有这条原则，会再走一遍同样的过程。

另外，这个成本主要是 Claude Code 特有的：按 t0-findings 第 3、4 节，Codex app-server 每个动作都发审批请求，agy 的 ACP 每个动作都发 `session/request_permission`，两家都有给外部审批的正式通道；Claude Code 的 hook 是后挂的，三家里最难接。

### 1.3 用户配置一刀切隔离，直接冲着首版成功标准

需求 1.5：「作者本人长期以 iWork 替代现有工具。」现状是：用户在 Claude Code 里调好的插件、技能、MCP、全局指令，进 iWork 全部没有；导入卡在 PD-1、PD-9 上（T10f 只交付「能列出、不能导入」）。

隔离的两条理由要分开看：

- 跨项目泄漏：成立。
- 放宽审批：要放回威胁模型。用户自己装的东西是同一个用户信任的东西；已确认的边界是同用户威胁（T06 P6 审查意见、需求第 9 章 v1.73）。真正不可信的是仓库和网页。

还有一点：PD-1、PD-9 卡住，是因为导入要 **iWork 去读** MCP 配置和技能目录，可能读到凭据（T10f 第一部分第 44 行）。如果是 **厂商 CLI 自己加载** 用户配置，iWork 什么都不读，就碰不到这条不变量。

## 2 建议

### 2.1 写一条去留规则（进需求 1.4 或 8.4）

> 厂商能力默认开放。只有满足下面任一条才关：
> 1. 动作离开本机或离开 iWork 的视野（云端执行、推送到设备、发给别的会话）；
> 2. 能突破底线或沙箱，又没有经过审批的出口；
> 3. 与 iWork 正在提供的同一职能冲突，两者同时运行会打架（团队、工作区、定时）。这一类标「暂缓」，写明哪个里程碑由 iWork 承载后开放。
>
> 「别家没有」不构成关闭理由。厂商特有的能力经 ACP 的 config options、`available_commands_update`、`_meta` 与能力矩阵（需求 8.4）展示，不为界面一致而砍。

现有禁用清单按这条复核：① 类照关；② 类改标「暂缓」并挂到 M2；③、④ 类按 2.2、2.3。

### 2.2 写清保证面（进需求第 9 章或技术设计 7.0）

硬保证只覆盖：系统底线 + 有副作用的动作（写、执行命令、删除、推送、发布、沙箱外执行、MCP 非只读调用），由审批与沙箱两道闸执行；AC05 拒绝不可绕过照旧。读类动作、厂商内部的编排（子代理怎么拆、技能怎么选、计划怎么排）承认由厂商决定，审计尽力记录。

接 Codex、agy 时只验这张保证面，不重走 Claude Code 的全部决定。

### 2.3 给用户定制一条知情路径

两种做法，选一：

- **a 每个助手一个开关「沿用我自己的 Claude Code 定制」**：开了就不屏蔽用户级配置，由 CLI 自己加载。开之前写明代价：插件带的 hook 不经审批、技能 `allowed-tools` 放宽读、内联命令不经审批。仓库的 `.claude/settings.json` 仍然不加载（不可信来源，规则不变）。
- **b 走需求 8.4 已写的退路：每家一个 iWork 专用配置目录**（`CLAUDE_CONFIG_DIR` 等），用户在里面用厂商自己的方式登录、装插件。比 a 干净（不混用户日常配置），代价是用户要重装一遍。

两种都不需要 iWork 读配置内容，绕开 PD-1、PD-9。

### 2.4 M2 的会话模型按「运行时可以自己动起来」设计

否则 ② 类会从暂缓变成永久关（后台子代理、后台命令、Monitor、定时）。这条不是新决定，是 D5 方向的落实提醒。

### 2.5 Codex 的自动审查二选一

t0-findings 3.1：Codex 有 `approvalsReviewer: "auto_review"`，与 iWork 自动档的 AI 审查是同一职能。两个都开会重复，还可能替用户批掉本该问的动作。M2 接入前实测它与 `approvalPolicy` 的配合，再定用哪一个。

## 3 不建议

- 继续往「最低公约数」砍：会丢掉需求 1.3「按角色各取所长」。
- 完全透传（Vibe Kanban 一类据第三方报道默认 `--yolo`）：破坏 AC05 与统一审批这个卖点。

## 5 依据与可信度

- 内部数字：`docs/plans/T06.md`（行数、审查轮次、第 18 节决定表）、`docs/tasks/M1/STATUS.md`（R2 token 数）、`git log --grep=T06`（2026-11-10 16 个、11-11 42 个、11-12 73 个）。
- 厂商审批通道：`docs/design/t0-findings.md` 第 1、3、4 节（本机实测，Codex 0.162.1、agy 1.5.2）。
- 外部调研（子代理，2026-11-12）覆盖不全，大多出自一个第三方博客，未与官方 changelog 对照，只作旁证：ACP 本身是「公共外壳 + `_meta`/扩展方法」的设计；三家在 AGENTS.md、SKILL.md、子代理、MCP 上趋同，统一开放的成本在下降；已查范围内没找到别的工具像 iWork 这样用自己的审批引擎接管各家调用。调研里「agy 不支持 ACP」一条与本机实测不符，以 t0 为准。

## 6 产品负责人的决定（2026-11-12）

supervisor 对过现有文档后带着两处异议交产品负责人：

- V1 第 ② 条和当天已接受的例外（PD-5 技能内联命令、技能文件头 hook、P17、P14）冲突；RC7 若证明内联命令在沙箱外执行，第 ② 条会直接推翻 PD-5。
- V2 只写「底线 + 有副作用的动作」漏了越界读：FR11 写明读敏感目录清单内的路径算越界、要问，T10e 的安全清单靠它；D1 接受的例外也只是工作目录内的读。
- V3 的技术口子：让 CLI 加载用户级配置会带进整份 `settings.json`（permissions、沙箱的排除命令等列表类设置、hook、env），列表类设置与 iWork 的合并，可能让命令跑到沙箱外。

| 编号 | 决定 |
|---|---|
| V1 | 采用 2.1 的去留规则；已接受的例外（PD-5、技能文件头 hook、P17、P14）列入第 9 章已知限制、不按第 ② 条关闭；新能力一律按规则判断，实测证明某项例外能突破沙箱时回产品负责人重定 |
| V2 | 采用并补上越界读：硬保证 = 系统底线 + 有副作用的动作 + 越界读（敏感目录清单内的路径） |
| V3 | 选 b（每家一个 iWork 专用配置目录）。专用目录里的权限、沙箱、hook 等设置不得放宽 iWork 给定的审批与沙箱；做法与实测由 T06 architect 出方案，定稿并实施之前维持现有隔离 |
