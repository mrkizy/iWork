## 0 一页总览

用户把文件拖进来、粘贴进来或从选择框里选，客户端只把路径（或粘贴的字节）交给后台。**收不收、怎么收，全在后台一处判**：

| 文件是什么 | 后台怎么收 | 怎么送到运行时 |
| --- | --- | --- |
| 在 iWork 数据目录里 | 拒 | — |
| 私钥（看名字，也看内容） | 拒，提示「私钥不能作为附件发送」 | — |
| 在凭据目录里（如 `~/.npmrc`） | 先存进 `private/`，标「待确认」；用户点「仍然附加」才算数 | 内容嵌进消息正文（文本块）；不进只读区 |
| 图片 | 存一份进附件区 `attachments/` | ACP image 块；运行时不支持就改发路径，界面有提示 |
| 工作区内的别的文件 | 只记路径 | resource_link（`file://` 绝对路径） |
| 剩下的（工作区外的文件、粘贴的非图片） | 复制进附件区 | resource_link，指向只读区里的副本 |

三条最要紧的保证：

1. 凭据文件没经用户确认，内容到不了模型厂商。把关的是存储写线程：没确认的凭据附件进不了任何一条消息（第 4 节 R3）。
2. 凭据文件的内容永远不进只读区 `attachments/`（R2）。
3. iWork 经附件送出去的**字节**都是检查过的快照：附加那一刻名字或内容像私钥的，拒；存下来的快照之后谁也改不了（R4、R8）。

这三条管的是 iWork 自己送出去的内容。**工作区内的文件只送一个路径，不送内容**：附加之后文件被改了、被换了，Agent 沿路径读到的是当时磁盘上的东西，归审批与沙箱管，和它不经附件自己去读工作区是同一条规则（3.4a；产品负责人已定只送路径、接受这个缺口，PD-6）。

本方案新加的东西：一个命令 `RemoveAttachment`、一个事件 `AttachmentRemoved`、`attachments` 表一列 `message_id`、`iwork-core::attachment` 一个纯函数模块、`iwork-host` 一个读文件的实现。协议里别的都已经在了（T01 定的），只加字段。

### 3.2 受理 `UploadAttachment`

按顺序做，哪一步不过就回对应的错，什么都不写：

| 步 | 做什么 | 不过回什么 |
| --- | --- | --- |
| 1 | 来源：`ctx.client_kind == DESKTOP` 且 `ctx.signature_checked`（与 `ReadArtifact`、`ExecuteUserAction` 同一个判断函数，谁先合入谁写，另一方复用） | `PERMISSION_DENIED` |
| 2 | 对话在、不在删除中（读模型先查一遍，给友好的错；真正把关在 3.6） | `NOT_FOUND` / `CONVERSATION_DELETING` |
| 3 | 取字节。**本机路径**：必须是绝对路径、不含 NUL；占一个「读位」，在读位的线程里先 `PathResolver::resolve` 得到 `entry`、`target`，再 `AttachmentSource::read(target, 20MB)` 读出字节；受理函数最多等 30 秒（3.3）。**粘贴**：从本连接的 `UploadBuffers` 里取走 `upload_id`（3.5），不碰用户文件、不占读位 | `ATTACHMENT_SOURCE_REFUSED` / `ATTACHMENT_TOO_LARGE` / `INVALID_ARGUMENT` |
| 4 | `classify`（3.4） | 见 3.4 |
| 5 | 要存的：`put_bytes(Private 或 Attachments, 字节)` | `STORAGE_FAILURE` |
| 6 | 提交 `AttachmentStored`，`actor = User` | 投影拒了回 `CONFLICT`（对话刚被删） |

- 文件名：本机路径的附件，名字取自路径本身，**不用**命令里的 `name`（客户端可以把 `~/.ssh/id_rsa` 报成 `a.txt`）；粘贴的用命令里的 `name`。都过一遍 `sanitize_name`：去掉控制字符与路径分隔符，截到 255 个字符，空了就叫「粘贴的文件」。
- `mime`：图片只认魔数（PNG、JPEG、GIF、WebP）；客户端说是图片而魔数不认的，按普通文件。别的类型用客户端给的（格式对才用），否则 `application/octet-stream`。
- 字节在内存里最多一份 20MB，读完就交给 `put_bytes`；判定在阻塞线程池里跑，不占写线程。
- 第 5 步存了、第 6 步没提交成（崩溃、被拒）：留下一个没人引用的对象，由现有的回收在宽限期后删掉，不用另写清理。
- 幂等：受理入口先查 `commands` 表，命中直接回上次结果（技术设计 5.2；**T10a 交付**）。粘贴的缓冲取走就没了，不先查的话重发会报「找不到上传」。

### 3.3 读文件：`AttachmentSource`（端口在 `iwork-ports`，实现在 `iwork-host`）

```rust
pub trait AttachmentSource: Send + Sync {
    /// 读 `target`（已完全解析的路径）的全部内容，最多 `limit` 字节。
    fn read(&self, target: &CanonicalPath, limit: u64)
        -> impl Future<Output = Result<Vec<u8>, AttachmentSourceError>> + Send;
}
pub enum AttachmentSourceError { NotAFile, TooLarge, ChangedWhileReading, Unreadable { message: String } }
```

实现（unix）：`open(target, O_RDONLY | O_NOFOLLOW | O_NONBLOCK | O_CLOEXEC)` → `fstat` 必须是普通文件，否则 `NotAFile` → `st_size > limit` 回 `TooLarge` → 从这个描述符读，最多读 `limit + 1` 字节，读到第 `limit + 1` 个字节回 `TooLarge`。末级是链接时 `open` 报 `ELOOP`，回 `ChangedWhileReading`（路径是解析过的，末级不该是链接；是的话说明解析之后被换了）。

每个标志各防一件事：`O_NOFOLLOW` 防解析之后末级被换成链接；`O_NONBLOCK` 防路径是 FIFO 时 `open` 卡死；先 `fstat` 再读、读的时候再数一遍，防 `/dev/zero`、一直在长的文件、`st_size` 不准的文件系统。

**`O_NONBLOCK` 管不了普通文件**。网络盘（NFS、SMB）没响应时，`lstat`、`open`、`read` 都可能卡在内核里，没有办法从外面叫停。所以把三样东西的寿命分开写，各有各的边界：

| 是什么 | 活多久 | 边界 |
| --- | --- | --- |
| 请求的等待（受理函数等读的结果） | 最多 30 秒（常量 `SOURCE_WAIT_LIMIT`；本机盘上读 20MB 远不到 1 秒） | 到点回 `ATTACHMENT_SOURCE_REFUSED{reason: timed_out}`「读取超时，文件可能在没响应的磁盘上」。连接先断了的话这次受理也就结束，没人等了 |
| 读的线程（解析路径 + 打开 + 读，一个读位一条专用线程） | 到系统调用返回为止。**断线、超时都停不了它** | 它只读、不写：结果经一次性通道交回，没人等就丢掉。存对象、提交事件都在受理函数里、等到结果之后才做，所以超时或断线之后什么都不会落盘 |
| 卡在内核里的系统调用 | 到磁盘响应、被卸载，或后台进程退出为止 | 读位一共 2 个（常量 `SOURCE_SLOTS`），由读的线程自己占着，系统调用返回才放。两个都卡住时，新的本机文件附件立刻回 `ATTACHMENT_SOURCE_REFUSED{reason: source_busy}`「有文件还没读完，可能在没响应的磁盘上」，不排队 |

- 读位用专用线程，不借 tokio 的阻塞线程池，也**不用 `ArtifactStore::put_file` 读用户路径**：制品 I/O 线程只有 2 个（`artifacts.rs` 的 `IO_THREADS`），卡住了长消息、工具输出都存不了。
- 读位占满时受影响的只有「从本机路径加附件」。粘贴、确认、移除、发消息、别的命令都不经读位。
- 止血：断开或弹出那个磁盘，系统调用返回，读位自己放出来；等不了就完全退出 iWork 再开（后台退出不等这些线程）。**硬挂载的网络盘上，卡住的线程可能让进程退不干净，要等内核放手；这一点没有实测，标「待证」**。产品负责人已接受为已知限制 L4，步 7 做一次手工演练（PD-7）。
- **附件摄入这条链路上，碰用户路径的系统调用只在后台的读位里做。客户端不碰**（2/F-1）。这条规则只管附件摄入（从拖入、选择、粘贴到存成附件）：版本控制读写仓库文件、审批的路径解析（`PathResolver` 在 hook 热路径上的调用）、系统选择框自己内部的文件操作都不归它管，各照各的方案。`client-core/src/attach.rs` 现在对本机路径做 20MB 预检，用的是 `std::fs::metadata`，在会话循环里同步调（`t09-2b` 的 `session/mod.rs` `on_attach` 里的 `attach::batch`）：磁盘没响应时整个客户端的事件循环跟着卡住。挪进 `spawn_blocking` 加超时也不行：超时只停了等待，已经开始的 `stat` 停不下来，用户重试几次就在 tokio 共用的阻塞池里攒下好几个卡住的任务，正常文件的预检排在它们后面，客户端退出时运行时还要等它们。这和后台第 1 轮的问题是同一类，再给客户端造一套读位就是两套机制守同一件事。所以改成**删掉这条路**：
  - 本机路径（拖入、选择框）：client-core 只从路径字符串里取文件名，不 `stat`、不打开，直接发 `UploadAttachment{local_path}`。大小由后台查，后台的读位本来就有容量、有超时、有退出时的说法（上面的寿命表），不用再定一遍。超过 20MB 时后台在 `fstat` 那一步就回 `ATTACHMENT_TOO_LARGE`，同机一次往返，照样是当场提示。
  - 粘贴的数据：字节已经在内存里，client-core 照旧查长度（`check_size`），不涉及文件。
  - 客户端因此没有任何阻塞任务：上传是异步任务，等的是后台的回包；回包最迟在后台的 30 秒上限到了就来。客户端退出时这些任务直接丢掉，不等谁。
  - 磁盘卡住时客户端看到什么，全由后台的边界决定：第一次、第二次各等 30 秒得到「读取超时」，两个读位占满之后立刻得到「有文件还没读完」；**这期间正常磁盘上的文件也加不了**（读位是共用的），粘贴照常；磁盘恢复或被弹出后读位放出，再加就成。
  - 行为上的一处变化：原来一批里任何一个超过 20MB 就整批不发；现在和后台别的拒绝（私钥、不是文件）一样，逐个受理，停在第一个被拒的文件上，它前面的已经加上，提示点名是哪个文件。

### 3.4 归类：`iwork-core::attachment::classify`（纯函数）

```rust
pub struct Candidate<'a> {
    pub source: Source<'a>,        // Path { entry, target } | Pasted
    pub names: &'a [&'a str],      // 路径：entry 与 target 的文件名；粘贴：客户端给的名字
    pub content: &'a [u8],
}
pub struct Zones<'a> {             // 调用方备好，全是规范路径
    pub credential: &'a [PathBuf], // protected_paths().credential
    pub data_dir: &'a [PathBuf],   // protected_paths().data_dir
    pub workspace_root: &'a CanonicalPath,
}
pub enum Intake {
    Refuse(Refusal),               // InsideDataDir | PrivateKey | CredentialNotText | CredentialTooLarge
    Credential,                    // 存 private/，needs_confirmation = true
    Image { mime: &'static str },  // 存 attachments/
    WorkspaceRef,                  // 只记路径
    Copy,                          // 存 attachments/
}
pub fn classify(c: &Candidate, zones: &Zones, fs: &impl PathResolver) -> Intake;
```

**顺序就是规则，从上往下第一条命中的算数**：

| 序 | 条件 | 结果 |
| --- | --- | --- |
| 1 | `entry` 或 `target` 任一个在数据目录之下 | 拒 `InsideDataDir` |
| 2 | `private_key::matches(names, content)` | 拒 `PrivateKey` |
| 3 | `entry` 或 `target` 任一个命中凭据位置 | 内容是 UTF-8 文本（不含 NUL）且不超过 256 KiB → `Credential`；否则拒（PD-3 已定） |
| 4 | 魔数是图片 | `Image` |
| 5 | `entry` 与 `target` **都**在工作区之下 | `WorkspaceRef`（PD-6 已定） |
| 6 | 剩下的 | `Copy` |

粘贴的数据没有路径，只走第 2、4、6 条。

- **凭据位置从哪来**：`protected_paths(snapshot_rules, env) -> {credential, data_dir}`。它就是 `constraints_for` 现在挑 `deny_read_write` 的那段过滤（底线层、`PathUnder | PathIs`、`UserActionEligible`），抽成一个函数，`constraints_for` 改成调它；数据目录那一条按 `env.data_dir` 分出来。`snapshot_rules` 用开会话的同一个 `snapshot_for`（带 `rule_paths_for` 的别名），所以 `~/.npmrc` 是指向 `~/dotfiles/npmrc` 的链接时，直接附加 `~/dotfiles/npmrc` 也算凭据位置。按对话取 `EnvPaths` 与规则快照的函数**由 T10a 交付**（它开会话要用）。
- **为什么两种视图都看**（照 T07「链接两种视图都过底线」）：工作区里放一个 `notes.txt → ~/.npmrc`，`entry` 在工作区、`target` 在凭据目录，只看 `entry` 就会当成工作区文件；`~/.npmrc → ~/dotfiles/npmrc`，只看 `target` 又会漏掉入口。
- **为什么第 5 条要两个都在工作区**：只要有一个在外面，Agent 沿这个路径去读就可能撞审批或读不到；复制一份进附件区，送达才有保证。
- **为什么图片排在工作区前面**：image 块要字节。存一份快照，发出去的就是用户附加那一刻的图；不存的话发消息时要再读一遍工作区文件，那时文件可能已经被 Agent 换成指向 `~/.ssh` 的链接，后台（不在沙箱里）替它读出来发给厂商，等于绕过底线。存快照让「读用户文件」只发生在用户动手的那一刻（PD-4 已定）。
- 工作区本身包住凭据目录时（家目录加成项目，T06 P12）：第 1–3 条排在前面，照样先判凭据。

**私钥特征**（`private_key.rs`，一张表；名字比较不分大小写）：

| 类 | 取值 | 出处 |
| --- | --- | --- |
| 文件名恰好是 | `id_rsa`、`id_ed25519` | 技术设计 9.2 第 3a 条 |
| 文件名恰好是 | `id_dsa`、`id_ecdsa`、`id_ecdsa_sk`、`id_ed25519_sk` | 本方案补（PD-2 已定） |
| 扩展名 | `.pem`、`.key` | 技术设计 9.2 第 3a 条 |
| 扩展名 | `.ppk`、`.p12`、`.pfx` | 本方案补（PD-2 已定） |
| 内容 | 任一行以 `-----BEGIN` 开头、同一行里有 `PRIVATE KEY` | 技术设计 9.2 第 3a 条 |
| 内容 | 开头是 `PuTTY-User-Key-File-` | 本方案补（PD-2 已定） |

`names` 里任一个名字命中、或内容命中，就是私钥。`id_rsa.pub` 不命中（名字不是恰好 `id_rsa`）。工作区里的文件附加那一刻像私钥的也拒：拦的是用户这一下误操作，规则不分位置更好记；它不保证这个路径以后不变成私钥（3.4a）。

### 3.4a 快照和路径引用：各保证什么

附件有两种送法，保证不一样，不能混着说：

| | 快照（凭据、图片、复制、粘贴） | 路径引用（`WorkspaceRef`） |
| --- | --- | --- |
| 送出去的是什么 | 存下的那份字节，或指向它的路径（`attachments/` 里按内容哈希命名的文件） | 一个路径字符串，没有内容 |
| 查过什么 | 位置、私钥、大小、类型，查的就是存下的那份字节 | 附加那一刻的内容查过私钥与大小，只为拦误操作 |
| 附加之后源文件变了 | 不影响。快照按内容寻址，存储不改写；`attachments/` 对 Agent 只读（底线与沙箱，三档相同） | Agent 读到的是**那一刻磁盘上的内容**。原地改写、换成链接都算 |
| 谁管 Agent 读到什么 | 不用管，字节是查过的 | 审批与沙箱，照「工作区内的读」「链接两种视图」的现有规则，和它不经附件直接读同一个路径完全一样 |

为什么路径引用不去追「内容还是不是查过的那份」：

- 需求 FR03 写的是「仓库内文件传路径引用」（已确认）。M1 的成员本来就直接读写用户的工作副本（技术设计 8.3），工作区内的读三档都放行。工作区里有一把私钥，Agent 不经附件 `cat` 它就读得到；附件给的那个路径不多给它任何东西。
- 所以这里的缺口要说清：**用户附加了一个工作区文件，之后这个路径被改写成私钥，或被换成指向工作区内另一把私钥的链接，Agent 沿它读到私钥，内容随工具结果进了模型。这不违反底线，但用户以为自己附加的是别的东西。** 换成指向工作区外的链接时照常过审批：指向凭据目录的底线拒；指向敏感目录的在手动档询问，自动档先过 AI 审查，而审查看得到用户消息里的附件说明，可能因此放行（AI 审查不是安全边界，需求第 9 章已知限制）。
- 发消息前由后台再查一遍堵不住：查完到 Agent 去读之间文件照样能变，还多出一个后台替 Agent 读文件的入口。要让这一类也有「送出去的是查过的字节」的保证，只有也存快照一条路（PD-6 选项 b），代价写在那里，产品负责人没选。
- PD-6 已定 a（产品负责人 2026-11-13）：照需求原文只送路径，缺口登记为 L7，由两条用例钉住行为（R9）。

### 3.5 分片上传：`UploadBuffers`

粘贴的数据先经 `Chunk` 帧到后台，再由 `UploadAttachment{upload_id}` 认领。缓冲按连接隔离：

| 规则 | 值 | 越界怎么办 |
| --- | --- | --- |
| 只收桌面客户端连接的分片 | — | `ChunkRefused(PERMISSION_DENIED)` |
| `offset` 必须等于这个 `upload_id` 已收的长度；`last` 之后不再收 | — | `ChunkRefused(INVALID_ARGUMENT)` |
| 单个上传 | ≤ 20MB | `ChunkRefused(ATTACHMENT_TOO_LARGE)` |
| 每条连接没认领的上传 | ≤ 4 个、合计 ≤ 40MB | 先丢掉 60 秒没动静的；还超就 `ChunkRefused(PAYLOAD_TOO_LARGE)` |
| 认领 | 只能由发分片的那条连接认领；没收到 `last` 的不能认领；认领即取走 | `INVALID_ARGUMENT` |
| 连接关闭 | 这条连接的缓冲全清（`connection_closed`） | — |

`ChunkRefused` 之后 ipc 会断开这条连接（`lanes.rs:243`），客户端按断线重连；正常客户端发之前自己查过 20MB，走不到这里。不设定时器，过期的在下一次收分片时顺手清。

### 3.6 存储：写线程把关

`attachments` 表加一列（迁移 `0002_attachment_message.sql`）：

```sql
ALTER TABLE attachments ADD COLUMN message_id TEXT;   -- 随哪条消息发出去了；没发为 NULL
```

「这个附件属于哪条消息」以这一列为准。T10a 填 G3（`GetConversationResult.attachments`）时也读它：一页消息引用的附件，加上 `message_id IS NULL` 的。

**G3 的附件契约**（R16）：查询结果里的每个 `Attachment`，`needs_confirmation` 照存下的快照原样给，`confirmed` 从 `attachments.confirmed` 列填。把行转成 proto 的函数只有一个：`attachment_to_proto(&Attachment, confirmed: bool)`，签名上就要这个值，`GetConversation`、订阅快照、本卡的查询都调它，不各自拼。客户端只在 Rust 侧算一次「还待不待确认」= `needs_confirmation && !confirmed`，托盘的确认框、发送时带不带都读这一个结果。

投影带条件，不满足就报 `StorageError::Projection`，整条命令回滚（和现有的 `exec_hit` 同一个机制，在线与重建走同一条路）：

| 事件 | 投影 | 不满足意味着 |
| --- | --- | --- |
| `AttachmentStored` | 对话行在、`state = 'active'` 才插入 | 对话刚被删 |
| `AttachmentConfirmed` | `UPDATE … SET confirmed = 1 WHERE id = ? AND needs_confirmation = 1`，要命中 | 附件已被移除 |
| `AttachmentRemoved` | 删这个附件的 `artifact_refs` 行；`DELETE … WHERE id = ? AND message_id IS NULL`，要命中 | 已经随消息发出，或已移除 |
| `MessageAppended`（`attachments` 非空时才多做） | 对每个附件：`UPDATE … SET message_id = ? WHERE id = ? AND conversation_id = ? AND message_id IS NULL AND (needs_confirmation = 0 OR confirmed = 1)`，要命中 | 附件被移除了、被别的消息用了、是别的对话的，或是**没确认的凭据附件** |

为什么放在写线程：受理函数「先查读模型、再提交」中间隔着异步边界，两条命令可以穿插（发消息和移除同一个附件、同一个附件发两次、上传时对话正在删）。写线程是唯一能「查了就写」的地方（技术设计 5.2 单写者）。受理函数里的读模型检查只为了给出说得清的错误，不当保证用。

这比 T02 方案 2.6 写的「状态前提只对审批、卡片两类」多了一处，实施前请 supervisor 知会 T02 的方案（第 11 节）。不带附件的消息不多执行任何语句，助手消息的写入路径不变。

`ReadModelPort` 加两个查询：`attachment(id) -> Option<AttachmentRecord{attachment, confirmed, message_id}>`；`attachments_by_ids(&[AttachmentId])`（发消息与续接时取）。

### 3.7 送达：发消息时附件怎么变成输入块

`iwork-ports::agent::ContentBlock` 改成：

```rust
pub enum ContentBlock {
    Text(String),
    Image { mime: String, data: Vec<u8> },
    /// 运行时自己去读的本机文件；path 是绝对路径
    FileLink { path: PathBuf, name: String, mime: String, size: u64 },
}
```

占位的 `Attachment{artifact, …}` 删掉（全仓只有 `content_to_acp` 一处匹配它）。`iwork-agent-acp::content_to_acp`：`Image` → ACP image 块（base64）；`FileLink` → `ResourceLink(name, "file://" + 百分号编码的绝对路径)`，带 `mime_type`、`size`。

怎么送由纯函数定，后台照做：

```rust
pub enum Delivery { InlineText, ImageBlock, PathLink }
pub fn plan_delivery(items: &[DeliveryInput], caps: &RuntimeCapabilities) -> Result<Vec<Delivery>, NotDeliverable>;
```

| 附件 | 条件 | 送法 | 块 |
| --- | --- | --- | --- |
| `CredentialInline`，已确认 | — | `InlineText` | `Text`：`[iWork] 用户附加了文件 <名字>（来自 <source_path>），内容如下：` + 内容 + `[iWork] 附件 <名字> 结束` |
| `CredentialInline`，没确认 | — | **`Err`**，这一轮不发 | — |
| 图片 | 运行时支持图片，且不超过 `IMAGE_INLINE_MAX`（等实测 A1） | `ImageBlock` | `Image`，字节从附件区读 |
| 图片 | 否则 | `PathLink` | `FileLink`，指向附件区里的副本 |
| `RepoPath` | — | `PathLink` | `FileLink`，路径就是记下的绝对路径；后台不读这个文件，`size` 填附加时记下的值 |
| `Copied` / `Pasted`（非图片） | — | `PathLink` | `FileLink`，指向附件区里的副本 |

- 「没确认的凭据附件 → `Err`」是 3.6 之外的第二道：就算投影条件哪天被改坏，内容也进不了输入块。
- 附件区副本的路径由 `ArtifactStore::attachment_path(&ArtifactRef) -> Result<PathBuf, ArtifactError>` 给，**只对 `Attachments` 区回路径**，`Private`、`Artifacts` 一律报错。这样没有任何调用方能把 `private/` 的路径递给运行时。
- I/O 部分是 `attachment_blocks(message 的附件, caps, store) -> Result<Vec<ContentBlock>, String>`：调 `plan_delivery`，按结果读字节、拼块。T10a 的「用户消息 → blocks」函数（新回合与续接共用的那一个，T10a 卡范围 2）在正文块后面接上它的结果；取不出来时新回合以失败收尾并写明是哪个附件，续接填 `ResumeRequest::Unavailable(原因)`（T06 方案 5.2a 已有这条路）。
- 路径链接送到桥接后变成一段写明路径的文字（T06 `input.rs`）。Agent 用 Read 或 `cat` 去读：附件区的读由 `baseline.data-dir.readonly.attachments` 放过底线、不算越界、不询问；写被 `baseline.data-dir` 拒（T07 `data_dir_zones`）；命令那一侧由沙箱 `allowRead` + `denyWrite` 管（T06 G4 ①e′、①f）。这一段本卡不加规则，只在端到端里验。

### 3.8 确认与移除

**`ConfirmCredentialAttachment`**：来源检查同 3.2 第 1 步（不是桌面客户端连接 → `PERMISSION_DENIED`）；附件不在 → `NOT_FOUND`；不需要确认 → `PRECONDITION_FAILED`；已确认过 → 直接回成功、不写事件（客户端不靠这条事件清状态：查询结果里带着 `confirmed`，R16）；否则提交 `AttachmentConfirmed`，`actor = User`。事件本身就是审计记录（谁、何时、哪个附件）。日志只写附件 id 与命中的规则 id（如 `baseline.cred.npmrc`），不写内容。

**`RemoveAttachment`**：附件不在 → `NOT_FOUND`；已随消息发出 → `PRECONDITION_FAILED`；否则提交 `AttachmentRemoved`。投影删掉引用行，副本过了回收宽限期被删（凭据副本同样；PD-1 已定上传时就存，这段留存是 L5）。

**`SendMessage`（T10a 受理，本卡加附件检查）**：受理时对每个 `attachment_id` 查一遍读模型，给出点名的错：不在或不是这个对话的 → `NOT_FOUND`；已发过 → `PRECONDITION_FAILED`；待确认 → `ATTACHMENT_NEEDS_CONFIRMATION`（82）。提交被 3.6 的条件拒了 → `CONFLICT`「附件状态变了，请重试」。这几种错的 `details["attachment_id"]` 带上是哪个附件，客户端靠它认出「这是附件引起的拒绝」（3.9）。`attachment_ids` 为空的 `SendMessage` 不查附件表、投影也不碰附件行：**附件的任何状态都挡不住一条不带附件的消息**（R15）。

| `intent.rs` 的 `SendMessage` | 随消息发出的附件由 Rust 定：网页给的 `attachment_ids` 里剔掉 `is_pending` 的；`without_attachments` 为真时整个清空。**待确认的附件不挡发送**，留在托盘里（R15） |

下面「待确认的附件不挡发送」「框点了就关」这两处改了安全类界面的行为，产品负责人已定这样做（PD-9 选 a）；文案与样式仍由设计窗口定（第 11 节第 8 条）。

确认框什么时候开：带 `confirm` 的附件新出现在托盘里时自动弹一次；点带「待确认」标注的卡片再开。「这个附件弹过没有」是网页本地的界面状态（和菜单开合一类，T09 方案 2.5），不进 Rust。两个按钮点了之后不管命令成不成，框都关：成了，卡片随事件变；没成，错误显示在输入框上方，卡片还是「待确认」。这样确认或移除命令坏掉时，框不会把界面卡死。刷新、重连、重开应用之后：还待确认的附件仍在托盘里带着标注；已确认的没有 `confirm`，不再弹。

私钥被拒、超限、不是文件这些错，沿用现有的路：命令的错误 → `IntentAck.error` 或 `attach_error`，显示在输入框上方；文字用后台给的 `message`（如「『id_rsa』是私钥，不能作为附件发送」）。

首页不动：没有对话就没有 `conversation_id`，回形针保持置灰（产品负责人 2026-11-12 定）。拖进来的是文件夹时，后台回 `not_a_file`；要不要改成走「添加项目」是 T10c 的事。

## 5 出事场景

每条写三件事：会出什么事 / 怎么止血和回退 / 由什么保证。

**S1 凭据文件没提示就发出去了**
- 出什么事：用户拖了 `~/.aws/credentials`（或工作区里一个指向它的链接、它的真实位置），位置判定漏了，按普通文件复制进附件区，所有对话的 Agent 都读得到，内容也可能进模型厂商。
- 止血：第一步轮换这份凭据。然后在 iWork 里删掉那个对话（引用随之删掉），并手动删 `attachments/sha256/<哈希前 2 位>/<哈希后 62 位>`（哈希在这条附件的事件里）；删文件不影响后台运行，之后读它的回合会以「附件读不到」失败。修判定后发新版。
- 保证：R1、R5 的测试；`credential_copy_never_in_attachments_area`。手动删文件后后台照常：`missing_attachment_object_fails_turn_with_reason`。

**S2 私钥漏过去**
- 出什么事：没有 PEM 头的二进制私钥（DER、改了扩展名的 `.p12`）、名字不在表里的密钥，按普通文件收了。
- 止血：同 S1，轮换密钥。表加一行发新版。
- 保证：表内的由 R4 保证。表外的是已知限制（第 9 节 L1）。

**S3 Agent 调包**
- 出什么事：① 用户附加工作区里的 `a.png`，Agent 在用户点发送之前把它换成指向 `~/.ssh/id_rsa` 的链接，想让后台替它读。② 上传那一瞬间，并发运行的 Agent 把文件换掉。
- 止血：① 走不通：图片附加时就存了快照，发消息时后台不读源文件；非图片只给路径，Agent 自己去读会被底线拒。② 末级被换成链接时 `O_NOFOLLOW` 让打开失败；读到的内容是私钥的由内容检查拦住；上级目录被并发换成链接、且换进来的是没有私钥特征的凭据文件，拦不住（第 9 节 L2，和需求 v1.70 是同一类）。
- 保证：R9 的前两条；`source_refuses_symlink_swapped_in`。

**S3a 工作区里的附件，附加之后变成了私钥**
- 出什么事：用户附加工作区里的 `notes.txt`（普通内容，归为路径引用）。发送之前或 Agent 去读之前，这个路径被原地改写成私钥内容，或被换成指向工作区内 `deploy/key.pem` 的链接（Agent 自己干的，或别的程序）。Agent 沿路径一读，私钥随工具结果进了模型。底线没被违反（工作区内的读本来就放行），但用户以为附加的是一份笔记。
- 止血：轮换那把密钥。工作区里本来就不该放不想让 Agent 读的私钥：不经附件它也读得到。想让某个文件以附加那一刻的内容为准，把它放到工作区外再附加（那样存快照）。
- 保证：这是路径引用的性质，不是能修的缺陷；登记为 L7，产品负责人已接受（PD-6）。现在的行为由 R9 的 `workspace_ref_rewritten_in_place_sends_path_only`、`workspace_ref_swapped_to_workspace_key_link` 钉住。

**S4 取消了确认，凭据副本还在盘上**
- 出什么事：用户在确认框点「取消」，`private/` 里那份副本要等回收（宽限期 24 小时）才删。
- 止血：这段时间它在 `private/`（目录 0700、文件 0600），Agent 读不到（底线与沙箱都挡）、`ReadArtifact` 读不到。要立刻清：退出 iWork 后手动删 `private/sha256/…` 下对应文件。
- 保证：`cancelled_credential_copy_is_collected`（移除后拨过宽限期跑回收，文件没了；对照：没移除的还在）。PD-1 已定上传时就存，这段留存登记为 L5。

**S5 超大或读不完的文件**
- 出什么事：拖进来的是 FIFO、设备文件、正在被写的日志；或者是没响应的网络盘上的普通文件，`lstat`、`open`、`read` 卡在内核里。
- 止血：FIFO、设备文件在 `fstat` 那一步就拒；在长的文件读到上限即停。**卡在内核里的那种停不了**，按 3.3 的寿命表分三层说：
  1. 这一次请求：最多等 30 秒，回「读取超时」，什么都没落盘。断线重连不会让它更快结束，也不需要。
  2. 读的线程：一直卡到磁盘响应。最多卡住 2 条（两个读位）；占满之后，新的本机文件附件立刻回「有文件还没读完」，粘贴、确认、移除、发消息、别的命令全都照常。
  3. 放出读位：断开或弹出那个磁盘；等不了就完全退出 iWork 再开。硬挂载的网络盘上进程可能要等内核放手才退得掉，这一点没有实测（待证）。
- 客户端这一侧：不碰文件，没有会卡住的东西；看到的就是上面三层透过回包的样子，读位占满时正常磁盘上的文件也加不了、粘贴照常；任何时候都能退出。
- 保证：R7 的 `blocked_source_times_out_and_commits_nothing`、`blocked_source_disconnect_then_retry`（用可控的阻塞源走完「卡住 → 超时 → 断线重连 → 重试 → 占满 → 放开恢复」）；客户端的 `stalled_disk_from_client_side`（卡住 → 超时 → 多次重试 → 到上限 → 正常文件被拒、粘贴成功 → 放开后恢复）与 `client_shuts_down_with_uploads_pending`。真实网络文件系统的部分待证：步 7 的手工演练里挂一个 SMB 或 NFS 共享、断网后拖一个文件，记下三层各自的表现与「完全退出」要多久，结果写进报告；演练做不成就照实写没做。L4「中止不了」产品负责人已接受（PD-7），演练结果出来再看要不要补。

**S6 分片上传被滥用或中断**
- 出什么事：客户端发了分片不认领、乱发 `offset`、崩在一半。
- 止血：上限挡住内存；连接一断缓冲全清。
- 保证：`upload_buffers_limits`、`upload_buffers_cleared_on_close`、`claim_from_other_connection_refused`。

**S7 两条命令穿插**
- 出什么事：见 R10 列的四种。
- 止血：后到的那条被拒，界面提示重试；不会留下「消息引用了已移除的附件」这种状态。
- 保证：R10 的测试。

**S8 崩溃**
- 出什么事：① 存了对象、还没提交事件就崩；② 分片收到一半后台崩；③ 有待确认附件时后台或客户端重启。
- 止血：① 对象没人引用，回收会删；② 缓冲在内存里，没了，用户重新粘贴；③ 还待确认的附件仍在托盘里带着「待确认」标注，点卡片开确认框；已确认的不用再确认（R16）。
- 保证：`crash_between_put_and_commit_leaves_only_garbage`（崩溃注入：重启后没有附件行，回收后没有文件）；`pending_confirmation_survives_restart`；`confirmed_attachment_survives_reconnect`。

**S9 发消息时附件取不出来**
- 出什么事：附件区的文件被手动删了、磁盘坏了；或图片大到运行时不收。
- 止血：这一轮以失败收尾，说明行点名是哪个附件；用户重新附加再发。回合失败不影响对话里别的东西。
- 保证：`missing_attachment_object_fails_turn_with_reason`；图片大小等实测 A1 定了上限后加 `oversized_image_goes_by_path`。

**S10 新版本有问题要退回去**
- 出什么事：这一版带迁移 `0002` 和新事件种类 `AttachmentRemoved`。库里一旦写进过 `AttachmentRemoved`，旧程序读到不认识的事件会以退出码 12 拒绝启动（T04 方案 S8、T07 PD6）。
- 止血：照 T04 方案 Q4 与 T07 方案 6.10.15 PD6（产品负责人 2026-11-10 定）、T07 方案 S6 的做法，只用现有能力：
  1. **停**：`CancelAll` 或「完全退出 iWork」，按取消流程结束各回合。问题只在附件上时不用停整个 iWork，照 S11 接着用。
  2. **数据不动**：不换回迁移前的备份，方案不给这个步骤、也不指引用户这么做。换回备份会让排着队的待发消息重投、拒绝记忆退回去、备份之后做过的外部动作再做一遍（T04 方案 Q4 当时的理由）。也不装回旧版：旧版读到 `AttachmentRemoved` 起不来。
  3. **向前修**：发紧急修复版，修复版不夹带迁移、不夹带新事件种类。装上后库原样可用。
- 保证：T04 已有 `process::unknown_event_kind_refuses_and_keeps_data`（旧程序遇到不认识的事件：拒绝启动、库不变）。本卡的修复版约束进发版检查表（STATUS 里 PD6 落地的那一项），不另写测试。

**S11 附件命令坏了（新版本的缺陷、存储里某一行对不上）**
- 出什么事：`UploadAttachment`、`ConfirmCredentialAttachment`、`RemoveAttachment` 三条全部或部分报错。托盘里已经有一个待确认的凭据附件，确认不了、也移除不掉。要是发送被它挡着，这个对话就发不出任何消息；助手私聊只有一条对话，等于这个助手整个用不了。
- 止血：不依赖附件命令（R15）。待确认的附件本来就不挡发送、不随消息发，普通消息照常发；确认框点了就关，不会卡住界面。托盘里能发的附件要是让发送被拒，提示上点「不带附件发送」。坏掉的附件留在托盘里带着标注，等修复版；项目对话也可以另开一个对话。全程没有任何一步绕过确认：没确认的凭据附件在客户端被剔掉、在写线程被拒、在 `plan_delivery` 报错，三处都没动。
- 保证：`pending_attachment_never_blocks_plain_messages`（起点就是「持久的待确认附件 + 三条附件命令都失败」，走真实的 client-core）、`rejected_send_offers_without_attachments`、`attachment_commands_isolated`。

## 7 性能（需求第 14 章）

- 附件不在热路径上。受理一个 20MB 的附件：读 + 算哈希 + 写 + fsync，都在阻塞线程池，不占写线程；提交只是一条小事件。
- 存储写入：不带附件的 `MessageAppended` 不多执行语句。动了投影，照 AGENTS.md 附 `cargo bench -p iwork-store --bench write_commit` 前后对比（同一时段交替多轮取中位数），预期没有差别。
- 后台内存（运行中 ≤ 200MB）：受理时最多一份 20MB；分片缓冲每条连接 ≤ 40MB；发消息时一张内嵌图片要原字节加 base64 两份。`IMAGE_INLINE_MAX` 定下来后，一条消息内嵌图片的总量设同样大小的预算，装不下的走路径（和 A1b 一起定，不另加机制）。
- 客户端：托盘多几个字段，帧合并不变。

## 13 ADR（developer 随组 B 写入 `docs/adr/`，编号合入时定）

### ADR-T10d-a 附件收不收在后台一处判；没确认的凭据附件由存储写线程挡在消息之外

- **背景**：附件有三种入口（拖入、粘贴、选择），文件可能在凭据目录、数据目录、工作区内外，可能是链接，可能在用户动手之后被 Agent 换掉。需求要凭据文件先确认、私钥一律拒、凭据内容不进只读区。
- **决定**：① 客户端只交路径或字节，位置、私钥、类型全由后台的一个纯函数 `classify` 按固定顺序判，凭据位置读底线那一份清单。② 要内容的附件在附加那一刻存内容寻址的快照，之后后台不再读用户文件。保证只对快照成立；工作区内的文件只送路径，Agent 读到什么归审批与沙箱（PD-6，产品负责人 2026-11-13 定）。③「没确认的凭据附件进不了消息」「一个附件至多属于一条消息」由存储写线程在投影里判，受理函数的检查只管报错好不好懂。④ 递给运行时的路径只能从 `attachment_path` 拿，它只认附件区。⑤ 附件的状态挡不住不带附件的消息。⑥ 读用户文件的线程只读不写、数量封顶，请求的等待另有上限。
- **放弃的做法**：在客户端判（网页与壳都可以被绕过，也违反「网页只渲染」）；应用服务里加对话级的锁（每个写附件状态的入口都得记得加锁，漏一个就没了保证）；工作区内的图片发消息时再读（判定多一个入口，还给了 Agent 调包的机会）；确认时才存凭据内容（见 PD-1）。
- **影响**：`attachments` 表多一列、多一个事件种类（只能向前修）；T02「投影不判状态」多了附件这一处例外；以后加新的附件来源（如 M2 的转发）只要走 `classify`，不用再想一遍凭据与私钥。
