## 2 推荐方案

### 2.1 数据目录（设计 5.1）

`iwork_store::data_dir::DataDir`：

```rust
pub struct DataDir { root: PathBuf }
impl DataDir {
    /// 三平台定位：macOS `~/Library/Application Support/iWork/`；Linux `$XDG_DATA_HOME/iwork/`
    /// （未设则 `~/.local/share/iwork/`）；Windows `%LOCALAPPDATA%\iWork\`。
    /// 环境变量 `IWORK_DATA_DIR` 存在时优先（开发与测试用；发布构建也认，便于诊断时换目录）。
    pub fn locate() -> Result<Self, DataDirError>;
    pub fn from_root(root: PathBuf) -> Self;
    /// 建全部子目录；Unix 下 root 与子目录 0700。已存在的不改权限（用户自己改过就尊重）。
    pub fn ensure_layout(&self) -> Result<(), DataDirError>;
    pub fn db_path(&self) -> PathBuf;                 // iwork.db
    pub fn backups(&self) -> PathBuf;                 // backups/
    pub fn area(&self, area: ArtifactArea) -> PathBuf; // artifacts/ attachments/ private/
    pub fn imports(&self) -> PathBuf; pub fn run(&self) -> PathBuf; pub fn logs(&self) -> PathBuf;
}
```

不引 `directories` crate：三个平台各读一个环境变量，手写比适配它的目录习惯（Windows 多一层 `data\`，Linux 把名字转小写）更直接。`DataDirError` 只有 `HomeNotFound`、`Io{path, message}` 两个变体，是 store 自己的类型；`open()` 把它映射成 `StorageError::Io`。

子目录清单：`iwork.db`（+ `-wal`、`-shm`）、`backups/`、`artifacts/`、`attachments/`、`private/`、`imports/`、`run/`、`logs/`。`backups/` 是设计 5.5 用到但 5.1 没列的（第 9 节）。

### 2.2 打开流程、迁移与协议主版本门（设计 5.5）

`SqliteStore::open(dir, codec, projector, clock, config)` 按顺序做：

1. `dir.ensure_layout()`。
2. **探测**（协议主版本门）：`iwork.db` 不存在或为 0 字节 → 新库，跳到第 5 步（首次初始化没提交的空库见下面「没有 `meta` 表」两条）。否则**在副本上探测，原文件不被任何 SQLite 连接打开**：
   - 把 `iwork.db`、`iwork.db-wal`、`iwork.db-shm`（后两个存在才复制）原样复制到 `backups/.probe-<ulid>/`（同一数据目录、同一文件系统）。此时单实例锁已拿到（T04 第 2 步），没有别的进程在写库，副本就是一份一致的快照；崩溃残留的 WAL 帧也在副本里。为什么不用只读连接直接读：审查用 SQLite VFS 探针证实，只读连接在「源库 WAL 模式、`-wal` 预先存在且为 0 字节」时会在关闭时删掉这个空 WAL，`-shm` 也会被创建或改写——「不写原库」靠只读连接证明不了，不碰原文件才证明得了。
   - 打开副本（读写都行，副本随后就删），读 `meta`：
     - 没有 `meta` 表，且副本的 `sqlite_master` 一个对象都没有（表、索引、视图、触发器都没有）→ **首次初始化没提交**（第 5 步的事务回滚了，或进程在提交前被杀；SQLite 文件头已写出，所以不是 0 字节），按新库处理，跳到第 5 步。空库里没有任何数据，重新初始化不会丢东西（第 1 轮代码审查 1/F-6，supervisor 2026-11-10 补）。
     - 没有 `meta` 表、但有别的对象 → 不是 iWork 的库，返回 `Io{message: "<路径> 不是 iWork 数据库（无 meta 表）"}`，不碰原文件。
     - `protocol_major ≠ codec.protocol_major()` → 从副本 `VACUUM INTO backups/<UTC 时间>-protocol-v<库里的>.db`（WAL 里已提交的帧一起合进备份），返回 `StorageError::ProtocolMajorMismatch{database, program, backup}`。备份失败（磁盘满、`backups/` 不可写等）同样拒绝，返回 `Io`，消息里带两个主版本号与备份失败原因。
     - `schema_version > MIGRATIONS.len()` → 新程序写过的库被旧程序打开，拒绝（`Io`，消息写明两个版本号）。
   - 无论哪条路径，最后先关闭副本连接，再删掉 `.probe-<ulid>/`；上次崩溃留下的 `.probe-*` 目录在这一步开头一并清掉。原来的三个文件自始至终字节与存在性都不变。
   - 清理失败（文件被占用、权限、I/O 错误）不改变探测结论：探测已经得出的结果照常返回（协议门拒绝时仍返回 `ProtocolMajorMismatch`，诊断不被遮盖；探测通过时照常往下走），清理失败只写一条 `warn` 日志，带目录路径与错误。残留的 `.probe-*` 只是临时文件，任何路径规则都不会把它当成主库（主库固定是数据目录根下的 `iwork.db`），下次启动在这一步开头重试清理；重试仍失败同样只记日志，不阻止启动。（supervisor 2026-11-09 按审查 2026-11-09-m1-t02-plan/3/F-1 补写）
   - 代价：复制一次 db + wal。M1 的库是几十 MB 量级，SSD 上几十毫秒，计入冷启动预算（7.2）；复制失败（磁盘满）→ `Io`，不往下走。
3. 打开读写连接，设 PRAGMA（见 2.3）。
4. **迁移**：`schema_version < MIGRATIONS.len()` → 先 `VACUUM INTO backups/<时间>-schema-v<旧>.db`，然后**本次全部待执行的迁移与 `UPDATE meta SET value = <目标版本> WHERE key = 'schema_version'` 放在同一个事务里**（SQLite 的 DDL 是事务性的）。任一步失败 → 整个事务回滚，`schema_version` 仍是升级前的值，关闭连接，返回 `Io`（消息含失败的迁移号、SQLite 错误、备份路径）。这样失败后库仍是旧程序认识的版本，装回旧程序即可打开（设计 5.5「失败保持旧库不动」）。不采用「每个迁移一个事务」：跨两个版本升级时前一个成功、后一个失败，库会停在中间版本，`schema_version > MIGRATIONS.len()` 的拒绝让旧程序也打不开，用户两头无路。
5. **新库**：在一个事务里跑全部迁移并写 `meta{schema_version, protocol_major, created_at}`。
6. 读 `COALESCE(MAX(seq), 0) + 1` 作 `next_seq`（下一个可分配的号；空库是 1）；起写线程与读线程池。

`meta` 表只有 `key/value` 两列，三个键：`schema_version`、`protocol_major`、`created_at`。`protocol_major` 的值在新库建立时取 `codec.protocol_major()`，之后只读不写。

迁移登记表：

```rust
pub(crate) const MIGRATIONS: &[Migration] = &[
    Migration { version: 1, name: "initial", sql: include_str!("migrations/0001_initial.sql") },
];
```

测试用的 `open_with_migrations(dir, …, migrations: &[Migration])` 让验收 5 能注入一个坏迁移（`pub(crate)` + `#[cfg(test)]` 暴露给集成测试的 `pub fn` 带 `#[doc(hidden)]`）。

### 2.3 连接与 PRAGMA

写连接（1 条，写线程独占）：`journal_mode=WAL`、`synchronous=FULL`、`foreign_keys=OFF`（投影表之间不设外键：级联删除由投影器显式做，重建时清表顺序也不受约束）、`busy_timeout=5000`、`temp_store=MEMORY`、`cache_size=-8000`（8MB）、`journal_size_limit=67108864`（checkpoint 后 WAL 截回 64MB 以内）、`wal_autocheckpoint=1000`（默认值，写明）。**macOS 上另加 `fullfsync=ON`**：macOS 的 `fsync()` 只保证数据交给了驱动器，不保证写到介质，`synchronous=FULL` 单独不能兑现设计 5.2「断电不丢已确认的事件」；`fullfsync` 用 `F_FULLFSYNC` 把驱动器缓存也刷下去。代价是每次 COMMIT 多约 10–20ms，组提交摊薄；基准两种设置都量（7.1），要不要放宽这条承诺由产品负责人看数据决定（第 10 节 Q3），默认先守住承诺。`StoreConfig.fullfsync: Option<bool>`，`None` = 按平台默认（macOS 开，其他平台无此 PRAGMA）。

读连接（`config.readers` 条，默认 2）：`SQLITE_OPEN_READ_ONLY`，`cache_size=-2000`，`busy_timeout=5000`，`query_only=ON`。

`rusqlite` 特性：`bundled`。`STRICT` 表与 `VACUUM INTO` 都要 SQLite ≥ 3.37，bundled 版本远高于此。

### 2.4 单写者线程与组提交（设计 5.2）

```
调用方 task ──WriteOp + Reply<T> 的发送端──▶ mpsc::Sender<WriteOp>
                                                    │
                                     写线程 loop：recv() 拿到第 1 条 → recv_timeout 直到
                                     「第 1 条到达 + 2ms」或凑满 max_batch(256) → 一批
                                                    │
                        BEGIN IMMEDIATE
                        for op in batch { SAVEPOINT op; apply(op) → Ok: RELEASE / Err: ROLLBACK TO + RELEASE }
                        COMMIT                              ← 一次 fsync
                        for op in batch { reply.send(result) }
```

- `WriteOp` 枚举：`Commit(CommitRequest, Reply<CommitReceipt>)`、`Checkpoint{message_id, offset, text}`、`OutboxMark{id, state}`、`ArtifactTouch{area, sha256, size}`（登记或刷新 `created_at`，2.10）、`ArtifactPin{..}` / `ArtifactUnpin{..}`、`GcCollect{candidates}`（复查 + 删行 + 删文件，2.10）、`Rebuild(Reply<RebuildReport>)`、`Maintenance`。`Rebuild` 与 `GcCollect` 不与其他 op 同批：写线程取到它们时先把手里已收的批提交掉，再单独跑。
- `next_seq` 的含义是**下一个可分配的号**：启动时取 `COALESCE(MAX(seq), 0) + 1`；分配时先用 `next_seq` 作本条事件的 `seq`，插入后 `next_seq += 1`；`head_seq`（最后一个已提交的号）= `next_seq - 1`。四个要测的用例写在 `tests/seq.rs`：空库第一条事件 `seq = 1`；重启后追加接在 `MAX(seq)` 后面不撞主键；空命令返回 `first_seq = last_seq = next_seq - 1`；整批回滚后追加仍连续。
- 第一条 op 到达后才开计时，空闲时写线程阻塞在 `recv()`，CPU 为 0（需求 14「空闲 CPU < 1%」）。
- `apply(Commit)`：
  1. `SELECT first_seq, last_seq FROM commands WHERE command_id = ?`：命中 → 不写任何东西，结果 `CommitReceipt{…, replayed: true}`。同一批里两条同 id 的命令：第二条在同一连接里能看到第一条刚插的行，也走这里。
  2. 记下 `seq_before = next_seq`；对每个事件：`seq = next_seq` → `codec.encode` → `INSERT INTO events(seq, stream_kind, stream_id, type, payload, command_id, actor, at)`（`at` = `clock.now()`，一条命令的全部事件同一个 `at`）→ `projector.project(&mut tx, seq, &event)`（`tx` 里带着这条命令的信封 `at/actor`，见 2.6）→ `next_seq += 1`。
  3. `INSERT INTO outbox(command_id, target, payload, state='queued', attempts=0, created_at, updated_at)` 逐条。
  4. `INSERT INTO commands(command_id, first_seq, last_seq, at)`，`first_seq = seq_before`，`last_seq = next_seq - 1`。`events` 为空时两者都等于 `next_seq - 1`，即当时的 `head_seq`（没有新事件；参照实现 `InMemoryStore` 的 `first_seq = head + 1 > last_seq` 是个空区间，这里改成更直白的「等于 head」，写进测试 `commit_without_events_returns_head`：空库上空命令返回 `(0, 0)`，有 3 条事件后返回 `(3, 3)`）。
  5. 任一步 `Err`（编码失败、投影失败、SQLite 错误）→ 先查 `conn.is_autocommit()`：
     - 为 `false`（事务还在，这是编码/投影错误与大多数约束错误的情况）→ `ROLLBACK TO` 这条命令的 savepoint 再 `RELEASE`，`next_seq = seq_before`，这条命令得到 `Err`，同批其他命令不受影响；
     - 为 `true`（SQLite 已经把**整个事务**自动回滚——审查用真实 SQLite 验证过：progress_handler 中断一条 DML 后整个事务没了，前面命令 `RELEASE` 过的行也没了，再 `ROLLBACK TO` 会报 `no such savepoint`），或者 `ROLLBACK TO` / `RELEASE` 本身失败 → 走**整批失败**收尾（下一条）：这一批里之前暂存的 `Ok` 一律作废、全部回 `Err`，停止处理剩下的命令，按下一条的顺序重新确定 `next_seq`。
     测试 `dml_error_aborts_whole_batch_when_tx_lost`：同批两条命令，第一条已 `RELEASE`，第二条的 `INSERT` 用 progress_handler 中断 → 两条都得到 `Err`，表里两条都没有，之后一批正常提交且 `seq` 从持久 head 接上。
- **整批失败收尾**（`COMMIT` 失败——磁盘满、I/O 错误；或上一条里「事务已没了 / savepoint 操作失败」）：SQLite 对失败分两类——有的错误（如 `SQLITE_BUSY`）让事务仍然开着，有的（如 `SQLITE_FULL`、`SQLITE_INTERRUPT`、`SQLITE_IOERR` 的一部分）会自动回滚。写线程不猜，按下面的顺序收尾：
  1. 查 `conn.is_autocommit()`：为 `false` 说明事务还在，执行 `ROLLBACK`；为 `true` 说明已自动回滚，跳过。
  2. `ROLLBACK` 本身失败 → 这条连接不可信，关闭它，store 标为不可用（之后所有写请求立即 `Err(Io{"写连接已失效"})`，由 T04 按设计 10.4 整体退出重启）。
  3. 回滚确认成功后，才 `SELECT COALESCE(MAX(seq), 0) + 1` 重设 `next_seq`——此时读到的一定是已持久化的行，不会把未提交的 `seq` 当成已用。
  4. 整批全部回 `Err(Io)`。没有任何一条已经回了 `Ok`，所以对外没有「已确认却丢了」的命令。
  测试 `commit_failure_rolls_back_then_reseeds` 分两种注入：让 `COMMIT` 返回「事务仍在」类错误（用 `sqlite3_progress_handler` / rusqlite `progress_handler` 在 COMMIT 阶段中断，得到 `SQLITE_INTERRUPT`，事务保留）与「已自动回滚」类错误（测试版 `WriteOp::FailNextCommit(Kind)` 直接模拟）；两种之后都断言：`next_seq` 等于持久 `MAX(seq) + 1`，下一批 `BEGIN IMMEDIATE` 成功，新事件连续。
- 回复在 `COMMIT` 返回之后才发，事件推送（T03）与对外动作（outbox 投递）都在拿到 `Ok` 之后，满足设计 5.2「提交后才推送事件、执行对外动作」。
- 背压：`mpsc::sync_channel(1024)`；满时 `send` 阻塞调用线程——对 async 调用方不友好，所以 `commit()` 用 `try_send`，满了直接返回 `StorageError::Busy`（可重试，T01 已把 `Busy` 定成 `retryable`）。
- 写线程 panic（只可能是程序缺陷）：`Reply` 的发送端被 drop，所有等待者收到 `Err(Io{"写线程已退出"})`；store 标记为不可用，之后的调用立即返回同样的错误。设计 10.4「存储层不可恢复错误时整体退出，由拉起方重启」归 T04，store 只负责把错误报出去。

`Reply<T>`（`reply.rs`，约 60 行）：`Arc<Mutex<Slot<T>>>` + `Waker`；发送端 `send(T)` 存值并唤醒；接收端实现 `Future<Output = Result<T, StorageError>>`，发送端被 drop 时得到 `Err`。不依赖任何运行时，`Send + 'static`，所以 `impl Future + Send` 的端口签名能直接满足，测试用 `pollster::block_on`。

读线程池（`reader.rs`）：N 个线程各持一条只读连接，共享一个 `Arc<Mutex<Receiver<ReadJob>>>`；`ReadJob = Box<dyn FnOnce(&Connection) -> … + Send>`，结果走同一种 `Reply<T>`。`read_events`、`head_seq`、`outbox_pending` 与 `ReadModelPort` 的全部查询都走它。读事务短：一次端口调用（含 `ReadModelPort` 里由几条 SELECT 拼成的复合查询）在**一个**显式读事务（`BEGIN` … `COMMIT`，出错也保证结束）里做完，返回值对应同一个提交时刻；调用结束即释放，不会长期挡住 WAL checkpoint（第 1 轮代码审查 1/F-1，supervisor 2026-11-10 改：原写「一条语句一个隐式事务」，会把不同提交时刻的数据拼进一个返回值）。

**可见性**：`commit()` 返回 `Ok(seq = N)` 后调用方马上 `read_events(from = N-1)`：回复在 `COMMIT` 之后发出，读连接随后开始的读事务按 WAL 规则一定看得到 `N`。测试 `read_after_commit_sees_it` 在 16 线程并发下验证。

```rust
pub struct SqliteProjector<C: EventCodec> { codec: Arc<C> }   // 不持有任何环境相关的默认值：投影必须只由事件决定
impl<C: EventCodec> Projector for SqliteProjector<C> {
    type Tx = WriteTx;
    fn project(&self, tx: &mut WriteTx, seq: Seq, event: &DomainEvent) -> Result<(), StorageError> {
        match event { /* 52 个变体穷举，各自调用一张表的更新函数 */ }
        artifact_refs::record(tx, event)?;     // 第二个穷举 match：事件里的 ArtifactRef 进 artifact_refs
        unread::bump(tx, seq, event)           // 未读计数（2.7）
    }
}
```

为什么 `Tx` 是拥有连接的结构体而不是 `rusqlite::Transaction<'_>`：`Projector::Tx` 是不带生命周期的关联类型，`Transaction<'conn>` 放不进去。写线程用显式 SQL（`BEGIN IMMEDIATE`、`SAVEPOINT`、`COMMIT`）管事务，`WriteTx` 只是连接加信封。信封在每条命令开始时由写线程填好，`project` 从 `tx.envelope.at` 取时间——`Approval.decided_at`、`Turn.ended_at`、`conversations.updated_at` 都从这里来，不改端口。

**投影规则**：

- 投影器**不跑状态机**：`TurnStateChanged{to}`、`ApprovalDecided{state}`、`UserActionStateChanged{state}` 直接把事件里的目标状态写进去。状态是否合法在提交前由 core/app 判过，投影只记结果；重建时也不需要规则快照。
- 快照更新：读 `snapshot` → `snapshot::decode_<entity>` → 改字段 → `snapshot::encode_<entity>` → `UPDATE … SET snapshot = ?, <索引列> = ?`。
- **快照覆盖范围核对表**：快照借的是「创建事件」的编码，`iwork-app` 的转换函数对创建事件里装不下的值会报错（`convert/model.rs:915` 的 `approval_to_proto` 拒绝 `Approved{decider}` / `Voided{reason}`，因为 proto `Approval` 没有决定人与作废原因字段，它们只在 `ApprovalDecided` / `ApprovalVoided` 事件上）。这个校验是防丢信息的，**不去掉**；凡是后续状态超出创建事件表达范围的字段，一律另立独立列，快照里写一个固定基底，读出时把列叠加回实体。逐个实体核对过（对照 `crates/iwork-app/src/convert/model.rs` 各 `*_to_proto`）：

  | 实体 | 创建事件装不下的后续状态 | 处理 |
  | --- | --- | --- |
  | `Approval` | `state = Approved{decider}`、`Voided{reason}`（`approval_to_proto` 报错） | 快照里 `state` 固定写 `Pending`；真值在列 `state` / `decider` / `void_reason` / `decided_at`；`review`（含 `review_id`、理由）proto 装得下，留在快照里。`snapshot::decode_approval(row)` 解出基底后按三列重建 `ApprovalState`（`approved` + `decider` → `Approved{decider}`，`voided` + `void_reason` → `Voided{reason}`，`denied` → `Denied`；列组合不合法（如 `approved` 却没有 `decider`）→ `Projection` 错误点名行） |
  | `UserActionCard` | 无：proto `UserActionCard` 带 `state/exit/error/void_reason`，全部状态往返 | 快照即真值 |
  | `Turn` | 无：`state + interrupt_reason`、`ended_at` 都在 proto 里 | 快照即真值 |
  | `Message` | 无：五种 `status` 与两种 `body` 都在；`Streaming` 且无正文也允许 | 快照即真值；流式正文另在 `message_checkpoints` |
  | `Conversation` | 无：三种 `state`、`approval_mode`、`context_project` 都在；proto 的 `unread` 字段转 domain 时忽略 | `unread`、`last_read_seq` 的真值在列（也是投影自己算的） |
  | `Attachment` | `confirmed` 不是 domain 字段 | 列 `confirmed` |
  | `Runtime` | `import_prompted` 不是 domain 字段 | 列 `import_prompted`（由 `LocalImportPrompted` 写，2.6「列归属」） |
  | `Project`、`Assistant`、`AssistantVersion`、`RuleEntry` | 无 | 快照即真值 |

  这张表就是 `snapshot_roundtrip_all_entities` 测试的用例清单：对每个实体，把它能到达的**每一种**状态（用 `finite_enum!` 的全量列表）经「投影写 → 读模型读」往返，断言逐字段相等；审批额外跑 `Pending → Approved{User|ModeSwitch|AiReview}` / `Denied` / `Voided{四种原因}` 的在线读取与重建后读取两条路径。
- **缺行报错**：更新事件找不到目标行（`UPDATE` 影响 0 行）→ `StorageError::Projection{seq, message: "<表> 里没有 <id>"}`，命令回滚。这是 app 层逻辑错误的信号，不吞。重建中碰到同样的错误 → 重建失败、回滚到旧投影。
- **级联**（显式写，不靠外键）：
  - `ConversationDeleted{id}`：删 `conversations` 行、该对话的 `messages`、`turns`、`turn_usage`、`tool_calls`（按回合）、`approvals`、`user_actions`、`attachments`、`conversation_member_modes`、`message_checkpoints`（非投影表，但消息没了它也没意义）、以及这些行贡献的 `artifact_refs`（按 `ref_kind/ref_id` 删）。规则由 `RulesDeleted` 事件单独删，这里不碰 `approval_rules`。
  - `AssistantDeleted{id}`：删 `assistants`、`assistant_versions`、该助手的私聊对话（`conversations.assistant_id = ?`）及其上面那一串。项目对话里它的消息保留（名字快照在 `snapshot` 里，设计 9.1a）。
  - `ProjectRemoved{id}`：删 `projects` 行、`agents_md_drafts`；项目对话由 app 先发 `ConversationDeleted`（9.0），投影不替它删。
- `ApprovalModeChanged{target, mode, cause}`（档位三层的落点，卡「范围 2」）：
  - `Conversation(id)`：`conversations.approval_mode = mode`，快照同步。
  - `Member{conversation_id, assistant_id}`：`mode = Some` → `INSERT … ON CONFLICT DO UPDATE SET mode`；`None` → `DELETE`（恢复跟随）。
  - `Project(id)`：写 `projects.default_approval_mode` 与快照里的 `settings.default_approval_mode`。`mode` 是 `Some(FullAccess)` 或 `None` 时返回 `Projection` 错误（项目默认只能手动/自动，需求 FR11；`ProjectDefaultMode` 类型写不出全开，app 层应当在提交前拒绝，投影器是最后一道）。与 `ProjectSettingsUpdated` 写同一个字段，见第 10 节 Q1。
  - `DmProjectSwitched{conversation_id, project_id}`：`context_project_id = project_id`，`approval_mode = NULL`（T01 Q7 已定全清；与 `Conversation::switch_dm_project` 的行为一致，但投影不调用它，直接写字段）。
- `MessageAppended`：插行，`appended_seq = seq`；`MessageCompleted{message_id, body, status}`：更新快照里的 `body/status`，`status` 列同步，`DELETE FROM message_checkpoints WHERE message_id = ?`。
- `TurnStateChanged{to}`：`state` 列 + 快照；`to.is_terminal()` → `ended_at = envelope.at`；进入 `Interrupted` → `interrupted_seq = seq`，离开 → `NULL`。`TurnFinished{usage}` 与 `UsageReported{usage}`：`INSERT … ON CONFLICT(turn_id) DO UPDATE SET` 六个用量列（两条事件都可能带用量，以后到的为准；两者写的是同一组列，没有别的事件写这张表）。
- `ApprovalRequested`：插行，`state = 'pending'`，`decider / void_reason = NULL`，快照按原样（此时就是 `Pending`），`awaits_user = approval.awaits_user()`；`ApprovalReviewUpdated{review}`：快照 `review` + `review_phase` + `awaits_user` 重算；`ApprovalDecided{state}`：`state` 列（`approved` / `denied`）、`decider` 列（`Approved{decider}` 的值；`Denied` 时 NULL）、`awaits_user = 0`、`decided_at = envelope.at`，快照不动（仍是 `Pending` 基底）；`ApprovalVoided{reason}`：`state = 'voided'`、`void_reason` 列、`awaits_user = 0`、`decided_at = envelope.at`。`ApprovalStaleResultDropped`、`ApprovalEvaluated`（audit 流）：不投影。
- `RuleRemembered` / `SecurityListEntryAdded`：都插 `approval_rules`（快照一律用 `RuleRemembered{rule}` 的编码）；`RuleRevoked` / `SecurityListEntryRemoved` / `RulesDeleted`：删行。
- `GlobalSettingsChanged{playful_ui?, autostart?, projects_root?}`：`INSERT INTO global_settings(id, …) VALUES (1, …) ON CONFLICT(id) DO UPDATE SET <只更新事件里给了值的列>`；没给的列保持 NULL。**投影器不持有任何默认值**：默认值（`playful_ui = true`、`autostart = false`、`projects_root = <用户主目录>/iWork/projects`）依赖环境，若在投影时补进去，换了主目录再重建就得到不同的表，违反 `Projector`「同一事件序列得到同一张表」。补默认值是读模型的事（2.7 `settings()`），读模型可以随环境变。测试 `rebuild_with_different_defaults_is_identical`：注入默认值 A 在线投影一段含 `GlobalSettingsChanged{playful_ui: Some(false)}` 的历史，换默认值 B 重建，`global_settings` 表逐字段相同（`autostart`、`projects_root` 两列都是 NULL）。
- **列归属**：同一张表被多个事件写时，每列只有一个写者，`UPSERT` 只更新自己拥有的列，绝不用 `INSERT OR REPLACE` 整行替换（它会把别的事件写的列清回默认值）。逐张核对：
  - `runtimes`：`RuntimeUpdated` 拥有 `kind / state / snapshot` → `INSERT … ON CONFLICT(id) DO UPDATE SET kind, state, snapshot`，不碰 `import_prompted`；`LocalImportPrompted` 拥有 `import_prompted`（行不存在时报 `Projection`：运行时还没登记就提示导入是 app 层错误）。测试 `runtime_updated_keeps_import_prompted`：`RuntimeUpdated → LocalImportPrompted → RuntimeUpdated`，在线与重建后 `import_prompted` 都是 1。
  - `attachments`：`AttachmentStored` 拥有除 `confirmed` 外的全部列；`AttachmentConfirmed` 拥有 `confirmed`。
  - `conversations`：`ConversationCreated` 插行；`ApprovalModeChanged / DmProjectSwitched / ConversationModelChanged / ConversationDeleting` 各改自己的字段与快照；`ConversationRead` 拥有 `last_read_seq`；`unread` 只由 `unread.rs` 写。
  - `approvals`：见上一条；`turns`：`TurnQueued` 插行，`TurnStateChanged` 拥有 `state / ended_at / interrupted_seq` 与快照里的 `state`，`TurnModelReported` 拥有快照里的 `model`。
  - `quota_snapshots`（`QuotaObserved` 独占）、`local_config_items`（`LocalConfigImported` 独占）、`conversation_member_modes`（`ApprovalModeChanged{Member}` 独占）、`turn_usage`（两条事件写同一组列）：独占的表可以用 UPSERT 更新全部列，但写法统一成 `ON CONFLICT DO UPDATE SET <列清单>`，不用 `INSERT OR REPLACE`（它在 SQLite 里是先 DELETE 再 INSERT，会触发不该触发的删除语义，以后加列也容易漏）。
  - 单测 `no_insert_or_replace_in_projector`：`grep` 源码里 `INSERT OR REPLACE` 为零——这是对规则本身的看守，行为由上面各表的测试验。
- `QuotaObserved{windows}`：每个窗口 UPSERT `quota_snapshots`。`LocalImportPrompted`：`import_prompted = 1`。`LocalConfigImported{items}`：每项 UPSERT `local_config_items`。`McpSecretSet`、`RecoveryCompleted`、`RepositoryInitialized`、`CloneFinished`：不投影（没有查询读它们；`CloneFinished` 的结果由 T10 经 `ProjectAdded` 落地）。
- `AgentsMdDraftProposed` / `AgentsMdDraftDecided`：插行 / 写 `decision`。
- `AttachmentStored` / `AttachmentConfirmed`：插行 / `confirmed = 1`。
- `ToolCallStarted` / `ToolCallFinished`：插行 / 写 `ok` 与输出制品三列。

**快照编解码**（`snapshot.rs`）：每种实体一对函数，内部构造该实体的「创建事件」交给 `codec.encode`，解码时用对应 `kind` 调 `codec.decode` 再取出实体。登记表：

### 2.7 读模型（`SqliteReadModel`，实现 `ReadModelPort`）

全部查询走读线程池。每个方法对应的 SQL 与规则：

| 方法 | 做法 |
| --- | --- |
| `conversation(id, page)` | 对话行 + 消息页 + 该页消息涉及的回合（`turns WHERE id IN (…)`）与该对话未结束的回合。消息页按有无游标拆成**两条**语句：无游标 `… WHERE conversation_id = ? ORDER BY id DESC LIMIT ?`，有游标 `… WHERE conversation_id = ? AND id < ? ORDER BY id DESC LIMIT ?`（返回时反转成升序）。不写成 `AND (? IS NULL OR id < ?)`：`OR` 让规划器用不上 `id < ?` 这个范围约束，深分页退化成从头扫。`status = streaming` 的消息，`body` 用 `message_checkpoints.text` 填（`Inline`），没有检查点就是空串——这是设计 3.5「崩溃后最多丢失 500ms 的显示文字」在读侧的体现。`unread` 取对话行 |
| `conversations(project)` | `project = None` → 全部；`Some(p)` → `project_id = p`（项目对话）。按 `updated_at DESC` |
| `projects()` | 全部项目 + 每个项目的 `unread` = 该项目全部项目对话 `unread` 之和 |
| `assistants()` | 全部，按 `builtin DESC, id` |
| `pending_items()` | 四个来源合并：`approvals WHERE awaits_user = 1`；`user_actions WHERE state_kind IN ('pending', 'unknown')`（`Unknown` 等用户「我已核对」，T01 4.3）；`agents_md_drafts WHERE decision IS NULL`；`turns WHERE state LIKE 'interrupted_%'`（ResumeCard）。按各自 id 升序，再按出现顺序拼接 |
| `quota()` | `quota_snapshots` 按 `runtime_id` 分组，`observed_at` 取组内最大 |
| `runtimes()` | 全部 |
| `rules(project)` | `None` → 全部；`Some(p)` → `scope_kind = 'global' OR (scope_kind = 'project' AND scope_id = p)`。更细的范围（助手、对话）由 T10 需要时加查询，不在这里猜 |
| `security_lists()` | `layer IN ('credential_commands', 'sensitive_dirs', 'writable_dirs')` |
| `settings()` | `global_settings` 单行；没有行、或某列为 NULL 时，该字段用注入的 `ReadDefaults.global_settings` 补（默认值只在读侧出现，2.6） |
| `artifact_is_referenced(r)` | `EXISTS (SELECT 1 FROM artifact_refs WHERE area = ? AND sha256 = ?)` |

**未读计数**（`unread.rs`，设计 9.1「只有发给用户的消息与待处理卡片两类事件计数」）：计数的事件是一张登记表 `UNREAD_COUNTED`：`MessageAppended`（作者不是用户）、`ApprovalRequested`、`UserActionProposed`、`TurnStateChanged{to: Interrupted{..}}`（继续卡片）。命中时 `seq > last_read_seq` 则 `unread += 1`；`ConversationRead{last_read_seq}` 时重算：`messages.appended_seq > ?` 且作者非用户的条数 + `approvals.requested_seq > ?` + `user_actions.proposed_seq > ?` + `turns.interrupted_seq > ?` 的条数（进入 `Interrupted` 时写入所在 seq，离开时清 NULL）。具体哪几种事件算「卡片」是产品行为，见第 10 节 Q4。

### 2.8 流式检查点（设计 3.5）

`checkpoint_message(message_id, offset, text)` → `WriteOp::Checkpoint` → `INSERT INTO message_checkpoints … ON CONFLICT(message_id) DO UPDATE SET offset, text, updated_at`。`text` 是**到 offset 为止的完整正文**（不是增量），调用方（T06 适配层/T03）每 500ms 调一次；store 不校验 `offset` 与 `text.len()` 的关系（offset 是运行时给的字符偏移，store 只存）。它和事件一起被组提交，不单独多一次 fsync。消息结束时 `MessageCompleted` 的投影删掉检查点行。

崩溃恢复（T04）需要把 `Streaming` 消息收尾成 `MessageCompleted{status: Interrupted, body}`：`body` 从 `ReadModelPort::conversation` 返回的消息里拿（读模型已填检查点正文），不需要新端口。

### 2.9 投影重建（设计 5.2；卡验收 3）

`rebuild_projections()` → `WriteOp::Rebuild`，写线程单独处理：

1. `BEGIN IMMEDIATE`。
2. 按 `PROJECTION_TABLES` 逐张 `DELETE FROM <表>`（不动 `events / commands / outbox / meta / message_checkpoints / artifact_objects`）。
3. `SELECT seq, type, payload, actor, at FROM events ORDER BY seq`，游标逐行：`codec.decode` → 填信封 → `projector.project`。一万条事件约几十毫秒；十万条约几百毫秒到一两秒，在一个事务里完成（WAL 临时增长，`COMMIT` 后 checkpoint 截回）。
4. `COMMIT`；返回 `RebuildReport{events, last_seq}`。

任何一步失败 → `ROLLBACK`，旧投影原样保留，返回错误（`Codec` / `Projection{seq}` 点名出错的事件）。重建本身不碰 `outbox`。

**重建只在启动阶段做**（规则，审查裁定）：
- 目的：卡验收 3「重建期间 outbox 无新投递」。写线程被重建占着只能挡住新的 `commit`，挡不住投递循环经读线程取出**已经在排队**的 outbox 条目去投递；投递到一半重建失败回滚，投影与已投递的动作就对不上。
- 手段：`rebuild_projections` 只允许在后台服务启动阶段、outbox 投递循环启动之前调用；运行中不提供重建入口。store 用一个 `delivery_started: AtomicBool` 看守：T04 起投递循环前调 `store.mark_delivery_started()`，之后的 `rebuild_projections` 直接返回 `Err(Io{"投递已开始，重建只能在启动阶段执行"})`，不动任何表。这是给 T04 的一条明确约束（3.4）。
- 由什么保证：`tests/rebuild.rs::rebuild_before_delivery_has_zero_deliveries`——造非空的待投递队列（3 条 `queued`），挂一个计数的假投递器（测试里的投递循环：`outbox_pending` → 计数 → `outbox_mark`），按 T04 的顺序「重建 → `mark_delivery_started` → 起投递器」，断言重建返回前投递次数为 0，重建后 3 条都被投递且只投递一次；对照：`mark_delivery_started` 之后再调 `rebuild_projections` 返回 `Err` 且投影表不变。

谁调用它：T04 启动流程里、崩溃恢复之前（有需要时）；T02 只提供方法与测试。

### 2.10 制品存储（`FsArtifactStore`，设计 5.4、9.2）

```rust
pub struct FsArtifactStore { dir: DataDir, writer: WriterHandle, io: IoPool /* 2 条 std 线程 */, ids: Arc<dyn IdGenerator>?, clock, grace: Duration }
```

`IdGenerator` 是 ports 的同步端口；临时文件名需要一个唯一串，用注入的生成器（daemon 组合时传同一个实例），不在 store 里自己造随机数。

**写入**（`put_bytes` / `put_file`，两者共用一条流式路径 `write_stream(area, reader)`）：

1. 临时文件 `<区>/tmp/<ulid>.part`，与最终目录同一文件系统（同一个区目录下），所以 `rename` 是原子的。
2. 64KB 一块读源、写临时文件、同时喂 `sha2::Sha256`，累计 `size`。
3. `fsync` 临时文件。
4. **先登记、再改名**：`WriteOp::ArtifactTouch{area, sha256, size}` → `INSERT INTO artifact_objects(area, sha256, size, pins, created_at) VALUES (…, 0, now) ON CONFLICT(area, sha256) DO UPDATE SET created_at = excluded.created_at`。同哈希已存在也刷新 `created_at`：旧对象交给新调用者时重新获得一整个宽限期，否则「put 返回引用 → 还没提交事件 → GC 看到老对象没引用就删」。这一步在写线程上，与 GC 的复查串行（见下），`Touch` 提交之后 GC 在宽限期内不可能选中它。登记失败返回 `Err(Io)`，删临时文件，不改名。
5. `create_dir_all(<前 2 位>)` → `rename(tmp, final)`，**目标已存在也照样改名覆盖**（内容按哈希相同，覆盖无害；`std::fs::rename` 在 Unix 与 Windows 上都替换已存在的文件）。Windows 上目标正被别的句柄读着时 `rename` 会失败：此时目标文件存在且大小相同 → 视为成功，删临时文件。Unix 上 `fsync` 目录。
6. 返回 `ArtifactRef{sha256, area, size}`。

顺序为什么是「登记 → 改名」而不是反过来：GC 是「复查 → 删行 → 删文件」一个写线程事务（见下）。若先改名后登记，GC 可能在改名之后、登记之前把同哈希的旧行与旧文件（连同刚改名进去的新文件）删掉，然后登记再插入一行——行在、文件没了。先登记（刷新 `created_at`）后，GC 的复查在写线程上排在 `Touch` 之后，看到新鲜的 `created_at` 就跳过。

`put_file` 不移动、不改源文件，只读它复制（仓库内文件由 T10 决定「只记路径引用」不进这里）。

**读取**（`read_range`）：查 `artifact_objects` 得 `size`（没有行 → `NotFound`）；`range.end > size` 或 `start > end` → `RangeInvalid`；打开文件 `seek + read_exact`。文件丢了（用户手删）→ `Io{path}`。

**引用与回收**：

- 「谁引用了它」的真值是投影表 `artifact_refs`（2.5），由 `artifact_refs::record` 在投影事务里从事件推导，对应实体被删时（2.6 的级联）删行。能带 `ArtifactRef` 的字段按 domain 源码逐个核对（`grep ArtifactRef crates/iwork-domain/src`：`message.rs` 的 `MessageBody::Artifact`、`attachment.rs` 的 `AttachmentOrigin::{Copied, Pasted, CredentialInline}`、`user_action.rs` 的 `UserActionCard.output_artifact`、`event.rs` 的三个事件字段），得到下表，就是 `record` 里穷举 `match` 的内容；加带 `ArtifactRef` 的新事件或新字段漏了这里编译不过（match 穷举）或对拍测试红（见下）：

  | 事件 | 字段 | `ref_kind` / `ref_id` |
  | --- | --- | --- |
  | `MessageAppended{message}` | `message.body = Artifact(r)`（用户或系统发的长消息创建时就是 `Sent + Artifact`，**不会再有 `MessageCompleted`**） | `message` / `message.id` |
  | `MessageCompleted{message_id, body}` | `body = Artifact(r)` | `message` / `message_id` |
  | `ToolCallFinished{turn_id, tool_call_id, output_artifact}` | `output_artifact = Some(r)` | `tool_call` / `<turn_id>/<tool_call_id>` |
  | `UserActionProposed{card}` | `card.output_artifact = Some(r)`（提议时一般为 `None`，照样处理） | `user_action` / `card.id` |
  | `UserActionStateChanged{card_id, output_artifact}` | `output_artifact = Some(r)` | `user_action` / `card_id` |
  | `AgentsMdDraftProposed{card_id, content_artifact}` | `content_artifact` | `agents_md_draft` / `card_id` |
  | `AttachmentStored{attachment}` | `attachment.origin = Copied(r) \| Pasted(r) \| CredentialInline(r)`（`RepoPath` 不是制品） | `attachment` / `attachment.id` |

  对拍测试 `artifact_refs_match_arbitrary_events`：用 `iwork-app` 测试里同款的任意事件生成器生成事件，把事件编成 proto 后递归扫出全部 `ArtifactRef` 消息（独立算法，不与 `record` 共用代码），与 `record` 提取出的集合相等——这样新字段在 proto 里出现而 `record` 没跟上时会红，不只靠人眼核对。
  长消息用例 `sent_message_with_artifact_body_survives_gc_and_rebuild`：用户发一条 `Sent + Artifact` 正文的消息 → 可 `read_range`；时钟拨过宽限期 → `collect_garbage` → 仍可读；`rebuild_projections` 后 `artifact_is_referenced` 仍为 true、再 GC 仍在。
- `retain` / `release`：`artifact_objects.pins ± 1`，是**显式 pin**，给「对象已写进去、引用它的事件还没提交」这种窗口用；app 可以不用它，因为还有宽限期兜底。对象没有登记行时两者都返回 `NotFound`；`pins` 已经是 0 再 `release` 是调用方配对错误，返回 `Io{path: 对象路径, message: "pins 已为 0"}`（`ArtifactError` 没有更合适的变体，不为它加一个）。
- `collect_garbage()`（T04 定时调，建议启动后 5 分钟一次、之后每 24 小时）。要点：**「有没有引用」的最终判断、删行、删文件在写线程的同一个事务里**，与引用提交（`commit` 里的投影）、`retain/release`、再次 put 的 `Touch` 全部串行，候选选出来之后再来的任何一种「还有用」都挡得住：
  1. 读侧预选（只为了不占写线程做全表扫描）：`SELECT area, sha256 FROM artifact_objects o WHERE pins = 0 AND created_at < ? - grace AND NOT EXISTS (SELECT 1 FROM artifact_refs r WHERE r.area = o.area AND r.sha256 = o.sha256)`，结果只是**候选**。
  2. `WriteOp::GcCollect{candidates}` 到写线程，单独一批：`BEGIN IMMEDIATE`；每个候选一个 `SAVEPOINT`：
     - 复查同一条件（`pins = 0`、`created_at` 仍过了宽限期、`artifact_refs` 仍无行）；不满足 → `RELEASE`，跳过（候选选出之后有人引用、pin、或重新 put 刷新了 `created_at`）。
     - `DELETE FROM artifact_objects WHERE area = ? AND sha256 = ?`。
     - 删文件（不存在也算成功）。删文件失败（Windows 被占用等）→ `ROLLBACK TO` 这个 savepoint（行留着，下次再试），记日志。
     - `RELEASE`。
     `COMMIT`。删文件放在事务里、删行之后：崩溃在删文件之后、COMMIT 之前 → 行回滚回来、文件已没了 → 行无文件，由启动恢复（下一条）处理；反过来「先 COMMIT 再删文件」会和 `Touch → rename` 形成 2.10 开头说的竞态，不采用。
  3. 返回 `GcReport{removed, freed_bytes}`。**运行中的 GC 只做上面这一条路径**，不扫目录、不按「有行无文件 / 有文件无行」删任何东西：运行中正常的 put 恰好处在「`Touch` 已提交、`rename` 还没做」时，就是一个「有行无文件」的对象；这时删了行，随后 `rename` 成功、调用方提交引用，文件和引用都在、登记行却没了，`read_range` 报 `NotFound`，再被当孤儿文件删掉。对称地，「有文件无行」在运行中也分不清是残留还是正在进行的操作。
- **残留清理只在启动恢复阶段做**（`FsArtifactStore::recover()`，与 2.9 的重建同一时机：单实例锁已拿到、任何 put 都还没开始、`mark_delivery_started()` 之前；之后调用直接返回 `Err`，不动文件）。此时没有进行中的 put，三类残留才能被安全判定：a. `<区>/tmp/` 下的 `.part` 全部删掉；b. 有行没文件的对象：无引用则删行，有引用则只记错误日志（数据已丢，不能假装没事；记为已知限制）；c. `<区>/sha256/` 下没有 `artifact_objects` 行的文件删掉。三类都用写线程删行、IoPool 删文件，不需要宽限期判断。
  宽限期 `grace` 默认 24 小时（`StoreConfig`）。回收条件用 `AND` 连接三件事，任何一个来源说「还有用」就不删。put 与 commit 之间的保护：`Touch` 刷新 `created_at` 给了至少一个宽限期；要是 app 想更稳，`retain` 一下再 `commit` 后 `release`，pin 的加减也在写线程上，和复查串行。
  四个屏障测试（`tests/artifacts.rs`，用 `FsArtifactStore` 的测试钩子：`gc_hooks.after_select` 在预选之后、`GcCollect` 入队之前执行一段闭包；`put_hooks.after_touch` 在 `Touch` 提交之后、`rename` 之前执行一段闭包）：`gc_barrier_reference_after_select`（闭包里提交一条引用该对象的 `MessageCompleted` → 对象保留）、`gc_barrier_retain_after_select`（闭包里 `retain` → 保留）、`gc_barrier_reput_after_select`（闭包里再 `put_bytes` 同内容 → `created_at` 刷新 → 保留，且返回的引用可读）、`gc_between_touch_and_rename_keeps_registration`（`after_touch` 闭包里跑完整的 `collect_garbage` → 返回后 put 继续 `rename`、提交引用该对象的事件 → `read_range` 能读到，`artifact_objects` 有行）。对照：`after_select` 闭包里什么都不做 → 对象被删；`recover()` 在 `mark_delivery_started()` 之后调用 → `Err`，目录不变。

**三个区**（需求 v1.68、9.2 第 3a 条）：`artifacts/`、`attachments/`、`private/` 三个独立目录，同一套代码按 `ArtifactArea` 选目录；`tmp/` 每个区自己一个（跨区没有引用，也不跨区去重：同一内容放在两个区就是两个文件，这正是「附件区对 Agent 只读可见、长日志不可见」的要求）。`private/` 的文件权限 Unix 0600，目录 0700。

**不做**：读时校验哈希（读路径是热路径，校验放到以后的「巡检」里，记为已知限制）；跨区去重；分块存储。

| T07 | 读 `approval_rules`（`rules()` / `security_lists()`）、`conversations.approval_mode`、`projects.settings` 算有效档位 | 成员单独设置的读端口 M1 不加（2.11） |
| T10 | `commit` 全部命令；`put_file/put_bytes` 附件；`artifact_is_referenced` + `read_range` 受理 `ReadArtifact`；`settings()` | `Private` 区的读由 app 拒绝（T01 3.3），store 不判 |
| T11 | `benches/write_commit.rs` 收编；崩溃注入测试并入故障矩阵 | 输出 JSON 字段名在第 7 节定好，T11 不用改 |

## 4 数据流

```
app(T10) ── CommitRequest{command_id, actor, events, outbox} ──▶ SqliteStore::commit
   │                                                                   │ try_send(WriteOp::Commit) → Reply
   │                                                      写线程：收第 1 条 → 等 2ms 收齐 → BEGIN IMMEDIATE
   │                                                        每条命令 SAVEPOINT：
   │                                                          commands 查幂等 → codec.encode → INSERT events(seq=next_seq)
   │                                                          → projector.project(WriteTx{conn, envelope}) → INSERT outbox → INSERT commands
   │                                                        COMMIT（1 次 fsync）→ 逐条 reply.send
   ◀── CommitReceipt{first_seq, last_seq, replayed} ────────────────────┘
   │
   ├─▶ T03 推送 Event{seq}        ├─▶ T04 outbox 投递循环：outbox_pending → 对外动作 → outbox_mark
   │
   读侧：ReadModelPort::conversation ──▶ 读线程池 ──▶ messages(键集分页) + snapshot 解码 + message_checkpoints 填 Streaming 正文

制品：put_file ──▶ IoPool：tmp/<ulid>.part 边写边哈希 → fsync → WriteOp::ArtifactTouch（写线程：登记或刷新 created_at）→ rename ──▶ ArtifactRef
      事件带 ArtifactRef 提交 ──▶ projector → artifact_refs 加行（含 MessageAppended 的 Sent + Artifact 长消息）
      collect_garbage（运行中）──▶ 读侧预选候选 ──▶ WriteOp::GcCollect（写线程事务：复查三条件 → 删行 → 删文件）；不扫目录
      recover()（只在启动阶段）──▶ 清 tmp/、有行无文件、有文件无行三类残留

启动：DataDir::locate → ensure_layout → 复制 db/wal/shm 到 backups/.probe-*/ → 在副本上读 meta（协议门 / schema 向下）→ 删副本 → 读写连接 → VACUUM INTO 备份 → 一个事务跑完全部待执行迁移 → COALESCE(MAX(seq),0)+1 → 起线程
      → [T04] 需要时 rebuild_projections → artifacts.recover() → mark_delivery_started → 崩溃恢复 → 起 outbox 投递循环
```

## 5 每条规则的「目的 + 手段」

| 规则 | 目的（防什么） | 手段 |
| --- | --- | --- |
| 一次命令一个事务 | 事件写了、投影没写（或反过来），视图与日志分叉；outbox 写了命令却没记，重发时重复执行对外动作 | 事件、投影、outbox、`commands` 四样在同一个 `SAVEPOINT` 里，任一失败整条回滚；回复在 `COMMIT` 之后 |
| 单写者 | 两条写连接抢锁产生 `SQLITE_BUSY`，或者两个线程各自算 `seq` 撞号 | 只有写线程持有写连接；别的地方拿不到它（`WriteTx` 不实现 `Clone`，不暴露连接） |
| `seq` 显式分配、失败回退 | 失败的命令在 `seq` 上留洞，T03 续传把洞当成丢事件；重启后首条撞主键 | 写线程内存里的 `next_seq` 是「下一个可分配的号」，启动与整批回滚后取 `COALESCE(MAX(seq),0)+1`；savepoint 回滚时退回；`tests/seq.rs` 四个用例 + 崩溃测试断言连续 |
| `COMMIT` 失败先确认回滚再重设 | 连接还在事务里就去读 `MAX(seq)`，读到未提交的行，下一批 `BEGIN` 失败 | `is_autocommit()` 判事务是否还在 → `ROLLBACK` → 失败则关连接标不可用 → 成功才重读持久 head |
| `synchronous=FULL`（macOS 加 `fullfsync`）+ 回复在 COMMIT 后 | 用户看到「已提交」，断电后它不在了（设计 5.2 的承诺） | WAL 每次 COMMIT fsync；macOS 用 `F_FULLFSYNC` 刷到介质；没 COMMIT 不回 `Ok` |
| 迁移整体一个事务 | 跨版本升级前一个迁移成功、后一个失败，库停在中间版本，新旧程序都打不开 | 全部待执行迁移 + `schema_version` 更新同事务；失败回到升级前版本，旧程序可开 |
| 协议门不碰原文件 | 探测本身改了原库（只读连接也会删空 WAL、建 `-shm`），回退旧程序时库已变；或用 `immutable` 读不到 WAL 里的已提交帧判错版本 | 复制三个文件到副本再读；五种磁盘状态测试断言三个文件的字节与存在性都不变 |
| 组提交 2ms 窗口 | 每条命令一次 fsync，16 成员并发时写线程成瓶颈 | 第 1 条到达后 `recv_timeout` 收齐 2ms 内的，最多 256 条；空闲时不轮询 |
| 幂等经 `commands` 表 | 客户端重试、daemon 重启后重发同一命令，事件写两遍、对外动作做两遍 | 同事务里先查后插；命中直接回上次的 `first_seq/last_seq` 且什么都不写（`replayed = true`） |
| 投影只记事件里的结果 | 投影器自己跑状态机，和 core 的判断不一致，重建出不同的视图；重建还得带上当时的规则快照 | `project` 只写事件载荷里给出的状态、字段；缺行报错不猜 |
| 投影只由事件决定，不读环境 | 重建时主目录等环境变了，`global_settings` 与在线投影不同，违反 `Projector` 的确定性要求 | 投影器不持有默认值；`global_settings` 未设的列留 NULL，默认值在读模型补；换默认值重建的对比测试 |
| 快照装不下的状态另立列 | 审批批准/作废时 `approval_to_proto` 报错，整条命令回滚；或者去掉校验，静默丢决定人与作废原因 | 快照覆盖范围核对表（2.6）：审批主状态/决定人/作废原因三列；codec 校验保留；全状态往返测试 |
| 每列一个写者，不用 `INSERT OR REPLACE` | `RuntimeUpdated` 整行替换把 `import_prompted` 清回 0，「首次接入只提示一次」失效 | 列归属表（2.6）；UPSERT 只更新自己拥有的列；`no_insert_or_replace_in_projector` 看守 |
| 重建 = 一个事务、只清登记表里的投影表、只在启动阶段 | 重建到一半崩溃留下半套视图；清掉了不该清的（检查点、制品登记、幂等记录）；运行中重建时投递循环把排队的 outbox 投出去，重建回滚后视图与已做的动作对不上 | `PROJECTION_TABLES` 登记表；单测断言登记表 = 库里全部表；`BEGIN … COMMIT` 包住；`mark_delivery_started` 之后拒绝重建 |
| 投影与重建同一个 projector 实例 | 两份投影代码各写各的，在线与重建结果不同 | `SqliteStore` 持 `Arc<P>`，两条路径都调它；`fakes.rs` 的计数测试原样跑 |
| 检查点不进事件日志、不是投影表 | 每 500ms 一条事件把日志撑大；重建清掉半截正文 | 独立表 `message_checkpoints`；`MessageCompleted` 投影时删行 |
| 快照借事件编码 | store 自己发明实体序列化，和 proto 两套格式，升主版本时漏一套 | `snapshot.rs` 登记表只调 `codec.encode/decode`；store 的 normal 依赖里没有 proto |
| 协议门在副本上探测 | 为了判版本把库写了（WAL checkpoint、删空 WAL、建 `-shm`），验收「原库哈希不变」失败，用户回退旧程序时库已变 | 先复制 db / wal / shm 到 `backups/.probe-*/`，在副本上读 `meta`、`VACUUM INTO` 备份；原文件不被任何连接打开；探测完删副本 |
| 迁移前备份、本次全部迁移一个事务 | 迁移写坏了库没有退路；前一个迁移成功、后一个失败，库停在中间版本，新旧程序都打不开 | `VACUUM INTO backups/<时间>-schema-v<旧>.db`；全部待执行迁移 SQL 与 `schema_version` 更新同一个事务，失败回到升级前 |
| schema 向下拒绝 | 旧程序打开新库，把不认识的表当坏数据 | `schema_version > MIGRATIONS.len()` 即拒绝，不写 |
| 制品先临时文件、校验后改名 | 写到一半崩溃，留下一个以哈希命名、内容不完整的文件，后面同哈希的写入被当成「已存在」跳过，永远读到坏内容 | `tmp/<ulid>.part` → fsync → 算完哈希才知道最终名 → `rename` |
| 引用由事件推导 + pin + 宽限期三者 AND | GC 删掉还被引用的对象（引用计数因崩溃少算）或永远删不掉（多算） | `artifact_refs` 可重建；pin 显式；宽限期保护 put 与 commit 之间的窗口；三者任一说「有用」就不删 |
| GC 复查、删行、删文件与引用提交同一串行边界 | 候选选出之后才提交的引用、pin、重新 put 挡不住，对象被误删；同哈希复用没有新宽限期 | `GcCollect` 在写线程事务里复查三条件再删；put 先 `Touch`（登记或刷新 `created_at`）再改名；三个屏障测试 |
| 带制品引用的字段全部登记 | 漏一种（如 `MessageAppended` 的 `Sent + Artifact` 长消息）→ 过宽限期被删，长消息打不开 | 2.10 的字段表 + `record` 穷举 match + 与 proto 递归扫描的对拍测试 |
| 三个区三个目录 | 长日志、Diff 进了 Agent 可读的附件区；凭据附件副本被 `ReadArtifact` 读到 | `DataDir::area(area)` 决定目录；不跨区去重；`Private` 区的读由 app 层拒绝（T01 3.3） |
| 日志不含正文 | 消息正文、附件内容进 `logs/` 被诊断包带走 | `tracing` 字段只有 id、seq、长度、耗时；测试 `logs_never_contain_payload` 用带标记正文的事件跑一遍后 grep 捕获的日志 |
| store 不依赖 tokio | 违反 `deps-policy.toml`；测试必须起运行时 | std 线程 + 自写 `Reply` future；`check-deps.sh` 看守 |

## 6 出事场景

每条写：会出什么事 / 怎么止血和回退 / 由什么保证。

**S1 提交过程中 daemon 被杀（卡验收 1）**
- 会出什么事：`BEGIN` 后、`COMMIT` 前进程没了。若事务不完整却被当成完成，用户看到的「已发送」消息重启后不见；或者 `seq` 跳号，T03 续传认为丢了事件。
- 止血和回退：SQLite WAL 保证未 `COMMIT` 的事务在重启后不可见；回复在 `COMMIT` 之后发，所以客户端没收到 `Ok` 的命令本来就要重试（带同一 `command_id`，幂等）。`next_seq` 启动时取 `COALESCE(MAX(seq),0)+1`，既不跳号也不撞主键。
- 由什么保证：`tests/crash_injection.rs`（6 节末的测试清单 T-1）≥ 200 次随机 `kill`，每次断言：已回 `Ok` 的 `command_id` 全在 `commands`；每条命令的 `first_seq..=last_seq` 全在 `events`；`seq` 从 1 连续到 `MAX`；`PRAGMA integrity_check` 为 ok；投影行数与事件推出的一致。

**S2 `COMMIT` 失败（磁盘满、I/O 错误）**
- 会出什么事：一批命令全部失败；若写线程把 `next_seq` 当成已用掉，之后的事件从错误的号开始，留洞。
- 止血和回退：整批回 `Err(Io)`，调用方按 `retryable = false` 报给用户（磁盘满不是重试能解决的）；写线程按 2.4 的顺序收尾：`is_autocommit()` 判事务是否还开着 → 还开着就 `ROLLBACK` → 回滚失败则关连接、store 标不可用（T04 整体重启）→ 回滚确认后才重读持久的 `COALESCE(MAX(seq),0)+1`。用户清出空间后下一条命令照常。
- 由什么保证：`commit_failure_rolls_back_then_reseeds`（2.4）：「事务仍在」与「已自动回滚」两类错误各注入一次，断言之后 `next_seq` = 持久 `MAX(seq)+1`、下一批 `BEGIN IMMEDIATE` 成功、新事件连续；再加 `rollback_failure_marks_store_unusable`：让 `ROLLBACK` 也失败（测试版注入），断言后续写请求立即得到 `Io{"写连接已失效"}`。

**S3 一条命令投影失败拖累同批**
- 会出什么事：没有 savepoint 的话，同批里一条命令的 `Projection` 错误会让整批回滚，无辜的命令也失败。
- 止血和回退：每条命令一个 `SAVEPOINT`，事务还在（`is_autocommit() == false`）时失败只回滚它，`next_seq` 退回它开始前的值；事务已被 SQLite 自动回滚、或 savepoint 操作本身失败时，走整批失败收尾（2.4）：暂存的 `Ok` 作废、整批 `Err`、重新确定 `next_seq`。整批失败对调用方只是「重试」，不会出现「回了 Ok 却没落盘」。
- 由什么保证：单测 `failed_command_in_batch_does_not_affect_siblings`：同批三条命令，中间一条用测试 projector 注入失败（事务仍在），断言另两条 `Ok` 且 `seq` 连续（1..n，没有为失败那条留号）；`dml_error_aborts_whole_batch_when_tx_lost`（2.4）：第一条已 `RELEASE`、第二条 DML 被中断导致整批自动回滚，两条都 `Err`、都不在表里，下一批正常且 `seq` 连续。

**S4 协议主版本升了，旧库被新程序打开（卡验收 5a）**
- 会出什么事：新程序用新类型解旧编码，字段错位，待审批可能显示成已批准（T01 S1）。
- 止血和回退：`open` 把三个文件复制到副本，在副本上读到 `protocol_major` 不符 → 从副本 `VACUUM INTO` 备份 → 拒绝；原来的 `iwork.db`、`-wal`、`-shm` 没被任何连接打开过，字节与存在性都不变（2.2）。用户装回旧程序，旧库原样可用（设计 5.5）。要带数据过去得先写显式转换并演练，那是门槛不是机制（T01 3.7）。备份失败照样拒绝，原文件仍没动。
- 由什么保证：`tests/protocol_gate.rs`，五种磁盘状态各一条，每条都造 `meta.protocol_major = 程序 + 1` 的库，`open` → `Err(ProtocolMajorMismatch{database, program, backup})`（备份失败那条 → `Err(Io)`），断言三个文件各自的「存在性 + sha256」与打开前完全相同，`backups/.probe-*` 已清掉，备份能用 rusqlite 打开且 `meta` 与数据和源库一致：
  1. **崩溃残留 WAL**：用一条写连接在 WAL 模式下写入数据后，不关连接，把 `db`、`-wal`、`-shm` 三个文件复制到新目录当「崩溃快照」（`-wal` 里有未 checkpoint 的已提交帧）；在快照上跑 `open`。另断言备份里能查到那些只在 WAL 里的行（证明读到了 WAL）。
  2. **缺 `-shm`**：同上快照删掉 `-shm`；`open` 后 `-shm` 仍然不存在。
  3. **预先存在的 0 字节 WAL**：正常关闭过的库旁边放一个 0 字节的 `iwork.db-wal`（审查的 VFS 探针证明只读连接会删掉它）；`open` 后它还在、仍是 0 字节。
  4. **已有 `-shm`**：正常关闭过的库（`-wal` 已 checkpoint 删除、`-shm` 残留）。
  5. **备份失败**：先让 `ensure_layout()` 正常建好目录，再把 `backups/<时间>-protocol-v<旧>.db` 这个目标路径预先占成一个只读目录（或用测试钩子让 `VACUUM INTO` 的目标路径落到不可写处），使 `VACUUM INTO` 失败——这样才走到「带两个主版本号的 `Io`」那条分支，而不是在建目录时就失败；断言消息含两个主版本号、三个原文件不变。
  对照：`protocol_major` 相等的库正常打开，`.probe-*` 清掉。
  6. **副本清理失败**：用测试钩子让删除 `.probe-<ulid>/` 失败；分别在 `protocol_major` 不符与相等两种库上跑 `open`：前者仍返回 `ProtocolMajorMismatch`（不被清理错误遮盖），后者正常打开；三个原文件不变。
  7. **带残留再启动**：数据目录里预先放一个 `backups/.probe-<旧 ulid>/`（内含一份库副本），`open` 正常完成探测，残留目录被清掉，原文件不变；残留删除失败时只记日志、`open` 结果不受影响。

**S5 迁移失败（卡验收 5）**
- 会出什么事：新版本的 `0002_*.sql` 在某个用户的库上报错（比如用户手工改过表）；若不回滚，留下半套新表，新旧程序都打不开。
- 止血和回退：本次全部待执行迁移在一个事务里，任一失败整体回滚，`schema_version` 仍是升级前的值，`open` 返回 `Io`（消息含失败的迁移号与备份路径）；用户装回旧程序即可用（schema 没变）；或等修复版。备份在 `backups/`，最坏情况手工恢复。
- 由什么保证：`tests/migration.rs`：① `open_with_migrations` 用 `[v1, v2(正确：加一张空表), v3(坏 SQL)]` 打开一个 v1 的库 → `Err`，断言 `schema_version` 仍为 1、v2 加的表不存在、用 `[v1]` 打开成功且数据在、`backups/` 里有文件（这正是「迁移 2 成功、迁移 3 失败后旧版本仍能打开」）；② 对照：`[v1, v2]` → 打开成功，旧数据查询结果不变，`schema_version = 2`；③ `[v1]` 打开一个 v2 的库 → `Err`（schema 向下），库不变。

**S6 投影重建中途崩溃或失败（卡验收 3）**
- 会出什么事：清了表、重放到一半没了，启动后视图空一半。
- 止血和回退：重建是一个事务，崩溃或失败都回滚到旧投影；重跑即可。事件里有解不开的（`Codec` 错误）是程序缺陷，错误点名 `seq` 与 `kind`。重建只在启动阶段、投递循环之前（2.9），所以不存在「投递做了一半、重建又回滚」。
- 由什么保证：`tests/rebuild.rs`：造一段历史（含审批 `Pending → Approved{AiReview}`、`Voided`，`RuntimeUpdated → LocalImportPrompted → RuntimeUpdated`，`Sent + Artifact` 长消息，`GlobalSettingsChanged` 只设一个字段），`dump_projections()`（按主键排序逐表取全部行）→ `rebuild_projections` → 再 dump，两份逐表相等；换一组 `ReadDefaults` 后读模型结果中只有默认值相关字段变、表不变；期间 `outbox` 行数与内容不变；用测试 projector 在第 k 条注入失败，断言重建 `Err(Projection{seq: k})` 且投影与重建前逐表相等；`rebuild_before_delivery_has_zero_deliveries`（2.9）。

**S7 制品写到一半崩溃（卡验收 4）**
- 会出什么事：留下不完整的文件；若它叫哈希名，后续同内容写入被跳过，读到坏内容。
- 止血和回退：半截只会在 `tmp/` 里，名字是 ULID；下次启动 `recover()` 清掉 `tmp/` 下全部 `.part`（运行中不清，2.10）。
- 由什么保证：`tests/artifacts.rs::crash_mid_write_leaves_no_hash_named_file`：用注入的「写到 N 字节后 panic/返回错误」的 reader 跑 `put_bytes`，断言 `<区>/sha256/` 下没有新文件、`tmp/` 下有一个 `.part`；运行中调用 `collect_garbage` 后这个 `.part` 仍在（运行中不扫目录，2.10）；模拟下一次启动、任何 put 之前调用 `recover()` 后 `tmp/` 为空（与第 5 步验收 `recover_cleans_three_kinds_of_residue` 一致）。（supervisor 2026-11-09 按审查 2026-11-09-m1-t02-plan/3/F-2 改正）

**S8 GC 误删有引用的对象 / 永不回收**
- 会出什么事：消息正文制品被删，用户点开长消息报 `ARTIFACT_NOT_FOUND`；或者删除对话后附件副本永远占盘。
- 止血和回退：引用来自投影表 `artifact_refs`（可重建），pin 与宽限期是另外两道；最终判断与删除在写线程事务里，和引用提交串行；真误删了没有回退（文件没了），所以靠三道 AND 加串行复查。永不回收只是占盘，`collect_garbage` 的报告里能看到候选数为 0 时排查 `artifact_refs` 是否漏删。
- 由什么保证：`tests/artifacts.rs::gc_keeps_referenced_objects`：四个对象——A 被 `MessageCompleted` 引用、A' 被 `Sent + Artifact` 的 `MessageAppended` 引用、B 只被 pin、C 都没有且 `created_at` 调到宽限期之前（测试时钟）；GC 后 A、A'、B 文件与行都在，C 文件与行都没了；对照：先 `release` B 并把时钟拨过宽限期，再 GC，B 没了。三个屏障测试（2.10）。`gc_after_conversation_deleted_frees_attachment_copy`：删对话后附件副本进入候选。`artifact_refs_match_arbitrary_events` 对拍（2.10）。

**S9 读线程池被慢查询占满**
- 会出什么事：两条读连接都在跑十万条消息的扫描，其他查询排队，`GetConversation` P95 超 200ms。
- 止血和回退：读队列用 `sync_channel(256)`，满了返回 `Busy`（可重试），不无限堆积；查询都走索引（2.5），没有全表扫描；`readers` 可配。
- 由什么保证：`tests/read_model.rs::conversation_page_with_100k_messages_is_indexed`：灌 10 万条消息后 `EXPLAIN QUERY PLAN` 断言用到 `messages_by_conversation`，且单次分页 < 50ms（宽松阈值，防回归，不是性能验收）；性能验收归 T11。

**S10 检查点丢失**
- 会出什么事：崩溃时最近一次检查点之后的流式文字（≤ 500ms）不见了；重启后消息停在半截。
- 止血和回退：这是设计 3.5 明确接受的；T04 恢复把 `Streaming` 消息按检查点正文收尾为 `Interrupted`，用户点「继续」续接。
- 由什么保证：`tests/checkpoint.rs`：写两次检查点后读 `conversation()`，`Streaming` 消息的 `body` 是第二次的正文；`MessageCompleted` 后检查点行消失、`body` 是事件里的；`rebuild_projections` 不清 `message_checkpoints`。

**S11 WAL 无限增长、内存超预算**
- 会出什么事：读连接长期开着读事务挡住 checkpoint，`-wal` 涨到几百 MB；8 小时后内存涨超 10%。
- 止血和回退：读事务是一次端口调用一个短的显式读事务，调用结束即释放；`journal_size_limit` 让 checkpoint 后截回；`maintenance()` 在空闲时 `wal_checkpoint(TRUNCATE)`（T04 调）。内存：3 条连接的 `cache_size` 合计 12MB 封顶；`Reply`、批次缓冲都是短命对象。
- 由什么保证：T11 的 8 小时长测（卡外）；T02 给一条快测 `wal_truncates_after_maintenance`：写 5000 条事件后 `-wal` 大小 > 0，`maintenance()` 后 ≤ `journal_size_limit`。

**S12 Windows 上的文件语义**
- 会出什么事：`rename` 到已存在的目标报错；删除被别的进程打开的文件报错；没有目录 fsync。
- 止血和回退：改名前先查目标存在；GC 删文件失败只记日志、下次再试；目录 fsync 只在 Unix 做。
- 由什么保证：CI 三平台跑 `tests/artifacts.rs`（含「同内容并发写两次」用例）。

**S13 两个 daemon 进程同时打开同一个库**
- 会出什么事：两个写线程各自分配 `seq`，一个拿到 `SQLITE_BUSY`，另一个成功，但两边内存里的 `next_seq` 对不上。
- 止血和回退：单实例锁是 T04 的 `run/daemon.lock`，store 不重复做；store 侧 `BEGIN IMMEDIATE` 拿不到锁 5 秒后报 `Busy`，不会写坏数据。记为对 T04 的依赖，不是 T02 的机制。
- 由什么保证：T04 验收 1（并发启动 10 个实例只活一个）。

**S14 快照解不开**
- 会出什么事：同主版本内 proto 加了字段，老快照解出默认值——正常；若有人违反只增不改的规则改了字段含义，老快照解出错值，读模型返回错数据。
- 止血和回退：这正是 T01 契约比对与金样本要拦的（T01 S1）；真出了，`rebuild_projections` 用事件重算快照（事件也是同一编码，所以只在「字段含义变了」这种人为错误下才需要）。
- 由什么保证：T01 `tests/compat.rs`；T02 `snapshot_roundtrip_all_entities`（11 种实体经 `encode → decode` 相等，用 `iwork-app` 的真实 codec）。

**已知限制（T02 登记，交产品负责人决定是否写进需求文档的清单）**

- 读制品时不校验哈希；磁盘位翻转或用户手改文件不会被发现。补法是以后的「巡检」任务，不在 M1。
- `commands` 幂等表只增不删；每条约 100 字节，十万条命令 10MB。M1 不清理。
- 有登记行却没有文件的制品（GC 删文件后、COMMIT 前崩溃，或用户手删）若仍被引用，启动恢复只记错误日志；内容已丢，不能恢复。
- 投影器对「缺行」报错会让一条命令失败，这是把 app 层缺陷暴露出来，不是兜底。

## 7 对写入基准的初版设计与性能影响

### 7.1 基准 `benches/write_commit.rs`（`harness = false`，卡验收 6）

- 环境：`tempfile::tempdir()` 里开 store，真实 `ProtoEventCodec`、真实 `SqliteProjector`；事件用「一条用户消息 + 一条助手消息 + 一次回合状态变化」的典型三件套（`MessageAppended ×2 + TurnStateChanged`），outbox 一条。
- 两个场景：`single`（1 个生产者串行提交 2000 条，量没有批量效应时的单命令延迟）、`concurrent_16`（16 个线程各提交 500 条，量组提交下的吞吐）。
- 量什么：每条 `commit()` 调用到返回的墙钟时间；输出 P50/P95/P99（排序取分位，不引 hdrhistogram）与每秒命令数。
- 输出：一行 JSON 到 stdout：`{"bench":"store_write","scenario":"concurrent_16","commands":8000,"p50_us":…,"p95_us":…,"p99_us":…,"commands_per_sec":…,"sqlite_version":"…","platform":"…"}`，人读的表到 stderr。T11 收编时只需要搬文件、读这个 JSON。
- 两种 fsync 设置都跑：`fullfsync = on` 与 `off` 各出一组（macOS 以外的平台 `fullfsync` 无效，只跑一组并在 JSON 里标 `"fullfsync": "n/a"`）。JSON 加字段 `"fullfsync": "on" | "off" | "n/a"`。
- 预期量级（实施后以实测为准，写进报告）：单条延迟 ≈ 2ms 窗口 + 一次 fsync（Linux SSD 1–3ms；macOS 开 `fullfsync` 时 10–20ms，关时与 Linux 接近）；16 并发下每次 fsync 摊给十几条命令，吞吐达数百到上千命令/秒。没有硬阈值（T11 表「记录 P95，进趋势」）。这组数字是 Q3 的决策依据。

## 8 风险与替代方案

| 选择 | 备选 | 为什么不选备选 |
| --- | --- | --- |
| std 线程 + 自写 `Reply` | 给 store 放开 tokio（`spawn_blocking` + `tokio::sync::oneshot`） | 要改 `deps-policy.toml` 把 tokio 加进 store 的豁免，store 绑定运行时，测试必须起 runtime；自写 `Reply` 约 60 行，`pollster` 直接能跑。真要换，只动 `reply.rs` 与 `writer.rs` 的 channel，端口与表不变 |
| 快照借事件编码 | 每张表每个字段一列，store 手写 11 种实体的列映射 | 多一套实体序列化，和 proto 两份；嵌套类型（`Action`、`RuleMatcher`、`Proposal`）要拆很多列或塞 JSON（domain 没有 serde，加了又改依赖白名单）。备选的好处是能用 SQL 按任意字段查，M1 的 11 个查询用索引列就够 |
| 引用从事件推导 + pin + 宽限期 | 只用 `retain/release` 计数 | 计数与事件提交不在同一事务，崩溃就算错；设计 5.4「引用计数在数据库里」我们是满足的，只是计数的真值换成了投影表 |
| `seq` 显式分配 | `AUTOINCREMENT` | savepoint 回滚时 `sqlite_sequence` 也回滚，理论上也连续，但依赖 SQLite 内部行为，不如自己保证并测试 |
| `STRICT` 表 | 普通表 | 普通表的类型亲和会把写错的类型悄悄转换；`STRICT` 需要 SQLite ≥ 3.37，bundled 满足 |
| 重建一个大事务 | 分批 + `meta.rebuilding` 标记 | 分批要处理「标记在、重建没完」的启动路径，多一个状态；十万条事件一个事务在 SQLite 里没问题 |
| 不建 `project_members` | 按 5.3 建空表 | 没有事件写它就重建不出来，违反「投影可从事件重建」；迁移只向前，M2 加表只是一个新 SQL 文件 |
| 在副本上探测协议主版本 | 只读连接直接读原库；或 `immutable=1` | 只读连接会删预先存在的空 WAL、建 `-shm`（审查 VFS 探针证实），原文件存在性就变了；`immutable` 跳过 WAL 会读错版本、备份不全。复制一次 db + wal 的代价几十毫秒，换来三个文件都不动 |
| 制品残留清理只在启动阶段 | 运行中定时扫目录与登记表 | 运行中分不清「残留」和「`Touch` 已提交、`rename` 未做」的正常 put，会删掉登记行；启动阶段没有进行中的 put，不需要任何额外机制就能判定 |

**Q1 项目默认档位有两条写入路径**
- 问题：T01 定的事件里 `ProjectSettingsUpdated{settings}`（带完整 `ProjectSettings`，含 `default_approval_mode`）与 `ApprovalModeChanged{target: Project(id), mode}` 都能改项目默认档位。两条路径写同一个字段本身没错，但 `ApprovalModeChanged.mode: Option<ApprovalMode>` 对 `Project` 目标能表达 `None` 与 `FullAccess`，这两个值对项目默认没有意义（需求 FR11：项目默认只能手动或自动）。
- 证据：`crates/iwork-domain/src/event.rs` 的 `ApprovalModeTarget::Project`、`ProjectSettingsUpdated`；`crates/iwork-domain/src/approval_mode.rs` 的 `ProjectDefaultMode` 只有两个变体；需求 FR11。
- 可选：（a）两条都保留，投影都写；`Project` 目标收到 `None` / `FullAccess` 时投影返回 `Projection` 错误（app 层应在提交前拒绝）；（b）`SetApprovalMode` 对项目目标统一走 `ProjectSettingsUpdated`，`ApprovalModeTarget::Project` 在 proto 里标 `deprecated`，投影器对它报错。
- 默认做法：（a）。影响：T07/T10 受理 `SetApprovalMode` 时知道两条路径都行；（b）要改 T01 的 proto 注释与 T10 的受理。

**Q2 `StorageError` 没有「迁移失败」与「不是 iWork 数据库」的变体**
- 问题：设计 5.5 要求迁移失败「拒绝启动新版本，提示回退」，T04 诊断页要显示迁移号与备份路径；现在只能塞进 `Io{message}` 的文字里。
- 证据：`crates/iwork-ports/src/store.rs` 的 `StorageError` 六个变体；`docs/tasks/M1/T04.md` 验收 3a 只提了协议主版本。
- 可选：（a）加 `StorageError::MigrationFailed{ from_version, to_version, backup: PathBuf, message }` 与 `StorageError::NotIworkDatabase{ path }`（只加变体，不改现有签名，`retryable()` 返回 false）；（b）用 `Io{message}`，T04 只显示文字。
- 默认做法：（b），不改端口；若选（a），由 T02 一并加进 `iwork-ports`（这是对 T01 端口的追加，T01 5.2 允许「加端口只动 iwork-ports」）。

**Q3 macOS 是否允许放宽「断电不丢已确认事件」、关掉 `PRAGMA fullfsync`**
- 问题：macOS 的 `fsync` 不保证数据到达磁盘介质，`synchronous=FULL` 在进程崩溃、系统崩溃下够用，**断电**时最后几次提交可能丢。设计 5.2 承诺「断电不丢已确认的事件」，所以 macOS 上必须开 `fullfsync`（方案默认已这样做，2.3）。代价是每次 COMMIT 约 10–20ms（Apple SSD 量级），组提交下单命令延迟上限随之抬高。
- 证据：SQLite 文档 `PRAGMA fullfsync`；设计 5.2；`AGENTS.md` 已知缺口原则「不造成无法挽回的损失」——丢已确认事件属于无法挽回。
- 可选：（a）守住承诺：macOS 默认开，`StoreConfig.fullfsync` 可关（调试用）；（b）放宽承诺：改设计 5.2 为「进程与系统崩溃不丢、断电尽力」，默认关。
- 默认做法：（a）。基准 7.1 两种设置各出一组数值写进报告；只有产品负责人看了数据决定改设计 5.2，才切到（b）。

**Q4 未读计数算哪些「待处理卡片」**
- 问题：设计 9.1 只写「发给用户的消息」与「待处理卡片」两类计数，没列卡片种类。
- 证据：设计 9.1 未读数一段；T01 3.3 的 `PendingItem` 四种（审批、亲手执行、AGENTS.md 草稿、继续卡片）。
- 可选：（a）消息（作者非用户）+ 审批请求 + 亲手执行卡片 + 回合中断的「继续」卡片；AGENTS.md 草稿属于项目不属于对话，不计入对话未读；（b）只算消息与审批。
- 默认做法：（a），登记表 `UNREAD_COUNTED` 改一行即可切换。

## 12 ADR（由 developer 随实现写入 `docs/adr/`，每条一个文件，格式照 `docs/adr/0003`）

**ADR-T02-a 存储层用单个 std 写线程做组提交，异步接口靠自写的无运行时 oneshot**
- 背景：`iwork-store` 按 `deps-policy.toml` 不能依赖 tokio；端口要求 `impl Future + Send`；SQLite 连接不是 `Send`，且只允许一个写者。
- 决定：一个 std 线程独占写连接，请求经 `sync_channel` 进去，2ms 窗口合并成一批，一个事务、每命令一个 savepoint、一次 fsync；应答用 `Reply<T>`（`Arc<Mutex<Slot>>` + `Waker`）实现 `Future`。读走 N 条只读连接的线程池。`seq` 由写线程显式分配。
- 备选：tokio `spawn_blocking` + `oneshot`（绑定运行时、改依赖策略）；每条命令一个事务（fsync 次数 = 命令数）；`AUTOINCREMENT`（依赖 SQLite 序列的回滚行为）。
- 影响：store 能用 `pollster` 测；写队列满返回 `Busy`；换运行时只动 `reply.rs`、`writer.rs`。

**ADR-T02-b 投影表的实体快照借用该实体「创建事件」的编码，装不下的状态另立列**
- 背景：投影表要存完整实体（含嵌套类型），store 不依赖 proto，domain 没有 serde，不想再发明一套实体序列化。但创建事件的 proto 消息不一定装得下实体后来的全部状态（proto `Approval` 没有决定人与作废原因，`approval_to_proto` 对终态报错）。
- 决定：每张实体表一列 `snapshot BLOB`，内容是把实体包进它的创建事件（如 `ApprovalRequested{approval}`）后 `EventCodec::encode` 的载荷；更新事件读快照、改字段、重编码；查询条件用的字段另抽成索引列。凡创建事件装不下的后续状态（核对表见方案 2.6），快照里写固定基底，真值放独立列，读出时叠加；codec 的防丢信息校验原样保留。
- 备选：每字段一列手写映射（两套格式，嵌套类型难拆）；domain 加 serde（改依赖白名单，第二套格式）；去掉 codec 校验让终态也编进 `Approval`（静默丢决定人与作废原因）。
- 影响：加实体字段只改 proto + domain + app 转换，store 自动跟上；新增「创建事件装不下」的状态时要更新核对表并加列；快照与事件共用同一个协议主版本门；读模型每行一次 proto 解码。

**ADR-T02-c 制品的「有无引用」由投影表从事件推导，最终判断与删除和引用提交同一串行边界**
- 背景：设计 5.4 说「引用计数在数据库里，定期回收无引用对象」；`ArtifactStore` 有 `retain/release`。但写对象与提交引用它的事件不在同一事务，纯计数在崩溃时会算错。
- 决定：`artifact_refs` 是投影表，投影器从带 `ArtifactRef` 的事件加行、从级联删除减行，可随投影重建；`retain/release` 维护 `artifact_objects.pins`；put 先在写线程登记或刷新 `created_at` 再改名；运行中的 GC 在读侧只做预选，复查三条件（无 `artifact_refs` 行 ∧ `pins = 0` ∧ 过宽限期，默认 24h）、删行、删文件都在写线程的同一个事务里，与引用提交、pin、再次 put 串行，不扫目录；`tmp/`、有行无文件、无行有文件三类残留只在启动恢复阶段（任何 put 开始之前）清理。
- 备选：只用 `retain/release` 计数（崩溃算错、不可重建）；只用宽限期（删除对话后的副本要等宽限期，且没有可审计的引用关系）；读侧选完直接删（选中之后的引用挡不住）。
- 影响：加带 `ArtifactRef` 的事件要在 `artifact_refs.rs` 的穷举 `match` 补一行（漏了编译不过，对拍测试也红）；GC 占用写线程的时间与候选数成正比，一次最多处理 `max_batch` 个候选；app 可以不调 `retain/release`。
