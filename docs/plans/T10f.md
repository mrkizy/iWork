## A0 一页总览

M1 里，用户在 设置 › 运行时 ›「从本机导入」看得到本机给 Claude Code 配了哪些 MCP 服务器、技能、插件，每一项都标着「还没启用」，导不了。成员会话里没有用户自己的 MCP 和用户级技能（需求附录 B，2026-11-12）。

A 交付四样：

| # | 东西 | 内容 |
| --- | --- | --- |
| 1 | 只到名字这一层的发现 | 本机有几台 MCP、各是哪种连接方式、要填几个键；有几个技能目录、几个插件。名字、键名、目录名显示不显示看第三个开关（等 PD-A1）：关着只显示「第 N 个」和个数；开着显示合乎语法的那些，不合语法的用固定文字顶替 |
| 2 | 导入列表与原因 | 查询 `ListLocalConfig` 把上面这些列出来，每项带 `blocked_reason`；命令 `ImportLocalConfig` 一律拒绝并逐项给原因 |
| 3 | 协议加法 | `LocalConfigItem` 三个字段、一个错误码、视图跟上。没有新命令、新事件、新表 |
| 4 | 三个开关 | `MCP_IMPORT_ENABLED`、`SKILL_IMPORT_ENABLED`，默认关，A 里只决定原因文字，没有「开着」能走通的路；`LOCAL_NAMES_SHOWN`，默认关，决定名字显示不显示（第 5 轮加的，等 PD-A1） |

A 不做（都在第二部分，待定）：导入、快照、系统钥匙串、填密钥、开会话时把 MCP 与技能交给 CLI、移除与撤回、首次导入弹窗。

四条保证：

1. **不读 MCP 配置里 `env`、`headers` 的值**（RA1）。
2. **产品负责人接受例外（PD-1、PD-9）之前，MCP 的命令、参数、地址和技能目录里的文件内容，iWork 不读、不算摘要、不发给客户端**（RA2）。做法不是「开关关着所以跳过」，而是 A 的发现只有 `discover_names` 这一个函数：它解析用的结构里没有这三个字段，对技能目录只列目录、不开文件。
3. **用户配置里的任何一段原文，都只能经一个出口离开发现这一层**（RA6）。名字、键名、目录名、插件键、连接方式也是用户写的字符串，同样可能被写成带凭据的样子（条目名写成 `https://…/mcp?token=…`）。出口只有三种产物：固定的枚举标签、合乎语法的短名字、不含原文的固定替代文字。条目 id 用序号，错误只带来源种类与行列号。**合乎语法的名字仍然可能是一串 token，语法检查证明不了它不是**；所以名字默认不显示，显示要产品负责人接受一条例外（PD-A1）。
4. **什么都导不进来，也不留任何持久的东西**（RA3、RA5）：查询与被拒的命令都不提交事件、不写文件。所以 A 的回退就是换回旧版本，没有数据要收拾。

## A3 设计

### A3.1 发现：只到名字这一层，原文只经一个出口

`iwork-import-claude::sources` 里一张来源表，发现只碰表里的路径、只取表里的东西：

| 来源 | 怎么碰 | 取（都要过下面的出口） | 不取 |
| --- | --- | --- | --- |
| user 范围的 MCP | **读** `<配置目录>/.claude.json` | 顶层 `mcpServers` 有几项；每一项的名字、`type`；`env`、`headers` 各有几个键、键名 | `command`、`args`、`url`；`env`、`headers` 的值；这个文件里别的顶层键 |
| 用户级技能 | **只列目录** `<配置目录>/skills/`，看每个条目是不是目录 | 有几个子目录；子目录的名字 | 任何文件的内容，`SKILL.md` 也不开；`skills/synced/`（厂商账号同步下来的） |
| 已装的插件 | **读** `<配置目录>/plugins/installed_plugins.json`；对每个 `installPath`：**只列目录** `skills/`，**读** `.mcp.json` | 有几个插件；插件键；技能子目录的个数与名字；自带 MCP 同第一行。`installPath` 只拿来定位文件，不输出 | `plugin.json`、技能文件、插件里别的一切 |

- `<配置目录>`：后台环境里有 `CLAUDE_CONFIG_DIR` 就用它，没有用 `~/.claude`；`.claude.json` 在配置目录是默认值时位于家目录（D1 核对）。
- **表外的路径一概不碰**：`.credentials.json`、`settings.json`、`projects/`、系统钥匙串都不在表里。local 范围和仓库里的 `.mcp.json` 不列（PD-3 的 a；改了是给表加行）。
- **被跳过的字段怎么跳**。解析用 `serde` 的选择性反序列化：目标结构只声明 `type` 一个字段，外加一个只收键名的访问器给 `env`、`headers`（值交给 `IgnoredAny` 吃掉）；`command`、`args`、`url` 和别的键因为结构里没有，也落到 `IgnoredAny`。文件的字节会经过进程内存（要读文件就免不了），但这些值不会变成任何一个 Rust 值。和 T06 读 `auth status` 是同一种做法（T06 方案第 10 节）。
- **读文件走接缝**：`trait LocalFiles { read(path), list(dir), kind(path) }`，生产实现是 `std::fs`，测试实现记下每一次调用（哪个方法、哪个路径）。

**出口：取到的原文怎么离开这一层**

上表「取」的那一栏里，名字、键名、目录名、插件键、`type` 都是用户写的字符串。第 4 版把它们当成天然安全的元数据原样往外送，这不成立：条目名可以写成 `https://…/mcp?token=…`，键名、`type` 也可以是任意字符串。所以这一版不再逐个字段说「这个可以送」，而是规定**原文只在 `iwork-import-claude` 的私有函数里出现，出这一层只有三种产物**，由类型挡住别的路（`DiscoveredName` 没有普通的 `String` 字段，A3.4）：

| 产物 | 怎么来的 | 用在哪 |
| --- | --- | --- |
| 固定的枚举标签 | `type` 和一张固定的表逐字比：没写或 `stdio` → `Stdio`；`http`、`streamable-http` → `Http`；`sse` → `Sse`；别的任何字符串 → `Other`。输出的是标签，不是原文 | 连接方式 |
| 合乎语法的短名字 `Label` | 只能经 `Label::parse` 构造：`[A-Za-z0-9._@-]`，1 到 64 个字符（`@` 是给插件键 `名字@市场` 用的）。不合的得不到 `Label` | 名字、键名、目录名、插件键 |
| 不含原文的替代 `Hidden` | 不合语法的，或者策略是「只给个数」时的全部 | 同上；显示成固定句式「第 N 个 MCP 服务器」「第 N 个技能」「第 N 个插件」「另有 K 个键名未显示」 |

- **两种策略**（`NamePolicy`，应用服务照开关 `LOCAL_NAMES_SHOWN` 传进来，A3.2）：
  - `CountsOnly`（开关关着，默认）：名字、键名、目录名、插件键一律 `Hidden`，只给个数和连接方式。解析时 `mcpServers` 的键、`env` / `headers` 的键、插件登记文件里的插件键也交给 `IgnoredAny`，只数个数，不变成字符串。目录名是操作系统列目录时给的，拿到之后只数、只判是不是目录，不留。
  - `Grammar`（开关开着，等 PD-A1）：合乎语法的给 `Label`，不合的给 `Hidden`。
- **合乎语法不等于没有凭据**。`ghp_` 开头的一串、一段不长的密钥都合乎上面的语法。语法检查挡得住的是 URL、带空格或标点的串、超长的串；挡不住有人把名字起成一串 token。这一点证明不了，只能由产品负责人决定接不接受（PD-A1）。没接受之前开关关着，一个名字都不出这一层。
- **条目的 id 不带原文**：种类加序号。`mcp:user:<n>`、`skill:user:<n>`、`plugin:<n>`、`mcp:plugin:<n>:<m>`、`skill:plugin:<n>:<m>`；序号是来源里的先后（JSON 里出现的次序；目录按名字的字节序）。来源没变时两次发现的 id 对得上；变了就可能对不上，A 里导入一律被拒，后果只是原因变成「找不到这一项」。B、C 需要跨重启稳定的 id 时再定（它们另有指纹）。
- **错误不带原文**：`Unreadable{ 哪个来源, io 的错误种类 }`、`Malformed{ 哪个来源, 行, 列 }`。「哪个来源」是一个枚举（用户配置、插件登记文件、第 N 个插件的 `.mcp.json`、技能目录、第 N 个插件的技能目录），不是路径。**`serde_json` 给的错误文字不往外传**：它会把看到的那个值原样写进去（如 `invalid type: string "…"`），只取它的行、列。操作系统的错误只取种类，不取带路径的文字。
- **`Debug` 与日志**：带原文的中间结构是私有的、不实现 `Debug`；`DiscoveredName` 的 `Debug` 里只有上面三种产物。发现只记条数。
- **读不了怎么办**：文件不存在 → 这个来源是空的（用户没装插件很正常）。文件在而读不了或看不懂（不是预期的形状）→ 整个查询回 `UNAVAILABLE`，带上面那种不含原文的错误。不拿「能读出来的那一部分」冒充全部。
- 插件自带的 MCP 列在 MCP 一组里，来源写它属于哪个插件（`Label` 或「第 N 个插件」）。

### A3.2 开关与判定（`iwork-core::local_import`，纯函数）

```rust
pub const MCP_IMPORT_ENABLED: bool = false;     // 等 PD-1
pub const SKILL_IMPORT_ENABLED: bool = false;   // 等 PD-9、PD-5、K3
/// 合乎语法的名字、键名、目录名、插件键显示不显示。关着：只给「第 N 个」与个数。等 PD-A1。
pub const LOCAL_NAMES_SHOWN: bool = false;
/// 生产代码只从上面的常量构造；测试可以给任意值。
pub struct Gates { pub mcp: bool, pub skill: bool }

pub enum Refusal {
    NotEnabled(LocalConfigKind),   // 「MCP 导入还没启用」/「技能导入还没启用」
    NotImplemented,                // 开关开着，可这一版没有导入的代码：「这一类导入还没实现」
    UnknownItem,                   // 勾选的条目不在这次发现的结果里
}
/// 这一项为什么导不了。A 里每一项都有原因。
pub fn refusal(kind: LocalConfigKind, gates: Gates) -> Refusal;
/// A 里没有「接受」：ImportPlan 是没有变体的枚举，这个函数只可能返回 Err。B、C 给它加变体。
pub enum ImportPlan {}
pub fn plan_import(found: &[DiscoveredName], selected: &[ItemId], gates: Gates)
    -> Result<ImportPlan, Vec<(ItemId, Refusal)>>;
```

- 技能与插件条目看 `gates.skill`，MCP 条目看 `gates.mcp`。
- **两个导入开关在 A 里不通向任何读或写**。有人把常量改成 `true` 而 B、C 的代码还没有：原因从「还没启用」变成「还没实现」，照样导不了，发现照样只到名字这一层。真正放开要随 B、C 的方案走。
- **`LOCAL_NAMES_SHOWN` 是 A 里唯一会改变「什么离开发现这一层」的开关**。它只在两种策略之间选（A3.1），两种都写、都测。把它改成 `true` 的那次提交要引用产品负责人对 PD-A1 的答复；选了 b 的话这个常量和 `Grammar` 策略一起删掉。

### A3.3 命令与查询

| --- | --- | --- |

### A3.4 协议加法

```proto
// model.proto
message LocalConfigItem {
  // …1–6 不变
  // MCP：要用户填值的键里，允许显示的那些键名（合乎语法，且名字开关开着）。别的种类为空。
```

## A5 出事场景

每条写三件事：会出什么事 / 怎么止血和回退 / 由什么保证。

**CA1 还没接受例外，iWork 就读了 MCP 的参数或技能文件**
- 出什么事：有人给 `discover_names` 的解析结构加了 `args` 字段想在列表里多显示一点，或者去读 `SKILL.md` 取说明；用户一打开导入列表，参数里的连接串、技能目录里的文件内容就经过了后台，前者还发给了客户端显示。
- 止血：这些内容只经过了内存，没有落盘（A 不写任何东西）。换回上一个版本即可；要不要轮换看读到了什么。
- 保证：RA2 的四条。断言的是文件接缝的调用记录和发给客户端的字节，不是「函数没被调」。

**CA2 `env`、`headers` 的值被读进来了**
- 出什么事：解析的代码被改坏，值被当成普通字段留了下来，随列表发给了客户端。
- 止血：同 CA1。
- 保证：RA1；`list_local_config_carries_no_sensitive_bytes` 的夹具里 `env`、`headers` 的值也放了暗号。

**CA3 Claude 的配置文件换了形状，或者读不了**
- 出什么事：Claude Code 升级后 `installed_plugins.json` 的结构变了，或者 `~/.claude.json` 没有读权限。
- 止血：导入列表打不开，报错写明是哪个来源（用户配置、插件登记文件、第几个插件的 `.mcp.json`）、第几行第几列；别的功能不受影响（A 不在开会话的路上）。等 iWork 发版跟上新形状。
- 保证：`discover_names_reports_malformed_source`（`installed_plugins.json` 换成别的结构：`Malformed{PluginRegistry, 行, 列}`）；`missing_source_is_empty_not_error`（没有 `plugins/` 目录：插件一组为空，查询成功）；错误里没有原文由 RA6 的 `errors_carry_no_source_text` 保证。

**CA4 开关被改成了开**
- 出什么事：B、C 的方案还没审，有人为了试一下把常量改成 `true` 并合了进去。
- 止血：没有后果要止：A 的代码里开关不通向任何读或写，列表上的原因变成「这一类导入还没实现」。改回来即可。
- 保证：`plan_import_reasons` 的「开关开」那一半；RA2 的测试不看开关，开着关着发现都只有 `discover_names`。

**CA5 用户以为导入成功了**
- 出什么事：界面上还留着能点的「导入所选」，点了之后没有任何反应或只闪一下错误，用户以为 MCP 已经能用，回到对话里发现模型没有那个工具。
- 止血：不涉及数据。界面改对。
- 保证：RA4 的客户端测试；A3.5 每项都显示原因。

**CA6 名字里带着凭据**
- 出什么事：① `mcpServers` 的条目名被写成了一整条带 token 的地址，或者键名、`type`、目录名里有 token；iWork 把它当名字显示在列表上、拼进条目 id、写进错误、经本机通道发给客户端，开发构建的帧格式化还会把它印出来。② 名字合乎语法、可它本身就是一串 token（有人把 MCP 起名叫自己的访问令牌）。
- 止血：①② 都只经过内存，没有落盘。真发生了：换回上一个版本；轮换那份 token。
- 保证：①：RA6。不合语法的原文出不了发现这一层，id 是序号，错误只有行列。②：语法检查证明不了它不是凭据。默认（`LOCAL_NAMES_SHOWN` 关着）一个名字都不出这一层，`counts_only_lets_no_source_text_out` 把合乎语法的暗号也算进去搜；开着的话它会显示出来，这要产品负责人接受（PD-A1）。

## A9 协调项、已知限制、要产品负责人定的

**要产品负责人定的**：一条，PD-A1。它不卡实施（默认照更严的那种做），只决定名字显示不显示。范围、撤回方向已经定了（需求 `3b5adc0`）。PD-3（发现哪些范围的 MCP）A 先按 a 做（只列 user 范围与插件自带的）；以后选了 b、c 是给来源表加行，A 写的不用改。PD-1～PD-9 原样留在第二部分第 12 节。

**PD-A1 列表上显不显示名字**
- 问题：需求 `3b5adc0` 批准的是「只读名字的发现」。可是 MCP 的条目名、环境变量与请求头的键名、技能目录名、插件键都是用户自己写的字符串，没有哪一种保证不带凭据。iWork 能做的是语法检查：只放行由字母、数字和 `. _ @ -` 组成、不超过 64 个字符的。它挡得住整条地址（`https://…?token=…`）、带空格与标点的串、超长的串；**挡不住有人把名字本身起成一串 token**（比如一台 MCP 就叫 `ghp_…`，或者把 token 当成了环境变量的名字）。这种名字会显示在列表上、经本机通道发给客户端、在开发构建的帧输出里出现。它不落盘（A 什么都不写）。
- a（推荐）接受为安全不变量第 1 条的一个小例外，登记进需求第 9 章：合乎上面语法的名字、键名、目录名、插件键，iWork 会读、会显示、会发给客户端；不合语法的一律不显示。理由：把 token 起成名字是用户自己在配置里写错了地方，很少见；而看不到名字的列表认不出哪个是哪个，A 剩下的那点用处也没了。代价：上面说的那种名字会被显示。
- b 更严：名字一律不显示。列表上是「第 1 个 MCP 服务器（stdio，要填 3 个键）」「第 5 个技能」「第 2 个插件（4 个技能目录）」。代价：用户只看得出本机有多少东西，对不上是哪一个；等 B、C 开导入时，要勾选就必须先解决「怎么让用户认出它」。
- c 折中：名字显示（照 a 的语法），键名不显示、只给个数。理由是键名离凭据更近（紧挨着值）。代价：例外照样要登记，只是小一点；列表上看不到要填哪些键。
- 没答之前：照 b 的样子做（`LOCAL_NAMES_SHOWN` 关着）。

## 0 一页总览

Claude Code 首次接入时，iWork 列出用户本机给它配的 MCP 服务器、技能、插件，用户勾选后导入。导入之后成员会话里只有导入过的这些，没导入的不出现。

| 导入什么 | 从哪读 | 存到哪 | 会话怎么拿到 |
| --- | --- | --- | --- |
| 技能（用户级的，和插件里的） | 技能目录的文件 | 复制进只读区 `imports/<运行时>/<一代快照>/`，目录由 iWork 自己拼成插件的样子；凭据文件范围内的不带（等 PD-9） | `--plugin-dir`（`SessionSpec.plugin_dirs`） |
| MCP 的启动配置（命令、参数、地址） | `~/.claude.json`、插件的 `.mcp.json` | 系统钥匙串，一台服务一条（等 PD-1） | 适配器从钥匙串取出来，放进 ACP `session/new` 的 `mcpServers` |
| MCP 的环境变量、请求头的**值** | **不读** | 用户在 iWork 里重填，进系统钥匙串，一个键的一版值一条 | 同上 |
| MCP 的名字、要填值的键名、每个键现在用哪一版 | 同启动配置 | 数据库（事件与投影） | 后台拼 `SessionSpec.mcp` |
| 插件里的 hook、命令、子代理、可执行文件、设置 | 不读 | 不导入 | — |

五条最要紧的保证：

1. **不读 MCP 配置里 `env`、`headers` 的值**。解析时直接跳过，不变成程序里的任何一个值（第 4 节 R1）。
2. **放宽安全不变量第 1 条的两处，各有一个默认关着的门槛，门槛挡在「读」之前**。一处是 MCP 的命令、参数、地址（里面可能写着密钥，iWork 分不出来），等 PD-1；一处是技能目录里的文件（里面可能有 iWork 认不出的凭据），等 PD-9。门槛关着时，这些内容 iWork 不读、不算摘要、不发给客户端，列表里只有名字（R21）。门槛开了之后，MCP 配置里读出来的值只进钥匙串，数据库、事件、日志里搜不到（R2）；技能文件按一张范围表排除，按名字就能判的不打开（R6）。
3. **用户的 hook 不随导入进会话，技能也不能给自己放行**。导入区里的插件目录是 iWork 自己拼的，只往里放技能目录；`SKILL.md` 的 frontmatter 只留一张白名单里的键（R4、R5）。
4. **用户确认的是哪一份，存进去、交出去的就是哪一份**。查询结果里每一项带指纹，导入时现读一次、指纹对不上就拒；会话读得到的东西都是写一次不改的版本，只由事件切换（3.4 的四条约定，R17–R20）。
5. **导入的东西出了问题，撤得回来，而且撤回有人负责到底**。移除的回执发出之后，带着旧配置的会话过不了启动边界；已经起来的由常驻的会话线表按已提交的状态一条条停掉，受理函数被中止、进程一时停不掉都不影响它接着做（R16、R22）。

本方案新加的东西：一个命令 `RemoveImportedConfig`、一个事件 `ImportedConfigRemoved`、一个错误码、一个消息 `McpLaunchConfig`（钥匙串里启动配置的编码）、一个端口 `LocalConfigSource` 和它的 Claude 实现（新 crate `iwork-import-claude`）、`iwork-host` 的钥匙串实现、`iwork-core::local_import` 一个纯函数模块、会话线表里的一段对账（表本身由 T10a 交付）。协议里别的都已经在了（T02 定的），只加字段。

## 3 设计

### 3.1 发现：读哪些文件、取哪些键

`iwork-import-claude::sources` 里一张来源表，发现只打开表里的文件，只取表里的键。**取哪些键看门槛**：`discover(scope, admit)` 的 `scope` 是应用服务照两个门槛常量填的（`DiscoverScope{ mcp_launch: bool, skill_files: bool }`）。

| 来源 | 打开的文件 | 门槛关着时取 | 门槛开着时多取 | 任何时候都不取 |
| --- | --- | --- | --- | --- |
| user 范围的 MCP（门槛 `MCP_IMPORT_ENABLED`，等 PD-1） | `<配置目录>/.claude.json` | 顶层 `mcpServers` 每一项的名字、`type`；`env`、`headers` 的**键名**；有没有 `headersHelper`、`oauth` 这两个键 | `command`、`args`、`url` | `env`、`headers` 的值；这个文件里别的顶层键 |
| 用户级技能（门槛 `SKILL_IMPORT_ENABLED`，等 PD-9、PD-5） | 关着：**一个文件都不打开**，只列 `<配置目录>/skills/` 下有哪些子目录。开着：`skills/<目录>/SKILL.md` 与那个目录下的文件 | 子目录的名字（当条目名用） | frontmatter 的 `name`、`description`；要带的文件的清单与内容摘要 | `skills/synced/`（厂商账号同步下来的）；3.2 按路径判成不带的文件（不打开） |
| 已装的插件 | `<配置目录>/plugins/installed_plugins.json`；开着技能门槛时再加每个 `installPath` 下的 `.claude-plugin/plugin.json`、技能目录；`.mcp.json` 照第一行的两种取法 | 插件键（登记文件里的）；插件自带 MCP 的名字与键名 | 插件名；技能同上一行；MCP 的 `command`、`args`、`url` | 插件里别的一切 |

- `<配置目录>`：后台环境里有 `CLAUDE_CONFIG_DIR` 就用它，没有用 `~/.claude`；`.claude.json` 在配置目录是默认值时位于家目录（待 D1 核对）。
- **表外的文件一概不打开**：`.credentials.json`、`settings.json`、`projects/`、系统钥匙串都不在表里。local 范围和仓库里的 `.mcp.json` 列不列，等 PD-3。
- **怎么做到不读值**。解析用 `serde` 的选择性反序列化：目标结构只声明要的字段，别的字段落到 `IgnoredAny`；`env`、`headers` 用一个只收键名的访问器，值一律交给 `IgnoredAny` 吃掉。MCP 门槛关着时，`command`、`args`、`url` 也落到 `IgnoredAny`（用另一个不声明这三个字段的目标结构），和 `env` 的值是同一种待遇。文件的字节会经过进程内存（要读文件就免不了），但值不会变成任何一个 Rust 值，函数返回之后就没有了。这和 T06 读 `auth status` 的做法是同一种（T06 方案第 10 节）。错误只带文件名和键的路径，不带内容。
- **门槛关着时条目长什么样**：`launch_preview`、`fingerprint` 为空，技能的 `description`、`notes` 为空，`blocked_reason` 写「MCP 导入还没启用」或「技能导入还没启用」。列表还在，用户看得见本机有什么；能导的一项都没有时首次导入框不弹（3.7）。
- **读文件走接缝**：`trait LocalFiles { read(path), list(dir), kind(path) }`，生产实现是 `std::fs`，测试实现记下每一次调用（哪个方法、哪个路径），还能在指定的那一次读之后把内容换掉。「只打开表里的文件」「门槛关着时不读」「按名字拒的不打开」「来源被换掉之后不会存错」都靠它测。
- **`discover()` 一次把要用的都读出来**（门槛开着时）：每个 MCP 条目带着它的启动配置（`McpLaunch`：命令、参数、地址、键名，没有值）；每个技能条目带着要带的文件清单与内容摘要。导入时不再为同一个条目去读第二遍来源的配置文件（3.4 约定三）。
- **条目的 id** 由来源拼出来，重启不变：`mcp:user:<名字>`、`skill:user:<目录名>`、`plugin:<插件键>`、`mcp:plugin:<插件键>:<名字>`、`skill:plugin:<插件键>:<目录名>`。插件自带的 MCP 作为普通的 MCP 条目列在 MCP 一组里，来源写插件名，不嵌在插件那一行下面（数据上不做嵌套；界面怎么摆见第 11 节给设计窗口的问题）。
- **导不了的条目照样列出来，写明原因**（`blocked_reason`），不悄悄藏掉：

| 情形 | 原因文字 |
| --- | --- |
| MCP 条目，而 `MCP_IMPORT_ENABLED` 关着 | 「MCP 导入还没启用」 |
| 技能或插件条目，而 `SKILL_IMPORT_ENABLED` 关着 | 「技能导入还没启用」 |
| `type` 是 `ws`、`sdk`，或有 `url` 却没有 `type` | 「这种连接方式 M1 不支持」 |
| 有 `headersHelper` 或 `oauth` 键 | 「用了动态请求头或 OAuth 配置，M1 不支持导入」 |
| MCP 名字不合规（3.3） | 「名字里有 iWork 不接受的字符」或「名字以 iwork 开头」 |
| 插件的 MCP 配置里有 `${CLAUDE_PLUGIN_ROOT}` 之外的 `${CLAUDE_…}` 变量 | 「配置引用了 iWork 不提供的插件变量」 |
| 插件是「根目录一个 SKILL.md」的布局 | 「这种插件布局 M1 不支持」 |
| 技能目录名不合规、`SKILL.md` 的 frontmatter 看不懂（3.2）、超过大小上限、里面有私钥 | 各自点名 |

- 不列出的：用户的 hook、权限模式、插件里的 `commands/`、`agents/`（FR20：不导入）；`commands/` 目录下的旧式命令。

### 3.2 技能：一代一份快照，iWork 自己拼

**目录**（`<数据目录>/imports/<运行时 kind>/`；kind 是 `runtimes.kind` 那个不透明字符串）：

```text
imports/claude/
  g-<ULID>/                       一代快照，建好之后不再改
    MANIFEST                      这一代里每个文件的相对路径与大小，最后写
    imported/                     用户级技能合成的一个插件
      .claude-plugin/plugin.json  iWork 写的，内容只有 {"name":"imported"}
      skills/<技能目录名>/…
    <插件名>/                     每个来源插件一个，保住原来的名字（技能名仍是 <插件名>:<技能名>）
      .claude-plugin/plugin.json  iWork 写的，只有 name
      skills/<技能目录名>/…
  .tmp-<随机>/                    正在建的；建完改名成 g-…
```

交给会话的 `plugin_dirs` = 当前这一代里每个插件子目录的绝对路径（排过序）。逐个给，不给上一级目录：T0f 的 V2 验过的是「一个插件根」这种给法；「给一个放了多个插件的目录」只在帮助和文档里写着，没验过。

**哪些文件带、哪些不带**（`iwork-core::local_import::admit`，纯函数，分两段；应用服务把它包成 `FileAdmit` 传给 `discover` 与 `build_snapshot`，两处用的是同一个判定）。先按路径判，**判成不带或拒的不打开文件**；判成「要看内容」的才读，再按内容判。名字比较不分大小写。

| 段 | 序 | 条件 | 结果 |
| --- | --- | --- | --- |
| 按路径（不打开） | 1 | 文件名命中私钥表的名字或扩展名那几行（`private_key::matches(名字, 空内容)`，T10d 方案 3.4，交付方 T10d） | `RefuseItem`：这个技能整个不导，原因点名文件 |
| 按路径 | 2 | 路径上任何一级的名字以 `.` 开头（`.env`、`.env.local`、`.npmrc`、`.netrc`、`.git/`、`.aws/`、`.docker/config.json` 等） | `Skip` |
| 按路径 | 3 | 相对路径里有连续几级等于底线凭据清单里某一条的路径（清单是相对主目录的路径，取自 `protected_paths().credential`，T07 的那一份；比的是整条路径，不是文件名）。例：`x/Library/Keychains/a.keychain` 命中 `Library/Keychains`；`.docker/config.json`、`.codex/auth.json` 命中的是它们各自的整条路径，单独一个 `config.json`、`auth.json` 不算 | `Skip`。清单里以 `.` 开头的条目已经被第 2 行盖住；这一行管不带点的（现在是 `Library/Keychains`），清单以后加了条目这里自动跟上 |
| 按路径 | 4 | 文件名去掉扩展名后恰好是 `credentials`、`credential`、`secrets`、`secret`、`token`、`tokens`、`apikey`、`api_key`、`api-key`、`password`、`passwords` | `Skip` |
| 按路径 | 5 | 扩展名是 `.keystore`、`.jks`、`.kdbx`、`.token`、`.secret`、`.secrets`、`.credentials` | `Skip` |
| 按路径 | 6 | 剩下的 | `Read`：读内容，进下一段 |
| 按内容 | 7 | 内容命中私钥表的内容那几行（`private_key::matches(空名字, 内容)`） | `RefuseItem` |
| 按内容 | 8 | 剩下的 | `Take` |

- 这张表就是「凭据文件的范围」。范围内的不带，被略过的文件按相对路径列进这一项的 `notes`（「不带：.env、config/credentials.json」），用户勾选之前看得到。宁严勿松：`secrets.md` 这种讲解文档也会被第 4 行略过。
- **表现在漏的三种，按 `Take` 处理，收不收进表等 PD-9**：目录名在第 4 行名字里的（`secrets/production.json`、`credentials/team.yaml`）；文件名带多段后缀的（`credentials.dev.json`、`secrets.prod.yaml`，去掉扩展名后是 `credentials.dev`，不等于 `credentials`）。PD-9 里列了这些例子和两行候选规则。
- **范围外的认不出**：`settings.json`、`deploy.yaml` 这类普通名字的文件里写着 token，脚本里写死了密钥，iWork 不看内容里有没有密钥（看也只能靠猜），会原样复制。这就是 PD-9 要产品负责人接受的那个例外。
- **门槛**：`iwork-core::local_import` 里一个常量 `SKILL_IMPORT_ENABLED`，默认 `false`。为 `false` 时：`discover` 不打开技能目录里的任何文件（3.1）；`plan_import` 对技能、插件条目一律拒（原因「技能导入还没启用」）。把它改成 `true` 的那次提交要同时满足三样：PD-9 有产品负责人的明确接受（提交信息里引用）、PD-5 定了并且它要的实测格通过（下面「技能正文里的命令」）、`skill_token_files_never_reach_imports` 通过。MCP 的导入不受它管（它有自己的门槛，PD-1）。

**怎么拼**（`LocalConfigSource::build_snapshot(plan, admit, dest)`，`dest` 是那个 `.tmp-` 目录，必须还不存在，`mkdir` 独占创建；写文件经接缝 `trait SnapshotFs { create_dir, write_file, sync_file, sync_dir, rename }`，生产实现是 `std::fs`）：

1. 留下来的条目从上一代复制（上一代是 iWork 自己写的，只有普通文件和目录）。不从来源重读：没让重导的技能保持导入那一刻的样子。
2. 新导入、重新导入的条目从来源复制。来源的技能根目录先解析一次链接（`~/.claude/skills` 本身、或单个技能目录是链接都很常见）；解析之后，用 `iwork-rootfs` 的读法（ADR-0010，路径上任何一级都不跟随链接）走这棵树：
   - 只复制普通文件和目录。链接、FIFO、socket、设备文件都略过，数目记进这一项的 `notes`（「略过 2 个链接」）。
   - 每个文件先过 `admit.by_path`，是 `Read` 的才打开，再过 `admit.by_content`（上面那张表）。
   - 上限：一个技能 2000 个文件、32 MiB；整代快照 256 MiB（三个具名常量，放 `iwork-import-claude::limits`）。超了 → 这一项不导，原因写明超了哪个。
   - 文件内容原样，权限只保留「可执行」这一位（0644 或 0755）。
   - **边复制边算摘要**（对每个带过去的文件：相对路径、可执行位、内容，和 `discover` 算摘要是同一个函数），每一项算出来的摘要交回给调用方；它和用户确认时的那个对不上，整次导入作废（3.4 约定三）。
3. `SKILL.md` 过 frontmatter 白名单（下面）。
4. `plugin.json` 由 iWork 写，只有 `name`。来源插件的 `plugin.json` 不复制。
5. **持久化的先后**（照 T02 方案 2.10「先 `fsync` 临时文件、改名、再 `fsync` 目录」的写法；macOS 上用不用 fullfsync 跟存储读同一个开关）：
   1. 每个文件写完 `sync_file`；
   2. 写 `MANIFEST`，`sync_file`；
   3. 从最深的目录往上，逐个 `sync_dir`，直到 `.tmp-…` 本身；
   4. `.tmp-…` 改名成 `g-<ULID>`（同一个目录下改名，原子）；
   5. `sync_dir` 上一级目录 `imports/<kind>/`；
   6. 这五步都返回成功之后，调用方才提交事件。之后这一代只读不写。

**启动恢复**（后台启动时、放开任何会话之前，排在 T04 的启动恢复里；先后不能换）：

1. 读投影里这个运行时的当前快照名。
2. 核实它完整：目录在、`MANIFEST` 在、清单里每个文件都在而且大小相等。
3. 完整 → 清扫：`imports/<kind>/` 下名字是 `g-*`、`.tmp-*` 而又不是当前这一代的目录都删（这时没有任何会话）；别的名字不碰、记一条日志。
4. 不完整 → **什么都不删**。这个运行时记「快照损坏」（内存里的状态，每次启动现查，不进投影）：`plugin_dirs` 给空，技能条目在列表里标「快照损坏，请重新导入」，写错误日志与一条审计。用户重新导入会生成新的一代。不自动退回上一代：上一代里可能有已经移除的技能。

运行当中，不再有会话绑着的旧一代由会话线表的对账删（3.4「撤回」第 4 步）。

**为什么是「自己拼」而不是「复制插件再删掉 hook」**：文档列的自动发现位置有十二种，还会再加。删掉认识的那几种，新版本多出来一种就漏了。只放 `skills/` 这一种，别的无论叫什么都进不来。

**frontmatter 白名单**（`iwork-import-claude::skill_md::filter(bytes) -> Result<Filtered, Unreadable>`，纯函数）：

- 留：`name`、`description`、`when_to_use`、`argument-hint`、`arguments`、`disable-model-invocation`、`user-invocable`、`paths`、`context`、`agent`、`background`、`disallowed-tools`、`license`、`metadata`、`compatibility`、`version`。
- 去掉：表外的一切。眼下已知的有 `allowed-tools`（让工具免询问）、`hooks`（注册 hook）、`model`、`effort`（iWork 每次都显式指定模型与思考强度，技术设计 9.6）、`shell`。去掉了哪些键写进这一项的 `notes`，导入前用户看得到。
- 做法：frontmatter 是开头两行 `---` 之间的那一段。按行切成「顶格的 `键:` 起头、到下一个顶格键之前」的块，整块留或整块去，正文原样。不引 YAML 库。
- **看不懂就不导**：开头是 BOM、有单独的 CR、顶格行不是 `键:` 的样子（带引号的键、`<<:` 合并键、`{…}` 流式写法、制表符缩进）→ `Unreadable`，这个技能不导，原因写「SKILL.md 的开头看不懂」。宁可少导一个，不猜。
- 没有 frontmatter 的 `SKILL.md` 原样复制。技能目录里别的 `.md` 不处理（只有 `SKILL.md` 的开头有这层含义）。

**技能正文里的命令（`` !`命令` ``）** 白名单管不到（它在正文里）。CLI 的权限层只拦它要问的命令，`cat` 这类只读命令它不问（1.4 引的 x2）。所以：

- 去掉 `allowed-tools` 之后，**CLI 要问的命令**（写文件、别的程序）照文档不执行（待 K3a）；**CLI 不问的只读命令**多半照样在技能加载时执行，读到的内容直接进模型上下文，不经 iWork 审批、没有审计（待 K3e）；读不读得到底线目录看这类命令在不在沙箱里跑（待 K3f）。
- 干净的办法是会话设置里加 `disableSkillShellExecution: true`（PD-5 的 a，待 K3c）。
- 这一条定下来、对应的格子通过之前，`SKILL_IMPORT_ENABLED` 不开。

### 3.3 MCP：名字进数据库，别的进钥匙串

**一台导入的 MCP 由三样东西组成**：

| 东西 | 内容 | 存在哪 |
| --- | --- | --- |
| 登记 | `mcp_server_id`（每次导入新生成的 ULID）、条目 id、名字、要填值的键名、每个键现在用哪一版 | 事件与投影 |
| 启动配置 | 消息 `McpLaunchConfig{transport, command, args, url, env_keys, header_keys}` 的 Protobuf 二进制 | 钥匙串，名字 `mcp/<mcp_server_id>/launch`（等 PD-1）。`mcp_server_id` 每次导入都是新的，所以这一条写一次、不会被覆盖 |
| 一个键的一版值 | 用户填的 | 钥匙串，名字 `mcp/<mcp_server_id>/key/<键名>/<版本 ULID>`。每填一次是新的一版、新的一条，不覆盖旧的 |

- 启动配置用 Protobuf 编码，是因为写它的（应用服务）和读它的（适配器）不在一个 crate 里，两边都已经依赖 `iwork-proto`；钥匙串里存的东西升级之后还得读得出来，进了兼容契约就只增不改。
- **名字**：`[A-Za-z0-9_-]{1,64}`，不以 `iwork` 开头（留给 iWork 自己的协作 MCP，需求 8.1）。同一个运行时下不重名。它会出现在工具名 `mcp__<名字>__<工具>` 和审批卡片上。插件自带的 MCP 用配置里的名字，撞名时这一项导不了，原因点名和谁撞。
- **env 与请求头的每个键都要用户填值**，iWork 不判断哪个是密钥、哪个只是普通配置（判断就得读值）。代价和别的做法见 PD-2。
- **齐不齐**（`readiness`，纯函数）：每个键在投影里都有当前版本 → `Ready`；否则 `MissingKeys(键名…)`。只有 `Ready` 的进 `SessionSpec.mcp`。
- **重新导入 = 换一台**：同一个条目再导一次（来源变了，或用户就是想重来），生成新的 `mcp_server_id`，键全部重填；旧的那台算退场（3.4 约定四）。目的：`~/.claude.json` 里那一项的命令被人改过之后，新命令拿不到用户以前填的密钥，用户得看着新的启动方式重新填一遍。
- **插件自带的 MCP**：配置里的 `${CLAUDE_PLUGIN_ROOT}` 在导入时换成那个插件的 `installPath`。程序留在用户的插件目录里跑，iWork 不复制它（第 9 节 L4）。
- **`mcp_read_only`**（哪些 MCP 工具声明了只读）：M1 给空集，所有 MCP 工具在手动、自动档都询问（T07 方案 3.1 写的安全侧做法）。等 PD-6。

### 3.4 命令与查询

#### 四条约定（导入、移除、填值三个命令都照它走）

文件、钥匙串、进程都不在数据库事务里。下面四条管它们和事务怎么对齐。

| # | 约定 | 目的 |
| --- | --- | --- |
| 一 | **写一次、带版本**。会话读得到的对象只有三种：一代快照（`g-<ULID>`）、一台 MCP 的启动配置（名字里是每次导入新生成的 `mcp_server_id`）、一个键的一版值（名字里有版本）。写了不改、不覆盖 | 提交之前写的东西，没有任何会话读得到 |
| 二 | **先持久、后引用；事件是唯一的切换点**。对象写好并且持久化之后（文件照 3.2 第 5 步；钥匙串以 `set` 返回成功为准）才提交事件。会话只经投影里的引用找对象 | 提交失败、崩溃、掉电，留下的只会是没被引用的对象；投影指着的对象一定是完整的 |
| 三 | **提交时核对**。(a) 改动导入状态的三种事件都带 `base_revision`：受理时读到的这个运行时的「导入修订号」。写线程投影时核对 `runtimes.import_revision` 还等于它，不等就让整条命令回滚，回 `CONFLICT`（`exec_hit`，和 T10d 方案 3.6 让写线程把关是同一个机制）；等的话把它改成这条事件的序号。**它管不到同一个 `command_id` 的重放**：写线程见到已有的 `command_id` 直接回上次的回执、不跑投影（1.1）；重放另由下面「重试与重放」两条管。(b) 用户确认过的内容带**指纹**：`ListLocalConfig` 的每一项带 `fingerprint`，`ImportLocalConfig` 把它带回来；受理时对来源只 `discover()` 一次，用这一次读到的内容算指纹、也用这一次读到的内容去存；对不上就拒 | (a) 两条不同的命令穿插时，后提交的那条不会把先提交的结果盖掉。(b) 用户看着 A 点的确认，存进去、拿到密钥、在沙箱外起来的不会是 B |
| 四 | **受理函数到提交为止；提交之后的事由常驻的会话线表按已提交的状态对账**。受理函数只做三样：校验、暂存对象、加一笔提交。停会话、删旧对象都不在受理函数里。受理函数只许清理**自己这一次暂存、并且确认没被提交引用**的对象，别的名字一概不删 | 受理函数被中止、重放、失败，都不会留下「要停的没人停」，也不会删掉投影还指着的东西 |

**每个运行时一把锁**（`iwork-app::import_gate`，异步互斥）：导入、移除、填值的整条命令在锁里做，从查重到提交返回。它让三种命令排队、不白算；不同命令之间的先后靠约定三 (a) 保证，锁没了写线程照样挡得住。同一个 `command_id` 的并发靠它排队（下面）。

**先后怎么排**：

| 两件事 | 先后怎么定 | 结果 |
| --- | --- | --- |
| 导入、移除、填值之间（不同的 `command_id`） | 锁里排队；写线程按 `base_revision` 核对 | 后提交的那条看到的一定是前一条之后的状态；看到旧状态的被拒，什么都没变（它暂存的对象没人引用，自己清掉） |
| 同一个 `command_id` 的两次请求 | 查 `commands` 表这一步在锁里做，所以第二次一定看得到第一次的提交，直接回上次的结果、什么都不写。万一两次都过了查重（锁被绕开了），写线程给后一次回 `replayed: true`：它只清自己这次暂存的 | 投影指着的版本不会被删 |
| 开会话 与 填值、导入（不带撤回的） | 开会话不拿导入锁，读的是已提交的投影 | 读到的引用要么全是改动之前的、要么全是之后的。旧一版的值要等没有「在开」的会话还绑着更早的状态才删（「撤回」第 5 步），所以读到之前的照样取得到 |
| 开会话 与 撤回 | 会话线表的启动边界（下面） | 撤回的回执发出之后，带着旧配置的会话过不了启动边界，不起进程；在那之前已经过了边界的，起来之后被对账停掉 |

**指纹怎么算**（`iwork-core::local_import::fingerprint`，纯函数，SHA-256 的十六进制）：MCP 条目 = 名字 + `McpLaunchConfig` 的编码（含参数、地址、键名）；技能、插件条目 = 名字 + 内容摘要 + `notes`。它只出现在 `ListLocalConfigResult` 和 `ImportLocalConfig` 里，不进事件、不进数据库；帧日志的遮盖表里和 `launch_preview` 一起遮掉（参数里要是有弱口令，摘要能被离线猜出来）。门槛关着的条目没有指纹。

#### 命令

受理函数的共同开头（★ 的三条）：① 拿导入锁；② 在锁里查 `commands` 表（T10a 交付的受理入口），命中 → 回上次的结果，结束；③ 读投影，记下导入修订号 R。共同的结尾：提交的结果分四种，各自只做表里写的那一件事，然后回执：

| 提交的结果 | 受理函数做什么 |
| --- | --- |
| 成功，`replayed: false` | 什么都不做（暂存的对象现在被引用了） |
| 成功，`replayed: true` | 这次暂存的对象没被引用（生效的是上一次那一笔）：删掉这次暂存的钥匙串条目和新建的目录。**不删别的任何名字** |
| 被拒（`CONFLICT` 等，明确没写） | 同上：删掉这次暂存的 |
| 去向不明（`Io` 等） | 什么都不删：这次暂存的可能已经被引用。留下的要是没人引用，就是 L6 说的垃圾 |

| 命令 / 查询 | 受理时做什么（按先后） | 失败 |
| --- | --- | --- |
| `ListLocalConfig{runtime_id}` | `discover(scope, admit)`；和投影里已导入的行合并：算 `imported`、`sync`、`missing_keys`、`fingerprint`；已导入而来源里找不到的也列出来（`SOURCE_MISSING`）；从会话线表取「还有几条会话在等着停、哪几条停不掉」。MCP 的 `launch_preview` 来自这一次 `discover`（门槛关着就没有）。**不写任何东西** | 来源读不了 → `UNAVAILABLE`，点名文件 |
| `ImportLocalConfig{runtime_id, selections}` ★ | ④ `discover(scope, admit)` **一次**；⑤ 每个勾选项：条目在、现算的指纹等于带来的指纹；⑥ `plan_import(当前状态, 发现结果, 勾选)`（门槛关着的种类在这里被拒）；⑦ 暂存：有技能或插件 → `build_snapshot`，每项交回的摘要要等于 ④ 里的；每台 MCP 用 ④ 里那一份启动配置，新生成 `mcp_server_id`，写钥匙串的 `launch`；⑧ 这次要换掉旧 MCP 的话先在会话线表上挂一个 `hold`（下面）；⑨ 一次提交：`LocalConfigImported{base_revision: R, …}`（带快照名，每项的 `mcp_server_id`、键名、来源摘要、在快照里的位置），还没提示过的话同一次提交里加 `LocalImportPrompted`，被换掉的旧 MCP 名下记住的规则一起处理（等 PD-7）；⑩ `hold.done(…)` | ⑤ 对不上、⑥ 有一项导不了、⑦ 摘要对不上 → `LOCAL_IMPORT_REJECTED`，`details` 里每个被拒条目一条原因（指纹对不上的原因是「来源在你确认之后变了，请刷新」），⑦ 已经暂存的删掉 |
| `RemoveImportedConfig{runtime_id, item_ids}` ★ | ④ 暂存：有技能或插件 → `build_snapshot`（只留剩下的，都从上一代复制；一个都不剩就没有新快照）；⑤ 在会话线表上挂 `hold`；⑥ 一次提交：`ImportedConfigRemoved{base_revision: R, …}`；⑦ `hold.done(…)`。到此为止：停会话、删旧一代、删钥匙串条目都由对账做 | 条目不是已导入的 → `NOT_FOUND` |
| `SetMcpSecret{mcp_server_id, key_name, value}` ★ | ④ 这台 MCP 在、`key_name` 在它登记的键名里；⑤ 暂存：生成新的版本号；把 `value` 从命令里**挪**出来（`mem::take` 再 `into_bytes`，不复制）包成 `SecretValue`，`SecretStore::set` 到**新的名字**（带这个版本）；⑥ 提交 `McpSecretSet{…, version, base_revision: R}`。上一版的那一条由对账删，受理函数不删 | ④ → `NOT_FOUND` / `INVALID_ARGUMENT`；⑤ → `SECRET_STORE_FAILURE`，不提交。任何失败之后，投影指着的还是上一版，新开的会话用的也是上一版 |
| `DismissLocalImportPrompt{runtime_id}` | 提交 `LocalImportPrompted`（已经提示过就什么都不做，照常成功） | — |

- **整条拒绝，不做「能导的先导」**：一条命令要么全成、要么什么都没变，界面只要把被拒的那几项标出来让用户去掉勾，或者刷新后重新确认。
- **重试与重放**：
  - 同一个 `command_id` 再来，上一次已经提交：锁里的查重命中，回上一次的结果，不写文件、不写钥匙串。上一次提交之后要做的事（停会话、删对象）不靠这次重发：对账早就在做了。
  - 同一个 `command_id` 的两次请求都过了查重（正常不会发生，锁保证不了的时候才会）：后一次的提交拿到 `replayed: true`，照上表只清自己暂存的。
  - 上一次崩在提交之前：`commands` 表里没有它，重试等于从头做一遍，生成新的快照名、新的 `mcp_server_id`、新的版本号；上一次留下的对象没人引用（快照由启动清扫删；钥匙串条目留着，L6）。
  - 受理函数在提交入队之后被中止（客户端断开）：那笔提交照样落盘，对账照样做；客户端重连后用同一个 `command_id` 重发，拿到上次的回执。
  - `CONFLICT` 可以重试（`retryable = true`）：客户端重新 `ListLocalConfig`，用户看到的是新状态。
  - 重放事件（重建投影）只动数据库，不碰文件和钥匙串。`base_revision` 的核对在重放时照样做，事件是按原来的先后来的，一定对得上。

#### 撤回：由已提交的状态驱动，会话线表负责到底

前两版在这里各被报了一轮，是同一类问题换了入口：

| 轮次 | 入口 | 当时让谁担着责任 |
| --- | --- | --- |
| 第 1 轮 1/F-5 | 移除只改配置，已经起来的进程没人停 | 「下一回合换会话线」 |
| 第 2 轮 2/F-4 | 受理函数在提交之后被中止，或 `terminate()` 失败 | 受理函数这个 future 活着；那个对话下次开会话 |
| 第 2 轮 2/F-3 | 取完密钥、还没起进程的在途开会话 | 「登记的时候再查」 |
| 第 2 轮 2/F-2 | 绑着更早一代快照的会话 | 一张「这次换下了谁」的名单 |

这一版换机制，和 T07 的审批引擎（方案 6.10）、T10e 的卡片宿主（方案 2.3、ADR-T10e-c）同一个做法：**要停哪些会话只由已提交的状态决定，由一个常驻的东西对账，受理函数不负责**。常驻的东西不新起：会话线表（T10a）本来就常驻、本来就管着每条会话的生死，给它加一段对账。唤醒用现成的提交观察者（T07、T10e 用的同一个）。

**1. 撤回水位（已提交的状态里的一个数）**

- `runtimes.import_revoke_seq`：最近一次「让东西退场」的事件的序号。投影里两种事件会抬高它：`ImportedConfigRemoved`；`LocalConfigImported` 里有条目顶掉了一台已导入的 MCP（重新导入）。新导入、重填值不抬。
- 每条会话线记着 `bound_revision`：拼它的 `SessionSpec` 时读到的导入修订号。
- **规则只有一句：`bound_revision` 小于撤回水位的会话都要停**。也就是这个运行时在最近一次撤回之前拼出来的会话，全停。
- 这是保守的：撤回之前开的会话，即使没用到被撤的那一项（比如它开在那一项导入之前），也一起停。换来的是不用记「哪一代里有谁」：绑着 g1、g2、还是别的哪一代，只要是撤回之前拼的就停，不会漏掉更早的一代（2/F-2）。M1 导入的东西对所有助手、所有项目生效，被多停的只有「开在那一项导入之前、一直活到现在」的会话；它们下一回合重开，回合里没做完的一步要用户再发一次（L12）。

**2. 启动边界（开会话和撤回共用的同步点）**

会话线表里每个运行时有两个内存里的数：`floor`（表已经知道的撤回水位）和 `holds`（正在提交撤回的命令数）。每条会话线一项，阶段是：`Opening`（拿到了 `SessionSpec`，在取密钥）→ `Crossed`（过了启动边界，正在起桥接与 CLI）→ `Live`。

```rust
// 会话线表（交付方 T10a；名字以 T10a 为准）
/// 登记「在开」。表的锁里：bound_revision < floor → 拒（调用方重拼 SessionSpec）；否则建一项 Opening。
fn begin_opening(&self, conv: ConversationId, runtime: RuntimeId, bound_revision: u64) -> Result<Opening, Stale>;
/// 启动边界，全仓只有这一处。等这个运行时的 holds 归零；然后在表的锁里：
/// bound_revision < floor，或这一项被对账标了「不许起」→ 拒；否则阶段置成 Crossed。
async fn cross(&self, o: &Opening) -> Result<(), Halt>;
/// 撤回要提交了：holds += 1。从现在起这个运行时没有会话能过启动边界。
fn hold(&self, runtime: RuntimeId) -> Hold;
impl Hold {
    /// 提交有了明确结果：revoked_at 是这笔提交的序号（没提交成给 None）。表的锁里 floor = max(floor, 序号)，holds -= 1。
    fn done(self, revoked_at: Option<Seq>);
    // 没调 done 就被丢掉（受理函数被中止）：这一个 hold 转交给对账，由它读了已提交的撤回水位之后再放（下面第 3 步）。
}
fn wake(&self);            // 提交观察者里调：置位、唤醒，别的不做
async fn run(&self);       // 常驻循环：被唤醒或退避到时 → reconcile()
async fn reconcile(&self); // 对账（下表）。幂等，可以随时调、并发调
```

适配器在**取完钥匙串里的值之后、起桥接进程之前**调一次 `cross`（经端口 `SpawnGate`，3.5）。被拒 → 取到的值丢掉，不起任何进程，开会话失败（可重试，重拼 `SessionSpec` 就是新状态）。

对每个在途的开会话只有两种先后，都在表的那一把锁里定：

- **撤回先到**（`hold` 先挂上）：`cross` 等着；`hold` 放开时 `floor` 已经是新的，`cross` 被拒，进程不起。撤回命令的回执在 `hold.done` 之后才发，所以**回执发出之后，带着旧配置的会话不会再起进程**。
- **`cross` 先过**：这一项已经是 `Crossed`，它是在撤回提交之前起的；对账等它变成 `Live`（或起失败）就停掉。

受理函数在 `hold` 和 `done` 之间被中止时，`hold` 不会自己放开：它转交给对账。对账先读已提交的撤回水位、把 `floor` 抬到位，再放它。所以 `holds` 归零的那一刻 `floor` 一定跟得上已经落盘的撤回，`cross` 不会带着旧水位放人。（中止时那笔提交要是还在队列里、过后才落盘：对账读的时候它还没生效，放开之后过了边界的会话算「`cross` 先过」，那笔提交一落盘、观察者一唤醒，对账就把它们停掉。这时命令没有给任何人发过回执。）

**3. 对账**（每个运行时；读投影里的 `import_revoke_seq`，记作 V）

| 步 | 做什么 |
| --- | --- |
| 1 | 表的锁里：`floor = max(floor, V)`；把转交过来的 `hold` 放掉（`holds` 减去它们的个数） |
| 2 | 逐项看 `bound_revision < floor` 的会话线：`Opening` → 标「不许起」（它走到 `cross` 会被拒）；`Crossed` → 标「起来就停」；`Live` 且有回合在跑 → 走现成的取消（提交 → `stop_accepting()` → `cancel()`，T06 方案 2.6 第 4 条），回合以用户取消收尾，然后 `retire()`；`Live` 且空闲 → `retire()`。`retire()` 就是 `session.terminate()` 确认整棵进程树清空再放掉会话（T06 方案 2.6；3.1b 停别的会话用的同一个接缝），MCP 服务是 CLI 的子进程，跟着这棵树一起结束 |
| 3 | `terminate()` 失败的：这一项留在表里，记成「停不掉」和原因，写一条审计（对话 id、原因）；之后每一轮对账再试，退避从 1 秒起、每次翻倍、封顶 60 秒，**没有次数上限**，后台活着就一直有人试。不等那个对话再开会话 |
| 4 | 旧一代快照：`imports/<kind>/` 下不是当前这一代、也没有任何一项（三个阶段都算）绑着的 `g-*` 目录，删掉。运行时记着「快照损坏」时不删 |
| 5 | 钥匙串：对账记着上一轮「已提交的状态引用了哪些名字」（各台 MCP 的 `launch`、每个键的当前版本），这一轮不再被引用的名字，删掉；删不掉记审计、下一轮再试。有 `Opening` 阶段的项绑着比「它不再被引用」更早的状态时先不删，等那一项过了边界或被拒。启动时「上一轮」取当前状态，所以启动不删任何东西 |

- 对账只读已提交的状态和表里的事实，不看是哪条命令触发的、那条命令还在不在。受理函数在任何一点被中止，结果只有两种：那笔提交落了盘（对账接着做完），或者没落盘（什么都没发生，转交的 `hold` 被放掉）。
- **进度看得见**：`ListLocalConfigResult` 带 `revoke_pending`（还有几条要停的会话没停完）和 `revoke_stuck`（停不掉的：对话 id 与原因）。设置页据此显示「还有 N 条会话在停」「有 N 条会话的进程没能停下」。
- **停不掉时用户能做的**：等（对账一直在试）；或者「完全退出 iWork」再打开：后台退出时桥接读到输入结束，会结束各自的 CLI 进程树（技术设计第 4 节），重启后没有任何旧会话。提示文案写在 `revoke_stuck` 的显示里（问设计窗口）。
- **管不到的**：MCP 程序自己另起的、脱离了进程组的后代（T06 实测 G7e：命令会脱离 CLI 的进程组），`terminate()` 杀不到；它们已经拿到手的密钥收不回来，只能轮换（L11）。
- T06 方案 3.1b「隔离失效时停同一个运行时的别的会话」是同一种义务（等于把水位抬到最高）。它走不走这段对账由 T06 / T10a 定，本卡不改它（第 11 节）。

**`sync` 怎么算**：技能、插件拿 `discover` 现算的摘要和投影里的 `source_digest` 比。MCP 把 `discover` 现读的启动配置和钥匙串里那份在内存里比，钥匙串读不到就是 `UNSPECIFIED`；数据库里不存启动配置的摘要。门槛关着的那一类没读来源，也是 `UNSPECIFIED`。

### 3.6 开会话：导入的东西怎么到 CLI 手里

1. **后台拼 `SessionSpec`**（T10a 的接线里加几行，读已提交的投影）：`plugin_dirs` = 当前这一代快照的各个插件子目录（这个运行时记着「快照损坏」时为空）；`mcp` = `Ready` 的那些 MCP 的 `McpServerRef`，带着每个键的当前版本；同时记下这一次读到的导入修订号。约束里的只读区 `imports/` T10a 本来就要填。
2. **登记「在开」**：`begin_opening(对话, 运行时, 那个修订号)`。被拒（撤回刚发生过）→ 回第 1 步重拼。
3. **适配器**（`iwork-agent-acp`）：去掉 `client.rs:174` 的报错。新模块 `mcp.rs`：对每个 `McpServerRef`，从 `SecretStore` 取 `launch` 和每个键那一版的值，拼成 ACP 的 `McpServer`（stdio：名字、命令、参数、环境变量；http / sse：名字、地址、请求头），放进 `session/new`、`session/load` 的标准字段 `mcpServers`。
   - `SecretStore` 在适配器构造时注入（泛型参数，后台组装）。
   - 每次取值限时 10 秒（钥匙串可能在等用户点系统弹框）。取不到、超时、钥匙串里那份解不出来 → 开会话失败，`AgentError::Protocol{"MCP「<名字>」的配置或密钥取不到（<键名或 launch>）"}`，不带值。不悄悄少挂一台：审批看到的清单和 CLI 实际加载的要是同一份。
   - **值都取到之后、起桥接进程之前，过启动边界**：`gate.cross()`。被拒 → 取到的值丢掉，不起进程，回 `SpawnRefused`。
   - 这段代码里不打日志、不 `{:?}` 请求；值只存在于这次调用的局部变量和发给桥接的那条消息里。
4. **桥接**（`iwork-bridge-claude`）：`Setup` 多一项 `mcp_servers`（值包在一个 `Debug` 只打印 `<redacted>` 的类型里）；`settings::mcp_json(&servers)` 生成 `{"mcpServers": {名字: {...}}}`，每台服务的值写在它自己的 `env` / `headers` 下；文件 0600，在会话目录里（T06 方案 3.3）。**值不进 CLI 的环境变量**：进了环境，CLI 起的每条命令、每个 hook、每台别的 MCP 服务都看得到。
   - 这个文件带着密钥明文，寿命和怎么收窄等 PD-4。T06 方案 3.3「残留的只是不含密钥的设置文件」那一句要跟着改（第 8 节）。
5. **会话内容核对多看一项**（`cli/facts.rs::check_content`，T06 方案 3.5 留的口）：`init.mcp_servers` 里每一项的名字都得在这次给的名字里，多出来 → `isolation_broken`（种类「MCP」，带名字），之后照 T06 方案 3.1b 停用运行时。给了而没连上的（状态不是 connected，或出现在 `mcp_server_errors` 里）不算隔离失效，记一条诊断（只有名字和状态），会话照开（L7）。
6. **本机验证与隔离重验带着当前的导入一起跑**（T06 方案 10.1、3.1b 第 6 条；它们用同一个 `build_launch`）：导入的插件目录让核对过不了时，在验证那一步就报出来，移除导入之后再验就能恢复。交付方 T06 S8 / T10a（第 11 节）。

### 3.7 首次提示

- 「提示过没有」只由 `LocalImportPrompted` 事件决定。它在两处产生：`ImportLocalConfig` 成功（同一次提交）、`DismissLocalImportPrompt`。
- 客户端连上之后看 `GetRuntimeStatusResult.import_unprompted`；里面有这个运行时、它又是就绪状态 → 调一次 `ListLocalConfig`；`prompt_due` 为真 → 弹首次导入框。`prompt_due` 是后台算的：没提示过，并且至少有一项导得了。两个门槛都关着时没有导得了的，不弹。
- 本机什么都没有时不弹，也不记「已提示」；以后有了东西，下次打开客户端会弹一次（等 PD-8）。
- 提示过之后，iWork 只在用户打开「从本机导入」时才去读用户的 Claude 配置。
- 设置 › 运行时 的「从本机导入」走同一个 `ListLocalConfig`，不看 `prompt_due`，不弹窗、不显示红点。

### 3.8 客户端

- 页面壳子 T09 的步 7d 已经对着假后台做了（`client/src/pages/ImportLocal`）。本卡接真数据，补这几样：每台 MCP 的每个键一个输入框；导不了的条目置灰加原因；`notes` 显示在条目下面；已导入条目的状态（缺密钥、来源有变化、来源不在了、快照损坏）；移除的入口；撤回的进度（还在停几条、哪几条停不掉）。这几样画布上没有，问设计窗口（第 11 节）。
- 「导入所选」发的是用户屏幕上这份列表里每个勾选项的 `item_id` 加 `fingerprint`。被拒且原因是「来源变了」→ client-core 重新 `ListLocalConfig`，界面回到列表让用户再看一遍、再点；用户填过的值清空（那些值是照着旧的那份填的）。
- 「导入所选」分两步发：先 `ImportLocalConfig`，从回来的 `LocalConfigImported` 事件里拿到每台 MCP 的 `mcp_server_id`，再逐个键发 `SetMcpSecret`，**一个发完、收到结果再发下一个**。输入框里的值只在这两步之间留在网页内存里，发完清空；不进 `ViewPatch`、不进 client-core 的 store、不进任何本地存储。`SetMcpSecret` 失败 → 这台 MCP 停在「缺密钥」，设置页能补填。因为 `mcp_server_id` 对应的启动配置写了就不改，值不会落到别的配置上。
- 移除的确认框写明「这个运行时现在开着的会话都会被停下」（文案问设计窗口）。
- 网页不做判断：能不能勾、弹不弹、显示什么状态文字，都是 client-core 照后台给的字段算好的。

## 5 出事场景

每条写三件事：会出什么事 / 怎么止血和回退 / 由什么保证。

**C1 导入时把用户的密钥读进了数据库**
- 出什么事：解析的代码被改坏，`env` 的值被当成普通字段留了下来；或者 PD-1 选了 b，`args` 里的连接串（`postgresql://用户:口令@…`）、`url` 里的密钥随 `LocalConfigImported` 进了事件。事件只追加不修改，进去了就洗不掉。
- 止血：第一步轮换那份密钥。然后移除这台 MCP（`RemoveImportedConfig`），开着的会话被停下，之后的会话不再带它。事件里那一条留在库里；M1 只有产品负责人自己用、库不外传，修好后发新版，库里那条记进已知问题。要彻底清掉只能删库重来。
- 保证：R1、R2 的测试。`imported_values_only_in_secret_store` 是合入门槛，搜的是库文件的原始字节。

**C2 用户填的密钥进了日志或事件**
- 出什么事：有人在受理函数里加了一行 `debug!(?cmd)`，prost 生成的类型 `Debug` 会把 `value` 打出来；或者开发构建开着帧日志。
- 止血：轮换密钥；删日志文件（`<数据目录>/logs/`，删了不影响运行）。修掉那一行发新版。
- 保证：R3；`frame_display_redacts_listed_fields`；日志的字段名黑名单（已有，`logging.rs:42`）只是第二层，不当主要手段。

**C3 导入的技能带进了 hook、给自己放行了工具，或者一加载就执行命令**
- 出什么事：① 来源插件带 `hooks/hooks.json`，原样复制的话每条成员会话都会在沙箱外、不经审批地跑它。② 技能的 frontmatter 里写了 `hooks`，技能一被调用就注册。③ 写了 `allowed-tools: Bash`：平时 iWork 的 hook 照样判，放宽不了；但 CLI 自己跳过 hook 的那一刻（AGENTS.md 安全不变量第 2 条的已知限制），这个技能激活期间的 Bash 可能照 CLI 的规则直接执行，已知限制的范围就从「工作目录内的读」变大了。④ 正文里有 `` !`命令` ``，技能加载时执行；去掉 `allowed-tools` 之后，只读命令多半照样执行（3.2）。
- 止血：移除那个技能或插件：开着的会话被停下（撤回），之后的会话里没有它。①② 已经跑过的 hook、④ 已经读进上下文的内容，iWork 收不回来，只能人去查。
- 保证：①：R4。②③：R5 加实测 K2。④：实测 K3 加 PD-5；这一条没定、格子没过，`SKILL_IMPORT_ENABLED` 不开，技能进不来。
- 这四样对**仓库里自带的技能**同样成立（需求 8.4 写的是照常加载）。那是改动前就有的问题，审查记为 `2026-11-12-m1-t10f-plan/1/F-8`，supervisor 已经交给 T06 与产品负责人；本方案只引用它，不解决。

**C4 技能目录里的凭据被 iWork 读了，或者被复制进了只读区**
- 出什么事：① 产品负责人还没接受 PD-9（或 PD-1），用户只是打开了导入列表，iWork 就把技能文件读了一遍算摘要、把 MCP 的参数读出来发给了客户端显示。门槛只挡住了「导入」，没挡住「读」。② 门槛开了之后：技能目录里有一个指向 `~/.ssh/id_ed25519` 的链接；作者把服务的私钥、`.env`、`credentials.json` 放在技能目录里；或者 token 写在一个普通名字的 `settings.json` 里。复制过去之后，所有项目、所有助手的 Agent 不经询问就读得到；`~/.claude/` 原本在敏感目录里，Agent 读它是要问的。
- 止血：①：真发生了，那些内容经过了后台与客户端的内存，没有落盘；修掉之后发新版，要不要轮换看读到了什么。②：移除那个技能（开着的会话被停下，新一代快照里没有它；旧的几代在没有会话绑着之后被对账删掉）；等不及就手动删 `imports/<kind>/g-…` 里那个文件。轮换那份密钥。
- 保证：①：R21，断言的是文件接缝的调用记录和发给客户端的字节。②：链接、私钥、范围内的凭据文件：R6，端到端那一条是放开门槛的条件，按名字拒的不打开由 `name_refused_files_are_never_opened` 保证。范围外的认不出：这是 PD-9 要产品负责人接受的例外，接受之前技能目录里的文件不读（R21）、导不了（R15）。

**C5 导入之后被改**
- 出什么事：① Agent 想改导入的技能，让以后每条会话都带上它写的指令。② iWork 自己重导时就地改文件，在跑的会话读到半新半旧的技能。③ 复制到一半后台崩了，半份技能被下一条会话加载。
- 止血：① 被拒，不用止血。②③ 要是真发生：移除再导入一次，生成新的一代。
- 保证：①：R8。②③：R7。
- 挡不住的：不在沙箱里的同用户程序（导入的 MCP 服务、用户批准的沙箱外命令）改导入区、改数据库（L5）。不为它加防篡改的校验：校验用的摘要也只能放在同一个数据目录里，改得了文件的程序同样改得了它。（启动时核实 `MANIFEST` 管的是掉电之后缺文件，不管这个。）

**C6 导入的 MCP 或技能越权，要立刻撤回**
- 出什么事：① MCP 服务进程不在沙箱里，以用户身份跑，每条会话一启动就起来，不经审批（需求第 9 章已知限制）。用户发现某台 MCP 不对劲，点了移除，可是已经起来的那几条会话里它还在跑。② 移除的时候正好有一条会话在开：密钥已经取到，进程还没起；移除显示成功之后它才把那台 MCP 起起来。③ 用户先加过别的技能、后移除技能 A：有的会话绑着两代之前的快照，里面有 A，撤回只看「刚换下的那一代」就漏了它。④ 用户点了移除就关了窗口，受理函数被中止；或者某条会话的进程一时停不掉：没人接着停。⑤ 工具的「只读」是服务自己说的。⑥ 用户把名叫 `github` 的 MCP 换成了另一个程序，以前记住的「`mcp__github__create_issue` 不再问」接着对新程序生效。⑦ `~/.claude.json` 里某台 MCP 的命令被别的程序改了：用户在预览里看到的是原来那份，点导入的时候已经被换掉；或者用户点了重新导入，新命令拿到旧密钥。
- 止血：移除那一项。移除的回执一发出，带着旧配置的会话就过不了启动边界；这个运行时在那之前拼的会话，由会话线表一条条停掉，在跑回合的、空闲的、正在起的都算，CLI 连同 MCP 进程一起结束；之后旧一代快照和它在钥匙串里的条目被删。进度在导入页上看：还在停几条、哪几条停不掉。停不掉的会一直重试；等不及就「完全退出 iWork」再打开，后台退出时所有 CLI 进程树都会结束。然后轮换交给过它的密钥；到设置里撤销它名下记住的规则（PD-7 选 a 的话已经一起删了）。
- 保证：
  - ①②③：R16。演练 `revoke_drill_all_phases`（假运行时，经真的受理路径与会话线表。五条会话：甲的回合正在等审批；乙空闲、会话活着，绑的是更早一代的快照；丙取完了钥匙串的值、还没过启动边界；丁已经过了边界、进程还没起来；戊在移除之后才拼 `SessionSpec`。移除之后：甲的回合以取消收尾、会话 `terminate()` 过；乙 `terminate()` 过；丙的 `cross` 被拒，假适配器的「起进程」对它一次都没调；丁起来之后的第一轮对账被 `terminate()`；戊照常开起来，`SessionSpec` 里没有被移除的那一项。全停完之后：旧的几代快照目录都没了，那台 MCP 在假钥匙串里的条目都没了，`revoke_pending` 是 0）。
  - ④：R22 的两条（受理函数在三个点被中止；空闲会话 `terminate()` 一直失败）。

**C7 用户改了自己的 Claude 配置，iWork 这边没跟上**

- 保证：`sync_reports_changed_and_missing_sources`（技能改一个字节、MCP 改一个参数、来源整个删掉各一例）；`sync_unspecified_when_secret_store_unreadable`；`rebuild_preserves_sync_state`（R20）。导入是复制一份快照，不自动跟随，这是定下来的做法（技术设计 9.5 第 4 条写的是「复制进」）。

**C8 导入的东西让所有会话都开不了**
- 出什么事：① CLI 报的插件 `path` 和 iWork 给的目录对不上（比如 CLI 把路径解析成了别的写法），每条会话第一轮都被判成隔离失效，运行时停用（T06 方案 3.1b）。② 某台 MCP 的程序起不来或很慢，每条会话的第一轮都要多等，最多 30 秒。③ 钥匙串取不到某个值，带这台 MCP 的会话全部开失败。④ 一个 `hold` 没被放开，所有会话都卡在启动边界上。
- 止血：①②③ 都是同一步：移除惹事的那一项（①③ 的错误文字里有名字；② 看诊断里哪台没连上）。① 之后在运行时详情页点「重新验证」，隔离重验带着当前的导入跑，过了就恢复。全部移除等于回到没有导入的状态，那是 T06 验过的配置。④：重启后台（`holds` 只在内存里）。
- 保证：R16 的 `remove_works_while_runtime_isolation_disabled`；演练 `bad_import_drill`（T06 方案 15.1 的假 CLI，经真实的后台、适配器、桥接：导入一个技能，假 CLI 把这个插件的 `path` 报成别处 → 隔离失效、运行时停用 → `RemoveImportedConfig` 成功 → 重新验证通过 → 会话开得了）。① 的预防：实测 N1 没过之前步 6 不合入。④：`revoke_completes_when_handler_aborted` 断言三种中止之后 `holds` 都回到 0。

**C9 钥匙串出问题**
- 出什么事：① 这台机器没有可用的钥匙串（Linux 上没有 Secret Service）。② 后台是没有界面的进程，钥匙串弹了「允许访问」的系统框没人点。③ 升级 iWork 之后签名变了，钥匙串不认新程序，每次读都弹框。④ 用户在「钥匙串访问」里手动删了条目。⑤ 填值填到一半，钥匙串写成了、提交没成；或者同一条填值命令被重发了一次。
- 止血：①：`SetMcpSecret` 报 `SECRET_STORE_FAILURE`，带系统给的原因；不用密钥的 MCP 在 PD-1 选 a 时同样导不了（启动配置也在钥匙串里），技能不受影响。②③：取值限时 10 秒，超时开会话失败并点名；用户点了「始终允许」之后重试。④：开会话失败并点名；到设置里重填那个键，或移除重导。⑤：什么都不用做，生效的还是已经提交的那一版；没提交成的界面报了错，用户再填一次。
- 保证：R13、R18；`secret_store_contract`（同一组用例对假实现和真钥匙串各跑一遍：存、取、删、取不存在的、删不存在的）；实测 H1–H3。

**C10 带密钥的 `mcp.json` 留在了盘上**
- 出什么事：桥接被 `SIGKILL`（取消、等待上限、撤回、后台崩溃都会），会话目录没删，里面的 `mcp.json` 带着密钥明文。
- 止血：下一次桥接启动时的清扫会删（T06 方案 3.3）；等不及就手动删 `<数据目录>/run/h/` 下的目录（没有会话在跑时删了没有影响）。这个目录 Agent 读不到；读得到它的是不在沙箱里的同用户程序，它们本来也读得到用户自己 `~/.claude.json` 里的同一份密钥。
- 保证：已有的 `sweep_removes_only_dead_owners_dirs`（`session_dir_tests.rs`）；PD-4 定了之后的那一条。

**C11 加了新的事件种类，旧版本读不了库**
- 出什么事：发了带 `ImportedConfigRemoved` 的版本之后想退回上一版，旧程序见到不认识的事件，以退出码 12 停下（T04 方案 S8）。
- 止血：只能向前修（T07 的 PD6，产品负责人 2026-11-10 定）。
- 保证：T10a 验收 4（真引擎读到不认识的事件种类时后台以 12 退出、数据不动）。

**C12 两条命令撞在一起**
- 出什么事：① 两个客户端窗口让「导入 B」和「移除 A」同时在做。导入那一条是在 A 还在的时候算的：它建的新一代快照里有 A。它后提交的话，刚移除的 A 又回来了。② 客户端超时重发了同一条 `SetMcpSecret`（同一个 `command_id`），两次请求都在做：第一次提交了 v1；第二次写了 v2，写线程认出是重放、没让 v2 生效。受理函数要是照「提交成功就删上一版」去做，会把正在用的 v1 删掉，之后每条带这台 MCP 的会话都开失败。
- 止血：① 真发生了就再移除一次。② 真发生了：到设置里把那个键重填一次。
- 保证：①：R19，后提交的那条被写线程拒掉，它建的那一代自己删掉。②：R18。锁里查重让第二次直接拿到上次的回执；万一都过了查重，`replayed` 的那一次只删自己写的 v2；删旧版这件事只有对账做，它只删已提交的状态不再引用的名字。

**C13 导入时掉电**
- 出什么事：只做了改名、没有 `sync` 的话，掉电之后可能是「事件已经在库里、新一代的目录项在、文件内容是空的或缺的」；启动清扫再把上一代删掉，技能就整个没了，会话加载到半份技能。
- 止血：真发生了：列表里标着「快照损坏」，重新导入一次。旧的各代目录这时都还在盘上（没清扫），要找回某个文件可以人手去拿。
- 保证：R7 的掉电注入与 `startup_verifies_current_before_sweeping`。

## 7 性能（需求第 14 章）

- 不在热路径上：事件推送、帧合并、存储写入、hook 都没动。`import_revision`、`import_revoke_seq` 只在三种导入事件的投影里多一条带条件的 `UPDATE`，别的事件不多执行任何语句。
- 提交观察者里多一次 `wake()`：置一个位、唤醒一个任务，不读存储、不拿表的锁（T10e 的卡片宿主同一种写法）。对账本身在观察者之外跑；每次被唤醒读一行 `runtimes`，表里没有要停的会话时到此为止。**这在每笔提交之后都会发生**，步 5 验收时用 `cargo bench -p iwork-bench --bench turn_stream` 做前后对比（同一时段交替多轮取中位数）。
- 开会话多出来的：登记「在开」与过启动边界各一次锁内判断（没有撤回在办时不等待）；每台 MCP 一次钥匙串读加每个键一次。步 2 验收时在 macOS 上量单次读的耗时，记进完成记录；单次超过 50 毫秒就回来商量要不要一台服务合成一条。
- 带 MCP 的会话，CLI 要等服务器连上才跑第一轮，文档说最多 30 秒。这段时间不在 iWork 自己的进程里（第 14 章只统计 iWork 自身进程），但用户感觉得到；M6 量出来之后写进运行时详情的说明。
- 发现：读一个可能有几 MB 的 `~/.claude.json`（流式解析，别的键跳过），技能门槛开着时再把每个技能要带的文件读一遍算摘要（本机 41 个技能约 13 MB）。只在首次检查和用户打开导入入口时做。步 3 验收时在本机配置上量一次，记进完成记录；超过 500 毫秒回来商量（摘要不能挪到勾选之后：指纹要它）。
- 导入：复制文件，每个文件一次 `sync`。本机 41 个技能约几百个文件，macOS 上开着 fullfsync 时可能要几秒。一次性的操作，界面上是一个等待态；步 4 验收时量一次记下。
- 启动恢复：对当前这一代的每个文件 `stat` 一次，不读内容。

## 9 已知限制（请产品负责人知情；定稿后由 supervisor 请他登记进需求第 9 章）

这一节只放**不放宽安全不变量**的缺口。放宽不变量的两处不在这里，在 PD-1（参数与地址）和 PD-9（技能文件），要明确接受才读、才启用。

- **L1** 导入的 MCP 是完全受信任的程序：不在沙箱里，读得到 iWork 的数据目录和它继承到的环境变量（含 hook 通道的令牌）。和需求第 9 章「MCP 服务进程不在沙箱内」是同一条，导入框上要说清。
- **L2** 技能导入后和在 Claude Code 里不完全一样：`allowed-tools`、`hooks`、`model`、`effort` 被去掉；名字多了前缀（用户级技能变成 `imported:<名>`）；名字以 `.` 开头的、范围表里的文件不带；插件里的技能要是用到插件根目录下 `skills/` 之外的文件（脚本、`bin/`），导入后找不到。
- **L3**（第 1 版在这里写的「技能目录里的密钥文件只认私钥表」挪走了：它放宽了不变量，改成 PD-9。）
- **L4** 插件自带的 MCP 留在用户的插件目录里跑：插件更新或卸载会改变、弄坏它，iWork 这边看到的是「来源有变化」或连不上。
- **L5** 不在沙箱里的同用户程序（导入的 MCP、用户批准的沙箱外命令）改得了导入区和数据库，iWork 不校验。和会话目录里的设置文件是同一类（需求 v1.73）。
- **L6** 钥匙串里可能留下不再用的条目：命令崩在提交之前、提交去向不明时受理函数不敢删、对账删之前后台退出了。它们没被任何引用指着，iWork 不会再读；要清得用户自己到「钥匙串访问」里删。
- **L7** 导入的 MCP 没连上（程序不在、密钥不对、超时）时，M1 的界面没有提示，只有诊断日志；模型会说它没有那个工具。
- **L8** 要 OAuth 登录的远程 MCP，iWork 里登录不了；连不连得上看用户有没有在自己的 Claude Code 里登录过（M7）。
- **L9** 用户填的值里有 `${…}` 时会被 CLI 当成环境变量引用（M5 量过之后定写法）。
- **L10** MCP 门槛开了之后，导入框上显示的启动方式是从用户配置里现读的，里面要是写着密钥，会显示在屏幕上，也会经过本机的进程间通道（不落盘；开发构建的帧日志里遮掉）。它随 PD-1 一起定；门槛关着时不读、不显示。
- **L11** 撤回停得掉的是 CLI 的进程树（含 MCP 服务本身）。MCP 程序自己另起的、脱离了进程组的后代停不掉；已经交到 MCP 程序手里的密钥收不回来，只能轮换。
- **L12** 撤回是保守的：这个运行时在撤回之前开的会话全停，包括没用到被撤那一项的。被停的回合照用户取消收尾，没做完的那一步不会自动续上；用户再发一条消息，新会话里没有被移除的东西。
- **L13** 撤回的回执只保证「带着旧配置的不再起进程」。已经起来的会话是回执之后一条条停的，中间有一小段它们还在跑；进程停不掉时会一直重试，界面上看得到，最后的办法是完全退出 iWork。

## 12 需产品负责人决定

**PD-1 MCP 的启动配置（命令、参数、地址）：接不接受 iWork 读它、存它；存哪**
- 问题：参数和地址里可能写着密钥（数据库连接串 `postgresql://用户:口令@…`、地址里带 key 的远程 MCP），iWork 不读值就分不出来。要导入 MCP，这几样又非读不可。所以不管存哪，iWork 都读了、存了、在导入框上显示了可能带密钥的内容，这放宽了安全不变量第 1 条，要明确接受。**接受之前这三样 iWork 不读**：导入列表里 MCP 只有名字和键名，没有启动方式，也导不了。任务卡和技术设计 9.5 写的是存数据库：存了就进事件，事件只追加不修改，进去了洗不掉，验收 1「数据库里搜不到密钥明文」对这类 MCP 不成立。
- a（推荐）接受例外，范围是：参数和地址读进内存、整份存进系统钥匙串、导入框上显示一次；数据库、事件、日志里没有。代价：没有钥匙串的机器上，不带密钥的 MCP 也导不了；开会话每台 MCP 多读一次钥匙串。
- b 照卡片原文存数据库。代价：上面说的那类 MCP 的密钥进库、洗不掉；例外的范围大得多，导入框上要提示「参数和地址会原样保存」。
- c 加一段识别「看上去像密钥」的规则，命中的不让导。代价：一套靠猜的新规则，会漏也会误伤，不推荐。
- d 不接受：M1 不导入 MCP 的启动配置，用户在 iWork 里手填命令和参数。代价：FR20 的 MCP 部分变成手工录入。
- 卡住：`MCP_IMPORT_ENABLED`（步 5 放开 MCP 条目）、步 6 里取启动配置的那一段。

**PD-2 环境变量和请求头的值，要不要一律重填**

**PD-9 技能目录里的凭据文件：边界划在哪，范围外的接不接受**

- 要定三件事。
- **① 范围表对不对**（3.2）。现在的表：私钥整个拒；路径上有一级以 `.` 开头的、命中底线凭据清单里某条路径的、文件名去掉扩展名后是 `credentials` / `secrets` / `token` 这类词的、几种密钥库扩展名的，不带也不打开。
- **② 表现在漏的这几种，收不收进来**。它们现在都会被原样复制：

  | 例子 | 为什么现在没被挡 | 候选规则 |
  | --- | --- | --- |
  | `secrets/production.json`、`credentials/team.yaml` | 表只看文件名，不看目录名；`production.json`、`team.yaml` 是普通名字 | 候选甲：路径上任何一级**目录名**等于第 4 行那些词的，整个目录不带 |
  | `credentials.dev.json`、`secrets.prod.yaml`、`token.staging.txt` | 「去掉扩展名」只去最后一段，剩下 `credentials.dev`，不等于 `credentials` | 候选乙：文件名**第一个点之前**的部分等于第 4 行那些词的，不带 |
  | `aws-credentials.json`、`my_token.txt`、`db-password.txt` | 词在名字中间 | 不建议收：按「名字里含这个词」会把 `tokenizer.py`、`password-policy.md` 这类一起挡掉 |

  推荐：甲、乙都收进表（各加一行，测试 `admit_table` 跟着加例子）；第三种不收，归到 ③。
- **③ 范围外的那一类接不接受**：普通名字的文件里写着 token（`settings.json`、`deploy.yaml`、上面第三种）、脚本里写死了密钥，iWork 认不出，会原样进只读区。
  - a（推荐）接受例外，范围是：范围表之外的文件 iWork 会读（算摘要、复制），里面要是有密钥，iWork 不知道，Agent 读得到；导入框上每个技能写明带多少个文件、哪些没带，技能一组加一句说明。登记进需求第 9 章，写清这是不变量第 1 条的例外。接受之后可以先跑一次 D1 的 `--skill-notes`，看本机 41 个技能里哪些文件会被略过。
  - b 更严：只带一张扩展名白名单里的文件（`.md`、`.txt` 与常见脚本扩展名），别的都不带、不打开。代价：技能用到的数据文件、模板、图片带不过来，一部分技能会坏；脚本里写死的密钥仍然认不出，所以例外照样要接受，只是面小一些。
  - c 不接受：M1 不做技能导入，只导 MCP。代价：FR20 的技能部分、验收 1 里「导入的技能出现在 `init`」M1 不满足，要改任务卡。
- 卡住：`SKILL_IMPORT_ENABLED`（步 3、步 4 里读技能文件的那一支；步 5 放开技能与插件条目）。

## 13 ADR（developer 随组 B 写入 `docs/adr/`，编号合入时定）

### ADR-T10f-a 导入只搬名字和形状；值进钥匙串，技能按白名单重拼成不可变的快照

- **背景**：要把用户本机 Claude Code 的 MCP 与技能搬进 iWork，同时守住三条：不读用户已有的凭据；用户的 hook 与放行规则不进成员会话；导入的东西 Agent 改不了。用户的配置文件里密钥和普通配置混在一起，插件目录里技能和 hook 混在一起，CLI 自动加载的位置还会随版本增加。
- **决定**：① 发现只打开一张来源表里的文件、只取表里的键；`env`、`headers` 的值在解析时丢掉，由用户重填。② 从 MCP 配置读出来的值，除了名字和键名，只进系统钥匙串；数据库和事件里没有启动配置。③ 导入区里的插件目录由 iWork 自己拼：只放技能目录，清单自己写，`SKILL.md` 的 frontmatter 只留白名单里的键，看不懂的不导；凭据文件范围内的不带，按名字能判的不打开。④ 重新导入一台 MCP 等于换一台，密钥重填。⑤ 放宽「不读取、不保存凭据」的两处（参数与地址、范围外的技能文件）各有一个默认关着的门槛，产品负责人明确接受之后才开；**门槛挡在读之前**，关着时列表里只有名字。
- **备选与放弃原因**：把启动配置存数据库（任务卡原文）：参数里的密钥会进洗不掉的事件。读出值再判断是不是密钥：判断本身就读了凭据，而且靠猜。复制整个插件再删掉 hook：删的是认识的那几种，CLI 多一种自动加载的位置就漏。把认不出的凭据文件登记成已知限制就上线：那是放宽不变量，不是限制。门槛只挡导入、不挡发现：列表一打开内容就已经读了、发给客户端了。
- **影响**：多一个事件种类（只能向前修）；没有钥匙串的机器上 MCP 导不了；技能导入后和在 Claude Code 里不完全一样（第 9 节 L2）；以后接 Codex、agy 的导入，写一个 `LocalConfigSource` 的实现，沿用同一套命令、存储和钥匙串的名字规则。

### ADR-T10f-b 事务之外的对象与进程：写一次带版本、先持久后引用、提交时核对；提交之后的事由会话线表按已提交的状态对账

- **背景**：导入要写文件和钥匙串，撤回要停进程，它们都不在数据库事务里。只说「先写对象、后提交事件、崩了清扫」不够：原地覆盖的对象在提交之前就被会话读到了；两条命令穿插时，算在前面、提交在后面的那条会把别人的结果盖掉；用户确认的和实际存的是两次读；改名不等于持久。把提交之后的事（停会话、删旧对象）放在受理函数里也不够：受理函数会被 ipc 中止、会被重放；按「这次换下了谁」列名单会漏掉更早的一代；登记时才查，挡不住已经取完密钥的在途开会话。
- **决定**：3.4 的四条约定。① 会话读得到的对象（快照、启动配置、键的一版值）写一次、名字带版本。② 对象持久化之后才提交事件，事件是唯一的切换点。③ 改动导入状态的事件带 `base_revision`，由写线程核对；用户确认的内容带指纹，受理时对来源只读一次；同一个 `command_id` 的重放不经这条核对，靠锁里查重和「只清自己暂存的」。④ 受理函数到提交为止。撤回是已提交状态里的一个水位：拼在水位之前的会话都要停。常驻的会话线表被提交观察者唤醒，按水位对账：挡在启动边界上的不许起，起来了的停掉，停不掉的退避重试到停掉为止，然后删没人绑着的旧一代和不再被引用的钥匙串条目。撤回的命令在提交前后挂一个 `hold`，让回执发出时启动边界已经知道新水位。
- **备选与放弃原因**：只靠应用层的一把锁：锁管不到以后多出来的调用方，也证明不了；锁留着管排队和同一个 `command_id` 的并发。固定名字的钥匙串条目加「提交失败就写回旧值」：写回本身会失败，中间那一段会话读到的已经是新值。受理函数提交之后自己停会话、删旧版：它被中止就没人做，被重放就可能删掉还在用的。记「哪一代里有谁」来精确地只停受影响的会话：多一张表，换来的只是少停几条撤回之前开的会话，不值。另起一个「导入宿主」：会话线表本来就常驻、本来就管会话的生死，T07 的引擎和 T10e 的卡片宿主已经定了「观察者唤醒、按已提交的状态对账」的写法，照它做。
- **影响**：三种事件各多一个字段，`runtimes` 多三列；投影判状态多一处（知会 T02）；钥匙串里一个键可能短时间有两条；`open_session` 多一个启动边界参数（知会 T06）；T10a 的会话线表要提供启动边界、`hold` 与对账；撤回会多停一些没用到被撤项的会话（L12）；以后再有「事务之外要落东西、提交之后要做事」的命令，照这四条写。
