## 0 一页总览

T09 把 `iwork-client-core` 从一行空壳做成客户端的全部逻辑，网页层只把 `ViewPatch` 画出来。五条主线：

- **一个任务独占状态库。** 连接来的数据、网页来的操作、定时器进同一个队列，由一个 tokio 任务顺序处理，没有锁。唯一写入口 `Store::apply`，吃的就是 T03 `Incoming` 给出的全序。
- **状态分两类，各一条更新规则。** 对话时间线按事件逐条改（流式要即时）；侧栏与待处理是后台算好的摘要，客户端不推演，订阅命中任何持久事件就失效、合并后重查。没有第三种。
- **帧在网页来取的那一刻才算。** 事件只改状态、记「哪块脏了」；网页来取时才从当前状态把可见且脏的部分算成视图模型，切成不超过 256 KiB 的块一块一块交出去。网页不来取，就没有数据离开状态库。
- **假数据走真协议。** 另起一个假后台进程，经 `iwork-ipc` 的真 `Server` 说话，客户端永远用真 `Client`。网页层的测试与界面审查吃 client-core 对着假后台跑出来的 `ViewPatch` 录像。
- **会随数据变的字和开关都在 Rust 侧。** 计数、标签文字、按钮可否点击、表情状态在 `derive`（纯函数）里算好；网页只留固定按钮字样和纯展示状态。

对照已合入代码发现的协议缺口在第 3 节（都是只增字段；第 1 步加进 proto，填值归 T10，已获同意）。第 10 节是已定的决定与等设计窗口答复的界面问题。

**两问**（good-code）：再加一种事件 → `apply_event` 的穷举 `match` 一臂（时间线 / 直接写 / 只失效，三选一）；再加一种时间线行 → 2.2 行登记表一行 + `RowView` 一个变体 + `derive::row` 一臂 + 网页 `rows/` 一个组件 + 假后台场景一行；再加一种用户操作 → `UiIntent` 一个变体 + `intent.rs` 一臂；再加一个页面 → 路由表一行。改这里牵动谁：`view.proto` 牵动 `derive` 与网页全部组件；`Store::apply` 牵动重连验收；第 3 节的字段牵动 T10 的读模型、查询受理与 `iwork-app::convert`。

### 2.2 状态库

```rust
pub struct Store {
    cursor: u64,                    // 最近一次已应用的持久事件 seq、snapshot_seq 或 ViewResult.seq
    summary: Summary,               // 项目、对话摘要、助手摘要、待处理项：只由查询结果写
    summary_stale: bool,
    runtimes, quota, settings,      // 事件带完整值，直接写
    open: Option<Timeline>,         // 当前打开的对话，M1 同时只开一个
    views: BTreeMap<u32 /*subscription_id*/, ViewState>,   // Loading | Ready
    dirty: DirtySet,
}
impl Store { pub fn apply(&mut self, item: IncomingItem) -> Applied; }   // 唯一写入口
```

**摘要：失效后重查，不推演。** 未读数（对话、项目两级）、自动标题、最近 5 个对话的顺序、对话在不在跑、助手的最近动态、待处理列表里有没有某张继续卡片——这些都是后台按自己的规则算出来的，客户端再算一遍就是第二份规则。所以：

1. 持久事件的 `subscription_ids` 含侧栏或待处理的订阅 → `summary_stale = true`。不按事件类型挑（挑漏一种，对应的值就永远不更新）。`ConversationRead`、`ConversationRenamed`、审批决定都落在这条规则里。
2. `refresh.rs`：`summary_stale` 且没有重查在飞、距上次发出 ≥ 250ms → 按顺序写出 `ListProjects`、`ListConversations`、`ListAssistants`、`ListPendingItems` 四条 `ViewQuery`，记下四个 `request_id`。**发出时不清标记。** 结果从 `Incoming` 回来，各自整份替换对应的表。「全部对话」列表页开着时多带一条 `ListConversations{project_id, title_contains, limit: 已加载条数}`，同样算在这一轮里。
3. **标记只在「这一轮的结果全部应用完、而且这一轮在飞期间没有新事件命中」时才清。** 在飞期间来了事件，记 `again`；这一轮结束时 `again` 为真就不清标记，过了节流间隔再查一轮。所以最后一个事件之后一定有一轮完整读到它的重查。
4. 这一轮没走完就不算数：连接关闭、或其中任何一条查询失败 → 这一轮作废（`request_id` 表清空），标记本来就没清，重新 `Live` 或过了节流间隔后整轮重发。已经应用的那几张表留着（它们各自是某个时刻的真值），整轮重发后四张表都会再对齐一次。走了快照的重连由快照替换四张表并清标记。
5. 代价：高负载下每秒最多 4 轮。第 6 节量它；量出来太贵的替代是后台在事件上带更新后的计数（加字段，归 T10），到时候再定，T09 不先做。

**直接写**的只有三种，事件本身带完整值：`RuntimeUpdated`、`QuotaObserved`、`GlobalSettingsChanged`（只带变了的字段，逐字段覆盖）。

**时间线：按事件改，行有登记表。**

```rust
pub struct Timeline {
    conversation_id: String,
    rows: BTreeMap<RowKey, Row>,          // RowKey = (seq: u64, slot: u8)
    by_id: HashMap<String, RowKey>,       // 行身份 → 键，变化事件靠它找行
    text: HashMap<String, String>,        // 流式正文，长度就是下一个期望 offset
    has_older: bool, at_tail: bool, new_below: u32,
    edge_older: Option<u64>, edge_newer: Option<u64>,   // 这一端被裁过：留下来的最外一行的 seq（「查询结果怎么进时间线」第 4 条）
}
```

不变量：**时间线里的每一行，从进入时间线起，流上属于它的事件一条没漏。** 顺序只有一个真值：创建这一行的事件的 seq——实时取事件信封的 `seq`，查询结果取第 3 节补的 `*_seq` 字段。字段是 0 当协议错误处理：时间线显示「数据不完整，无法显示这个对话」，日志点名实体 id，不把它排到最前面。

| 行 | 身份 | 创建事件 | 查询结果里的排序字段 | slot |
| --- | --- | --- | --- | --- |
| 消息（用户、助手、系统） | `message.id` | `MessageAppended` | `Message.created_seq` | 1 |
| 工具活动 | `turn_id/tool_call_id` | `ToolCallStarted` | `ToolCall.created_seq` | 1 |
| 审批卡片（含切档放行后的折叠形态） | `approval.id` | `ApprovalRequested` | `Approval.created_seq` | 1 |
| 亲手执行卡片 | `card.id` | `UserActionProposed` | `UserActionCard.created_seq` | 1 |
| 回合结束行（改动摘要与印章，或失败、取消的原因） | `end:<turn_id>` | `TurnFinished` | `Turn.ended_seq` | 1 |
| 继续 / 放弃卡片 | `resume:<turn_id>` | 不由事件创建：出现在待处理表里才有这一行 | `ResumeCard.created_seq` | 1 |
| 模型切换说明（重建得出的） | `model:<turn_id>` | 相邻两个回合的模型不同时，贴在后一个回合前 | `Turn.created_seq` | 0 |
| 项目分隔线（重建得出的） | `divider:<message_id>` | 相邻两条消息的 `context_project_id` 不同时，贴在后一条前 | `Message.created_seq` | 0 |
| 当次说明（档位切换提示、刚切的模型、刚切的项目） | `note:<seq>` | `ApprovalModeChanged`、`ConversationModelChanged`、`DmProjectSwitched` | 没有：时间线重建时丢弃（D5） | 1 |

- 上一个锚点到这一个锚点之间已经有同类的当次说明时，不再贴重建得出的那一行，免得同一次切换显示两遍。
- AGENTS.md 草稿卡片没有对话归属，不进时间线，显示在添加项目流程与「待你处理」；进了新对话后要不要再显示见第 10 节 Q11。「已回到最新消息」是标题栏下的提示条，不是行。
- 带完整实体的事件按身份写入（重复写结果不变）；只带 id 的变化事件改已有行，**找不到目标就丢掉并记一次 debug 日志**（待处理范围订了整类回合流，别的对话的回合事件本来就会到）；`ConversationDeleted` 关掉时间线。
- `MessageDelta`：`offset == 已有长度` 追加；小于则丢掉重叠部分；大于（中间缺了一段）停止追加，发一次最新页查询拿检查点正文，每个对话每秒最多一次。`ToolOutputDelta` 同理。瞬时事件不动游标。

**查询结果怎么进时间线**（第 1 轮 F-5 的修法）：

1. 订阅快照里的最新页（打开对话、重连走了快照）：游标跨过了一段事件，不变量对这一页以外的行不再成立，所以**整个时间线重建，只留这一页**，更早翻出来的页与当次说明一起丢。往上翻会重新查到。这不违反「查询结果不删实体」（R3）：丢的是缓存，界面不会因此显示「已删除」。
2. 连接没断时收到的最新页（`ViewResult`）：流一直是连续的，旧行仍有效。`at_tail` 时按身份合并；`at_tail == false`（见第 4 条）时重建。
3. 翻页结果：带 `before_message_id` 的往前接，`has_older` 取结果里的；带 `after_message_id` 的往后接（只在 `at_tail == false` 时发），结果里 `has_newer` 为假说明接到了最新，`at_tail` 置真——这个结果在全序里有确定位置，之后的新消息事件都排在它后面，不变量成立。带 `around_seq` 的居中一段（跳到没加载的锚点，2.9）和已加载的行不保证接得上，所以**整个时间线重建成这一段**，`at_tail = !has_newer`。这一条说的是边界落在消息上时的翻页；某一端被上限裁过之后，那一端改用行级游标（第 4 条）。
4. **上限 5000 行，每次写入之后都成立**（组 2b 审查 5/F-3 后重写，supervisor 2026-11-12 定）。
   - **目的**：时间线占的内存有上界（第 6 节）；裁掉的部分翻得回来，不重、不漏。
   - **出事场景**：原来只写了「超限从远的一端丢」，翻页游标却只有消息 id。一个回合里有几千次工具调用时，5000 行里两端可以一条消息都没有；裁掉之后手里没有哪个消息 id 能把被裁的那一段接回来。居中加载（`around_seq`，按消息数取 50 条）一次回来的行数也可能超过上限，原来没说这时怎么办。
   - **上限什么时候查**：每一次往时间线里放东西之后都查，没有例外——最新页、居中的一段、往前往后翻的页、实时到的事件。超了就一组一组从两端丢，丢到不超为止；丢哪一端照下面「丢哪一端」的次序。一页自己就超上限时两头都会丢。
   - **丢哪一端：先保住锚，再看可见窗口**（T09 组 2b 第 6 轮 6/F-1、6/F-3 之后重写，2026-11-12；上一版「按 seq 距离比远近」作废）。
     - **出事场景**：上限 40，对话里两段行之间隔着一万个 seq（别的对话的事件占掉的）。用户往上翻，取回 200 行更旧的。上一版拿 seq 差当距离：新取回的这一页离窗口一万多，被整页当成远端丢掉，边界没动、`has_older` 还是真，会话循环照旧去查同一个游标，一直转。往后翻同理。
     - **锚**：每次裁剪有一组行不许丢，叫锚。哪一组看这次是什么操作：

       | 操作 | 锚 | 网页声明过的窗口 |
       | --- | --- | --- |
       | 往前翻的结果（消息游标或 `before_seq`） | 这一页里**紧挨游标的那一组**（这一页最新的一组） | 照用 |
       | 往后翻的结果（消息游标或 `after_seq`） | 这一页里紧挨游标的那一组（这一页最旧的一组） | 照用 |
       | 居中加载的一段 | 目标行那一组 | **作废**：它说的是旧时间线的行 |
       | 整条重建成最新页（订阅快照；连接没断时 `at_tail == false` 收到最新页；「回到最新」） | 最新一组 | **作废**（6/F-3） |
       | 实时事件、继续卡片与派生行的同步 | 没有专门的锚：有窗口用窗口最新的一组，没有窗口用最新一组 | 照用 |

       窗口作废 = 把记着的窗口清掉，等网页下一次声明；清掉之前不拿它做任何判断。
     - **每丢一组之前，看两端最外面的那一组，照这个次序定**（前一条分得出就不看后一条）：
       1. 锚所在的那一组不丢。两端都是它（只剩一组）就停。
       2. 一端最外一组在可见窗口里、另一端的不在 → 丢不在的那一端。
       3. 比两端最外一组到窗口的距离，**按已加载的行一行一行数，不是 seq 相减**；远的那一端丢。没有窗口时拿锚当窗口。
       4. 一样远 → 翻页的结果丢「不是这次取回来的那一端」；别的丢旧端。
     - **为什么翻页一定前进**：往前翻的锚在游标之前、是这次取回来的，它不丢，所以裁完之后最旧一行的 seq 小于原来的边界；页是空的时候 `has_older` 照 `has_more` 置假。往后翻对称。对话里的行有限，所以翻有限次到头。前提是上限不小于一组的行数（一组最多两行，上限小于 2 在构造时拒绝）。
     - **窗口已经离开这一端、又装不下的翻页结果不合并**：结果到达时，网页声明过窗口，窗口和这一端之间已经隔着别的已加载的行，**而且**把锚、中间这些行和整个窗口一起留下会超上限 → 丢掉这次结果，在飞表里清掉，时间线不动；窗口再贴上来时照 2.3 重发。不这样的话，第 1 条为了保住锚会把用户正在看的那一屏丢掉。**窗口还贴着这一端时一定合并**（发起翻页的条件就是贴着，所以只要用户没走开，每一次结果都合并、都前进，不会在「取了又丢」里打转）；没声明过窗口时也照常合并。
   - **窗口的单位**：网页声明的窗口是两个行号（行号 = seq × 2 + slot）。它只用来认「哪些已加载的行在窗口里」，认出来之后一律按行的先后位置算，不再拿 seq 做加减。
   - **数的是最后留在时间线里的全部行**（6/F-2）：实体行、重建得出的行（模型切换说明、项目分隔线）、当次说明、继续卡片都算。
     - **出事场景**：上限 4。裁剪丢掉了一条模型的当次说明；之后重算派生行，原来被那条说明压着不贴的「模型切换」行这时贴了出来，结果是 5 行。裁剪完再派生、派生完不再查，上限就破了。派生行会因为裁剪**变多**，不只是变少。
     - **手段**：同步与裁剪放在一个循环里，**循环的最后一步永远是查上限**：按已加载范围同步继续卡片、重算派生行 → 行数不超就结束 → 超了就照「丢哪一端」丢一组 → 回到开头。每一轮至少丢掉一组实体行，实体行有限，所以会停；只剩锚那一组时最多两行，不会超。不允许「重算派生行之后直接返回」这种出口。
   - **同一个 seq 的行一起丢**。重建得出的行（slot 0）和它贴着的那一行（slot 1）seq 相同；只丢一个的话，边界 seq 正好落在这两行中间，行级游标是严格大于、严格小于，留在外面的那一行就再也取不回来。所以裁剪按 seq 成组丢，边界两侧的 seq 一定不同。当次说明（`note:<seq>`）被裁掉就没了，翻回来时由重建得出的那一行顶上，和时间线重建时一样（D5）。
   - **裁剪时记下边界**。`Timeline` 加两个字段 `edge_older: Option<u64>`、`edge_newer: Option<u64>`：哪一端丢了行，就把那一端「留下来的最外一行的 seq」记进去（比它旧、或比它新的，这一侧都不在时间线里了）。丢旧的一端同时 `has_older = true`；丢新的一端同时 `at_tail = false`。
   - **翻页用哪种游标，只看这一端的边界有没有值**：有值 → 用行级游标，往前 `GetConversation{before_seq: edge_older}`，往后 `GetConversation{after_seq: edge_newer}`，`limit` 是行数（一页 200 行，常量只写一处；**上限比一页小的时候**，一页合并进来再裁，净增不到 200 行，但锚不丢、边界每次都往外挪，翻页始终在前进，理由见上面「为什么翻页一定前进」；测试里上限设 40 就是这种情形）；没值 → 边界落在消息上，照第 3 条用消息游标。
   - **行级翻页的结果怎么进时间线**。结果里的 `turns` 比后台选中的行多：选中行所属的回合也带来了，它们的结束位置可能在这一页之外。把这种回合的结束行也建出来，时间线中间就有洞（边界被它带到更远的地方，中间那一段再也不会去取）。所以客户端照后台同一个办法再挑一遍：把结果里能造出来的行（四个实体列表的行，加上 `turns` 里 `ended_seq` 在游标这一侧的结束行）按排序字段排好，**只取紧挨游标的 `limit` 行**放进时间线，剩下的不建，等翻到那里再建。后台选中的行都在这批候选里，候选又都在游标这一侧，所以挑出来的正好是后台选中的那些，不用猜范围。前提是两边用同一个 `limit`：客户端发的 `limit` 不超过后台的封顶值（2.9）。合并后把这一端的边界改成新的最外一行的 seq（结果为空时边界不动）；`before_seq` 的结果 `has_older` 取 `has_more`，`after_seq` 的结果 `has_newer` 为假说明接到了最新，`at_tail` 置真、`edge_newer` 清空（和第 3 条 `after_message_id` 同一个道理：这个结果在全序里有确定位置）。合并完照样查上限，超了照「丢哪一端」丢、记边界（这一页紧挨游标的那一组是锚，不丢）。
   - **继续 / 放弃卡片不靠查询翻回来**（它来自待处理表，不在 `GetConversation` 里）。它的行只在 `created_seq` 落在已加载范围里时才有：旧的一侧，`has_older == false` 就没有界，否则以最旧的非卡片行为界；新的一侧，`at_tail` 就没有界，否则以最新的非卡片行为界。范围变了（翻页合并后、裁剪后、重建后）和待处理表换了，都照这条重放一次。不这样的话，被裁掉的卡片翻回原位时不会再出现；待处理表一换，它又会被放回到没加载的位置上去。现有的 `sync_resume_cards` 不看范围，这是要改的地方。「已加载范围」的两端只看实体行，继续卡片与重建得出的行不算。
   - **模型切换说明也只贴在已加载范围里**（步 5c 实施时补的，2026-11-12）。它由相邻两个回合的模型算出来，贴在后一个回合的 `created_seq` 上。行级翻页的结果会带来范围外的回合（选中行所属的回合，`created_seq` 可以比这一页旧得多），照着贴就在范围外长出一行，和继续卡片是同一个毛病，所以用同一个范围判断。项目分隔线不用另管：它由相邻两条已加载的消息算出来，本来就在范围里。
   - **边界什么时候清空**：时间线整个重建时（最新页的快照、居中的一段、「回到最新」），两个边界先清空、记着的窗口作废，再按这次的结果查上限、需要的话重新记。**重建成最新页之后一定 `at_tail == true`**：锚是最新一组，窗口已经作废，超了只会从旧端丢（6/F-3 的情形是沿用了旧窗口，把最新的行当远端丢了，回到最新之后还停在旧位置、`at_tail` 还是假）。
   - `at_tail == false` 时新消息不进时间线，只加 `new_below`，界面出「回到最新（N）」，点了发最新页查询。关掉对话即丢弃整个 `Timeline`。
   - **由什么保证**：属性测试 `timeline_never_exceeds_cap`（随机的事件、各种查询结果、可见窗口位置，任何一步之后行数 ≤ 上限；测试里把上限设成 40，逼出裁剪）；`trim_both_ends_then_page_back`（一个回合 200 次工具调用、上限 40：居中加载后两端都没有消息行，往前、往后各翻到头，拼出来的行键序列等于不设上限时一次全取的）；`row_page_skips_out_of_range_end_row`（一页的最后一行属于一个还要很久才结束的回合，结果的 `turns` 里带着它的 `ended_seq`：这一页合并后时间线里没有它的结束行，再翻两页才出现，中间没有缺行）；`trim_keeps_same_seq_rows_together`（上限正好卡在一条带分隔线的消息上，两种方向各一例）；`resume_card_follows_loaded_range`（卡片被裁掉后翻回原位重新出现；待处理表更新时范围外的卡片不进时间线）；`edge_cleared_on_rebuild`；原有的 `timeline_cap_detaches_tail`。第 6 轮之后加的（6/F-1～F-3）：
     - `sparse_seq_paging_makes_strict_progress`：两段行之间隔一万个 seq，上限 40。往前一页页翻，**每一步断言 `edge_older` 严格变小**，直到 `has_older == false`；再往后翻，每一步 `edge_newer` 严格变大，直到 `at_tail`。哪一步边界没动就失败，不靠「最后翻到头了」来证。窗口声明过、没声明过各跑一遍。
     - 属性测试 `paging_always_terminates`：随机的稀疏 seq、随机上限（不小于 2）、随机窗口位置，往一个方向翻，步数不超过对话的行数就到头，途中边界严格单调。
     - `timeline_never_exceeds_cap` 的操作里加上「换模型并留下当次说明」「裁剪正好丢掉当次说明」，断言的是**同步完成之后**的行数（含派生行）；另加确定的一例 `derived_row_appearing_after_trim_is_trimmed_too`（上限 4，6/F-2 的原样）。
     - `back_to_latest_ends_at_tail`：往上翻到尾巴被裁掉，再回到最新（连接没断时收到最新页那条路）。断言 `at_tail == true`、最新一行在时间线里、记着的窗口已清掉；`snapshot_rebuild_ends_at_tail`、`around_load_discards_old_window` 同理。
     - `stale_page_result_is_dropped_when_window_left_the_edge`：结果到达时窗口已经离开那一端、和锚一起装不下，时间线不变，在飞表清掉，不重发；窗口贴回去才重发。对照 `page_result_merges_while_window_touches_the_edge`（窗口贴着时哪怕窗口加锚已经超上限也合并，窗口远的那一侧被裁，边界前进）。
     - `anchor_group_is_never_trimmed`（纯函数，表驱动：五种操作各一行，另加「窗口离锚很远」一行）。
5. 重建那一刻用户正在看旧消息时界面怎么表现（回到最新并提示，还是按原位置重新加载），见第 10 节 Q9；数据规则不随答复变。

### 2.3 连接与重连

```rust
/// 拿一条握手完成的连接。T04 合入前只有 DirectDialer（连默认端点，不拉起）；合入后给 Launcher 实现它。
pub trait Dialer: Send { fn dial(&mut self) -> impl Future<Output = Result<(Client, Incoming), DialError>> + Send; }
pub enum DialError { Connect(ConnectError), NotReady(Diagnostics), Environment(String) }   // 与 T04 LaunchError 同形
```

主循环一个 `select!`：`Incoming`、网页操作、帧节拍、重连与重查定时器。决策是纯函数 `reconnect::next(state, outcome) -> Action`：

| 结果 | 界面（`ConnectionPatch`） | 接下来 |
| --- | --- | --- |
| 连上 | 等全部 `Subscribed` 应用完才算 `Live` | 一次写出全部范围的 `Subscribe`（`subscribe_nowait`，同一个 `from_seq`）；在飞命令按原 `command_id` 重发 |
| `Connect(e)`，`e.wait_prompt() == VersionMismatch`（`PeerRejected`、`ClosedBeforeWelcome`） | 整页中性提示，文字与两个出口取 `WaitPrompt` | `Backoff` 退避重拨；不拉起、不结束进程 |
| `Connect(VersionMismatch{..})` | 「正在切换版本」 | 同上 |
| `Connect(Timeout / Protocol / Io)`、`NotReady(d)` | 诊断页：日志目录、锁里的 pid 与是否还在、启动阶段、拒绝原因与备份路径、「重试」；库比程序新时照 T04 提示「装回更新的那一版可继续使用」 | `Backoff` 退避重拨；连上后诊断页自动消失 |
| `Environment(msg)` | 整页显示 `msg`（M1 的 Windows 走这里） | 不自动重拨，只留「重试」 |
| `Closed(_)` | 顶部细条「正在重新连接」；会发命令的按钮全部不可点 | 立即重拨；更新下面的计数 |

`from_seq` 只在这一处算，用一个计数 `same_cursor_closes`（与 T03 2.11 的说法逐字对应）：连接关闭时游标与上一次关闭时相同就加一，不同就置 1；应用了任何带 seq 的项（事件、快照、查询结果）就清零。

- 游标为 0、或有视图还是 `Loading`、或 `same_cursor_closes ≥ 2` → `from_seq = 0`；否则 = 游标。
- `same_cursor_closes ≥ 3` → 顶部提示「后台负载过高，稍后重试或重新打开 iWork」，继续退避；计数清零时撤掉。

打开对话 = `Subscribe{Conversation, from_seq: 0}`（T03 定的：一次全范围快照）；离开 = `Unsubscribe`。常驻范围：侧栏、待处理、额度、运行时状态、设置。

在飞命令：发出即登记 `command_id → Command`，收到 `CommandAccepted` 或不可重试的错误才删。断线期间不接新命令（D8：发送禁用，草稿留在网页本地）。

**在飞的视图查询**（第 2 轮 2/F-1：发出不等于完成）。`queries.rs` 一张表 `request_id → 用途`，结果从 `Incoming` 应用完才删；**连接关闭时整张表清空，每种用途回到「还要再发」**，不留任何「已经发过」的记号：

| 用途 | 「还要再发」记在哪 | 断线或失败之后 |
| --- | --- | --- |
| 摘要重查（一轮四或五条） | `summary_stale`（2.2） | 整轮重发 |
| 往前翻页（游标是消息 id 还是 `before_seq`，看 `edge_older` 有没有值，2.2） | 时间线的 `has_older` 与网页声明的窗口：窗口顶到了已加载的最旧一行 | 重新 `Live` 后窗口还顶着就重发，游标按重发那一刻的时间线重新取；走了快照则时间线已重建，按新窗口算 |
| 回到最新 | `at_tail == false` 且用户点过（`want_tail`） | 重新 `Live` 后重发 |
| 往后翻页（游标是消息 id 还是 `after_seq`，看 `edge_newer` 有没有值，2.2） | `at_tail == false` 且网页声明的窗口底到了已加载的最新一行 | 重新 `Live` 后窗口还顶着就重发；走了快照则时间线已回到最新 |
| 锚点窗口（2.9） | `anchors_stale`，或当前位置落在已取的锚点窗口之外 | 重新 `Live` 后重发；走了快照后按最新位置重取 |
| 以锚点为中心加载（2.9） | `pending_jump` 还在 | 续传重连后重发；走了快照则时间线已回到最新（Q9），`pending_jump` 清掉，不再跳 |
| 流式缺口对齐 | 缺口本身：`text` 的长度小于下一个增量的 offset | 下一个增量到达时再触发；消息完成事件自带全文 |
| 规则、本机导入列表、「全部对话」下一批 | 对应页面可见且它的视图是 `Loading` | 重新 `Live` 后重发 |

加一种视图查询 = 表里加一行，必须写出「还要再发」记在哪。

`ReportPresence`（2.8）不在这张表里也不在在飞命令表里：它是期望状态，每次重新 `Live` 后发当前值。`GetOpenTarget` 是 `SideQuery`，断线时那一次作废，下次获得焦点再问。

### 2.4 `ViewPatch` 与帧合并

`view.proto` 只加字段与变体，不 import `model.proto`：

- `ConversationPatch` 加 `repeated RowView rows = 7`；原来的 `upserts = 3`（`MessageView`）标 deprecated、不再填，不改它的类型。`RowView{ sint64 ordinal; string key; oneof row {…} }`，变体对应 2.2 行登记表。`ordinal` 是 Rust 侧发的稳定行号（往前翻页发负数），网页拿它当高度缓存的键。
- 行里全是画的时候要的东西。例：`ApprovalRow{ title, tags[], code, review_line, state_label, bool can_decide, remember_options[{scope, label}], bool muted, bool folded }`。
- 其余六个 patch 各带一个 `optional` 整体视图模型，脏了就整份发；大小没有假设（助手提示词可以有几 MiB），靠下面的通用分块过传输。`SidebarPatch` 的形状照 `ui-m1.md` 第 2 节第 3 条与 2a：项目行（名、未读、置顶、路径状态）、每个项目最近 5 个对话（圆点状态与状态名、标题、可否重命名；Rust 侧从全部对话摘要里按项目取）、助手行（名、头像、表情、最近动态一行、未读）。圆点状态在 `derive::sidebar` 一处算（2a 第 1 条）：这个对话在待处理表里有项 → 等你处理；否则 `last_turn_state` 是失败 → 出错；是排队、运行、等审批、取消中 → 运行中；其余空闲。助手未读 = 它那条私聊的 `unread`（2a 第 3 条），不另要字段。
- `UiIntent{ oneof kind {…} }`、`IntentAck{ optional Error error }`，以及取帧用的 `FrameChunk{ uint32 epoch; uint64 frame; uint32 index; bool last; bytes data }` 也放在 `view.proto`。

**帧怎么到网页：网页来取，不推**（第 1 轮 F-1、第 2 轮 2/F-2、2/F-3 是同一类问题第三次出现，这一轮换机制，见第 13 节）。

事实（读了 Tauri 2.12.5 源码，第 9 节「已知事实」列了位置）：`Channel` 发 ≥ 1 KiB 的原始字节时，先存进按 webview 分的 `ChannelDataIpcQueue`，等网页回头来取；这个暂存没有上限，只在窗口或 webview 关闭时清，页面刷新不清。`invoke` 有两条路：

| 路 | 什么时候走 | 回包怎么回去 | 请求头 |
| --- | --- | --- | --- |
| 自定义协议（`ipc://`） | 桌面平台默认 | 就是那一次请求的回包，原始字节，不进暂存 | Tauri 自己加了 `Tauri-Callback`、`Tauri-Error`、`Tauri-Invoke-Key` |
| postMessage | 自定义协议请求失败过一次（被 CSP 或 WebView 挡住）之后，这个页面此后全走它 | 成功的原始字节回包被转成 JSON 数字数组再 `eval` 进页面（macOS 一律如此；别的平台在「协议被挡」时如此，否则走 `Channel` 回包、≥ 1 KiB 进暂存，而且不经过 `channel_interceptor`）；错误回包一律是一小段 `eval` | 只有调用方自己在选项里给的头 |

所以上界不能靠「我们少发几帧」，要让数据只在网页伸手时才离开状态库，而且**只在第一条路上交数据**：

1. `apply` 与本地视图状态变化只往 `DirtySet` 记键。
2. **三个命令**：`attach() -> epoch`；`next_frame(epoch, applied) -> FrameChunk`；`ui_intent(bytes) -> bytes`。都走原始字节。不用 `Channel`。
3. **代次**：`attach` 让 `epoch` 加一，丢掉上一代没交完的帧，让上一代挂着的那次 `next_frame` 立刻以「代次过期」返回，全部可见视图记脏。带旧代次的 `next_frame` 一律回「代次过期」，不给数据。已经交出去、网页回调还没执行的旧回包 Rust 收不回来，由网页那一侧挡（第 8 条）。
4. **取帧**：`next_frame` 是一次长等待，同一时刻最多挂一个（新来的顶掉旧的）。`applied` 是网页已经应用到的 `(frame, index)`：
   - 和上一次交出去的块对不上（回包丢了）→ 原样再交一次那一块，网页按 `(frame, index)` 去重。
   - 对得上，当前帧还有剩下的块 → 交下一块。
   - 当前帧交完了 → 等到「有脏键、且距上一帧开始 ≥ 16ms」，这时才 `derive` + 编码出新的一帧，交第一块。
5. **分块对所有 patch 一视同仁**：一帧是编码后的 `ViewPatch` 字节，多大都行，按 `FRAME_CHUNK_MAX = 256 KiB` 切；网页收齐 `last` 再解码、`applyPatch`。没有「哪种 patch 才能拆」的规则，也没有单帧上限，所以不存在装不进去的模型。
6. **上界**：在传输里的最多是一次 `next_frame` 的回包，≤ 256 KiB。Rust 侧另外只留着当前这一帧没交完的字节，它不超过可见视图模型的大小（时间线只含窗口里的行）。网页不取、窗口隐藏、页面卡死：没有新的帧被算出来，变化只留在状态库里。没有超时、没有「失联后照发」。
7. **只认自定义协议这一条路**（第 3 轮 3/F-1；上一版想用 `channel_interceptor` 守，守不住：回退时的回包要么是 `eval` 的 JSON、根本不经 `Channel`，要么走的 `Channel::from_callback_fn` 不调拦截器）。能认出实际走了哪条路的地方有两处，各守一道：
   - **Rust 命令入口**：三个命令都先看请求头里有没有 `Tauri-Callback`（只有自定义协议那条路才有；网页代码不许在 `invoke` 选项里传任何 `Tauri-` 开头的头，组件测试检查）。头名比较不区分大小写。没有 → 不算帧、不交任何数据，返回错误 `transport_fallback`。这个头**只用来区分走的是哪条路，不是认证凭证**：页面里的脚本想伪造它，挡的是 R7（不让不可信内容变成能跑的脚本），不是这一条。网页这边三个命令都经 `bridge/` 里同一个调用函数发出，这个函数不接受调用方传自定义头。错误回包在 Tauri 里一律是一小段 `eval`，不经 `Channel`、不带帧数据，所以回退路上既没有 JSON 化的帧，也没有东西进暂存。
   - **网页取帧循环**：收到 `transport_fallback`、或成功的回包不是 `ArrayBuffer` → 立刻停掉取帧循环，不应用，显示网页自带的固定诊断页「界面传输不可用，请重新打开 iWork」（文字固定、不依赖帧；带日志位置的说明）。不重试、不接受 JSON 回退。
   - 发布层 CSP 必须放行 Tauri 的自定义协议，配置检查里有一条；三个平台的发布构建是不是都走第一条路由第 0 步实测（E1），哪个平台做不到就记为该平台不达标，交 supervisor。
8. **网页的取帧循环绑定代次**（第 3 轮 3/F-2）。模块里只有一个「当前代次」；`attach` 时先把它置成「换代中」（旧循环从此失效），拿到新 `epoch` 后清空 store、起一个新循环。循环自己带着 `epoch` 与组装缓存（缓存是循环的局部变量，循环结束就没了）。**每次 `await` 回来先核两件事，再碰数据**：当前代次还是不是自己这一代；`chunk.epoch` 是不是自己这一代。任一不是 → 这个回包整个丢掉、循环结束，不收块、不 `applyPatch`。核过了才按 `(frame, index)` 去重、收块，收齐 `last` 再解码应用。
9. 发帧时对每个脏键：视图不可见 → 丢掉；可见 → `derive` 从当前状态算。行只发落在网页声明的窗口（`SetVisibleRows`，前后各多带 30 行）里的。流式文字走 `appends`；同一帧里这条消息也要整行重发时只发整行。
10. 时钟注入（`tokio::time` 暂停模式可测）。

帧由「推」改成「取」，原先偏离技术设计 3.6 第 3 条与任务卡范围 1 的字面；产品负责人 2026-11-10 已同意，那两处已改成现在的写法（第 10 节 C1）。每 16ms 最多一帧、原始字节、不经 JSON 都没变。

### 2.5 网页层：只渲染的边界

| 网页层可以有 | 网页层不许有 |
| --- | --- |

### 2.6 假数据源，以及怎么换成真连接

- **假后台** `iwork-fake-daemon`：内存里一条带 seq 的事件日志；用 `iwork-ipc::Server` 监听一个 Unix socket（DevTrust，只在 `dev` feature 下）；按范围过滤推送并填 `subscription_ids`；从日志折叠出内存表回答 11 种视图查询；命令只受理场景要用的几种，其余回 `UNIMPLEMENTED`。数据形状按第 3 节补完字段后的协议造，`*_seq` 都填真值。

### 2.8 提醒：Dock 角标与跳动、报在看哪、被叫到前台时跳转

背景（探针实测，第 14 节）：这台机器上没有 Developer ID 签名，任何形态的 iWork 程序都拿不到 macOS 的通知权限。所以 M1 的提醒分两层：**Dock 角标与跳动**不要权限，现在就能用；**系统通知**的代码照写，由后台发，拿不到权限时只记日志，等有 Developer ID 签名的构建时自动生效。

**Dock 角标与跳动**（只在 macOS；`attention.rs` 算，壳执行）

- 角标数字 = 待处理表的条数，和侧栏「待你处理」的计数是**同一个函数**算出来的（`derive::pending_count`），不另数一遍；为 0 时清掉角标。摘要每次重查或快照之后更新；断线期间保留最后的数字。
- 跳动：新的一份待处理表里出现了上一份里没有的条目 id → `Effect::RequestAttention`。上一份表在进程里一直留着（跨重连），所以同一项不会跳第二次；一项刚处理掉、同时又来一项，数字没变也会跳。系统只在应用不在前台时才让图标跳，所以「用户正在看」的情况不用客户端判断。跳一次还是一直跳到用户切回来，见第 10 节 Q15。
- 网页不参与：窗口关着、没有网页在取帧时，client-core 照常连着后台、照常重查摘要、照常发这两个效果。
- **这要求 macOS 上关窗不退出客户端进程**（产品负责人的决定里「窗口关了也算」就是这个意思）：关窗只关窗口，进程留在 Dock；点 Dock 图标重新开窗，新窗口 `attach` 后换一代取帧。客户端进程退出（Cmd+Q）之后 macOS 上没有任何提醒，这是已知限制。Linux 维持原样：关窗即退出客户端，没有角标与跳动。菜单里「只退客户端」和「完全退出 iWork」怎么摆，见 Q16。

**报在看哪**（`presence.rs`）。新命令，连接级状态：

```proto
// 桌面客户端报「用户现在看得到什么」。不产生事件、不落库、不进幂等记录（与 ShutdownDaemon 一样是不产生事件的命令）；
// 这条连接断开即视为没人在看。只受理 DESKTOP 连接。
message ReportPresence {
  bool window_focused = 1;                       // 窗口在前台、没有最小化；窗口关着时为假
  optional string viewing_conversation_id = 2;   // 主区域正显示且已加载完的对话；不在对话页时不设
  bool viewing_pending_list = 3;                 // 主区域正显示「待你处理」页
}
```

- 由「窗口焦点 + 当前路由 + 视图是否 `Ready`」算出，值变了就发；每次重新 `Live` 之后发一次当前值。它和订阅范围一样是期望状态，不进在飞命令表，断线不重发旧值。
- **离开立刻报，到来延后 500ms 报**（R11）：失焦、切走、最小化、关窗马上发；反过来等稳定了再发。
- 它只供后台决定要不要发系统通知。Dock 跳动不看它。

**被系统通知叫到前台时跳转**（`open_target.rs`）。新查询，`SideQuery`：

```proto
message GetOpenTarget {}
message GetOpenTargetResult {
  uint64 token = 1;                    // 每记下一个新目标加一；0 表示没有
  string pending_item_id = 2;
  optional string conversation_id = 3; // AGENTS.md 草稿这类没有对话归属的项不设
  google.protobuf.Timestamp at = 4;    // 用户点这条通知的时刻。只记用户确实点过的那一项
}
```

- client-core 在窗口获得焦点、以及启动后第一次 `Live` 时问一次。`token` 比上次处理过的新、且 `at` 在 30 秒内 → 走和「待你处理」列表点一项**同一个**内部动作；没有对话归属的打开「待你处理」页。`token` 只记在内存里。
- 后台拿不到「点了哪一项」时不记目标，客户端停在原来的页面，不猜（N2）。
- 这条路在没有通知权限的机器上不会被走到；自动化测试用假后台给目标，真机验证等有 Developer ID 签名的构建（第 14 节）。

### 2.9 消息锚点（`ui-m1.md` 2a 第 11 条，画布 `16-Anchor-*.png`）

**锚点列表从哪来：后台给，按窗口取，客户端不自己挑。** 理由：

- 锚点要覆盖整个对话，时间线却只加载了一段（最多 5000 行，十万条的对话里只是零头）。只从已加载的行里挑，「第一处」就成了「已加载的第一处」，也就不存在界面说明里那个「跳到还没加载的旧消息」。
- 一半客户端算、一半后台给，就有两份「哪些算锚点」的规则，加载边界一移动两份就可能对不上。所以只留后台一份，和侧栏摘要同一个做法：**失效后重查，不推演**（2.2）。
- 不能一次给全量：十万条的对话里用户消息可以有几万条。用起来只看当前位置前后几处，所以按「以某个位置为中心、前后各取 N 条」来取。

协议形状（G10、G11，见第 3 节）：

```proto
// queries.proto。登记为 ViewQuery：结果写视图，事件也会改它。
message ListAnchors {
  string conversation_id = 1;
  uint64 around_seq = 2;   // 以这个位置为中心；0 = 从最新往回取
  uint32 before = 3;       // created_seq 不大于 around_seq 的，最多取这么多条
  uint32 after = 4;        // 大于 around_seq 的，最多取这么多条
}
message ListAnchorsResult {
  repeated Anchor anchors = 1;         // 按 created_seq 升序
  bool has_before = 2;
  bool has_after = 3;
  uint32 waiting_count = 4;            // 整个对话里等你处理的锚点数
  uint32 failed_count = 5;             // 整个对话里失败回合的锚点数
}
message Anchor {
  uint64 created_seq = 1;              // 与时间线行的排序键同一个数（2.2 行登记表）
  google.protobuf.Timestamp at = 2;
  oneof kind {
    UserMessageAnchor user_message = 10;   // { message_id, excerpt }：正文开头，后台截到 200 个字素簇
    WaitingAnchor waiting = 11;            // { pending_item_id }：审批、亲手执行卡片、继续卡片；处理掉就不再是锚点
    FailedTurnAnchor failed_turn = 12;     // { turn_id, reason, had_output }
  }
}
// GetConversation 的取页方式。什么都不设 = 最新页；下面五个字段至多设一个，设了两个以上回 INVALID_ARGUMENT。
// 按消息数取（limit 是消息条数，连同范围内的回合、工具调用、审批、卡片）：
//   optional string before_message_id  往前翻一页（原有）
//   optional string after_message_id   往后翻一页
//   optional uint64 around_seq         以这个位置为中心取 limit 条消息
// 按行数取（2026-11-12 加；limit 是行数）：
//   optional uint64 before_seq         排序字段小于它的各类行里，紧挨着它的 limit 行
//   optional uint64 after_seq          排序字段大于它的各类行里，紧挨着它的 limit 行
// GetConversationResult 加 bool has_newer；has_more（更旧的还有没有）、has_newer（更新的还有没有）六种取法都照实填。
```

**行级游标的语义**（`before_seq`、`after_seq`；假后台与真后台照同一份做）：

- **「行」是哪几种**：消息、工具调用、审批、亲手执行卡片，排序字段是各自的 `created_seq`；回合结束行，排序字段是 `Turn.ended_seq`。**一个回合有没有结束行，两边用同一个条件**（步 5c 实施时定的，2026-11-12）：`ended_seq` 不是 0、回合不在跑、**状态不是中断**。中断的回合在时间线里显示的是继续 / 放弃卡片，不是结束行，所以数行的时候不算它。后台要是把中断的回合也数成一行，按行数取的一页就比客户端建出来的多一行，客户端「只取紧挨游标的 `limit` 行」挑出来的就和后台选中的对不上，翻页会重行或漏行。就是 2.2 行登记表里「查询结果里的排序字段」那一列。继续 / 放弃卡片不在这个查询里（它来自待处理表）；模型切换说明、项目分隔线是客户端从相邻实体算出来的，后台不数它们。
- **取哪些**：`before_seq = s` → 把各类行按排序字段合在一起，取小于 s 的里面最大的 `limit` 个；`after_seq = s` → 取大于 s 的里面最小的 `limit` 个。两种都按排序字段从旧到新返回。
- **结果里放什么**：选中的行对应的实体放进各自的列表（`messages`、`tool_calls`、`approvals`、`user_actions`）；`turns` 放这些行所属的回合，以及结束行被选中的回合，回合自己的 `created_seq`、`ended_seq` 可以在范围外；`attachments` 放选中消息的附件。
- **两个布尔值**：`has_more` = 对话里还有比结果里最旧一行更旧的行（结果为空时 = 还有比 s 更旧的行）；`has_newer` = 还有比结果里最新一行更新的行（结果为空时 = 还有比 s 更新的行）。
- **`limit`**：0 回 `INVALID_ARGUMENT`；大于 1000 按 1000 取。`s` 为 0 回 `INVALID_ARGUMENT`。
- **客户端怎么用**见 2.2「查询结果怎么进时间线」第 4 条：只在某一端被行数上限裁过之后才用，一页 200 行；`turns` 里带来的回合，结束行不在选中的 `limit` 行里的，这次不建。

**client-core**（`store/anchors.rs`，状态挂在打开的 `Timeline` 上）

- **锚点窗口**：`ListAnchors` 的结果整份替换，前后各取 60 条。失效规则和摘要一样不挑事件类型：持久事件的 `subscription_ids` 含这个对话的订阅 → `anchors_stale`，并进摘要重查的同一轮（2.2 第 2～4 条的节流、「一轮走完才清标记」、断线作废都照用）。打开对话后先取一次（`around_seq = 0`），取到之前视图模型里没有锚点，组件不显示。
- **当前位置**：纯函数 `current_anchor(窗口, 可见窗口第一行的 seq)` = `created_seq` 不大于它的最后一个锚点；在第一个锚点之前就取第一个。网页每次报 `SetVisibleRows` 时重算。口径（按第一行还是按屏幕中线）等 Q17，换口径只改这一个函数。算出来的位置落在已取窗口之外、而那一侧还有（`has_before` / `has_after`）→ 以它为中心重取。
- **翻看**（网页在滚轮上换到哪一处是网页自己的展示状态）：预览到离窗口边缘 8 处以内、那一侧还有时，网页发 `AnchorBrowse{key}`，Rust 以那一处为中心重取；新列表到了，网页按 key 把「正在预览哪一处」对回去。
- **跳转**：`JumpToAnchor{key}`（点刻度或信息卡）与 `JumpRelative{-1 | +1}`（⌥↑ / ⌥↓，相对当前位置；目标不在已取窗口里就先重取再跳）走同一个函数：
  1. 目标行已在时间线里 → 发一次性的 `scroll_to{key, highlight_ms: 1000, token}`。`token` 每次跳转加一，网页只对没见过的 `token` 滚动并高亮；高亮的 1 秒由网页计时。
  2. 不在 → 记 `pending_jump`，发 `GetConversation{around_seq: 锚点的 created_seq, limit: 50}`。结果到了按 2.2 第 3 条重建时间线，再发 `scroll_to`。结果里没有目标行（这期间对话被删、行已不在）→ 只显示这一段，不高亮，`pending_jump` 清掉。
  3. 加载期间用户又滚动、又跳别处、切了对话 → `pending_jump` 换成新的或清掉，迟到的结果按第 2 步的规则正常进时间线，但不再滚动。
- **视图模型**（`ConversationPatch` 加两个 `optional` 字段，都是只增）：`anchors = AnchorsView{ items[], has_before, has_after, has_waiting, has_failed }`，列表变了才整份发；`anchor_cursor = { current_key }`，位置变了只发它。`AnchorItem{ key, kind, kind_label, time_label, preview }`：类型文字（你 / 等你处理 / 失败）、时间文字（今天显示时刻，更早显示日期，按本机时区）、预览文字都在 `derive` 里出——用户消息用 `excerpt`；等你处理的用待处理表里那一项的摘要文案（和「待你处理」页同一份）；失败的按 2a 第 10 条的两种说法拼。网页只把预览限制成两行。
- **和别的规则怎么配合**
  - 上限 5000 行：居中加载、往后翻页都受它管（2.2 第 4 条），居中的一段自己超了也当场裁，留下离目标行近的。被裁掉的一端用行级游标翻回来。锚点窗口不占时间线的行数。
  - 翻页空洞：时间线始终是连续的一段。跳到没加载的地方不是在中间挖洞，是换成另一段，「回到最新（N）」照常出现；往下翻到 `has_newer` 为假时自动接回最新。
  - Q9（重连走了快照，回到最新并提示）：时间线重建成最新页，`pending_jump` 清掉，锚点窗口按最新位置重取，网页收起滚轮。续传的重连什么都不变。
  - 流式增量、工具输出不产生锚点，也不让锚点失效（它们是瞬时事件）；一轮结束或失败时的持久事件才触发重取。

**网页**（`client/src/anchor/`，归步 7a）

- 位置与显隐：对话区左边距、上下居中。视图模型里没有锚点、或内容没超出一屏（布局事实，网页自己量）时不渲染。
- 静止态：三条短线；`has_waiting` 出芥末黄点，`has_failed` 出赭红点，都没有就不出。
- 展开：鼠标进左边距或键盘焦点到达时展开成刻度滚轮，停在 `current_key` 那一处；上下最多各 4 条刻度，越靠中间越长、越远越淡，颜色按 `kind`；中间刻度旁是信息卡（类型标签、时间、两行预览、指向中间刻度的小三角）。没有箭头按钮，不显示「第几处 / 共几处」。
- 滚轮：鼠标滚轮每格换一处（刻度滑一格约 120ms，信息卡淡入换内容）；触控板的位移累计到阈值才换一处；甩动时每秒最多换约 10 处；到第一处或最后一处（那一侧 `has_before` / `has_after` 为假）轻轻回弹并停住，不循环。翻看期间对话不动，不发跳转。
- 点中间刻度或信息卡 → `JumpToAnchor`，收起；点别的刻度 → 直接 `JumpToAnchor` 那一处。Esc 立即收起；鼠标移开 300ms 后收起；两种都不动对话。⌥↑ / ⌥↓ 不展开滚轮，直接发 `JumpRelative`。
- 系统开启「减少动态效果」时去掉滑动与淡入。刻度与信息卡带 `aria-label`（类型 + 时间 + 预览）。
- 这些都是展示状态与手势处理；哪些算锚点、文字、当前位置、有没有更多，都来自 patch。

- G6：侧栏订的是整类会话键，会收到所有对话的流式增量，client-core 只能收了再丢。**只把增量的路由键写成 `conversation:<id>` 解决不了**——`StreamKey::covers` 里整类键照样覆盖它；要避开得给增量换一个流类，或让范围声明要不要增量。请 T10 定路由时处理，或在基准里量这部分的代价。
- D6（2026-11-11 改定）：系统通知全部由后台发。归 T10a 的有：`Notifier` 的 `iwork-host` 实现（申请权限，拿不到就只记日志，不重试打扰；Linux 只记日志）；端口 `SystemNotification.open` 加条目 id；发不发的规则（纯函数，放 `iwork-core`：桌面连接报了窗口在前台，并且正看着这一项的对话或「待你处理」页 → 不发；同一项只发一次；已处理或作废的不发）；去重与接线（建议走 T04 的 outbox 投递登记表加一行）；通知文案（不出现「主管」，只用卡片上已有的摘要）；`ReportPresence` 与 `GetOpenTarget` 的受理，连接关闭时清掉那条连接的状态；用户点通知后记下目标并把客户端叫到前台。
- T10 汇合时用真后台重录场景，与假后台录像对拍（第 11 步）。

## 4 规则（目的 + 手段）

| # | 目的 | 手段 |
| --- | --- | --- |
| R1 | 界面状态和后台一致，重连后不重、不漏、不倒退 | 状态库只从 `Incoming` 按到达顺序写；游标在应用完之后才推进；`from_seq` 只在 `reconnect::next` 一处算 |
| R2 | 有视图没拿到快照时不能假装齐了 | 视图有 `Loading / Ready`；任何视图 `Loading` 时重连一律 `from_seq = 0` |
| R3 | 翻页和快照不能把还存在的东西当成删了 | 查询结果只换视图成员；对话与项目的删除只由事件或下一次完整列表体现；时间线丢缓存不产生「已删除」的显示 |
| R4 | 界面上不留过期的值 | 时间线的不变量（2.2）：事件被跨过就重建；摘要一律失效重查，不按事件类型挑 |
| R5 | 网页慢、窗口隐藏、页面反复刷新时，离开状态库又没被网页收下的数据有上界 | 帧由网页来取，一次回包 ≤ 256 KiB，同一时刻最多一次；不用 `Channel`；只在自定义协议那条路上交数据，认出回退就停、不交；所有 patch 走同一套分块 |
| R6 | 同一件事不出现两个说法 | 计数、文案、可否点击只在 `derive`；后台给的文字原样用；摘要值只读后台的 |
| R7 | 网页里显示的内容（模型输出、文件名、标题）不能变成操作 | 四道，都在真实 WebView 里取证（第 7 节）：渲染不产生可执行节点；主窗口不能被导航到别的来源、不能开新窗口；发布层 CSP 不许内联脚本与远程来源；三个 Tauri 命令只接受主窗口、应用自身来源的调用，网页拿不到文件与 shell 能力。`ExecuteUserAction` 的提议哈希由 Rust 从实体取，网页只给卡片 id |
| R8 | 客户端里没有只为测试存在的分支 | 假数据在另一个进程里走真协议；`IWORK_DEV_ENDPOINT` 只在 `dev` feature 下读 |
| R9 | 安全类界面保持严肃（FR22） | 印章只由回合结束行的 `celebrate` 驱动；审批、亲手执行、继续卡片的行类型里没有这个字段 |
| R10 | 版本验证状态不打扰日常使用（T06 P2） | `derive` 只在设置 › 运行时、引导页与诊断页输出验证状态的标签；侧栏与标题栏的视图模型里没有这个字段。输入框被挡住时在输入框上方说明（2a 第 8 条），这是告诉用户为什么发不了，不是状态栏 |
| R11 | 窗口和后台对「在看哪」的认识有时差时，只多弹、不漏弹 | 离开立刻报、到来延后 500ms 报；连接断开即视为没人在看 |
| R12 | 没有通知权限时，用户仍然知道有事在等他；提醒的数字不出现第二个说法 | Dock 角标 = `derive::pending_count`，与侧栏计数同一个函数；跳动只看「出现了新的条目 id」；两样都由 client-core 发效果、壳执行，网页不参与，窗口关着也有效 |
| R13 | 时间线只加载了一段时，锚点的范围、类型、先后仍然是整个对话的，而且只有一个说法 | 锚点只来自 `ListAnchors`，按窗口取；client-core 不从已加载的行里挑锚点；失效重查与摘要同一套；跳到没加载的锚点时换成以它为中心的一段，不在时间线中间留洞 |
| R14 | 时间线的行数上限严格成立：任何一次写入之后都不超（**数的是同步完成之后留下的全部行，派生行也算**），裁掉的部分翻得回来，不重、不漏，**翻页每一步边界都往外挪**（2026-11-12，组 2b 审查 5/F-3；第 6 轮 6/F-1～F-3 后补了加粗的两处） | 每次往时间线放东西之后都查上限：同步继续卡片与派生行和裁剪在一个循环里，最后一步永远是查上限；超了按 seq 成组丢，丢哪一端先保住锚（翻页的锚是这一页紧挨游标的一组，重建成最新页的锚是最新一组并且旧窗口作废），再看可见窗口，距离按已加载的行数、不按 seq 差；记下边界 seq。被裁过的一端用行级游标 `before_seq` / `after_seq` 按行翻回来，结果照后台同一个办法只取紧挨游标的 `limit` 行（2.2 第 4 条、G11）。它和 R5 是一类规则的两头：R5 管离开状态库的数据有上界，这一条管状态库里时间线自己有上界 |

叠起来推：

- R1 + R5：网页不来取时游标照常推进，脏键留着，下一次来取时从当前状态算，不漏。
- R2 + 过载：快照本身也被关时计数不清零，继续 `from_seq = 0`，不会退回续传。
- R4 + R1：摘要重查走 `ViewQuery`，结果在全序里，位置一定在触发它的事件之后，不会被旧事件盖回去；重查没走完就断线，标记从没清过，重连后整轮重发（2.3 在飞查询表）。
- R4 + R3：时间线重建丢掉旧页，用户往上翻时按 `before_message_id` 重新查，拿到的是当前状态。
- R5 + 刷新：旧页面挂着的 `next_frame` 在新 `attach` 时以「代次过期」结束，回包里没有数据；旧代没交完的帧直接丢。反复刷新留下的东西是零，不是「每次一块」。
- 同一页面里重新 `attach`（热更新）+ 旧回包迟到：旧回包在新代的全量之后才到，网页先核代次，对不上就丢，新代的界面不会被旧数据盖掉（2.4 第 8 条）。
- R5 + 超大模型：2 MiB 的助手提示词切成 8 块，每块交出去都要等网页回来取下一块；交到一半又有变化不打断这一帧，下一帧再带上。
- 时间线与摘要对同一张审批卡片各有一份：对话里的卡片随事件立刻变，「待你处理」计数最多晚一轮重查（约 250ms）。两边最终一致，中间不会出现「能点两次」：可否点击只看时间线那一份。

**S14 的三条路**（第 1 轮 F-7；客户端与后台在同一个安装包里，「只换客户端」不成立）：

1. **有证书的构建，新旧两版协议主版本相同，新版没带数据库迁移**：装回上一版安装包。后台发现安装的程序换了就自行重启成旧版（T04 2.9，降级同样触发）；重启前的窗口里旧客户端 × 新后台同一张证书互认、握手通过，新字段旧客户端忽略。回合按中断处理、可续，待审批保留。由 T04 升级演练脚本的回退段保证。
2. **无证书的构建**（清单只登记这一版的映像）：同样整包装回。后台重启前客户端与后台互不相认，客户端停在「后台服务与客户端版本不一致」并退避重连，后台重启成旧版后自动连上。只换一个二进制永远连不上。由 `rejected_then_recovers_after_daemon_restart`（T09，假后台换身份模拟）与 T04 演练保证。
3. **新版带了迁移，库已经迁移过**：装回旧版后台起不来，**没有回退路**，只能装回新版等修复版（T04 Q4：带迁移只能向前修，紧急修复版不夹带迁移）。T09 自己不落盘、不带迁移，但和它同版发布的改动可能带。这种情况下界面坏了期间：后台照常跑，回合继续、待审批保留；诊断页在旧版被拒时按 T04 的原文提示「装回更新的那一版可继续使用」（`diagnostics_shows_newer_schema_hint`）。

## 7 测试清单与验收对照

**Rust**（`cargo test -p iwork-client-core`；连假后台的放 `tests/`）

- 属性测试 P1 `reconnect_equals_fresh`：随机事件脚本 + 随机断线点（含连续断、断在订阅途中、断在重查途中）、范围开关、翻页；收敛后可见视图的视图模型 == 由假后台独立折叠出的查询结果算出的视图模型。生成器要能造出「旧行在断线期间变化且不在最新页」。对照：故意让 `apply` 跳过一类事件时必红。
- 属性测试 P2 `patches_compose_to_full`：任意事件序列 × 任意取帧时刻 × 回包丢失与重复取 × 任意 `attach` 时刻 × 很小的分块上限（测试里设 64 字节，逼着每种 patch 都被切）× 随机的超大字段，把网页会接受的块（按 2.4 第 8 条的两项核对，模型里包含「旧代回包迟到」）拼回、折叠，等于终态一次全量；任何时刻交出去没被确认的字节 ≤ 一块。

## 12 ADR（developer 随实现写入 `docs/adr/`，编号合入时定）

**ADR-T09-a 客户端状态：单任务状态库，时间线按事件改、摘要失效重查，发帧时才算视图。** 背景：事件多路并发到达；侧栏上的值是后台按自己的规则算的；网页每 16ms 最多收一帧，还会隐藏、刷新、卡死；Tauri 的 `Channel` 自带无上限的暂存。决定：一个任务独占状态库；时间线保持「行的事件一条没漏」的不变量，被跨过就重建；摘要不推演，订阅命中事件就失效、节流重查，一轮走完才算数；帧由网页来取，取的时候才从当前状态算，按 256 KiB 分块，所有 patch 同一套。放弃：按事件在客户端推演未读数等摘要值（第二份规则，漏一种事件就永远不对）；按区间重叠保留旧行（重叠证明不了旧行没变）；用 `Channel` 推帧再靠确认限流（确认超时照发等于没有上界；不照发也管不到 Tauri 自己的暂存，刷新不清）；只给某一种 patch 定拆分规则（别的 patch 大了就没有出路）；网页层自己持有协议实体。影响：摘要最多晚一轮重查；每帧多一次 `invoke` 往返；技术设计 3.6 第 3 条已随这个决定改写；加一种界面元素要同时动 `view.proto`、`derive` 与组件。

**ADR-T09-b 假数据走真协议，网页测试吃录像。** 背景：T04、T10 没合入前界面要先做，之后还要给界面审查与截图测试稳定的数据。决定：假后台是独立进程，经真 `iwork-ipc` 服务端；网页层的测试数据是 client-core 对着它跑出的 `ViewPatch` 录像。放弃：在 client-core 里加数据源 trait 与假实现；手写 TS 假数据。影响：多一个 crate；录像要在测试前生成；T10 汇合时有一次现成的对拍。

| 时机 | 做什么 |
| --- | --- |

### 15.5 规则（目的 + 手段；编号带 D，不和第 4 节的混）

| RD1 | 网页里的内容不能让 iWork 去碰一个它指定的本机路径（R7 的延伸：模型输出、文件名要是能在网页里变成一次调用，带路径的意图就是现成的口子） | 添加项目这一组意图都不带路径；路径只从系统选择框、拖入、后台的 `CloneFinished` 进来，只存在 client-core 的草稿里；带路径的 `add_project` 删掉并保留编号。网页只拿得到写成 `~` 的显示文字 |

叠起来推：

- RD1 + 拖入：拖入的路径是壳从系统拿的，不经网页；网页伪造不出 `Dropped`。
- RD2 + RD4：检查结果过期了也只是画错一下，点「添加」时后台照盘上现在的样子判；被拒后重查，界面回到对的。
- RD3 + 重发：`AddProject` 走在飞命令表，断线重发是同一个 `command_id`，后台幂等，草稿任务不会排两次。
