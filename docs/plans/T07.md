## 0 一页总览

T07 在 `iwork-core` 里实现技术设计第 7 节：把每次工具调用归一成动作，按七步求值得出五种结果之一，再把询问、AI 审查、拒绝记忆、作废、记住、审计串成一个有状态的引擎。方案的骨架：

1. **三层结构**：`iwork-shell`（新 crate，纯 Rust，只做 Bash 语法解析，把第三方解析器的 AST 收成我们自己的小 AST；表达不了的形态直接返回「解析不了」）→ `iwork-core::approval::{action, rules, evaluate}`（纯函数：归一、规则集、七步求值、亲手执行判定、安全清单校验）→ `iwork-core::approval::engine`（有状态：等待登记、拒绝记忆、一次性放行、AI 审查回合、作废、审计；只经端口碰外界）。路径事实（符号链接、大小写）要碰文件系统，经新端口 `iwork-ports::fs::PathResolver` 取来，归一本身是纯函数（3.1「取事实」与「纯归一」分开）。
2. **只放行能证明安全的形态，其余一律保守**（AGENTS.md 安全设计原则「只覆盖常见场景，覆盖不了就登记已知限制」）：一个 Bash 子命令只有在程序名落在一张短白名单里、参数全是字面值、没有会改变语义的选项、路径是字面的，才归为读、写或删除；否则归为执行（按档位默认）或「解析不了」（询问、不能记住、不经 AI 审查）。任何位置出现命令替换、进程替换、未加引号或双引号里的展开、可展开的 here-doc、`cd` / `pushd`、前置环境变量赋值、通配，整条调用都按「解析不了」处理，不去追踪（3.4–3.6）。
3. **组合命令保留每个子动作的约束**：任何一个子动作是必问、强制询问或解析不了，整条调用都不能自动批准、不能记住；放行路径（AI 审查、档位切换、一次性放行）答复前都要在串行约束下复查全部子动作的拒绝记忆（5.3、6.1、6.3）。
4. **规则即数据**：内置规则集 `m1-1` 的每条底线、必问、默认值、禁用工具、清单条目都是 `RuleEntry`，ID 由固定的 slug 派生，审计记 ID、版本与两个规则游标（会话快照的、活规则的）。T01 的 `RuleEntry` / `RuleMatcher` 缺三样东西（按档位生效、组合条件、按标记匹配），不补就表达不了 7.1 表与 7.2 第 5 步，也写不出带动作种类的记住规则；补法见第 14 节 Q1（已决定）。`Approval` 另加一个 `call` 字段持久化恢复所需的最小调用记录（Q8，已决定）。
5. **会话绑定启动时注入的快照**：需凭据命令、敏感目录、可写目录这些进了 CLI 设置的清单，hook 侧用的是会话启动时的同一份快照，不随规则表的变化漂移；要立即生效就重建会话（4.3、6.9）。
6. **五个遗留问题**（派活说明第 1–5 条）的结论：① 审计不加「决定人」字段，7.4 的「决定人」由 `ApprovalEvaluated.layer_hit` 与 `ApprovalDecided.decider` 两条事件合起来满足（Q2）；② 内置需凭据命令清单写到子命令一级，云服务 CLI 与 `scp` / `sftp` / `rsync` 不内置，第 9 章与全开确认框补「清单内命令不受此保护」（Q3）；③ 可写目录拒收「会被自动执行的配置」所在目录及其上级，复用 `AutorunConfig` 层条目（4.4）；④ hook 侧匹配与 `excludedCommands` 出自同一份会话快照、同一个函数生成，再用一份对拍语料在 T06 的 O1 ④ 上和真实 CLI 对照，匹配器只许比 Claude Code 更保守（3.7）；⑤ AC05 的「强制询问一次」用每个对话一份 `DenialMemory{指纹 → AutoDeny | ForceAskOnce}` 实现，拒绝时记下被拒调用的**全部**子动作指纹，用户消息把全部条目翻成 `ForceAskOnce`，命中时结果下限为询问且跳过放行规则（6.3）。

### 2.3 新端口 `iwork-ports::fs::PathResolver`

```rust
/// 把工具或命令里写的路径变成规范路径。同步：归一在 hook 的热路径上，一次调用只做几次 lstat。
pub trait PathResolver: Send + Sync {
    /// `raw` 相对 `cwd` 解析，按文件系统自己的顺序**逐个分量**处理：开头的 `~/` 展开为主目录；
    /// 每遇到一个分量，先把它接到已解析的真实前缀上，若它是符号链接就先解析链接（相对链接相对于
    /// 当前真实前缀），再处理下一个分量；`..` 作用在**已解析的真实前缀**上，不作用在文字上。
    /// 遇到第一个不存在的分量后，剩余分量原样接上（目标可能还不存在，如将要写的文件）；
    /// 不存在的尾段里再出现 `..` 或符号链接无从判断，返回 `Unresolvable`。
    /// 大小写不敏感的文件系统上，已存在的分量取磁盘上的实际大小写。
    /// 失败（权限、链接循环、非 UTF-8、`~其他用户`）返回错误，调用方按「解析不了」处理。
    /// `follow_last`：末级分量是符号链接时要不要跟随。写穿目的文件的操作（`cp`、`install`、`tee`、
    /// 重定向、Edit / Write 工具）传 `true`；替换目录项的操作（`mv`、`ln`、`rm`，末级不跟随，父路径仍解析）
    /// 传 `false`（实施审查 8/F-3）。
    /// 错误区分「目标本身解析失败」与「假设候选不成立」：`NotADirectory`（某个已存在的前缀分量是普通文件）
    /// 单独一个变体，取事实边界据此丢弃虚构的「目录 / 源名」候选而不把整条调用降成解析不了（8/F-2）。
    fn resolve(&self, cwd: &CanonicalPath, raw: &str, follow_last: bool) -> Result<CanonicalPath, PathResolveError>;
    /// 两条规范路径在这个文件系统上是否指同一处（大小写不敏感时忽略大小写）。
    fn same_path(&self, a: &CanonicalPath, b: &CanonicalPath) -> bool;
    /// `child` 是否在 `dir` 之下（含相等）；用 `same_path` 的比较规则逐分量比。
    fn is_under(&self, child: &CanonicalPath, dir: &CanonicalPath) -> bool;
}
```

「先消 `..` 再解析链接」是错的：`link/../config`（`link → .git/objects`）按文字消 `..` 得到 `config`，按文件系统得到 `.git/config`。所以顺序必须是文件系统的顺序（第 1 轮审查 F-9）。假实现 `iwork-ports/tests/fakes.rs::FakeFs{ case_insensitive: bool, symlinks: BTreeMap<PathBuf, PathBuf>, existing: BTreeSet<PathBuf> }` 按同一套顺序实现，核心的全部单元测试与 proptest 用它；真实实现在 `iwork-host::fs`，用临时目录做符号链接、`..`、链接后接 `..`、大小写、`/private` 别名五类测试（验收 5）。`CanonicalPath` 仍是 domain 已有的类型，不另造。

## 3 动作归一（技术设计 7.1）

### 3.1 输入、上下文、输出；取事实与纯归一分开

```rust
/// 第一段（有 I/O）：把调用里出现的字面路径词交给 PathResolver，拿回规范路径或「解析不了」。
pub fn gather_path_facts(req: &PermissionRequest, cwd: &CanonicalPath, fs: &impl PathResolver) -> PathFacts;
/// 每个要解析的路径带两样元信息：是「真实目标」还是「假设候选」（目录目标语义虚构出来的「目录 / 源名」，3.4），
/// 以及末级要不要跟随链接（写穿 / 替换目录项，3.4）。真实目标解析失败 → 整条 Unparsable；假设候选遇到

pub enum PathOrigin { Real, Hypothetical }
pub struct PathQuery { pub literal: String, pub origin: PathOrigin, pub follow_last: bool }
pub struct PathFacts { resolved: BTreeMap<PathQuery, Result<CanonicalPath, PathResolveError>> }

/// 第二段（纯）：归类。只认 `facts` 里给出的事实，不碰文件系统、不读时钟。
pub fn normalize(req: &PermissionRequest, ctx: &NormalizeContext, facts: &PathFacts) -> NormalizedCall;

    pub paths: &'a EnvPaths,          // workspace_root、home、data_dir、iwork_root、tmp_dirs、dm_private_dir、platform

}
pub enum CallShape {
    /// 非 Bash 工具：一个动作
    Tool,
    /// 恰好一个简单命令（允许字面重定向与引号界定符的 here-doc；不允许管道、&&、;、子 shell、任何展开）
    SingleSimpleCommand { command_text: String },
    /// 多个简单命令，且每个都归类成功
    Compound,
    /// 解析失败、含任何展开 / 通配 / cd / 前置赋值、或含小 AST 表达不了的形态（3.6）

pub struct NormalizedCall {
    pub actions: Vec<Action>,         // 每个子命令一个执行动作 + 每个路径参数、重定向目标各一个路径动作；Tool 形状恰好一个
    pub shape: CallShape,
    pub placement: SandboxPlacement,  // Inside | Outside | Ambiguous（3.7；Bash 以外恒为 Inside）

    pub description: Option<String>,  // Bash 的 description，亲手执行卡片的「理由」
```

`gather_path_facts` 先用 `iwork-shell::parse` 找出全部**字面**路径词（3.5 的定义），逐个 `resolve`：归类成功的调用送 `ArgSpec` / `PathOptions` 切出的路径；`Unparsable` 调用送 3.6 兜底规则的全部候选；含非字面内容的词不送去解析（它们会让整条调用 `Unparsable`）。两段分开的原因：归一要进 proptest，而符号链接与大小写是磁盘上的事实，只能取来当输入。引擎里两段连着调（6.1）。

`PermissionRequest.raw_input` 是运行时给的 JSON 文本，字段名随工具而定，登记在 `action/tool_input.rs` 的表里（Read / Write / Edit 的 `file_path`、NotebookEdit 的 `notebook_path`、Grep / Glob 的 `path`、Bash 的 `command` / `description` / `dangerouslyDisableSandbox`、WebFetch 的 `url`）；**字段名以 T06 从 2.1.319 导出的清单为准**（第 12 节需实测 ①）。取不到必要字段（比如 Bash 没有 `command`）→ `Unparsable`。`Action.tool` 原样记工具名（只进审计），`bypass_sandbox_requested = req.bypass_sandbox || tool_input.dangerouslyDisableSandbox == true`（Claude 的清单外重试与 agy 的 `BypassSandbox` 都走这个标记，t0-findings 第 4 节）。

### 3.3 Bash 解析器选型与 `iwork-shell` 的小 AST

| 候选 | 许可 | 维护 | 语法覆盖 | 纯 Rust | 结论 |
| --- | --- | --- | --- | --- | --- |
| `brush-parser` 0.4.0 | MIT | 活跃（2026-05 发版，brush shell 的解析器，89 万次下载） | 完整 bash：管道、`&&`/`||`/`;`/`&`、子 shell、花括号组、函数、here-doc、here-string、进程替换、数组、`[[ ]]`、算术；词保持**未展开**的原文，正合我们只看文字、不执行的需要 | 是（`peg`），MSRV 1.88 | **选它**。隔离在 `iwork-shell` 里 |
| `tree-sitter-bash` 0.25 | MIT | 活跃 | 完整，但**容错解析**：错误输入也产出带 `ERROR` 节点的树，「解析不了一律询问」要靠遍历找错误节点，容易漏 | 否（C 语法库 + `tree-sitter` 运行时，`cc` 构建） | 不选：容错是反需求，且带 C 构建进 CI 三平台 |
| `yash-syntax` 0.25 | **GPL-3.0-or-later** | 活跃 | POSIX 为主 | 是 | 不选：许可不在 `deny.toml` 白名单，CI 会红 |
| `conch-parser` 0.1.1 | MIT / Apache-2.0 | **2019 年起无更新** | POSIX + 部分 bash | 是 | 不选：无人维护，安全关键路径不能押在上面 |
| 自写解析器 | — | — | 只能覆盖子集 | 是 | 不选：bash 引号、here-doc、展开规则的边角正是攻击面，自写等于重新踩一遍坑 |

`iwork-shell` 的 AST 只保留求值要的东西，`brush-parser` 的类型不外露。**包装层的原则：小 AST 表达不了的节点，转换直接返回 `Unparsable`，不能丢掉字段后算作解析成功**（第 1 轮审查 F-7）。

```rust
pub struct ShellScript { pub items: Vec<ListItem> }
pub struct ListItem { pub pipeline: Vec<CommandNode>, pub negated: bool, pub connector: Option<Connector> /* And | Or | Seq | Async */ }
pub enum CommandNode {
    Simple(SimpleCommand),
    /// 子 shell 与花括号组：只接受**没有重定向**的；带重定向的整条 Unparsable
    Subshell(ShellScript), BraceGroup(ShellScript),
    /// if / while / until：条件与各分支都是 ShellScript，全部展平进求值；带重定向的整条 Unparsable
    If { branches: Vec<ShellScript> }, Loop { condition: ShellScript, body: ShellScript },
}
pub struct SimpleCommand { pub words: Vec<Word>, pub redirects: Vec<Redirect> }   // 前置赋值词不在这里：出现即 Unparsable
pub struct Word { pub raw: String, pub literal: Option<String> }  // literal = Some 当且仅当整个词只由裸字面、单引号、双引号内无任何展开的内容组成
pub struct Redirect { pub kind: RedirectKind /* Read | Write | Append | Clobber | ReadWrite */, pub fd: Option<u32>, pub target: Word }
/// 放弃转换之前已经可靠识别出来的字面事实（第 2 轮复审 2/F-2）。
pub struct PartialFacts {
    pub literal_redirects: Vec<(RedirectKind, String)>,  // 任何节点（含复合命令、函数体）上的字面重定向目标
    pub literal_words: Vec<String>,                      // 全部简单命令里的字面词
}
pub struct Unparsable { pub why: String, pub facts: PartialFacts }
pub fn parse(text: &str) -> Result<ShellScript, Unparsable>
```

`parse` 分两遍：第一遍遍历 `brush-parser` 的**完整** AST（不管节点支不支持），收集所有字面重定向目标与字面词，并且**递归进入命令替换（`$(…)`、反引号）、进程替换与可展开 here-doc 正文里的命令替换**：替换体是另一段 shell 文字，对它再跑同一遍收集——用显式工作队列迭代，不递归，所以**没有深度上限**，10 层嵌套的 `echo $(… $(printf x > .git/config) …)` 照样收到 `(Write, ".git/config")`；唯一的资源上限是**处理过的 shell 文字总字节数 ≤ 256 KiB**（原文 + 全部替换体），命中上限时**不能**退成「空事实 + 普通询问」：第一遍立即停止，`PartialFacts.resource_limit = true`，归一给承载命令文字的执行动作打 `ActionFlag::ResourceLimitHit`，命中 4.2 的内置条目 `toolconfig.resource-limit`（`ToolConfig` 层，效果 `Deny`，三档相同）→ `Deny(DenyRule(id))`，不出卡片、不能被批准；已收集到的事实也照常进路径动作（底线更先判）。`ActionFlag` 因此多一个变体 `ResourceLimitHit`（Q1 的 additive 包里再加一个值，实施审查 8/F-1）。里面的字面重定向与字面词一样进 `PartialFacts`（实施审查 1/F-6）——整条调用因为含替换仍是 `Unparsable`，但 `echo $(printf x > .git/config)` 的 `(Write, ".git/config")` 不会丢，归一后命中 `.git` 底线 → `Deny(Baseline)`，而不是可批准的询问。第二遍转换成小 AST，遇到不支持的节点返回 `Unparsable{why, facts: 第一遍的结果}`。第一遍只认字面值（`Word.literal = Some`），含展开的词本身不收（它内部的替换体已递归收过）。这样 `{ printf x; } > .git/iwork-marker` 虽然因「复合命令重定向」解析不了，`facts.literal_redirects` 里仍有 `(Write, ".git/iwork-marker")`，归一照常抽成 `Write` 动作过底线（3.6）。测试 `partial_facts_survive_unparsable`：对每种不支持形态各一例，断言 `facts` 含其字面重定向与字面词。

转换时直接返回 `Unparsable{why, facts}` 的形态（每种一条测试，`shell_unparsable_forms`）：`for` / `select`（值列表要展开）、`case`（选择词要展开）、函数定义（定义体与调用点分离）、复合命令上的重定向、协进程、算术命令、`[[ ]]` 以外的测试命令带展开、时间统计 `time`、任何词里的 `$var` / `${…}` / `$(…)` / 反引号 / `$((…))` / 进程替换 / 波浪展开 `~user`（`~/` 开头允许，由 `PathResolver` 展开）/ 未加引号的通配 `*` `?` `[…]` 与花括号展开、here-doc 界定符没加引号（内容会展开）、here-string、`&>` 以外的 fd 复制重定向（`>&2` 允许，它没有文件目标）、`$'…'` 以外的 ANSI 引用、未知的 `brush-parser` 节点。**可以**表达的：字面词、单引号、不含展开的双引号、`~/` 开头的路径、字面重定向、`<<'EOF'` 这类引号界定的 here-doc（内容不展开，不产生动作）。

`parse` 是纯函数；`brush-parser` 的 `cached` 缓存不用（调 `uncached_tokenize_str`），避免全局状态。

### 3.4 子命令归类：白名单与保守默认（第 1 轮审查总体方向；F-6、F-8、F-10、F-11、F-12、F-13）

**原则**：只有能证明安全的形态才归为读、写或删除；其余归为执行（按档位默认求值，手动问、自动放行），或整条调用 `Unparsable`。证明安全的条件（四条同时成立）：① 程序名（第一个词，必须是字面值、不带路径前缀）在 `SafeCommands` 白名单里；② 该命令的全部词都是字面值（`Word.literal = Some`）；③ 没有出现该程序「危险选项」表里的选项（短选项合并形式如 `-rf` 逐字母拆开比；`--opt=value` 与 `--opt value` 两种写法都认）；④ 路径参数是字面的（③ 的推论，另外排除 `-` 代表标准输入这类特殊值）。不满足 ① 但其余成立 → `Execute`；不满足 ②（词里有展开或通配）→ 整条调用 `Unparsable`。

**整条调用 `Unparsable` 的触发**（任何一个子命令出现即整条，不去追踪它对别的子命令的影响）：3.3 列出的全部形态；`cd` / `pushd` / `popd`（之后的相对路径无从解析）；前置环境变量赋值（`GIT_SSH=… git pull`、`PATH=… cmd`，会改变程序行为与查找）；包装词 `command`、`exec`、`nohup`、`time`、`nice`、`env`、`xargs`、`sudo`、`doas`、`su`（以别的身份或别的方式执行）；`eval`、`source`、`.`、`bash -c` / `sh -c` / `zsh -c` 等 `-c` 形式、`python -c`、`node -e`、`perl -e`、`ruby -e`（程序文本来自参数）；程序名带路径前缀且不在白名单（`./build.sh` 是 `Execute`，见下）。

**参数规则：一份 `ArgSpec`，白名单程序与表外程序共用**（第 2 轮复审 1/F-11、1/F-12）。每个登记过的程序有一张 `ArgSpec`：

```rust
pub struct ArgSpec {
    pub options: &'static [OptSpec],          // 允许出现的选项；不在表里的任何选项 → 不是安全形态
    pub operands: OperandRoles,               // 位置参数的角色：AllRead | AllWrite | AllDelete | SourcesThenDest | Exact(&[Role]) | None
    pub max_operands: Option<usize>,          // 超出 → 不是安全形态
}
pub struct OptSpec { pub short: Option<char>, pub long: Option<&'static str>, pub value: OptValue }
pub enum OptValue { None, Pattern, Number, Path(Role), Dir(Role), Word }   // Role: Read | Write | Delete
```

选项的四种形态都认：`-o VALUE`、`-oVALUE`（短选项粘值，只对登记了取值的短选项）、`--opt VALUE`、`--opt=VALUE`；合并短选项 `-rf` 逐字母拆开，拆开后任一字母登记为取值的，后面的字符就是值；`--` 之后全部是位置参数（以 `-` 开头的文件名也算）。`OptValue::Path(Role)` / `Dir(Role)` 的值抽成对应角色的路径动作。

- **白名单程序**：出现 `options` 之外的任何选项（含未知长选项、未知短字母），或位置参数个数、角色对不上 `operands` → **不是安全形态 → 归 `Execute`**。未知选项可能取值、可能改语义，不猜。**降级只能更严，不能丢已知约束**（实施审查 1/F-1）：每个 `ArgSpec` 另登记一组 **保底角色** `floor: FloorRoles`。**标准**（实施审查 8/F-4）：保底角色是「这个程序在**任何**选项组合下可能对位置操作数做的最重的事」，不是安全形态下的角色；登记时逐个程序问「有没有哪个选项能让位置操作数被写或被删」。结果：`rm` / `rmdir` / `unlink` / `shred` → 全部 `Delete`；`cp` / `install` / `ln` → 源 `Read`、目的 `Write`（`install -d` 时全部 `Write`）；`mv` → 源 `Read` + `Delete`、目的 `Write`；`touch` / `mkdir` / `truncate` / `chmod` / `chown` / `chgrp` / `tee` → 全部 `Write`；**`find` → 起点目录 `Read` + `Write` + `Delete`**（`-delete`、`-exec rm`、`-fprint` 都作用在起点之下）；**`uniq` → 全部 `Read` + `Write`**（第二个操作数是输出文件）；`cat` / `head` / `tail` / `wc` / `stat` / 校验和 / `od` / `strings` / `cmp` / `diff` / `ls` / `du` / `readlink` / `realpath` / `basename` / `dirname` / `cut` / `tr` / `nl` / `tac` / `rev` / `column` / `fold` / `fmt` / `expand` / `unexpand` / `grep` / `rg` / `sort` / `comm` / `join` / `paste` → 全部 `Read`（它们写文件只经选项值，如 `sort -o`，选项值由 `fallback_candidates` 记 `Read` + `Write` 覆盖）；`dd` → 有 `if=` / `of=` 的按其角色。登记表每行的保底角色在 `safe_commands_corpus` 里各有一条「带未登记选项仍保留保底角色」的用例。降级时：结果归 `Execute`，**同时**产出保底角色的路径动作（与正常归类产出的路径动作同形，不标成「仅从参数抽出的候选」），再叠加 `fallback_candidates` 的 `Read` + `Write` 候选（3.6 同一个函数）。于是 `rm --recursive --force <工作区根>` 是 `Execute` + `Delete(workspace_root)` → 关键路径底线拒；`rm --no-preserve-root a` 是 `Execute` + `Delete(a)` → 必问（手动、自动问，不是放行）。保底角色给不出的程序（白名单里目前没有；以后加的程序若连操作数的最低角色都说不清，不进白名单）整条 `Unparsable`。
- **表外程序**（不在白名单，归 `Execute`）：位置参数（不以 `-` 开头的字面词，以及 `--` 之后的全部字面词）一律抽成 `Read` + `Write` 路径动作；位置参数形如 `name=value`（`make OUT=.git/x`、`LC_ALL=C` 以外的程序内赋值）时**整词与第一个 `=` 之后的值都抽**（用 3.6 的 `paths::split_assignment`，一处真值；值里再有 `=` 原样保留），都记 `Read` + `Write`；`--opt=VALUE` 的 `VALUE` 同样抽成 `Read` + `Write`；`-o VALUE` 形式里的 `VALUE` 是独立的字面词，已按位置参数抽取。白名单程序里登记了 `key=` 角色的（`dd` 的 `if=` / `of=`）继续用精确角色，不走这条。**短选项粘值**（`-oVALUE`）只按**登记**处理（第 4 轮，1/F-12）：表外程序也可以在 `registry.rs` 登记一张只含路径角色选项的 `PathOptions`（不进白名单，只告诉参数规则「这个短选项取值、值是什么角色」），粘值与分开写的值都按登记角色抽路径动作；**没登记的短选项带粘值的组合一律整条 `Unparsable`**，不看值里有没有 `/`、`~`、`.`——`-Elog` 的 `log` 是写目标、`-Ffile` 是读目标，只凭字符判断不了角色，相对名字也可能经 `cwd` 指到敏感处。M1 登记的 `PathOptions`：`ssh`：`-E Path(Write)`（调试日志）、`-F Path(Read)`（配置）、`-i Path(Read)`（身份文件）；`curl`：`-o Path(Write)`、`-K Path(Read)`；`wget`：`-O Path(Write)`、`-i Path(Read)`。加一个程序 = 加一行。

**`SafeCommands` 白名单**（`registry.rs`；加一个程序 = 加一行 `ArgSpec`，连同选项表一起审；`xxd`、`less`、`more`、`file`、`tree` 已移出：`xxd` 双操作数时第二个是输出文件且 `-r` 反向写入，`less` / `more` 可交互执行命令，`file -C` 编译 magic 文件会写，`tree -o` 写文件——它们一律 `Execute`）：

**目录目标语义**（`SourcesThenDest` 的程序：`cp`、`install`、`mv`、`ln`；实施审查 1/F-7）：目的可能是目录，真正写入的是「目录 / 源文件名」，而 `./config` 可能是指向 `.git/config` 的链接，只检查目录本身拦不住 `cp src/config .`。归一对每个源 `s` 与目的 `d` **同时**产出两个路径查询：`Write(d)`（`PathOrigin::Real`）与 `Write(d / basename(s))`（`PathOrigin::Hypothetical`，3.1），每个都送 `PathResolver` 解析（链接在这一步显形）；`-t D` / `--target-directory=D` 同样对每个源产出 `Write(D)`（真实）与 `Write(D / basename(s))`（假设）；`-T`（明确不是目录目标）只产出 `Write(d)`；`mv` 的两个候选都还带源的 `Read` + `Delete`。保底角色（上面）里的目的 `Write` 也按这条展开。

- **目的是已存在的普通文件时**（实施审查 8/F-2）：假设候选 `d / basename(s)` 在取事实边界解析出 `NotADirectory`，这是「假设不成立」不是「目标解析失败」，**丢掉该候选即可**，不把整条调用降成 `Unparsable`；真实目标 `Write(d)` 照常。于是 `cp a existing.txt` 是普通的工作区写（手动问、自动放行），`cp src/config .git/config` 单条命令是 `Write(.git/config)` 底线命中 → 亲手执行卡片照常生成（5.4 的形状仍是单个简单命令）。真实目标自己解析失败（`Unresolvable`、权限）仍按 3.5 整条 `Unparsable`。
- **写穿与替换目录项**（实施审查 8/F-3）：登记表给每个写类操作标 `WriteMode`：**`Through`**（写穿目的文件，末级跟随链接）——`cp`、`install`、`tee`、`touch`、`truncate`、`chmod` / `chown` / `chgrp`（跟随）、重定向、Edit / Write 工具；**`ReplaceEntry`**（替换或删除目录项，末级**不**跟随，父路径仍逐分量解析）——`mv` 的目的、`ln` 的链接位置、`rm` / `rmdir` / `unlink` 的目标。`ReplaceEntry` 的查询以 `follow_last = false` 送 `PathResolver`（2.3）。于是 `cp src/config .`（`./config` 链接到 `.git/config`）→ 假设候选跟随链接解析到 `.git/config` → 底线拒；`mv src/config .` 与 `ln -sf src/config config` 只替换 `<工作区>/config` 这个目录项，解析结果不在 `.git` 下 → 普通工作区写，不误拒；`mv src/config .git/config` 的父路径 `.git` 仍解析 → 底线拒。`rm config`（链接指向 `.git/config`）删的是链接本身 → `Delete(<工作区>/config)`，必问而不是底线。

**路径动作总是抽取**（F-12）：不论子命令归为什么，它的每个**字面**路径词（判断规则在 3.5，提取规则在上面的 `ArgSpec` 段）都抽成一个路径动作：重定向 `>`、`>>`、`>|`、`&>` 的目标 → `Write`；`<` → `Read`；白名单程序按 `ArgSpec` 的角色；`Execute` / `Publish` 类程序的字面路径词 → 既记 `Read` 又记 `Write`（不知道它会读还是写，两种都要过底线与越界）；`Unparsable` 调用的 `PartialFacts`（3.3）里的字面重定向按其 `RedirectKind`、字面词按 `Read` + `Write` 抽取。沙箱外执行（3.7）只是整条调用的一个**约束**，改变的是执行动作的种类，**不替换、不删除任何路径动作**：`rsync ~/.netrc ./copy` 产出 `Execute(rsync…)`（清单内时为 `OutsideSandbox`）+ `Read(~/.netrc)` + `Write(~/.netrc)` + `Read(./copy)` + `Write(./copy)`，`Read(~/.netrc)` 命中底线 → 整条拒绝。

### 3.5 路径词的字面性与规范化（验收 5、4a「经符号链接或 `..` 指向凭据目录的同样拒绝」）

- **字面路径词**：`Word.literal = Some(s)` 且 `s` 不是 `-`、不是纯选项；`~/` 开头、`/` 开头或相对路径都算。含任何展开或通配的词不是字面词——而且它的出现已经让整条调用 `Unparsable`（3.6），所以归一只会见到字面词。
- 每个字面路径词经 `PathResolver::resolve(cwd, raw)`（顺序见 2.3）。得到的 `CanonicalPath` 进 `ActionTarget`，所以 `ActionFingerprint` 比较的是同一处文件的同一种写法（AC05「换工具同一动作」）。
- `PathUnder` / `PathIs` 的比较全部经 `PathResolver::is_under` / `same_path`，不用 `Path::starts_with`——否则大小写变体与别名的测试过不了。
- 解析失败（`Unresolvable`、权限、循环）：整条调用 `Unparsable{why: "路径无法解析：<词>"}`，不猜。
- 相对路径只相对 hook 给的 `cwd`；`cd` 已经让整条调用 `Unparsable`，所以不存在「cd 之后的 cwd」。

### 3.6 整条调用按「解析不了」处理的情形与结果（技术设计 7.1「解析不了的命令一律询问」；F-6、F-8、F-10、F-11）

触发清单在 3.3（AST 表达不了）与 3.4（`cd`、前置赋值、包装词、`-c` 形式、展开、通配、未登记的粘值、解析失败）。`shape = Unparsable{why}`。路径动作的来源只有两处，字面重定向与字面词都是**扁平**的，不带参数结构：`parse` 本身放弃的，用 `Unparsable.facts`（`PartialFacts`，3.3）；`parse` 成功但归类阶段放弃的，用小 AST 里全部简单命令的字面重定向与字面词。两处读的都是词的 **`literal`**（去掉引号与转义之后的字面值，3.3 的 `Word.literal`），不是 `raw`：`-E".git/config"`、`"-E.git/config"`、`-E.git/con\fig`、`of=".git/config"`、`"of=.git/config"` 都先变成 `-E.git/config` / `of=.git/config` 再抽。两处都经**同一个**兜底函数 `paths::fallback_candidates(literal) -> BTreeSet<String>` 抽路径（第 6 轮根因修法；第 7 轮按 6/F-1、6/F-2 修正）：

| 规则（按顺序累加，最后去重） | 追加的候选（每个都记 `Read` + `Write`） | 例 |
| --- | --- | --- |
| **完整字面值恒为候选**（不管以什么开头） | 整词 | `host` → `host`；`-out` → `-out`（真实文件名就叫 `-out`）；`--out=value` → `--out=value` |
| `--opt=值` | 再追加第一个 `=` 之后的非空部分 | `--log=.git/x` → 加 `.git/x` |
| `name=值`（不以 `-` 开头、含 `=`、`=` 前非空） | 再追加第一个 `=` 之后的非空部分；值里再有 `=` 原样保留，不猜嵌套 | `of=.git/config` → 加 `.git/config`；`OUT=.git/x` → 加 `.git/x`；`A=b=c` → 加 `b=c` |
| `-X值`（单个 `-` 开头、长度 ≥ 3） | 再追加**每一个**可能的切分位置之后的剩余部分：去掉 `-` 后，对 k = 1..len-1 取 `rest[k..]`。组合短选项 `-vE.git/config` 得到 `E.git/config`、`.git/config`、`git/config`、… 全部候选；不查登记表、不猜哪个字母取值 | `-E.git/config` → 加 `.git/config`、`git/config`、…；`-p2222` → 加 `2222`、`222`、`22`、`2` |
| 重定向目标 | **真实目标**（整个 `literal`）按重定向种类记（`>` / `>>` → `Write`，`<` → `Read`）；目标词再按上面各行追加的候选记 `Read` + `Write` | `> .git/x` → `Write(.git/x)`；`> -out`（`-out` 预先链接到 `.git/config`）→ `Write(-out)` → 解析到 `.git/config` → 底线拒 |

`--` 之后的位置参数（以 `-` 开头的文件名）已被第一行覆盖：`rm -- -rf` 的 `-rf` 整词是候选。表外程序归类成功时的位置参数拆词（3.4）用**同一个助手**里的 `name=value` 规则（`paths::split_assignment(literal) -> Option<&str>`），已登记选项（`dd` 的 `if=` / `of=`、`PathOptions`）继续用精确角色——一处真值，两种路径只是「精确角色」与「Read + Write」的差别。

宁可多抽：候选里多数是无意义的相对名字（`git/config`、`2222`），它们只有**恰好解析到受保护路径**（凭据目录、数据目录、`.git/`、关键路径）时才会让结果从询问变成拒绝；其余候选只是多几个越界 / 工作区内的路径动作，对 `Unparsable` 的结果（本来就是询问）没有影响。误报范围写进已知限制（第 13 节）：`Unparsable` 调用里某个选项粘值的后缀、或 `name=值` 的值（含归类成功的表外程序，如 `make OUT=.git/x`）恰好解析到受保护路径时会被拒绝而不是询问，这是刻意的保守。例：`git -c core.hooksPath=.git/hooks rev-parse …` 拒绝（单个简单命令可走亲手执行）；`env GIT_DIR=.git git rev-parse …` 因 `env` 包装整条 `Unparsable`，三档拒绝且不出亲手执行卡片，改用不带包装的 `git rev-parse` 或由用户自行执行（第 7 轮复审补充说明）。另加一个 `Execute` 动作承载整条命令文字（目标 `Command{program: 第一个字面词或 "?", subcommand: None, argv: []}`，只用于审计与卡片）。`gather_path_facts`（3.1）对 `Unparsable` 调用把全部候选都送去 `PathResolver`（解析失败的候选丢掉，不影响别的候选）；对归类成功的调用只送 `ArgSpec` / `PathOptions` 切出的路径。

结果（5.2）：步骤 1–5 对抽出的路径动作与执行动作照走：`{ printf x; } > .git/iwork-marker` 因复合命令重定向解析不了，但 `PartialFacts` 里有 `(Write, ".git/iwork-marker")`，抽成 `Write` 命中 `.git` 底线 → **整条 `Deny`**（不是普通询问，用户允许不了）；`eval "cat ~/.ssh/id_rsa"` 里 `~/.ssh/id_rsa` 是字面词 → 底线拒绝；`ssh -v -E.git/config -p2222 host`、`LC_ALL=C ssh -v -E.git/config host`（前置赋值，`parse` 放弃）、`ssh -v -E.git/config host; echo "$UNUSED"`（同行别处有展开，`parse` 放弃）三条都是 `Unparsable`，兜底规则从 `-E.git/config` 抽出候选 `.git/config` → `Write` 命中 `.git` 底线 → **整条 `Deny(Baseline)`**，不是普通询问；`-p`、`LC_ALL`、`$UNUSED` 都不需要被理解。第 6 步跳过（放行规则对它无效）；第 7 步 `Ask(UnparsableCommand)`，**三档相同**（Q4 已定，产品负责人 2026-11-10）；不经 AI 审查（审查员同样看不出它会做什么）；只能允许一次，不能记住。

必须进用例的反例（每条断言 `shape == Unparsable` 且结果不是 `Allow`，`bash_corpus.rs`）：`echo $(git push)`、`grep "$(git push)" file`、`cat <<EOF … EOF`（未加引号的 here-doc）、`{ printf x; } > .git/iwork-marker`（断言结果是 **`Deny(Baseline)`**，测试名 `unparsable_keeps_literal_redirect_facts`；同组还有 `for f in $(ls); do :; done > .git/x`、`f() { :; } > .git/x` 两条）、`for x in $(git push); do :; done`、`cd .git && touch iwork-marker`、`touch .g*/config`、`cat ~/Doc*/private.txt`、`GIT_SSH=x git pull`、`env git pull`、`sudo rm -rf /`（`sudo` → `Unparsable`，且 `/` 字面词按 `Read`+`Write` 不撞删除底线；它是询问而不是放行，拒绝记忆与必问照常生效）。危险选项的用例（`shape` 不是 `Unparsable`，但归 `Execute` 而不是 `Read`）：`find . -delete`、`find . -exec rm {} \;`、`sort -o out in`、`awk '{print > "x"}' f`（`awk` 不在白名单）。

代价：自动档下带 `$VAR` 的日常命令会多问（`echo $HOME`、`npm run $TASK`）。这是有意的取舍：文字层面判断不了展开结果，问比猜安全；登记为本方案的已知限制（第 13 节）。

### 3.7 需凭据命令匹配：hook 侧与 `excludedCommands` 用同一份会话快照、同一套规则（派活说明第 4 条；F-5）

**目的**：审批以为命令在沙箱内（`Execute`，自动档放行）而 Claude Code 实际把它排除出沙箱跑了，这是唯一会让「沙箱外执行」绕过审批的路径。反过来（我们判沙箱外、Claude 实际沙箱内）只是多问一次。

**手段**：

1. **一份数据，且是会话启动时的那一份**：会话启动时 `session::snapshot_for(mode, rules, scope, env)` 算出 `SessionSnapshot{ constraints, boundaries, ruleset_version, lists_seq }`（6.9），T06 把 `constraints.excluded_commands` 翻成文字写入 `--settings`，并把这份快照原样放进 `SessionKeys.snapshot` 交给引擎。求值用的匹配器 `credential::classify(script, &snapshot.constraints.excluded_commands)` 吃**同一个** `Vec<CommandPattern>`。规则表后来怎么变，运行中的 CLI 还在用注入时的清单，hook 也必须用它；用户加删清单条目后要立即生效，由调用方停掉并重建会话（6.9），不能只更新一侧。T06 把 `CommandPattern{program, subcommand}` 翻成文字 `"<program> *"` / `"<program> <subcommand> *"`（Claude 文档：没有通配符是精确匹配，`docker *` 匹配带或不带参数的 `docker`）。T06 以外没有第二处生成清单文字。
2. **一套规则**（按 Claude Code 文档「Sandbox settings › excludedCommands」）：整条调用里**每一个**简单命令都要命中某个条目；有重定向、`cd`、`$(...)` 的整条留在沙箱内；匹配的是调用文字，`/usr/local/bin/docker` 与 `make` 里间接调用的 `docker` 都不算。
3. **只许更保守**：`classify` 返回三态 `Inside | Outside | Ambiguous`，`Ambiguous` 在求值里**按 `Outside` 处理**（技术设计 7.1「两边结果可能不一致时一律按沙箱外执行求值」）。判 `Ambiguous` 的情形：程序名带路径前缀（`/usr/bin/git pull`，文档说不匹配，但我们不赌）；子命令前有以 `-` 开头的词（`git -c x=y pull`：`-c` 后的 `pull` 是不是子命令，文档没说）；含重定向但每个命令都命中条目（文档说留在沙箱内，我们记 `Ambiguous` 保险）。前置赋值、包装词、`cd`、`$()` 已是 `Unparsable`，不到这里。只有「每个简单命令的首词精确等于条目程序名、第二词精确等于条目子命令（或条目无子命令）、没有上述任何干扰」才是 `Outside`；任何一个简单命令不命中任何条目且没有干扰才是 `Inside`。
4. **对拍语料**：`crates/iwork-core/tests/credential_corpus.rs` 里一张表 `(命令文字, 清单, 我们的结果, Claude 实测结果)`，至少 40 条，覆盖上面每一种边界各正反两例。T06 的 O1 ④ 实测脚本用同一张表（从同一个 Rust 常量导出 JSON）对固定版本的真实 CLI 跑，把第四列填回来。测试断言：**Claude 为 Outside 的每一行，我们必须是 Outside 或 Ambiguous**；我们为 Inside 的每一行，Claude 必须是 Inside。第四列填不上的行标 `untested`，CI 跳过但报告里列出。

**出事场景 N2（Claude Code 升级后 `excludedCommands` 匹配规则变了）**：某种写法 Claude 新版排除出沙箱而我们判 `Inside`。止血：固定版本（FR17）——版本变化先重跑对拍语料，红了就把对应形态加进 `Ambiguous` 判定（宁可多问），再放行新版本。由什么保证：对拍语料进 CI；版本登记（T05）阻断未验证版本。

**出事场景 N4（用户删了清单条目，会话还在跑）**：旧会话的 CLI 仍把 `git pull` 排除出沙箱；若 hook 用新规则表判它为普通 `Execute`，自动档就放行了一条沙箱外命令。手段：hook 用 `SessionKeys.snapshot`，与 CLI 注入的是同一份，所以仍判 `Outside`；新会话才用新清单。由什么保证：`snapshot_pins_excluded_commands`（会话中删条目 → 仍 `Outside`；重建会话 → `Inside`）；`rebuild_session_needed` 的测试。

### 3.8 越界与标记（需求 FR11、v1.51；技术设计 7.2 第 3 步）

`Boundaries::from_snapshot(snapshot, scope)` 抽出：敏感目录（`SensitiveDirs` 层，内置 + 用户，含「iWork 登记的其他项目目录与其他助手的私聊目录」——这两组由 daemon 组装 `EnvPaths.other_project_roots` / `other_dm_dirs` 时转成临时条目，不入库）、可写目录（`WritableDirs`）、可写缓存（`WritableCache`）、自动执行配置（`AutorunConfig`）、需凭据命令（`CredentialCommands`）。全部来自会话快照（4.3）。

- `Write` / `Delete` / `WriteAutorunConfig`：目标不在 {`workspace_root`、`tmp_dirs`、可写缓存、可写目录、私聊私有目录（私聊时）} 之下 → `out_of_bounds = true`。
- `Read`：目标在某个敏感目录之下、且不在 `workspace_root` 之下 → `out_of_bounds = true`（「自己的工作区即使位于清单目录之内也照常可读」）。工作区外的其他读不算越界。数据目录的只读区读不算越界（它由底线层的只读区条目放行）。
- `bypass_sandbox_requested = true` → 执行动作 `out_of_bounds = true`（t0-findings 第 4 节：agy 的 `BypassSandbox`；Claude 的清单外重试同理）。
- `Network` 永不越界（需求 v1.38）。
- **沙箱外执行是整条 Bash 调用的约束，不是某一种动作的属性**（实施审查 1/F-2）：`placement ∈ {Outside, Ambiguous}` 或 `bypass_sandbox_requested` 时，对调用里的**每个简单命令**：已有 `Execute` 种类的子动作 → 改为 `OutsideSandbox`（目标仍是 `Command{…}`）；**没有**执行类动作的（白名单读 / 写 / 删除、纯重定向、`Push` / `Publish` / `Delete` / `WriteAutorunConfig` 这些保留了具体种类的命令）→ **额外加一个** `OutsideSandbox` 动作承载该命令（目标 `Command{program, subcommand, argv}`），原有的路径动作与具体种类动作一个都不动、不改。于是 `cat src/a.rs` 带 `bypass_sandbox_requested` 产出 `Read(src/a.rs)` + `OutsideSandbox(Command{cat…}, bypass)`：手动、自动档按清单外重试问（原因 `OutOfBounds`），全开档 `Deny`（4.2 `default.outside.retry.full`），不再因为「只有一个 Read」被放行；`git push` 既在清单内又是必问：`Push` 保留，另有 `OutsideSandbox(Command{git push…})`，三档都问，`Approval.kind = OutsideSandbox`。清单内与否另由引擎决定 `Approval.kind` 与卡片文案（6.2）。带 `bypass_sandbox_requested` 的 Bash 重试：这些 `OutsideSandbox` 动作 `out_of_bounds = true`，这就是「清单外重试」。

### 3.9 指纹（AC05）

`Action::fingerprint()` 已由 T01 定义：`kind + 归一后的 target`。本方案保证送进去的 `target` 已经规范：路径是 `CanonicalPath`；命令是 `Command{program（字面、不带路径前缀）, subcommand, argv（全部词的字面值，引号已去除）}`。于是 `Write a.txt`（Edit）与 `echo > a.txt`（重定向）都产出 `Write(Path(a.txt))`，指纹相同（验收 3）；`npm test` 与 `npm test --watch` 指纹**不同**（参数不同）——这符合 AC05「动作类型 + 目标」，记住规则才按程序名 + 子命令放宽（6.4）。一条调用的**指纹集合** `call.fingerprints()` = 全部子动作指纹去重后的 `BTreeSet`，拒绝记忆（6.3）与一次性放行（6.2）都按集合工作。

## 4 规则（需求第 9 章「安全规则的组织」；技术设计 7.2c）

### 4.1 层、条目与 T01 类型要补的三处（→ Q1）

T01 的 `RuleEntry{id, layer, matcher, effect, source, scope, created_at, label}` 能表达底线路径、清单、按程序名的记住规则，但表达不了技术设计 7.1 表与 7.2 第 5 步里的三件事，也写不出带动作种类的记住规则（第 1 轮审查 F-14）：

| 要表达的 | 例子 | 缺什么 |
| --- | --- | --- |
| 条目只在某些档位生效 | 必问层的「删除」只在手动、自动档必问，全开放行；默认层每种动作三档结果不同 | `RuleEntry` 没有档位字段 |
| 一条条目同时限定种类与路径 / 程序 / 标记 | 「写 `.git/` 内部」= 种类是写或删 **且** 路径在 `.git` 下；默认层「写文件 · 越界」= 种类是写 **且** `out_of_bounds`；记住的「允许读 `notes/`」= 种类是读 **且** 路径在 `notes/` 下 | `RuleMatcher` 只有单条件 |
| 按 `ActionFlags` 匹配 | 越界、清单外重试（`bypass_sandbox_requested`） | 没有按标记的匹配器 |

建议补（全部 additive：proto 加字段与枚举值，`update-contract --additive` 登记；旧事件解出来 `applies_in` 为空 = 三档都生效）：

```rust
pub struct RuleEntry { …, pub applies_in: ApprovalModes }          // BTreeSet<ApprovalMode>；空集 = 全部档位
pub enum RuleMatcher { …, All(Vec<RuleMatcher>), Flag(ActionFlag) }
pub enum ActionFlag { OutOfBounds, BypassSandboxRequested, OpaqueScript, ResourceLimitHit /* 实施审查 8/F-1：解析资源上限命中，三档拒绝 */ }
```

Q1 未决前没有可开工的替代：第 15 节第 0 步依赖它。**若产品负责人不同意改类型**，退路是默认层与必问层不做 `RuleEntry`，改为 `iwork-core` 里带 ID 与版本的 const 表（`DEFAULT_TABLE: &[(RuleId, ActionKind, Option<flag>, [Effect; 3])]`），审计照记 ID，`ListRules` 查不到它们；记住的规则则退回「只按程序 / 路径」并在求值时额外比对 `Approval` 里记下的动作种类——两处真值，所以不作为推荐。

语义约定（写在 `matcher.rs` 的文档注释里，测试逐条守）：

- `PathUnder(d)`：目标路径在 `d` 之下（含相等），用 `PathResolver::is_under`。目标是 `Paths` 时任一命中即命中。
- `PathIs(p)`：目标等于 `p`。**例外**：底线层里对 `Delete` 动作，`PathIs(p)` 还匹配「目标是 `p` 的上级」（需求第 9 章「删除目标是下列路径之一或它们的上级目录」）。这条例外只存在于底线层，别的层的 `PathIs` 是精确匹配。目标是 `Command` 时任何路径匹配器都不命中。
- 底线层里 `effect = Allow` 的条目表示**只读区**：命中时只对 `Read` 动作放过底线，`Write` / `Delete` 照旧由更外层的数据目录条目拒绝。底线层不存在别的放行语义。
- `ProgramSubcommand{program, subcommand}`：目标是 `Command`，程序名相等，且（条目无子命令，或子命令相等）。
- `ToolName(n)`：目标是 `ToolName(n)`。
- `ActionKindIs(k)`、`Flag(f)`、`All([…])`、`Any` 字面义。
- 范围 `scope` 与档位 `applies_in` 不命中的条目当不存在。

### 4.3 规则快照：会话绑定的部分与活的部分（F-5）

规则分两类，真值仍只有一处（`rule` 流事件与内置规则集），但**生效时机不同**：

| 类 | 内容 | 生效 | 为什么 |
| --- | --- | --- | --- |
| **会话快照** `SessionSnapshot` | 内置规则集（含底线、必问、默认层、禁用工具、拒收名单）+ 三张安全清单（内置 + 用户条目，范围过滤后）+ 由它们算出的 `SessionConstraints` 与 `Boundaries`；记下 `ruleset_version` 与读取时的 `lists_seq`（`rule` 流的最新事件序号，进审计的 `snapshot_lists_seq`） | 会话启动时算一次，之后不变；T06 注入 CLI 的就是这份 | 清单的一部分进了 CLI 的 `sandbox` 设置（`excludedCommands`、`allowWrite`、`denyRead`），CLI 运行中不会变；hook 若用新表，两边就对不上（技术设计 7.2c「对新启动的会话生效；正在进行的回合不变」） |
| **活规则** | `Remembered` / `ProjectAllow` / `UserDeny` 层的条目 | 下一次求值即用（AC13「撤销权限在下一次调用即生效」） | 它们不进 CLI 设置，只在审批里用；撤销要立即生效 |

`RuleSet` 快照 = `snapshot.rules` ∪ 活规则（`ReadModelPort::rules`）∪ 临时的「其他项目 / 其他私聊目录」敏感条目（`EnvPaths` 里给出，`source = Builtin`、不入库、ID 由路径派生，也属于会话快照）。引擎缓存活规则，收到 `RuleRemembered` / `RuleRevoked` / `RulesDeleted` 就重算；收到 `SecurityListEntryAdded` / `SecurityListEntryRemoved` / `ProjectAdded` / `ProjectRemoved` / `AssistantCreated` / `AssistantDeleted` 时**不改运行中会话的快照**，只把受影响对话标为 `rebuild_session_needed = true`（6.9）。

范围过滤 `applies_to(entry, scope: &ScopeKeys)`：`Global` 恒成立；`Project(p)` 要 `scope.project == Some(p)`（私聊选「私聊」时 `project = None`，项目级条目都不生效）；`Assistant(a)` 要 `scope.assistant == a`；`Conversation(c)` 要 `scope.conversation == c`。

同层多条命中：底线取最具体；放行层与拒绝层任一即可，`matched` 记全部命中的 ID，`layer_hit` 记决定结果的层。用户条目与内置条目**不互相覆盖**：用户加的敏感目录只是多一条，删不掉内置的（`RuleEntry::is_builtin` → `RULE_NOT_REVOCABLE`）。

合并后的不变量（测试 `merged_ruleset_invariants`）：ID 唯一；内置条目全部在；用户条目的层只能是三张清单或 `Remembered` / `ProjectAllow` / `UserDeny`——用户条目若出现在 `Baseline` / `MustAsk` / `Default` / `ToolConfig` 层，`RuleSet` 构造函数返回错误（防止持久化层被篡改后放宽底线）。

### 5.2 七步（`evaluate/mod.rs`；每一步对应技术设计 7.2 的同号条目）

严格序（`strictness.rs`）：`Deny` > `UserAction` > `OutsideSandbox` > `Ask` > `Allow`。下面「下限」指最终结果至少这么严。

0. **前置**：`shape == Unparsable` 时，动作只有抽出的字面路径动作（含解析放弃前收集的 `PartialFacts`）与一个承载命令文字的执行动作（3.6）；步骤 1–5 照走，第 6 步跳过，第 7 步用 `Ask(UnparsableCommand)`（三档相同，Q4 已定）。
1. **底线**（`layer_hit = Baseline`）：动作目标含路径时，取底线层命中的最具体条目。命中且不是只读区放行 → 结果 `Deny(Baseline(id))`；卡片资格由 `evaluate_call` 在整条调用层面判（5.4），成立时改成 `UserAction(proposal)`。底线不看档位、不看记忆、不看工具。目标是 `Command` 的动作不会命中任何路径底线。
2. **拒绝记忆**（`layer_hit = DenialMemory`）：`ctx.denial.get(fingerprint)`：`AutoDeny` → `Deny(DenialMemory(fp))`，到此为止（不生成卡片）；`ForceAskOnce` → 记 `forced_ask = true`，继续（结果下限为询问，第 6 步跳过）。
3. **工具配置与边界**（`layer_hit = ToolConfig`）：① `ToolConfig` 层条目命中（永久禁用工具）→ `Deny(ToolSetExcluded)`；② 工具属于 `disabled_groups` 里的分组（`registry.group_of(tool)`）→ `Deny(ToolDisabled)`；③ 工具不在 `tool_set` 内（系统回合的工具集之外，或 ① ② 以外的任何不在集合内的）→ `Deny(ToolSetExcluded)`。越界标记在归一时已算好（3.8），这一步不再算。
4. **拒绝规则**（`layer_hit = UserDeny`）：`UserDeny` 层范围内命中 → `Deny(DenyRule(id))`。排在必问之前（v1.58）。M1 没有产生拒绝规则的命令，引擎支持、测试注入。
5. **必问**（`layer_hit = MustAsk`）：`MustAsk` 层里 `applies_in` 含当前档位的条目命中 → `Ask(MustAsk)`，并把 `must_ask` 记进调用约束；`forced_ask` 时也是 `Ask(MustAsk)`。不进 AI 审查。
6. **放行规则**（`layer_hit = Remembered | ProjectAllow`）：跳过的情形：`forced_ask`；`shape == Unparsable`；`kind == OutsideSandbox && bypass_sandbox_requested`（清单外重试不能记住，也不受放行规则影响）。否则 `Remembered` / `ProjectAllow` 层范围内命中 → `Allow`。记住的规则都带动作种类（6.4），所以「允许读 `notes/`」不会放行写 `notes/`，「允许执行 `git pull`」不会放行沙箱外执行的 `git pull`。越界动作可以被放行规则放行（技术设计 7.2 第 6 步原文）。
7. **默认**（`layer_hit = Default`）：`forced_ask` → `Ask(ForcedAfterDenial)`，或 `kind == OutsideSandbox` 时 `OutsideSandbox(ForcedAfterDenial)`（三档相同、不受放行规则影响，AC05）。否则按 4.2 默认层顺序取第一条 `applies_in` 含当前档位的命中条目，效果 → 结果：`Allow`；`Ask` → `Ask(原因)`，原因按条目：越界条目 `OutOfBounds`、MCP `McpNotReadOnly`、未归类 `Unclassified`、其余 `Default`；`OutsideSandbox` → `OutsideSandbox(原因)`，清单外重试 `OutOfBounds`、清单内 `Default`；`Deny` → `Deny(DenyRule(id))`（全开档清单外重试）。默认层没有命中是程序缺陷：`debug_assert!` + 返回 `Ask(Default)` 兜底并记日志（`Default` 层以 `ActionKindIs` 覆盖了全部 11 种 `ActionKind`，测试 `default_layer_total` 穷举证明）。

**系统回合**（技术设计 7.2b，验收 6a、6c）：七步算完后，`turn_kind != Assistant` 且结果是 `Ask` / `OutsideSandbox` / `UserAction` → 改为 `Deny(SystemTurnOutOfToolSet)`，`layer_hit = ToolConfig`。系统回合里只有 `Allow` 与 `Deny` 两种结果，不会产生审批、卡片与 AI 审查。

**一次性放行**（6.2）不在这七步里，也不在它们之前：引擎先把七步跑完，只有结果是 `Ask` / `OutsideSandbox`（也就是「这次本来要问」）时才去查 `grant_once`；`Deny`（含底线、拒绝记忆、禁用工具）与 `UserAction` 照常，`grant_once` 豁免不了它们（F-2）。

### 5.3 组合命令：取最严，并保留每个子动作的约束（技术设计 7.1「每个子命令单独归类，取最严的结果」；F-1）

`evaluate_call`：对 `call.actions` 逐个 `evaluate`；`representative` = 严格序最大者（并列取最靠前的）；`evaluation` = 它的结果，`matched` 合并全部子动作的命中 ID；`constraints` = 全部子动作约束的**或**；`fingerprints` = 全部子动作指纹。

约束怎么用（引擎 6.1、6.2、6.4、6.6）：

| 情形 | 结果 |
| --- | --- |
| `git pull && git push`（自动档） | 子结果 `OutsideSandbox(Default)` 与 `Ask(MustAsk)`；代表动作 `OutsideSandbox`，但 `constraints.must_ask = true` → `review_eligible() == false`，**不交 AI 审查**，直接问用户；`remember_eligible() == false`，只有「允许一次」 |
| `cat a && rm b`，`rm b` 处于 `ForceAskOnce` | `forced_ask = true` → 不审查、不记住、三档都问 |
| `npm test && echo $X` | `Unparsable` → 三档问、不审查、不记住 |
| `cat ~/Documents/x && npm test`（自动档） | `out_of_bounds = true`、没有必问 / 强制 / 解析不了 → 可交 AI 审查；通过后放行整条 |
| `rsync ~/.netrc ./copy`（清单外） | `Read(~/.netrc)` 底线 `Deny`；整条 `Deny`，不是单个简单命令以外的形状，但有多个子动作且有一个是底线 → 卡片资格看 5.4 |

测试 `call_strictest_is_max`（proptest）：`evaluate_call(...).evaluation.verdict` 的严格度等于各子动作结果的最大值；`call_constraints_are_union`：任一子动作必问 / 强制 / 越界 ⇒ 调用约束为真；`compound_with_must_ask_not_reviewable`、`compound_with_forced_ask_not_rememberable` 两条表驱动（含 `git pull && git push`）。

### 5.4 亲手执行判定（技术设计 7.2a 第 1 条；AC36；验收 4d）

```rust
pub fn propose_user_action(call: &NormalizedCall, eval: &CallEvaluation, raw_input: &RawToolInput) -> Option<Proposal>
pub fn proposal_hash(p: &Proposal) -> Sha256   // sha256("cmd\0" + command + "\0" + cwd) 或 sha256("patch\0" + path + "\0" + old + "\0" + new)
```

生成条件（全部成立）：① 代表动作的结果是底线拒绝（`layer_hit == Baseline`）；② `shape == SingleSimpleCommand`（Bash：恰好一个简单命令，全部词字面，允许字面重定向与引号界定的 here-doc）或 `shape == Tool` 且工具是 `Edit`；③ 调用的**任何**子动作指纹都不在拒绝记忆里（第 9 章「被用户拒绝过的同一动作不生成卡片」）；④ 不是系统回合。内容：Bash → `Proposal::Command{command: 原文（整条命令文字）, cwd}`；Edit → `Proposal::Patch{path, old: old_string, new: new_string}`。`Write`（整文件写入）与 `NotebookEdit` 不生成卡片，只拒绝，拒绝说明里写「请改用 Edit 或一条命令表达」（见 Q6）。理由：Bash 的 `description`，没有则「Agent 未说明」。组合命令、`Unparsable`（含 `cp ~/.ssh/id_rsa $DEST`）只拒绝。

一条单个简单命令可能产出多个路径动作（`cp ~/.ssh/config ./c` → `Read(~/.ssh/config)` 底线 + `Write(./c)`）；只要形状是单个简单命令，卡片照常生成，用户看到的是整条命令。档位不影响卡片（全开也出现）；卡片没有记住；`ExecuteUserAction` 只接受客户端连接、校验哈希（T10 受理，T01 已定）。

### 6.1 `ApprovalEngine`、`PermissionHandler` 与每对话串行锁（F-2、F-4）

`on_permission(req)` 的顺序：

1. `t0 = clock.monotonic()`；`facts = gather_path_facts(req, keys.cwd, fs)`（I/O，在锁外）；
2. **进该对话的决策锁**；
3. `rules = snapshot.rules ∪ live_rules(scope)`；`mode = effective_mode(conv.mode_inputs)`；
4. `call = normalize(req, ctx, facts)`；`eval = evaluate_call(call, rules, ctx)`（七步完整跑完，拒绝记忆读的是锁下的当前值）；
5. 结果是 `Ask` / `OutsideSandbox` 时查 `grant_once`（6.2）：命中且匹配 → 消费、结果改为 `Allow`，`layer_hit = Remembered`；
6. 写 `ApprovalEvaluated`（6.8）；
7. 按 5.5 回复，或登记 `pending` / `pending_cards`；**出锁**；等待在锁外。

**非用户本人的放行路径**（AI 审查通过、档位切换自动放行、一次性放行）在答复 `Allow` 之前都要**在决策锁下用当前状态重新判定授权资格**（第 2 轮复审 1/F-4），不是只查一张表：

```rust
/// 在决策锁下调用。对持久化的调用记录（Approval.call，6.2）重新跑七步，用的是此刻的活规则、
/// 拒绝记忆（两种相位都看）、有效档位与会话快照。
fn still_eligible(&self, approval: &Approval, pending: &PendingAsk, waiver: Waiver) -> Result<(), NotEligible>
pub enum Waiver { AiReviewPassed, ModeSwitch { new_mode: ApprovalMode }, GrantOnce }
```

判定：重新 `evaluate_call(pending.call, 当前规则, 当前 ctx)` 得到 `now`，与审批发起时的 `pending.eval` 比较：

| `now` 的情况 | 结论 |
| --- | --- |
| 任一子动作 `Deny`（底线、`AutoDeny`、用户 / 项目拒绝规则、禁用工具） | `NotEligible::Denied`：AI 审查按不通过处理（理由「同一动作已被用户拒绝」/「已被规则拒绝」/「规则已变化」），切档跳过这条，一次性放行作废 |
| `now.constraints.forced_ask`（有子动作处于 `ForceAskOnce`） | `NotEligible::ForcedAsk`：**旧的 AI 结果与旧的一次性放行都不能覆盖它**——用户发过新消息后要再问一次（AC05）。AI 审查按不通过处理，理由「用户已拒绝过同一动作，需重新确认」；切档跳过；一次性放行作废 |
| `now.constraints.must_ask` 或 `unparsable`，而发起时没有（规则变了） | `NotEligible::Changed`：同上处理 |
| `Waiver::ModeSwitch`：`now` 不是全部子动作 `Allow` | 不放行（6.5） |
| 其余（结果仍是当初那类询问，或已变成 `Allow`） | 放行 |

用户本人点「允许」不比对拒绝记忆（用户的新决定覆盖旧拒绝，6.3 会删掉条目），但同样跑 `still_eligible(…, Waiver::User)`：只看 `Deny` 一行（防止规则表在等待期间变化后放行底线或被拒绝规则命中的动作——`Ask` 级的审批本来不含底线动作，这是防御性检查，命中即 `DecideError::NoLongerAllowed`）。测试：`late_review_pass_after_sibling_denied_asks_user`（`AutoDeny`）、`late_review_pass_after_user_message_asks_user`（拒绝 → 新消息 → 旧 AI 通过回来 → `ForceAskOnce` → 转问用户，不放行）、`late_review_pass_after_deny_rule_added_asks_user`、`grant_once_voided_by_force_ask`。

**事件怎么提交**：hook 触发的不是客户端命令，但同样走 `StoragePort::commit`（事件 + outbox + `command_id` 同事务，AGENTS.md）。`command_id` 由 `ids.next()` 生成，`actor = Actor("agent:<assistant_id>")`；审计事件没有幂等重放的需要（每次求值都是新事实）。

### 6.2 询问流程、等待登记、一次性放行（技术设计 7.3；6.3 的等待上限；F-2）

1. 结果是 `Ask` / `OutsideSandbox`：生成 `Approval{ id, turn_id, conversation_id, kind: if constraints.outside_sandbox { OutsideSandbox } else { Ask }, action: 代表动作（raw_summary 为整条命令）, call: ApprovalCallRecord（**Q8**，新字段，见下）, matched_rules, ruleset_version, state: Pending, review: NotReviewed, offered_remember, remember_label, requested_at }`；`offered_remember` / `remember_label` 由 `remember::offered_remember(&call, &eval)` 算（6.4）。一次 `commit`：`ApprovalRequested` + `TurnStateChanged{PermissionAsked}`；`pending` 登记回答通道（`oneshot`，不进事件）与 `PendingAsk{ call: NormalizedCall, eval: CallEvaluation, turn }`——`PendingAsk.call` 能从 `Approval.call` 无损重建（E1）。系统通知与「待你处理」计数由 T09 / T04 消费事件完成。

   **持久化的调用记录**（第 2 轮复审 2/F-3；Q8 已定「只加不改」）：

```rust
/// 崩溃后重建 PendingAsk 与 GrantOnce、重跑 still_eligible 所需的最小调用记录。全部是归一后的值，不含原始 JSON 全文。
pub struct ApprovalCallRecord {
    pub tool: ToolRef,
    pub cwd: CanonicalPath,
    pub shape: CallShapeKind,                  // Tool / SingleSimpleCommand / Compound / Unparsable
    pub placement: SandboxPlacement,           // Inside / Outside / Ambiguous
    pub bypass_sandbox_requested: bool,
    pub actions: Vec<Action>,                  // 全部子动作，保持顺序（代表动作是其中之一，索引在 representative）
    pub representative: u32,
    pub raw_input_digest: Sha256,              // sha256(工具名 ‖ 规范化 JSON（键排序、无空白）)
    pub normalized_digest: Sha256,             // sha256(有序的 actions 摘要 ‖ shape ‖ placement ‖ cwd)
}
```

   `fingerprints` 不单独存，由 `actions` 算（`call.fingerprints()`，3.9），一处真值。proto：`Approval.call`（新消息 `ApprovalCallRecord`，字段同上，`actions` 用已有的 `ActionSummary`），additive。旧事件没有 `call` 时：拒绝记忆退化为 `[action.fingerprint()]`；恢复时该审批**不能**走一次性放行——用户允许后只 `Resume`，续接后模型重发的调用照常走七步再问一次（「缺字段时走明确的重新询问」），审计里 `layer_hit` 照记。
2. 等待没有超时（需求 AC04）。T06 的桥接在 hook 的等待上限到期前会**自己**给 hook 返回拒绝并中断回合（`WaitLimitReached`）；引擎收到 `TurnStateChanged{Interrupted{ApprovalWaitLimit}}` 时把该回合在 `pending` 里的通道置 `None`（`detached`），审批**保持 `Pending`**（需求 12、T01 `VoidReason` 没有这个原因）。
3. 用户决定（`decide`，T10 调用，锁下）：`Approval::apply(UserAllow{remember} | UserDeny, ctx{mode_now})` → `ApprovalDecided`；允许且 `remember != Once` → `RuleRemembered`（6.4）；拒绝 → 拒绝记忆记全部指纹（6.3）。通道还在：发 `Allow` / `Deny`，回合 `PermissionDecided`。通道已 `detached`（等待上限中断过）：允许 → 写入 `grants[approval_id] = GrantOnce{…}`，再触发 `Resume`（T06 用 `--resume` 续接；续接后模型重发同一调用，hook 再来一次，6.1 第 5 步命中、消费、放行，**只放一次**）；拒绝 → 不续接，回合保持 `Interrupted`，对话出「继续 / 放弃」卡片（T01 Q2 已定做法 (a)），用户点继续时把「用户已拒绝」随续接的提示送给模型（T06）。
4. **一次性放行的绑定与匹配**：

```rust
pub struct GrantOnce {
    pub approval_id: ApprovalId,
    pub turn: TurnId,                               // 被中断又续接的那个回合（Resume 不换 TurnId，T01 回合表）
    pub record: ApprovalCallRecord,                 // 获批调用的完整记录（上面），含两个摘要
}
```

   匹配条件（全部相等才算**同一次调用**，第 2 轮复审 1/F-2）：同一对话、同一回合；新调用算出的 `ApprovalCallRecord` 与 `record` 在 `tool`、`cwd`、`shape`、`placement`、`bypass_sandbox_requested` 上相等；**`raw_input_digest` 相等**（原始工具输入规范化后的摘要——`&&` 改 `;`、调序、改重定向归属都会改变它）；**`normalized_digest` 相等**（有序子动作列表的摘要——指纹集合相同但顺序或重复次数不同也不算）。两个摘要一起比：原始输入摘要防文字层面的改写，归一摘要防同文字不同解析（版本升级后归一结果变了也不放行）。所以 `rm a.txt && touch a.txt` 获批后，续接改发 `touch a.txt && rm a.txt`、`rm a.txt; touch a.txt`、`rm a.txt && rm a.txt && touch a.txt`、`rm a.txt > log && touch a.txt`（重定向换了归属）、`rm a.txt && git push` 都不命中，照常走七步。命中后在锁下原子地 `remove`，并发的两次请求只有一次拿到。`grants` 在回合到终态（`TurnFinished` / `Cancelled`）或对话删除时清空；一个回合里同时最多只有它被中断时正在等的那几条审批的放行。命中之后还要过 6.1 的 `still_eligible(…, Waiver::GrantOnce)`（拒绝记忆两种相位、规则变化）。
5. 卡片（`UserAction`）同样登记 `pending_cards`，到终态（`UserActionStateChanged{Done|Failed|Unknown|Dismissed|Voided}`）时按 5.5 回复；`Unknown` 回「结果未知」。

**出事场景 E1（后台服务崩溃时有询问在等）**：通道随进程消失；审批事件已落盘（`Pending`）。重启后 T04 把持有进程的回合标 `Interrupted{Crash}`，引擎启动时从**事件**（`ApprovalRequested` 里的 `Approval.call`）把 `Pending` 审批装回 `pending`（全部 `detached`，`PendingAsk.call` 由 `Approval.call` 无损重建：动作、形状、沙箱位置、cwd、两个摘要都在里面——这就是 Q8 要持久化完整调用记录而不只是指纹的原因）；用户随后允许 → 走第 3 步的 `grant_once` + `Resume` 路径，`GrantOnce.record` 就是重建出来的记录；拒绝 → 「继续 / 放弃」。没有 `call` 的旧审批：允许后只 `Resume`、不发一次性放行，续接后重新询问。止血：无需人工；回退：用户「放弃」回合即作废其余待审批。由什么保证：`engine_recovers_pending_from_events`（用 `ProtoEventCodec` + 内存 store 写入真实的 `ApprovalRequested` / `TurnStateChanged` 事件序列，**丢弃全部内存状态**后重建引擎，断言重建的 `PendingAsk.call` 与原值相等；`decide` 允许 → `GrantOnce.record` 等于原记录；续接后同一原始输入命中、改一字不命中）、`recovery_without_call_record_reasks` + T04 验收 3 的故障注入。

### 6.3 拒绝记忆（AC05；技术设计 7.2 第 2 步；派活说明第 5 条；F-3、F-4）

```rust
pub enum DenialPhase { AutoDeny, ForceAskOnce }
pub struct DenialMemory { entries: BTreeMap<ActionFingerprint, DenialEntry { phase: DenialPhase, from_approval: ApprovalId }> }   // 每个对话一份，在 ConversationState 的锁下
```

| 事件 / 调用 | 变化 |
| --- | --- |
| `ApprovalDecided{Denied}` | 对 `approval.call.fingerprints()` 里的**每一个**指纹：`entries[fp] = AutoDeny`。被拒调用里的全部需要保护的动作都进记忆，拆开重发任何一个都自动拒绝；代表动作只用于展示（F-3） |
| `MessageAppended{author: User}`（本对话） | 全部 `AutoDeny` → `ForceAskOnce`；已是 `ForceAskOnce` 的不变 |
| 求值命中 `AutoDeny`（任一子动作） | 该子动作 `Deny(DenialMemory)` → 整条 `Deny`，不生成卡片，回「用户已拒绝，不要换方式重试」 |
| 求值命中 `ForceAskOnce`（任一子动作） | `forced_ask`：结果下限询问、跳过放行规则、三档相同（5.2 第 7 步 `ForcedAfterDenial`）；不启动 AI 审查；只能允许一次；卡片与普通询问相同，不额外标注 |
| 该次强制询问的审批 `ApprovalDecided{Approved{User}}` | 删除该审批 `call.fingerprints()` 里全部处于 `ForceAskOnce` 的条目。只有**用户本人**的允许能删；AI 审查通过、切档放行、一次性放行遇到 `ForceAskOnce` 一律不放行（6.1） |
| 该次强制询问的审批 `ApprovalDecided{Denied}` | 这些条目回到 `AutoDeny`（并把新审批里其他指纹也加进来） |
| 该次审批被作废（回合取消等） | 条目**保持 `ForceAskOnce`**：用户没有表态，下次仍强制问 |
| `ConversationDeleted` | 整份删除 |

「同一动作」的范围：按对话，不按回合、成员、运行时——`DenialMemory` 的键是 `ConversationId`，`SessionKeys.conversation` 相同就共享，所以换成员、`--resume` 续接、中断后续接都在同一份里（验收 3）。私聊切换项目是同一个对话，记忆不清（它记的是指纹，与项目无关）。

**与放行路径的串行化**（F-4）：同一对话里两条相同动作的待审批 A、B，用户拒绝 A → 在决策锁下写入 `AutoDeny`；B 的 AI 审查随后「通过」回来 → 6.1 的复查在同一把锁下读到 `AutoDeny` → 按不通过处理、转问用户，不放行。反过来 B 先通过再 A 拒绝：B 已放行、已执行，A 的拒绝只影响之后的请求——这是时序上的既成事实，不是漏洞。测试 `late_review_pass_after_sibling_denied_asks_user`、`mode_switch_release_skips_denied_fingerprints`、`grant_once_voided_by_later_denial`。

重建：`DenialMemory` 是 `approval` 流（含 `Approval.call`）与 `conversation` 流事件的确定性函数（上表），引擎启动时对每个有 `Pending` 或近期 `Denied` 审批的对话按事件重放重建；也写一个纯函数 `DenialMemory::replay(events) -> Self`，重建与在线走同一个函数（`denial_memory_replay_equals_online`）。不加投影表。

**出事场景 E2（模型换写法绕过）**：`rm a.txt` 被拒后改用 `python -c "import os; os.remove('a.txt')"`。前者指纹 `Delete(a.txt)`，后者 `Unparsable` → 询问（不是放行），用户再拒一次；需求第 9 章已登记「换一种写法为已知限制」。止血：无需；由什么保证：`denial_memory_cases` 里这一条断言结果是 `Ask` 不是 `Allow`。

### 6.4 记住 → 规则（FR11 v1.61；技术设计 7.3 第 2 条；AC40；F-14）

```rust
pub fn offered_remember(call: &NormalizedCall, eval: &CallEvaluation) -> (Vec<RememberScope>, String /* remember_label */)
pub fn remember_rule(approval: &Approval, scope: RememberScope, by: Actor, now: Timestamp, id: RuleId) -> Option<RuleEntry>
```

记住的规则**必须**带动作种类（Q1 的 `All`），路径或程序只是第二个条件；清单变化不会扩大旧批准，因为种类变了就不匹配：

| 代表动作 | 可记住的范围 | 匹配器 | 文案示例 |
| --- | --- | --- | --- |
| `Execute` | 一次 / 本对话 / 本项目 / 永久 | `All([ActionKindIs(Execute), ProgramSubcommand{program, subcommand}])` | 「本项目内 `npm test …` 不再问」。以后 `npm test` 进了需凭据清单变成 `OutsideSandbox`，这条不再匹配，重新询问 |
| `OutsideSandbox` 且清单内（`placement == Outside`，非重试） | 一次 / **本项目** | `All([ActionKindIs(OutsideSandbox), ProgramSubcommand])` | 「本项目内 `git pull …` 直接在沙箱外运行」。它反过来也不匹配普通 `Execute` 的 `git pull` |
| `OutsideSandbox` 且清单外（重试） | 一次 | — | （无记住） |
| `Write`（非越界或越界） | 一次 / 本对话 / 本项目 / 永久 | `All([ActionKindIs(Write), PathUnder(目标所在目录)])` | 「本项目内写 `src/` 不再问」 |
| 越界 `Read` | 一次 / 本对话 / 本项目 / 永久 | `All([ActionKindIs(Read), PathUnder(目标所在目录)])` | 「永久允许读 `~/Documents/notes/`」；写 `notes/` 仍询问 |
| `McpCall`、`Unclassified` | 一次 / 本对话 / 本项目 / 永久 | `All([ActionKindIs(kind), ToolName(名)])` | 「本对话内 `mcp__x__y` 不再问」 |
| `Push`、`Publish`、`Delete`、`WriteAutorunConfig`（必问）、`Unparsable`、强制询问、清单外重试，以及**多子动作的调用**（`constraints.remember_eligible() == false`，或 `call.actions` 里可记住的动作多于一个） | 一次 | — | （无记住；强制询问那次允许后「之后按正常规则求值」，不生成规则） |

多子动作调用只能允许一次：`echo x > a.txt` 有 `Execute(echo)` 与 `Write(a.txt)` 两个动作，记住其中一个另一个仍会问，记住多条规则又会让用户看不懂卡片上的「记住范围」。登记为已知限制（第 13 节），M2 再看是否值得做多条。

规则条目：`layer = Remembered`，`effect = Allow`，`source = Remembered{approval_id, by}`，`scope`：本对话 → `Conversation(id)`；本项目 → `Project(id)`（私聊选「私聊」时没有项目，不提供「本项目」）；永久 → `Assistant(id)`（FR11「永久记在助手上」）。`DecideApproval.remember` 不在 `offered_remember` 里 → `DecideError::RememberNotOffered`（T10 映射错误码；T01 没有专门的码，用 `INVALID_ARGUMENT` 类的通用码，T10 定）。撤销：`RevokeRule` → `RuleRevoked`，内置条目 `RULE_NOT_REVOCABLE`；删除对话 / 助手时 `rules_owned_by(scope) -> Vec<RuleId>` 给 T10 发 `RulesDeleted`。

### 6.5 档位与切换（FR11；技术设计 7.2、7.3 第 6 条；验收 2、1c）

`effective_mode` 已由 T01 实现；引擎为每个对话（与成员）维护 `ModeInputs` 的当前值，来源是 `ApprovalModeChanged` 事件（`cause: User / ProjectSwitch / NewConversation`）与 `ProjectSettingsUpdated`。

```rust
pub fn switch_mode(&self, target: ModeTarget, mode: ApprovalMode, follow_supervisor: bool, by: Actor, now: Timestamp) -> Result<Vec<DomainEvent>, ModeError>
```

1. 校验：`target = Project` 且 `mode = FullAccess` → `ModeError::FullAccessNotAllowedAsDefault`（`APPROVAL_MODE_NOT_ALLOWED`）；`follow_supervisor = true` 只对 `Member` 目标有效，等于清掉 `member_override`。
2. 事件：`ApprovalModeChanged{target, mode, cause: User}`。
3. 受影响的成员集合 `affected`：`Conversation` 目标 = 该对话里没有单独设置的全部成员；`Member` = 该成员；`Project` = 不影响进行中的对话（项目默认只对新对话生效，`NewConversation` 时取）。对 `affected` 的每条 `Pending` 审批，在对话的决策锁下：
   - 用**新档位**重新 `evaluate_call`（活规则与拒绝记忆都是现在的，快照是会话的）。全部子动作都是 `Allow` 且 6.1 的复查通过 → `Approval::apply(ModeSwitchAllows)` → `ApprovalDecided{Approved{ModeSwitch}}`，回答通道 `Allow`（通道 `detached` 的进 `grants` + `Resume`）。任一子动作仍是询问（例如 `git pull && git push` 切到全开，`push` 仍必问）→ 整条保留。
   - 新档位是 `Manual` 且审查 `InProgress` → `apply(ModeChangedToManual)` → `ApprovalReviewUpdated{Abandoned}`，转问用户，取消审查任务。新档位是 `Auto` 且审批在 `NotReviewed` 等用户 → **不补 AI 审查**（用户已经看到卡片；补审查会让卡片忽隐忽现），保留（第 13 节补充）。
   - 卡片不受影响（T01 卡片表没有这种触发）。
4. 全开确认框的文案与受影响成员列表是 T09 的事；`affected` 由查询给出（T10 在 `SetApprovalMode` 受理前查 `pending_items`）。

档位对求值的影响只在第 5 步（必问的 `applies_in`）与第 7 步（默认层），记住的规则三档都生效（技术设计 7.2）。属性测试 `mode_monotonic`：同一输入下 `strictness(Manual) ≥ strictness(Auto) ≥ strictness(FullAccess)`，例外只有 `Push`（三档相等）、清单外重试（全开 `Deny` 比手动的 `OutsideSandbox` 严——这是设计有意为之，AC38「不出现沙箱外重跑」）、底线、拒绝记忆与 `Unparsable`（三档相等）。

### 6.6 AI 审查系统回合（技术设计 7.2 第 7 步、7.2b；验收 6、6a；F-15）

启动条件（全部成立）：`mode == Auto`；`eval.constraints.review_eligible()`（只有越界或沙箱外这两种「问」的原因，且没有必问、强制询问、解析不了，5.1）；`project.settings.ai_review.enabled`；`turn_kind == Assistant`。

```rust
pub struct ReviewInput { pub actions: Vec<ActionSummaryText> /* 全部子动作 */, pub command_text: String, pub task_goal: String /* 本对话最近一条用户消息 */, pub recent_context: String /* 最近 ≤ 2000 字符的助手输出摘要 */ }
pub fn review_prompt(input: &ReviewInput) -> (String /* system */, String /* user */)   // 纯函数，快照测试
pub fn parse_review_output(text: &str) -> Result<ReviewOutcome { pass: bool, reason: String }, ReviewParseError>  // 只认最后一行 JSON {"pass": bool, "reason": "..."}
```

流程：① `review_id = ReviewId(新 TurnId)`，`Approval::apply(AiReviewStarted{review_id})` → `ApprovalReviewUpdated{InProgress}`；② 记一个 `Turn{kind: SystemAiReview}`（`TurnQueued` / `TurnFinished` 事件照常，客户端按 `kind` 不渲染——第 13 节补充）；③ `reviewer.open_session(SessionSpec{ cwd: workspace_root, model: ai_review.model 或 iWork 默认, system_prompt, mcp: [], constraints: snapshot.constraints, tool_set: SessionToolSet{enabled_groups: ∅, include_always_on: false}, resume: None, kind: SystemAiReview }, handler_for(审查回合的 SessionKeys))`；④ `prompt` 并读完更新流，同时用 `clock.monotonic()` 计时，`ai_review.timeout_secs`（默认 60）到期 → `session.cancel()`、`AiReviewTimedOut`；流结束 → `parse_review_output`：通过 → `AiReviewPassed`，不通过 → `AiReviewFailed{reason}`，解析失败或 `Failed(AgentError)` → `AiReviewErrored`；⑤ 结果回来后，**在决策锁下按这个顺序，只 `apply` 一次**（第 2 轮复审 2/F-4）：(a) 在审批的**克隆**上试 `apply(结果)`，看是不是 `Stale`——是就只写 `ApprovalStaleResultDropped`（T01 已定），结束；(b) 结果是「通过」时，先跑 6.1 的 `still_eligible(…, Waiver::AiReviewPassed)`；(c) 据此决定**真正**施加的触发：通过且资格仍在 → `apply(AiReviewPassed)` → `Approved{AiReview}`，`ApprovalDecided` + 回答 `Allow`；通过但资格不在 → `apply(AiReviewFailed{reason: "同一动作已被用户拒绝" | "用户已拒绝过同一动作，需重新确认" | "已被规则拒绝" | "规则已变化"})`，主状态**仍是 `Pending`**、子状态 `Failed`、`awaits_user() == true`，转问用户；不通过 / 出错 / 超时 → 对应的 `apply`，转问用户。任何一条路径都只有一次 `apply`，不存在「先进 `Approved` 再想回 `Pending`」。测试 `review_recheck_fail_keeps_pending`：A、B 同指纹，用户拒 A 后 B 的审查通过 → 断言 B 仍 `Pending`、`awaits_user() == true`、事件流里**没有** `ApprovalDecided{Approved}`、只有一条 `ApprovalReviewUpdated{Failed}`。

**崩溃后失去执行者的审查**（F-15）：后台服务在 `Pending + InProgress` 时崩溃，重启后没有人在跑那个审查回合，审批既不计入「待你处理」（`awaits_user()` 为 false）也等不到结果。启动恢复时，对每条 `Pending + InProgress{review_id}` 的审批：`Approval::apply(AiReviewAbandoned{review_id, reason: ExecutorLost})`（**Q9**：T01 的子状态表只有 `ModeChangedToManual` 一个到 `Abandoned` 的触发，要加一个；`ReviewState::Abandoned` 与 proto 的 `ABANDONED` 已有，`ApprovalReviewUpdated.reason` 填「后台服务重启，审查中止」）→ 转问用户；旧 `review_id` 的迟到结果按 T01 三条件 `Stale`。与崩溃恢复的其他步骤同一事务（T04 `RecoveryCompleted` 之前）。

审查回合里的任何工具调用（工具集为空，正常不会有）经同一个引擎求值，`turn_kind = SystemAiReview` → 5.2 的系统回合规则直接拒绝，不会再起一层审查（无递归）。审查的输入输出全文不进事件（T01 3.3），理由进 `ApprovalReviewUpdated.reason`。AI 审查通过不生成规则、不影响拒绝记忆（它不是用户决定）。

**出事场景 E3（审查运行时挂死或不停输出）**：超时计时用单调时钟，到期 `cancel`，3 秒未结束由 T05 监管结束进程树；结果 `TimedOut` 转问用户。由什么保证：验收 6 的四种假运行时脚本（通过 / 不通过 / 超时 / 崩溃）。

**出事场景 E4（审查中崩溃）**：见上段。由什么保证：`review_in_progress_abandoned_on_recovery`（内存 store 写入 `ApprovalRequested` + `AiReviewStarted` 后重建引擎 → 产生 `ApprovalReviewUpdated{Abandoned}`、`awaits_user() == true`；随后对旧 `review_id` 发 `AiReviewPassed` → `Stale`）；归入 T04 验收 3 的故障矩阵（交接）。

### 6.8 审计（技术设计 7.4；派活说明第 1 条；F-16）

每次 `on_permission` 一条 `ApprovalEvaluated{turn_id, action: 代表动作, matched_rule_ids, ruleset_version, verdict, layer_hit, duration_ms, snapshot_lists_seq, live_rules_seq, sub_actions, call_shape}`，放行也记，`audit` 流按 `turn_id`。`duration_ms` 从进入 `on_permission` 到求值完成（不含等待用户）。

后四个字段是本方案加的（**Q10** 已定，proto additive）。两个游标**分别**持久化，不取 max（第 2 轮复审 1/F-16）：`snapshot_lists_seq` = 会话快照生成时读取三张清单的 `rule` 流游标（`SessionSnapshot.lists_seq`，6.9），`live_rules_seq` = 活规则缓存最后应用的 `rule` 流 `seq`；内置部分由 `ruleset_version` 定。`sub_actions` = 全部子动作的 `ActionSummary`；`call_shape` = `Tool / SingleSimpleCommand / Compound / Unparsable`。没有游标，「按审计事件的 `seq` 重放规则」会把求值与写审计之间插进来的撤销也算进去；取 max 则丢掉「快照比活规则旧」这个信息，重放时会把快照生成之后新加的清单条目也算进快照（F-16）。

「决定人」：T01 的 proto 没有这个字段，`ApprovalDecider{User, ModeSwitch, AiReview}` 是「谁让审批离开 Pending」，与求值不是一回事——求值时还没有人决定。建议（Q2）：**不加字段**。7.4 要求的四样信息分布在两条事件里：动作、命中的规则与层、结果、耗时在 `ApprovalEvaluated`；决定人在 `ApprovalDecided.decider`（直接放行或拒绝的求值，决定人就是规则引擎本身，`layer_hit` 说明是哪一层）。技术设计 7.4 的措辞由 supervisor 改为「每次求值写一条事件：动作、命中的规则与层、结果、耗时；询问的决定人记在 `ApprovalDecided`」。备选：加 `ApprovalDecider::RULE_ENGINE` 与 `ApprovalEvaluated.decider` 字段——多一个永远等于「规则引擎」的字段，没有信息量。

可还原规则快照（验收 7）：`ruleset_version` 定内置部分；三张清单按 `rule` 流事件重放到 `snapshot_lists_seq`、活规则重放到 `live_rules_seq`，两份合起来就是求值时用的规则集。测试 `audit_snapshot_reconstructible`：随机加删清单条目与活规则穿插求值（含「撤销插在求值与写审计之间」的用例：求值后、`commit` 审计前，另一个线程提交 `RuleRevoked`；含「会话启动后又加了清单条目」的用例：快照旧、活规则新），对每条审计事件**丢掉引擎内存里的快照与缓存**，只凭事件日志按两个游标重建规则集，再对 `sub_actions` 求值一次，结果相同。

清单变化（`SecurityListEntryAdded` / `Removed`、项目或助手增删影响临时敏感条目）：引擎把受影响对话的 `rebuild_session_needed` 置 true，`ListSecurityLists` 的调用方（T10）可据此提示「对新会话生效；要立即生效请重新开始当前回合」；若产品负责人要求立即生效，做法是 `CancelTurn` 当前回合再 `SendMessage`（新会话），不能只更新 hook 一侧（第 1 轮审查 F-5）。

`constraints_for`：`deny_read_write` = 底线层 `UserActionEligible` 的凭据条目与 `{data_dir}`（不含 `.git`、关键路径——那些只由审批拦）；`read_only` = 只读区两条；`allow_write` = 手动、自动档 `Whitelist([workspace, tmp_dirs, 可写缓存条目, 可写目录条目（范围内）, 私聊私有目录])`，全开 `Anywhere`；`excluded_commands` = `credential::to_command_patterns`（3.7）；`allow_unsandboxed_retry = mode != FullAccess`；`network = Open`。三档的 `deny_read_write` 与 `read_only` 相同（测试 `constraints_baseline_mode_independent`）。档位切换后：沙箱的 `allow_write` 与 `allow_unsandboxed_retry` 随档位变，但 CLI 进程里的设置不会变——技术设计 7.0 已写「档位切换后下一次启动或续接会话时使用对应配置」（T06 卡第 5 条）；审批侧的档位即时生效。审批比沙箱严（手动、自动档沙箱放开的写由审批问），所以「沙箱还是旧档位」只会多拦不会少拦。

`tool_set_for`：`Assistant` → `enabled_groups = 全部四组 − disabled_groups`，`include_always_on = true`；`SystemAgentsMdDraft` → `{ReadAndSearch}`，`include_always_on = false`；`SystemAiReview` → 空集，`false`。`ToolRegistry::group_of(tool) -> Option<ToolGroup>`（Read / Grep / Glob → 读文件与搜索；Edit / Write / NotebookEdit → 编辑文件；Bash / 后台输出 / 停止后台 → 执行命令；WebFetch / WebSearch → 网页）；不属于四组的「始终开启」工具按 `include_always_on`；永久禁用工具永远不在集合里。求值第 3 步用同一个 `registry` 与 `tool_set` 判 `ToolSetExcluded`，所以启动参数与 hook 兜底出自同一份数据（验收 6b）。

```
                                                                                     │ ── 出锁 ──
```

规则数据流：会话启动时 `snapshot_for`（内置 + 三张清单）→ `SessionSnapshot` 同时交给 T06（注入 CLI）与引擎（hook 侧）；活规则（记住 / 项目 / 拒绝）经 `rule` 流事件进引擎缓存，下一次求值即用。拒绝记忆与一次性放行只在引擎内存里，是事件的确定性函数，重启时重放。

## 8 每条规则的「目的 + 手段」

| 规则 | 目的（防什么） | 手段 |
| --- | --- | --- |
| 求值是纯函数，I/O 在外面 | 判定结果依赖磁盘状态、时钟或网络，proptest 失真，线上复现不了 | `gather_path_facts` 取事实（I/O），`normalize` / `evaluate_call` 只拿值；引擎在外面取数、提交 |
| 只放行能证明安全的形态 | 把 Bash 语义建模漏一处，就把有副作用的命令当读放行 | 短白名单 + 危险选项表 + 全词字面；其余归 `Execute` 或 `Unparsable`；复合命令上的重定向、`for`、`case`、函数、任何展开 / 通配 / `cd` / 前置赋值 → 整条 `Unparsable` |
| 宁可多问 | 文字层面拿不准的命令被当成安全的放行 | `Unparsable` 三档询问、不受放行规则影响、不审查、不记住；`Ambiguous` 按沙箱外 |
| 路径动作总是抽取、不被沙箱位置替换 | 复制 / 传输类命令把凭据文件搬出去，或清单内命令整条放行 | 每个字面路径词都成为路径动作过底线与越界；沙箱外只改执行动作的种类 |
| 底线先于一切、三档相同 | 档位、记住的规则、AI 审查任何一个放宽底线 | 第 1 步最先判；底线层条目的效果只有 `UserActionEligible` / 只读区 `Allow`；`RuleSet` 构造拒绝用户条目进底线层；proptest `baseline_hit_never_allows` |
| 丢弃改动不伪造成删除目录 | `git reset --hard` 撞关键路径底线三档都拒，回退被堵死 | `Delete` + `Command` 目标；必问层按种类命中，底线层按路径不命中 |
| 拒绝 > 询问 > 放行 | 必问把用户的拒绝规则变成询问；放行规则跳过必问 | 步骤顺序 4 → 5 → 6；proptest `deny_rule_beats_must_ask`、`must_ask_never_allow` |
| 组合命令保留每个子动作的约束 | `git pull && git push` 被 AI 审查整条放行，push 没问用户 | `CallConstraints` 取或；`review_eligible` / `remember_eligible` 看整条 |
| 拒绝不可绕过（AC05） | 换工具、换成员、续接后、拆开重发同一动作被放行 | 指纹 = 种类 + 规范化目标；拒绝记全部子动作指纹并持久化；记忆按对话；`ForceAskOnce` 跳过放行规则、三档相同 |
| 非用户的放行路径答复前复查 | A 被拒后 B 的迟到审查通过仍放行 | 每对话决策锁；AI 审查通过、档位切换放行、一次性放行都在锁下复查拒绝记忆与底线 |
| 一次性放行只放一次、只放同一次调用 | 等待上限中断后续接，模型借机多做一步、换命令、调序或改重定向归属 | 绑定回合与完整调用记录（工具、cwd、形状、沙箱位置、原始输入摘要、有序归一摘要）；七步跑完只豁免 `Ask`；命中即消费，之后仍过资格复查 |
| 非用户放行路径用当前状态重判资格 | 旧的 AI 通过或旧的一次性放行覆盖用户新消息后的「强制询问一次」，或覆盖新加的拒绝规则 | `still_eligible` 重跑七步：`Deny`、`ForceAskOnce`、新出现的必问 / 解析不了都不合格；只有用户本人的允许能清 `ForceAskOnce` |
| AI 审查结果只 `apply` 一次 | 先进 `Approved` 再复查失败，回不到 `Pending` | 克隆上判 `Stale` → 复查 → 一次 `apply(Passed | Failed)` |
| `Unparsable` 兜底抽词不认结构、宁可多抽 | 粘在选项上或 `name=value` 里的路径（`-E.git/config`、`--log=.git/x`、`of=.git/config`）在解析放弃后抽不出来，或真实文件名以 `-` 开头被漏掉，底线被普通询问放开 | `fallback_candidates` 读 `literal`：完整字面值恒为候选，再追加 `=` 后的值与每个短选项切分位置之后的剩余部分，记 `Read` + `Write`；重定向保留真实目标与角色；两条 `Unparsable` 路径同一个函数，表外程序的 `name=value` 拆值共用同一个助手 |
| 解析放弃前保留字面事实 | 复合命令上的字面重定向目标随 `Unparsable` 丢掉，写 `.git` 只剩普通询问 | `parse` 第一遍收集 `PartialFacts`，归一照常抽路径动作过底线 |
| 白名单是允许清单，参数角色登记到选项 | 黑名单漏一个写文件的选项或操作数角色就把写当读放行；选项参数里的路径漏抽 | `ArgSpec`：未登记选项即 `Execute`；取值选项按角色抽路径；改变操作数角色的选项（`install -d`、`grep -e` / `-f`）登记角色变化；表外程序位置参数与 `--opt=VALUE` 抽 `Read` + `Write`，粘值只按 `PathOptions` 登记角色抽，没登记的整条 `Unparsable` |
| hook 侧与 `excludedCommands` 同源且同一快照 | 审批以为在沙箱内、实际在沙箱外；清单改了两边不一致 | `SessionSnapshot` 同一份给 CLI 与 hook；匹配器三态且 `Ambiguous` 按沙箱外；对拍语料进 CI；要立即生效就重建会话 |
| 记住的规则带动作种类 | 「允许读」放行写；普通执行的批准变成沙箱外执行的批准 | `All([ActionKindIs, …])`；清单变化改变种类即不匹配 |
| 系统回合只有放行与拒绝 | AI 审查回合或草稿回合把询问弹给用户，或递归再起审查 | 工具集为空 / 只读；结果 `Ask` 一律改 `Deny(SystemTurnOutOfToolSet)` |
| AI 审查结果只在本次、进行中、自动档下生效；失去执行者即放弃 | 迟到的通过放行已交给用户或已切回手动的审批；崩溃后审批永久卡住 | T01 三条件 + `Stale`；恢复时 `AiReviewAbandoned{ExecutorLost}` 转问用户 |
| 规则即数据、ID 稳定、审计带两个游标 | 审计里的 ID 下个版本对不上；加规则要改求值流程；按审计重放得到不同结果 | slug 派生 ULID、快照测试；加规则 = 加一行；`snapshot_lists_seq`、`live_rules_seq` 与 `sub_actions` 进审计 |
| 可写目录拒收底线与自动执行配置的上级 | 用户无意间把 `~/Library` 整个放开，LaunchAgents 可写 | 校验复用 `AutorunConfig` 与底线条目做「之下或上级」检查 |
| 必问动作、清单外沙箱外执行、多子动作调用不可记住 | 一次允许变成永久放开 `git push` / 任意沙箱外命令 / 看不懂范围的规则 | `offered_remember` 只给 `Once`；`decide` 校验 `remember ∈ offered_remember` |
| 卡片只对单个简单命令或 Edit | 组合命令里夹带别的动作被用户一键执行 | `shape == SingleSimpleCommand` 或 Edit；哈希校验；没有记住 |

## 9 出事场景

每条写：会出什么事 / 怎么止血和回退 / 由什么保证。N1–N4、E1–E4 已写在对应小节，这里补叠加场景与紧急路径。

**S1 内置规则集有一条写错（比如某个凭据目录路径拼错）**
- 会出什么事：那个目录的读写只剩沙箱一道闸；Agent 用 Read 工具（不在沙箱内）能读到。
- 止血和回退：按 S6 的紧急路径处理（停会话、退版本、重建）；修条目、升 `ruleset_version` 发版；不需要迁移（内置条目不入库）。审计里 `ruleset_version` 能圈出受影响的时间段。
- 由什么保证：验收 4a 对需求第 9 章清单逐条测试（期望路径手写，不从条目推）；`builtin_ids_stable` 快照防无意改动。

**S2 用户记住了一条放行规则，后来又在同一动作上点拒绝**
- 会出什么事：放行规则还在，拒绝记忆也在；下次请求若放行规则先生效就违反 AC05。
- 止血和回退：步骤顺序保证记忆（第 2 步）先于放行（第 6 步）；用户消息后 `ForceAskOnce` 也跳过第 6 步。规则仍可在设置里撤销。
- 由什么保证：验收 1b「已记住的放行规则不能跳过这次询问」；proptest `forced_ask_ignores_allow_rules`。

**S3 全开档 + 需凭据命令清单里有 `gh`**
- 会出什么事：`gh api -X DELETE …` 在全开档不询问、在沙箱外运行（设计如此，FR11）。清单越宽，全开档等于放开越多。
- 止血和回退：切回手动 / 自动（即时生效）；从清单删掉用户条目并重建会话；内置条目删不掉，所以内置清单必须窄（Q3）。
- 由什么保证：Q3 的措辞改动让用户在确认框里看到这件事；内置清单的测试 `credential_builtin_is_subcommand_level` 断言除 `gh`、`ssh` 外全部带子命令；`rsync` / `scp` / `sftp` 在拒收名单。

**S4 切到全开时有审查进行中、有必问待审批、有卡片**
- 会出什么事：三种待处理项各走各的：审查中的越界审批 → 重新求值为 `Allow`、复查通过 → `ModeSwitchAllows`（子状态保持 `InProgress`，迟到结果 `Stale`）；`git push` 必问 → 仍询问；`git pull && git push` → 整条仍询问；卡片 → 不动。
- 止血和回退：切回手动即可；已放行的不能收回（需求 7.3 第 6 条的既定行为）。
- 由什么保证：验收 2 的表驱动测试（FR11 原文逐句）+ `mode_switch_release_cases` 覆盖这几种同时存在。

**S5 `PathResolver` 在某个平台上行为不一致（比如 Windows 大小写、macOS `/private` 与 `/var` 链接、链接后接 `..`）**
- 会出什么事：`~/.ssh` 经 `/private/var/...` 别名、或 `link/../config` 这类写法逃过 `PathUnder`。
- 止血和回退：`OsPathResolver` 按文件系统顺序逐分量解析，两边（规则模板与目标）都经同一个解析器；失败按不可解析询问。
- 由什么保证：`iwork-host` 的真实文件系统测试在三平台 CI 跑（符号链接、`..`、**链接后接 `..`**、大小写、`/private` 别名各一条）；`FakeFs` 用同一套顺序，核心测试复刻。

**S6 紧急路径：某条内置规则导致误放行或误拒（F-17）**
- 会出什么事：误拒：比如白名单漏了一个日常命令的选项，自动档下每条都问，用户寸步难行；误放行：比如某条危险选项没登记，自动档放行了写文件。
- 止血和回退（只用现有能力，不加「关闭底线」之类的开关）：
  1. **停**：`CancelAll`（对话内全部回合）或「完全退出 iWork」（`ShutdownDaemon{cancel_running: true}`，T04）：按取消流程结束各回合，进程树由 T05 监管收掉；待审批作废，卡片按 T01 规则处理。
  2. **退**：装回上一个验证过的 iWork 版本（T04 升级流程「保留上一个可用组合」）。规则集随代码发布，退版本就退了规则；内置条目不入库，没有迁移要撤。Claude Code 版本不变（FR17 固定）。
  3. **核**：重启后 `ListRules` 里内置条目的 `ruleset_version` 等于预期旧版本；审计里新事件的 `ruleset_version` 已变；用 `bash_corpus` 里的日常命令组在本机跑一遍冒烟。
  4. **建**：用户重新发消息即开新会话、取新快照；活规则（记住 / 撤销）不受版本影响。
  5. **修**：加行、升 `ruleset_version`、过对拍语料与日常命令组，再发版。
- 由什么保证：`everyday_commands_not_denied` 表驱动测试（`git status`、`ls`、`cargo build`、`npm test` 在自动档放行）；第 15 节第 8 步的回退演练（在临时验证副本里装两个版本的 daemon、按上面五步走一遍并记录）。

**S7 两个成员同时请求同一动作，一个被拒**
- 会出什么事：M1 单成员，M2 起多成员共享一个对话的拒绝记忆。A 的请求被拒后，B 的同一指纹请求自动拒绝（AC05 要求）；B 正在等待的询问不会被追溯拒绝（已弹出的卡片由用户处理），但 B 的任何非用户放行路径（AI 审查、切档）都会在复查时被拦下。
- 由什么保证：`denial_memory_cases` 的并发用例 + `late_review_pass_after_sibling_denied_asks_user`。

## 10 性能（需求第 14 章；AGENTS.md「动到热路径必须附基准」）

hook 路径是热路径：每次工具调用都要过 `on_permission`，它的耗时直接加在成员每一步上。预算：取事实 + 归一 + 求值 ≤ 1ms（P95，普通命令、规则快照 ≤ 500 条）。

- `iwork-shell::parse` 对一行命令是微秒级（`peg` 生成的解析器，不缓存）；复杂脚本（几 KB 的 here-doc）毫秒级，可接受。
- `PathResolver::resolve` 每个路径词几次 `lstat`；一条命令通常 ≤ 5 个路径词；保守归类后含展开的命令直接 `Unparsable`，不解析路径。
- 规则匹配是线性扫描（条目数小），`Boundaries` 在快照生成时预先按层分好，求值不再过滤。决策锁按对话分，不同对话互不等待；锁内只有纯计算与一次 `commit`。
- 基准：`iwork-bench` 加 `approval_evaluate`（T11 填数）：① 1 条 `git status` × 内置规则集；② 20 段管道 + 10 个路径词；③ 内置 + 500 条记住的规则。T07 交付基准代码与本机数值（报告里附），阈值由 T11 定。
- `ApprovalEvaluated` 每次调用一条事件：16 成员压力下每秒几十条，组提交吃得下（T02 写入基准）；事件体带全部子动作摘要与 ID 列表，单条仍在几 KB 内。

**Q3 内置需凭据命令清单的条目、`scp` / `sftp` / `rsync` 的去留、「全开档守住底线」的措辞**（已决定：(a)；第 9 章与确认框文案由 supervisor 改）
- 问题：清单内命令在全开档不询问、在沙箱外运行。整程序条目（`docker`、`aws`）等于在全开档放开该程序能碰到的一切；`scp` / `sftp` / `rsync` 这类传输工具虽然本地路径动作仍过底线（3.4），但整程序进清单后，全开档可以不询问地把任意工作区外、非底线的文件传到远端（第 1 轮审查 F-12）。第 9 章「使全开档不询问也守住底线」与全开确认框文案「凭据和 iWork 数据仍受保护，只有需凭据的命令（如 git pull）会在沙箱外运行」没有说清「清单内命令不受此保护」。
- 建议：(a) 内置清单按 4.2 表：`git` 的 `pull` / `fetch` / `clone` / `push` / `ls-remote` / `remote` / `submodule` / `lfs`；`docker` 的 `login` / `logout` / `pull` / `push`；`npm` / `pnpm` / `yarn` 的 `publish` / `login` 等账号类子命令；`cargo` 的 `publish` / `login` / `owner` / `yank`；`twine upload`；`gem push` / `signin`；整程序只有 `gh` 与 `ssh`。`scp` / `sftp` / `rsync` **不内置且进拒收名单**（它们没有子命令，等于不能加入清单；要传文件用 `git` 或经亲手执行卡片）。云服务 CLI（`aws`、`az`、`gcloud`、`kubectl`、`helm`、`terraform`）不内置，用户按项目添加（AC41 的 `terraform apply` 就是这种用法；FR11 已写「清单外又需要凭据的命令会直接失败，可加入清单」）。第 9 章与确认框文案补一句：「需凭据命令清单内的命令在沙箱外运行，不受沙箱底线保护，审批只看得到命令本身」。
- 备选：(b) 内置云服务 CLI 整程序条目，开箱即用但全开档风险大；(c) `gh` 也不内置；(d) `scp` / `rsync` 内置但只在手动、自动档生效（需要清单条目带 `applies_in`，Q1 的类型支持，但「清单内命令全开放行」是 FR11 原文，改它要改需求）。
- 依据：需求 FR11、第 9 章已知限制第 1 条；技术设计 7.2c 的例子写了 `gh`；派活说明第 2 条；第 1 轮审查 F-12。代价 (a)：用户第一次用 `aws` 会失败一次再去加条目；`rsync` 用户要换工具或亲手执行。影响范围：内置条目表、拒收名单、第 9 章一句话、T09 确认框文案。

**Q4 不可解析命令在全开档的结果**（已决定：(a) 三档都询问）
- 问题：技术设计 7.1 写「解析不了的命令一律询问」，没写档位；FR11 写全开档「边界内外都不询问」。
- 建议：(a) 三档都询问（现行文档的字面含义，第 1 轮审查 F-18）。理由：文字层面判断不了展开结果，问比猜安全；全开档本来就只守底线与 `git push`，多一类询问的代价是用户在全开档偶尔要点一下。
- 备选：(b) 手动、自动询问，全开放行——与 FR11「边界内外都不询问」更一致，但 `eval` 一类写法在全开档就成了绕过必问的通道（`eval "git push"` 不会被识别成 `Push`）。
- 依据：技术设计 7.1 Bash 段；FR11 全开档定义；任务卡范围 1。影响范围：默认层 `default.unparsable` 一条条目的 `applies_in`。

**Q5 「无副作用工具」要不要一个专门的 `ActionKind`**（已决定：(a) 不加）
- 问题：`Agent`、`Skill`、`TodoWrite` 等按 7.1 放行，但 `ActionKind` 没有对应种类。
- 建议：(a) 不加种类：归一为 `Unclassified` + `ToolName`，由 `Default` 层内置条目 `default.harmless.<工具名>` 放行三档；审计里 `layer_hit = Default`、`matched = [该条目]`，看得出是「登记过的无副作用工具」而不是真的未归类。
- 备选：(b) 加 `ActionKind::NoSideEffect`（proto `ACTION_KIND_NO_SIDE_EFFECT = 12`，additive），审计更直白，多三处改动。
- 依据：技术设计 7.1 工具表；`action.rs`。代价 (a) 零；(b) 半小时。可随 Q1 一起决定。

**Q6 整文件 `Write` 命中底线时不生成亲手执行卡片**（已决定：(a)）
- 问题：AC36「写明精确命令或补丁」；`Proposal::Patch{old, new}` 需要旧内容，`Write` 工具只给新内容，核心读不到文件。

- 备选：(b) 给 `Proposal` 加 `WholeFile{path, content}` 变体，host 的 `apply_patch_as_user` 加整文件写入——改 T01 类型与端口。
- 依据：`user_action.rs::Proposal`；`exec.rs::UserPatchRequest`；技术设计 7.2a 第 1 条「Write / Edit 取目标路径与新旧内容」（Write 没有旧内容，设计写法有歧义）。影响范围：卡片生成条件一行；Agent 多一步。功能范围取舍，交产品负责人。

**Q7 组合命令被拒时拒绝记忆记哪些指纹**（已决定：(a) 记全部）

- 备选：(b) 只记代表动作——与 AC05「任何方式都不能绕过」冲突，不推荐。
- 依据：AC05；`approval.rs::Approval.action`。影响范围：`denial.rs`、`Approval` 加一个字段（Q8）。

**Q8 `Approval` 加 `call` 字段：恢复所需的最小调用记录（已决定：只加不改；第 3 版把字段范围从「指纹集合」扩成完整调用记录，仍是只加）**
- 问题：拒绝记忆（Q7）、一次性放行的绑定（6.2）、崩溃后重建 `PendingAsk` 与 `GrantOnce`（E1）、非用户放行前的资格复查（6.1）都需要被审批调用的完整归一结果；T01 的 `Approval` 只有单个 `action`。只存指纹集合不够：重建不出 cwd、形状、沙箱位置、有序子动作与原始输入摘要（第 2 轮复审 2/F-3）。

## 16 ADR（由 developer 随实现写入 `docs/adr/`，每条一个文件；编号合入时由 supervisor 统一）

**ADR-T07-a Bash 命令用 `brush-parser` 解析，隔离在 `iwork-shell`，只放行能证明安全的形态**
- 背景：审批要按文字理解 Bash 命令，解析器的质量直接决定底线能不能被绕过；候选见 3.3。完整建模 Bash 语义不可能不漏。
- 决定：用 `brush-parser`（MIT、活跃、纯 Rust、完整 bash 语法、词不展开）；只在 `iwork-shell` 里出现，对外是我们自己的小 AST；小 AST 表达不了的形态与任何展开、通配、`cd`、前置赋值都返回 `Unparsable` → 三档询问、不记住、不审查；子命令只在「白名单程序 + 全词字面 + 无危险选项」时归为读 / 写 / 删除，其余归执行。
- 备选及放弃原因：`tree-sitter-bash`（容错解析与需求相反，带 C 构建）；`yash-syntax`（GPL-3）；`conch-parser`（无人维护）；自写（攻击面）；完整语义建模（漏一处即放行有副作用的命令，第 1 轮审查）。
- 影响：传递依赖多约 70 个 crate；换解析器只改 `iwork-shell`；自动档下带 `$VAR` 的命令会多问（已知限制）；对拍语料与 `Unparsable` 规则不随解析器变。

**ADR-T07-b 需凭据命令的 hook 侧匹配与 `excludedCommands` 同源、同一会话快照，匹配器三态且只许更保守**
- 背景：Claude Code 按自己的规则决定哪些命令排除出沙箱；iWork 要在求值前知道这件事，两边不一致时「审批以为在沙箱内」是唯一会让沙箱外执行绕过审批的路径；运行中的 CLI 不会跟着规则表变。
- 决定：会话启动时算一份 `SessionSnapshot`，T06 注入 CLI 的与引擎 hook 侧用的是同一个对象；求值用三态匹配器，`Ambiguous` 按沙箱外；对拍语料进 CI，Claude 为 Outside 的行我们不得为 Inside；清单变化只对新会话生效，立即生效须重建会话；固定版本变化先重跑语料。
- 备选及放弃原因：两边各写一份规则（迟早分叉）；引擎实时读规则表（与 CLI 不一致，F-5）；一律按沙箱外求值（每条 `git status` 都要问，不可用）。
- 影响：匹配器会多问（带路径前缀的命令）；版本升级多一步对拍；清单改动后要重开会话才生效。

**ADR-T07-c 拒绝记忆与一次性放行是对话内状态、在每对话决策锁下更新与复查、由事件重放重建**
- 背景：AC05 的拒绝记忆与等待上限中断后的一次性放行都是「某些动作指纹在本对话里的临时状态」；非用户的放行路径（AI 审查、切档）与用户的拒绝之间有竞态；`RuleMatcher` 表达不了精确指纹集合，它们也不该成为可查看、可撤销的规则。
- 决定：两者都在引擎内存里，键是对话，与待审批、审查任务同在一把决策锁下；拒绝记忆记被拒调用的全部子动作指纹；`Approval.call` 持久化恢复所需的最小调用记录（工具、cwd、形状、沙箱位置、有序子动作、原始输入摘要、归一摘要）；一次性放行绑定回合与这份记录（两个摘要都要相等），七步跑完只豁免 `Ask`；AI 审查通过、切档放行、一次性放行答复前都在锁下用当前状态重判资格（`Deny`、`ForceAskOnce`、新出现的必问都不合格），AI 审查结果先判 `Stale` 再复查、只 `apply` 一次；两者是 `approval`、`conversation`、`turn` 流事件的确定性函数，启动时重放重建，重放与在线用同一个函数；审计里 `layer_hit` 分别为 `DenialMemory` 与 `Remembered`。
- 备选及放弃原因：只记代表动作（拆开重发可绕过，F-3）；只按指纹集合放行（调序、改连接符、重复、改重定向归属都能命中，第 2 轮 1/F-2）；只查 `AutoDeny`（放不过用户新消息后的强制询问，第 2 轮 1/F-4）；先 `apply(Passed)` 再复查（回不到 `Pending`，第 2 轮 2/F-4）；无锁（迟到的审查通过放行刚被拒的动作，F-4）；生成临时 `RuleEntry`（需要精确指纹集合匹配器，且会出现在规则列表里）；加投影表（多一份真值）。
- 影响：引擎启动要重放近期对话的审批事件（数量小）；崩溃后行为与在线一致；`Approval` 多一个 `call` 字段（Q8）；没有 `call` 的旧审批恢复后重新询问。
