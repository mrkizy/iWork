## 0 一页总览

T03 交付 `iwork-ipc`：客户端与后台服务之间唯一的一条线。它要同时守住三件事——两端都只跟同用户、同签名的进程说话（需求 11「不把 localhost 视为可信」）；持久事件按序号不丢不重；一个慢客户端拖不垮后台服务。关键决定：

| 决定 | 内容 | 依据 |
| --- | --- | --- |
| 传输是 trait，三平台各一个实现，远程只留 trait | `Listener` / `Connection` / `Connector` 三个 trait（2.2）；macOS、Linux 用 Unix domain socket，Windows 用命名管道；`Connection::peer()` 把对端身份交给上层，两端都能调 | 设计 3.1、3.8；卡「范围 1、6」 |
| **双向**校验：后台验客户端，客户端也验后台，同一个纯函数 | 两端在发出任何帧之前都调 `judge_peer`（2.4）：第 1 步同用户，第 2 步同签名或同安装身份。三平台把操作系统给的事实装进 `PeerIdentity`，判定三平台一份、都能单测 | `AGENTS.md`「建连先校验对端同用户、同签名」对两端都成立；设计 3.2；卡「验收 1」 |
| 核验的是**正在运行的映像**，不是路径上的文件 | Linux 读 `/proc/<pid>/exe` 的 inode；macOS 用审计令牌拿到进程的动态 `SecCode`，证书与 cdhash 都从它读；Windows 验证与取证书用同一个文件句柄，开句柄前后两次查进程映像路径一致才算绑定。绑定实测不过的平台暂不支持（2.4b；Q1 已决定） | 设计 3.2 第 2 步 |
| 信任根在进程启动时固定，运行中不扩大 | 有证书的构建只认自己的叶证书 SHA-256；无证书的构建只认启动时读进内存的安装清单 `iwork-manifest.json`（只登记这一版的映像身份），之后不再读磁盘（2.4、2.4a） | 设计 3.2；Q1、Q2 已决定 |
| 升级是后台自己的事：发现安装的程序换了版本就自行重启，回合按中断处理 | 客户端不结束任何进程；身份不匹配时（无论是哪一端拒绝）客户端只显示中性的「后台服务与客户端版本不一致」，给「重新打开 iWork」「查看诊断」两个出口，并指数退避重连，不发 `Hello`、不接受陌生对端、不猜谁新谁旧（2.4c）。检测与重启归 T04。跨主版本仍是数据库门备份后拒绝启动、只承诺回退旧程序 | 设计 4「升级」（`bf73ed9`，产品负责人 2026-11-10）；设计 5.5 |
| `--dev-trust` 整段代码只在 `dev` feature 下存在，两端都一样 | 解析开关、`TrustPolicy::DevTrust`、日志字样全部 `#[cfg(feature = "dev")]`；CI 查三样：feature 图里没人默开 `dev`、打包产物里 grep 不到、发布进程收到 `--dev-trust` 时拒绝启动 | 设计 3.2 第 3 步；卡「验收 2」 |
| 帧上限与路由键是协议常量/类型，放 `iwork_proto::{limits, routing}` | `MAX_FRAME_LEN = 4 MiB`、`MAX_CHUNK_DATA = 1 MiB`、`MAX_HELLO_LEN = 64 KiB`；`StreamKey` 是 app 与 ipc 都能依赖的纯值类型 | 设计 3.3；T01 3.3 |
| 握手：先验身份，再读 `Hello`，`check_hello` 不过就回错误并断开 | 身份不过**不发任何帧**直接断开并审计；`Hello` 过了 `check_hello` 才回 `Welcome`；在此之前收到的任何别的帧都当协议违规断开 | 设计 3.3；卡「验收 3、3a」；`crates/iwork-proto/src/handshake.rs` |
| 命令串行；会写视图的查询走事件流的交接；其余查询并发 | 命令按到达顺序一个一个处理。会改视图成员或内容的查询（打开对话、翻页、各列表）不走独立查询道：连接把流暂停为缓冲，在一个读事务里取结果与 seq S，先发 ≤ S 的事件、再发结果、再发 > S 的事件——与订阅快照同一条交接路径，客户端只按到达顺序应用，不比 seq。不改视图的查询（`ReadArtifact`、`ListModels`）走并行查询道（≤ 4） | 设计 3.4；需求 14「唤醒延迟 ≤ 1s」；第 5 轮复审 5/F-1、5/F-2，产品负责人「从根因上修」 |
| **每条连接一条按 seq 排好的事件流**，范围只是过滤条件 | 连接上所有范围的路由键取并集作为过滤；流有一个游标，不漏、不重、严格递增。范围集合变化就整条重订阅：快照（全部活动范围的视图）+ 从快照 seq 起补发 + 实时。客户端不做跨订阅合并，不需要实体版本（2.8、2.11） | 设计 3.5；卡「验收 4」；第 3 轮审查后产品负责人选定 |
| 快照只替换视图，不删全局实体 | 快照的每个部分替换对应范围的视图（成员列表 + 实体内容）；分页查询结果只更新视图成员；实体表只由事件流改。所以不存在「版本挡掉增量」「删除后复活」「分页缺席误删」（2.8「为什么第 3 轮的三类问题不再成立」） | 设计 3.6；第 3 轮 3/F-1～F-3 |
| 补发读存储、按登记时的 `head` 封顶、缓冲算进 8 MiB、补发有保底预算 | ipc 不缓存历史；`EventSource::replay(keys, from, to, limit)` 带扫描游标；补发缓冲与发送队列共用 8 MiB；放不下、等预算超时、交接超时都走 `fail_connection` 关掉这条连接，客户端重连续传；同游标第二次被关由客户端改用 `from_seq = 0` 拿快照——正确性靠这一条；1 MiB 的补发保底只是让多数情况不至于一满就断的优化 | 设计 3.5；第 1 轮 F-5、第 2 轮 2/F-4、第 3 轮 3/F-6 |
| 历史与实时走同一套路由 | 补发返回的每条事件都带 `routes`，由 daemon/app 用同一个 `routes_for` 算；回合、审批事件带会话 ID（Q3 已决定） | 设计 2「ipc 只依赖 proto」 |
| 背压：每连接 8 MiB 有界预算，满了先合并增量，仍满就关闭这条连接；流的任何异常只有这一个出口 | 响应永不丢；瞬时事件先合并相邻 `MessageDelta`，仍满则 `fail_connection(QueueFull)`。补发等预算超时、交接超时、发布停滞同样走它。客户端只有一条恢复路：重连、一次写出全部 `Subscribe` 续传；同游标第二次被关就改用 `from_seq = 0` 拿快照。没有「落后」状态与落后通知（2.9） | 设计 3.5；需求 14；卡「验收 5」；第 7 轮 6/F-2、6/F-4、6/F-5 |
| `published_head` 有启动基线 | `serve` 接受连接前把库里已持久化的 head 设为基线，之后由有序 publish 推进；否则非空库重启后第一次交接等不到 S | 第 7 轮 6/F-3；2.10 |
| 客户端只有一个有序出口 | 持久事件、会写视图的查询结果、快照都从 `Incoming` 按到达顺序出来；`view_query` / `subscribe` 的 future 只说完成或失败 | 第 7 轮 6/F-1；2.11 |
| 审计走 `tracing` 的 `iwork.ipc.audit` target | 拒绝连接记 pid、uid、可执行文件路径、原因；不记任何消息内容；不新增领域事件 | 卡「注意」；设计 10.3 |

## 1 现状与约束

**现状**（T01 已合入 main，`bb6d69a`；技术设计第 4 节已按 Q5 改写，`bf73ed9`）：

- `iwork_proto::handshake::check_hello(hello, server_major)` 已实现，两个方向的单测已有；`iwork_proto::PROTOCOL_MAJOR` 由构建脚本从包名解析。`iwork-proto` 已经有手写的纯 Rust 模块（`handshake`、`compat`），再加 `limits`、`routing` 两个有先例。
- `iwork-ports::store::StoragePort::read_events(filter, from, limit)` 按流过滤读事件；`DomainEvent::stream()` 给出每条事件的 `(StreamKind, Option<StreamId>)`。回合事件的流是 `turn:<turn_id>`，审批事件的流是 `approval:<approval_id>`；产品负责人已决定给这些事件加会话 ID（Q3）。

- 技术设计第 4 节「升级」已改为：后台发现安装的程序换成新版本就自行重启，运行中回合按中断处理、待审批保留，客户端不结束旧后台。
- `Cargo.lock` 里已经有 tokio 1.54、tokio-util 0.7、tracing 0.1、libc、windows-sys 0.61、sha2 0.10（经 tauri 等传递进来），T03 直接加成 workspace 依赖不会引入新的许可。
- CI 三平台矩阵在 `.github/workflows/ci.yml`，Windows 用 Git Bash 跑同一套脚本。
- `docs/design/t0-findings.md` 没有 IPC、代码签名、命名管道的任何实测。

**约束**：

- 依赖只向下：`iwork-ipc` 只依赖 `iwork-proto`（设计 2）。所以 ipc 看不到 `DomainEvent::stream()`，也看不到 `StoragePort`；补发、快照、路由都要通过 ipc 自己定义的 trait 由 daemon 注入（2.10）。`iwork-app` 不能依赖 `iwork-ipc`，两者共用的值类型只能放在 `iwork-proto`。
- 安全不变量（`AGENTS.md`）：只走 Unix domain socket / 命名管道，建连先校验同用户、同签名；任何构建都不开 TCP 端口，含 `--dev-trust`。「建连先校验」对客户端一侧同样成立。
- 安全设计原则（需求 v1.50、v1.69）：先找现有机制覆盖缺口，覆盖不了记已知限制，不为一个缺口加一串新机制。本方案新加的东西只有 ipc 自己的 trait、两个常量/类型模块和一个安装清单文件；对端校验没有超出设计 3.2 的两步，只是两端都做。
- 状态变化一律经事件；命令只返回受理结果与 `seq`（设计 3.4）。ipc 不解释命令，只搬运。
- 性能（需求 14）：流式输出延迟 P95 ≤ 100ms；唤醒 ≤ 1s；daemon 空闲 CPU < 1%、内存 ≤ 80MB。ipc 是这几条的热路径，见第 6 节。
- 文档、日志用中文，标识符、日志字段用英文。

**两问的答案**（good-code「动手前」）：

- 再加一种东西要动几处？加一种订阅范围：`frame.proto` 的 `SubscriptionScope` 一个 oneof 字段 + `iwork-app::subscription` 两张表各一行（范围 → 路由键、范围 → 快照查询）；ipc 不改。加一种瞬时事件：`events.proto` 一个 oneof 字段 + 合并表（2.9）一行（能合并的才加）。加一个平台：`transport/` 下一个文件实现三个 trait + `peer/` 下一个文件装 `PeerIdentity`；`judge_peer` 不改。加一种事件：`routes_for` 加一个分支（真值在 app，历史与实时共用）。
- 改这里牵动谁？帧格式与上限牵动 `iwork-client-core`（T09）与 `ReadArtifact` 受理（T10）；`RequestHandler` / `EventSource` / `Publisher` 的签名牵动 `iwork-daemon` 的组合（T04）与 `iwork-app` 的受理（T10）；`LocalEndpoint` 与 `SelfIdentity` 牵动 T04 的拉起、单实例锁与升级重启、T09 的连接与等待提示；安装清单牵动打包流程；路由键的约定牵动 T02（存储读取方式）与所有发事件的地方。

### 2.2 传输 trait 与三平台实现（设计 3.1、3.8）

```rust
/// 本机端点。远程实现（D05，QUIC）以后加 Remote 变体，协议与续传语义不变。
pub enum Endpoint { Unix(PathBuf), Pipe(String) }

pub trait Listener: Send {
    type Conn: Connection;
    fn accept(&mut self) -> impl Future<Output = io::Result<Self::Conn>> + Send;
    fn endpoint(&self) -> &Endpoint;
}

pub trait Connection: Send + 'static {
    type Read: AsyncRead + Unpin + Send;
    type Write: AsyncWrite + Unpin + Send;
    /// 操作系统告诉我们的对端身份。两端都在读写任何字节之前调用：服务端看客户端，客户端看服务端。
    fn peer(&self) -> impl Future<Output = Result<PeerIdentity, PeerError>> + Send;
    fn into_split(self) -> (Self::Read, Self::Write);
}

pub trait Connector: Send + Sync {
    type Conn: Connection;
    fn connect(&self, endpoint: &Endpoint) -> impl Future<Output = io::Result<Self::Conn>> + Send;
}
```

写法沿用 T01 的 RPITIT + `Send`（ADR-0002），不用 `async-trait`。`Server` 与 `Client` 对这三个 trait 泛型；测试用进程内的 `tokio::io::duplex` 实现一个 `MemoryTransport`，`peer()` 返回测试指定的身份（两端各自指定）——这样订阅、背压、握手、双向校验的测试不碰文件系统，也不依赖平台。

| 平台 | 实现 | 要点 |
| --- | --- | --- |
| macOS、Linux | `tokio::net::{UnixListener, UnixStream}` | `bind` 前由调用方持有 `run/daemon.lock`（T04），`bind` 自己负责删掉残留的 socket 文件再绑定（前置条件写进文档注释，T04 的并发启动测试会验证）；`peer()` 两端都用 `UnixStream::peer_cred()` 取 uid/gid/pid，再按平台补映像身份（2.4） |
| Windows | `tokio::net::windows::named_pipe::{ServerOptions, ClientOptions}` | 第一个实例 `first_pipe_instance(true)`（名字已被占就报错，由 T04 当「已有实例」处理），之后每接受一个连接立刻 `create` 下一个实例；`reject_remote_clients(true)`；安全描述符用 SDDL `D:P(A;;GA;;;<当前用户 SID>)` 经 `ConvertStringSecurityDescriptorToSecurityDescriptorW` 生成，走 `create_with_security_attributes_raw`。客户端 `ClientOptions::open`，`ERROR_PIPE_BUSY` 时 `WaitNamedPipeW` 重试。服务端取客户端 pid 用 `GetNamedPipeClientProcessId(handle)`，**客户端取服务端 pid 用 `GetNamedPipeServerProcessId(handle)`**，之后两端走同一条进程校验路径（2.4） |

### 2.3 端点路径与目录权限（设计 3.1、5.1）

| 平台 | 路径 | 校验 |
| --- | --- | --- |
| macOS | `~/Library/Application Support/iWork/run/d.sock` | 路径字节数 ≤ 103（`sun_path` 104 含结尾 0）；目录按 0700 创建；已存在则 `symlink_metadata` 不是符号链接、属主 = `geteuid()`、权限位 `& 0o077 == 0` |
| Linux | 设了 `XDG_RUNTIME_DIR`：`$XDG_RUNTIME_DIR/iwork/d.sock`；没设：`<数据目录>/run/d.sock`，数据目录 = `$XDG_DATA_HOME/iwork/`，`XDG_DATA_HOME` 没设时按 XDG 基本目录规范取 `~/.local/share/iwork/` | 路径字节数 ≤ 107；其余同 macOS |
| Windows | `\\.\pipe\iwork-<当前用户 SID 文本>` | 无目录；DACL 只有当前用户一条 ACE（2.2） |

不满足任何一条返回带路径与原因的 `EndpointError`（`PathTooLong{path, max}`、`InsecureDirectory{path, found_mode, owner}`、`IsSymlink{path}`），不自动修复：目录权限不对是环境问题，悄悄 `chmod` 会把别人放进来的东西当成自己的（设计 3.1「不满足则拒绝启动并提示」）。

目录权限与 DACL 是第一道门，挡的是其他用户；同用户的进程它挡不住，所以 2.4 的双向校验才是对「假后台」「假客户端」的真正防线。

**数据目录的真值**：设计 5.1 的数据目录由 T02 的 `iwork-store` 实现，客户端依赖不了它，所以 ipc 按设计 3.1 的字面路径自己算 socket 位置，只算这一个用途。两处对同一个根目录的算法会分叉，所以 daemon（同时依赖两者）加一条对拍测试 `socket_dir_is_under_data_dir`：macOS 与 Linux 无 `XDG_RUNTIME_DIR` 时，`LocalEndpoint::run_dir()` 的父目录必须等于 store 的数据目录。这是 good-code「抄不了的配一条对拍测试」的做法；更干净的做法（新建一个纯路径 crate）要改 T01 的 crate 清单，见第 9 节。

### 2.4 对端身份校验（设计 3.2），两端都做

**类型**（`peer/mod.rs`，全平台编译，纯数据）：

```rust
pub struct PeerIdentity {
    pub pid: u32,
    pub user: UserId,                 // Unix: Uid(u32)；Windows: Sid(String)
    pub exe: Option<PathBuf>,         // 审计用；判定不看它（2.4b 的「同目录」检查除外）
    pub signer: SignerIdentity,
}
/// 对端正在运行的映像的身份。怎么保证「是运行中的映像而不是路径上的文件」见 2.4b。
pub enum SignerIdentity {
    /// 有效的代码签名，带叶证书哈希（macOS、Windows）
    Certificate { leaf_sha256: [u8; 32] },
    /// 没有证书：Linux 的文件哈希、macOS 的 ad-hoc cdhash、Windows 的未签名文件哈希
    Image(ImageId),
    /// 取不到：进程已退出、/proc 不可读、WinVerifyTrust 报结构错误、映像绑定没有通过
    Unavailable { reason: String },
}
/// 映像身份的两种形式。清单里按同样的标签写：`sha256:<hex>`、`cdhash:<hex>`。
pub enum ImageId { Sha256([u8; 32]), CdHash(Vec<u8>) }

pub struct SelfIdentity {
    pub user: UserId,
    pub signer: SignerIdentity,       // 自己是哪一种，决定走哪条判据
    pub exe_dir: PathBuf,             // 安装目录（2.4b）
    pub manifest: Option<Manifest>,   // 启动时读一次就固定在内存里；之后磁盘上的清单怎么变都不影响（2.4a）
}
pub enum TrustPolicy {
    /// 发布与默认：第 1、2 步都查
    RequireSigner,
    /// 只在 dev feature 下存在：跳过第 2 步，第 1 步照查
    #[cfg(feature = "dev")]
    DevTrust,
}
pub enum PeerVerdict { Accepted { signature_checked: bool }, Rejected(RejectReason) }
pub enum RejectReason {
    DifferentUser { peer: UserId, own: UserId },
    SignerMismatch { peer: SignerSummary, own: SignerSummary },
    ImageNotTrusted { image: ImageId },
    NoManifest { expected_at: PathBuf },
    OutsideInstallDir { exe: PathBuf, install_dir: PathBuf },
    Unavailable { reason: String },
}

/// 唯一的判定入口。纯函数，三平台同一份，服务端验客户端、客户端验服务端都调它。
/// 信任根全在 own 里，启动时定下就不变：没有任何运行期输入能扩大它。
pub fn judge_peer(own: &SelfIdentity, peer: &PeerIdentity, policy: TrustPolicy) -> PeerVerdict;
```

判定规则（按顺序，第一条命中即返回）：

1. `peer.user != own.user` → `DifferentUser`。任何 policy 都查。
2. policy 是 `DevTrust` → `Accepted{signature_checked: false}`。
3. `peer.signer` 是 `Unavailable` → `Unavailable`（拿不到身份按拒绝处理，和 hook「失败即关闭」一个道理）。
4. `own.signer` 是 `Certificate{own_leaf}`：要求 `peer.signer == Certificate{leaf}` 且 `leaf == own_leaf`，否则 `SignerMismatch`。**只认自己的叶证书**（Q2 已决定），清单对这条分支没有任何作用。
5. `own.signer` 是 `Image(_)`（Linux 永远是；macOS、Windows 的无证书构建也是）：`own.manifest` 为 `None` → `NoManifest`（无证书构建没有清单就谁也连不上，日志会说清楚——这就是开发期为什么需要 `--dev-trust`）；`peer.exe` 的目录 ≠ `own.exe_dir` → `OutsideInstallDir`（设计 3.2「可执行文件路径属于安装目录」）；`peer.signer` 不是 `Image(id)` 或 `id ∉ own.manifest.binaries` → `ImageNotTrusted`；否则 `Accepted{signature_checked: true}`。

第 4、5 条里「有证书的后台 × 无证书的客户端」或反过来，都被拒：同一次构建出来的两个二进制要么都签了要么都没签，混搭就是不对的组合。

**信任根在启动时固定**：`SelfIdentity::detect()` 只在进程启动时跑一次，证书哈希来自自己正在运行的映像，清单在那一刻读进内存。之后磁盘上的清单被改、被换、mtime 变了，正在运行的进程都不看。理由：能往 JSON 里写一行的同用户进程，并没有控制正在运行的代码，不能因此变成可信对端；运行中扩大信任，等于把 L2「能改安装目录的攻击者」从「要换掉二进制」放宽到「改一个文本文件」。升级期间新旧版本互不相认是预期行为，出路见 2.4c。

**两端怎么用它**：

| 端 | `own` | `peer` 从哪来 | policy | 不过怎么办 |
| --- | --- | --- | --- | --- |
| 后台服务 | 启动时 `SelfIdentity::detect()` 一次 | `Listener::accept` 后 `Connection::peer()` | `ServerConfig.trust` | 不发任何帧，关闭，审计 `peer_rejected` |
| 客户端 | 启动时 `SelfIdentity::detect()` 一次 | `Connector::connect` 后 `Connection::peer()`（Unix：`peer_cred` 给服务端 pid；Windows：`GetNamedPipeServerProcessId`） | `ClientConfig.trust`（发布恒 `RequireSigner`；`iwork-client` 的 `dev` feature 下可为 `DevTrust`） | **不发 `Hello`**，关闭，返回 `ConnectError::PeerRejected(reason)`；T09 按 2.4c 显示等待提示并退避重连 |

客户端验后台用的是同一个 `judge_peer`、同一个清单、同一套平台代码（只是 pid 的来源不同），没有第二套逻辑。它防的是 S10：同用户的进程抢先占住管道名或 socket 路径、回一个合法的 `Welcome`，把用户输入、附件、审批选择都骗过去。

**三平台怎么取** `PeerIdentity`（两端共用；「对端 pid」在服务端是客户端的，在客户端是服务端的）：

| | 同用户 | pid | 映像身份 | 备注 |
| --- | --- | --- | --- | --- |
| Linux | `SO_PEERCRED`（`UnixStream::peer_cred()`）的 uid | 同上 | 打开 `/proc/<pid>/exe` 得到 fd（它是指向 inode 的魔法链接，读到的就是对端正在跑的那份映像，磁盘上的路径被替换、改名、删除都不影响），读全文算 SHA-256 → `Image(Sha256)`；`readlink` 的结果去掉 ` (deleted)` 后缀后作为 `exe` | pid 在 `peer_cred` 与打开 `/proc` 之间被复用的窗口极小但存在，记已知限制 L1 |
| macOS | `getpeereid`（`peer_cred()` 的 uid） | `LOCAL_PEERPID` | `getsockopt(SOL_LOCAL, LOCAL_PEERTOKEN)` 取 `audit_token_t`，`SecCodeCopyGuestWithAttributes(kSecGuestAttributeAudit)` 拿到对端的**动态** `SecCode`（审计令牌不受 pid 复用影响），`SecCodeCheckValidity(kSecCSDefaultFlags, NULL)` 验运行中映像的签名完整性，`SecCodeCopySigningInformation(kSecCSSigningInformation)` 从同一个对象取 `kSecCodeInfoCertificates[0]` 算叶证书 SHA-256 → `Certificate`；没有证书（ad-hoc）→ 取 `kSecCodeInfoUnique`（cdhash）→ `Image(CdHash)`；`kSecCodeInfoMainExecutable` 作为 `exe` | 用 `security-framework` crate 的 `code_signing` 模块；实施时核对版本是否暴露 `GuestAttributes::set_audit_token`，没有就用 `core-foundation` + 手写 FFI。全部行为列为需实测 N1 |
| Windows | 对端 pid → `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)`（句柄在手，pid 不会被复用）→ `OpenProcessToken(TOKEN_QUERY)` → `GetTokenInformation(TokenUser)` → `EqualSid` 与自己比 | `GetNamedPipeClientProcessId` / `GetNamedPipeServerProcessId` | 按 2.4b 的「两次查名 + 按句柄验」打开映像文件得到 `hFile`；`WinVerifyTrust(WINTRUST_ACTION_GENERIC_VERIFY_V2, WTD_UI_NONE, WTD_REVOKE_NONE, WTD_STATEACTION_VERIFY, hFile)`；返回 `ERROR_SUCCESS` 或 `CERT_E_UNTRUSTEDROOT`（自签证书，链不受信但签名完整）→ 用 `WTHelperProvDataFromStateData` → `WTHelperGetProvSignerFromChain` 从**同一次验证的状态**里取签名者证书，算 `CERT_SHA256_HASH_PROP_ID` → `Certificate`；`TRUST_E_NOSIGNATURE` → 对同一个 `hFile` 读全文算 SHA-256 → `Image(Sha256)`；其他错误（`TRUST_E_BAD_DIGEST` 等）→ `Unavailable` | 链不受信也接受的理由：判据是「和我同一把私钥签的」，不是「被微软信任的」；完整性错误仍然拒。需实测 N2 |

`SelfIdentity::detect()` 在进程启动时算一次：对自己跑同一套函数（Linux 读 `/proc/self/exe`；macOS 用 `SecCodeCopySelf` 的动态对象；Windows 对 `GetModuleFileNameW(NULL)` 打开句柄）；`exe_dir` = 自己的可执行文件所在目录；`manifest` = `exe_dir/iwork-manifest.json`（客户端与后台服务同目录，这是打包的前置条件）。算不出自己的身份（比如 `current_exe` 失败）直接拒绝启动——不知道自己是谁就没法判断别人。

#### 2.4a 安装清单 `iwork-manifest.json`（只给无证书构建用）

```json
{
  "manifest_version": 1,
  "app_version": "0.2.0",
  "binaries": {
    "iwork-daemon": ["sha256:<hex>", "cdhash:<hex，macOS 才有>"],
    "iwork-client": ["sha256:<hex>", "cdhash:<hex，macOS 才有>"]
  }
}
```

- **只登记这一版**：没有签名者列表，没有上一版条目。有证书的构建根本不读它（2.4 第 4 条）。
- **产生**：`scripts/write-install-manifest.sh <目录>`：对目录里的两个二进制算 `sha256:`（macOS 再用 `codesign -dvvv` 取 `cdhash:`）。打包流程调用它（放进 Tauri 的 `beforeBundleCommand` 或 T04 的升级打包，归属由 supervisor 定），放在两个二进制旁边。
- **位置与信任边界**：与两个二进制同目录。能改清单的人也能直接换掉二进制，所以不另加签名；清单不是密钥，只是「这一版装了什么」的登记。**启动时读一次**（2.4），之后不再碰磁盘上的它。
- **自己不在清单里**：启动时 `warn` 一条，不拒绝启动。清单坏了只会让对端连不上，不会放进来不该放的。
- **真实 .app 包上的补充**（T04 N5 实测，2026-11-11，`t0-findings.md` 7.1；产品负责人定）：
  - 事实：`tauri build` 没配签名身份时不做整包签名，主程序只有链接器的 ad-hoc 签名，包没有资源封印。包主程序（`CFBundleExecutable`）的静态代码对象代表整个包，按默认参数做静态校验会报 -67056（`errSecCSResourcesNotFound`）。所以客户端算不出自己的身份，后台判客户端时也得到 `Unavailable`。包里别的程序和散放的二进制不受影响；T03 的实测（6.3）只测过散放的二进制。
  - 改法：`peer/macos.rs` 的 `check_image_file` 静态校验带上 `kSecCSDoNotValidateResources`。主程序的代码页哈希照样逐页验，「改了还没调入的页」照样拒（`crates/iwork-ipc/tests/peer_bundle_macos.rs` 有用例；T03 实测脚本重跑见 `tools/t0/out/t04-t03-rerun/`）。清单外的映像照样以 `ImageNotTrusted` 拒。
  - 代价（已知缺口，登记在技术设计第 1 节「本机通信校验对端映像时不验包资源」一行）：握手时不验对端包里的资源、嵌套程序与 Frameworks 里的库，这个参数把它们一起放过了，换掉嵌套程序或 dylib 照样通过（审查实测）。T04 的安装检查只在「磁盘上的后台不是我」时跑，查的是后台自己的安装目录，不覆盖对端。
  - 约束：有证书的包里不放会被加载的 dylib、framework 或影响行为的资源；嵌套程序可以放（如 Contents/MacOS 里的 iwork-daemon），前提是别的进程只经握手校验过的连接和它往来；被信任进程直接起、且不经握手就信其结果的程序同样不放。将来包里要放这类东西时，证书分支改回默认校验参数（整包签名的包默认参数能过，T04 N5 B1）。

#### 2.4b 核验的是运行中的映像

设计 3.2 说「按 pid 取可执行文件，校验代码签名」。只按路径重新打开文件，验的可能不是正在跑的那个：同用户的攻击者先运行自己的程序，再把路径上的文件换成原版。每个平台要说清「被核验的东西」和「运行中的映像」怎么绑在一起；绑不住的平台，**有证书、无证书两个分支都**返回 `Unavailable{reason: "image binding unverified"}`，该平台暂不支持（Q1 已决定），等有了绑定办法另出方案。

| 平台 | 绑定方式 | 还剩什么 | 实测项 |
| --- | --- | --- | --- |
| Linux | 不用路径。`/proc/<pid>/exe` 打开后是映像 inode 的 fd，哈希从这个 fd 读；路径上的文件被换掉、改名、删除都不改变读到的内容。`exe` 只用于「同目录」检查与审计：`readlink` 去掉 ` (deleted)` 后缀 | pid 复用窗口（L1） | N3：连接期间 `mv` 走、原地覆盖、`rm`，三种情况下 fd 读到的哈希不变 |
| macOS | 不用路径。审计令牌 → 进程的动态 `SecCode`；`SecCodeCheckValidity` 验的是内核跟踪的运行中代码的签名；证书与 cdhash 从同一个 `SecCode` 对象读。文件被改名：动态对象仍指向原映像；被原地覆盖：内核把进程的签名标为无效，`SecCodeCheckValidity` 失败 → `Unavailable` | — | N1：连接期间 `mv` 替换、原地 `dd` 覆盖，两种情况下 `SecCodeCheckValidity` 与证书读取的结果；证明不了就拒绝 |
| Windows | 运行中的映像文件被系统锁住不能写、不能删，但**能改名**，所以路径会说谎。绑定靠句柄与两次查名：① `QueryFullProcessImageNameW(PROCESS_NAME_NATIVE)` 取路径 P1；② `CreateFileW(P1, GENERIC_READ, FILE_SHARE_READ \| FILE_SHARE_DELETE)` 得到 `hFile`；③ 再查一次进程映像路径 P2，`GetFinalPathNameByHandleW(hFile)` 得到 H；要求 P1 == P2 == H（规范化后），否则 `Unavailable`（有人在①②之间换了文件）；④ 验证与取证书全部按 `hFile` 做（同一次 `WinVerifyTrust` 状态），不再按路径打开第二次。**有证书、无证书两个分支都先过这一步**，证书不是绑定失败的退路 | 依赖「进程映像名反映改名后的当前名」这一事实 | N2：对运行中的进程改名其 exe，`QueryFullProcessImageNameW` 返回新名还是旧名；原地写入被拒（`ERROR_SHARING_VIOLATION`）；①②之间换文件被③拦住。「返回旧名」就证明不了绑定，Windows 暂不支持 |

支持矩阵（平台 × 构建 × 取法 × 绑定 × 证据 × 不通过时）见第 10 节 Q1；矩阵里没有「退路」一栏。

#### 2.4c 升级期间的客户端行为（设计 4「升级」，`bf73ed9`）

升级是后台自己的事：后台发现安装目录里的程序已经换成新版本，就自行重启切换；有回合在跑也不等，按中断处理（与崩溃恢复相同，出「继续」卡片），待审批保留、不作废；**客户端不结束任何进程**。检测「安装的程序换了」与自行重启的机制归 T04（建议：后台启动时记下自己映像的身份与安装目录里两个二进制的身份，之后定期或在收到连接被拒的审计时重新算安装目录里的文件身份，与启动时记的不同就走「完全退出」流程的中断分支再由 T04 第 1 条拉起；具体写法由 T04 方案定）。

信任根固定（2.4）意味着升级窗口里新旧版本互不相认，客户端在这个窗口里只做一件事——等：

| 客户端看到的 | 含义 | 客户端做什么 |
| --- | --- | --- |
| `ConnectError::PeerRejected` | 我认不出对端。可能是对端还是旧后台、我自己是旧客户端（新后台也在同时拒我，只是我先关了连接）、或连到了别的东西——**客户端分不出这三种**，只知道「版本不一致」 | 不发 `Hello`，关闭连接；显示中性提示「后台服务与客户端版本不一致」，带两个出口：「重新打开 iWork」（我是旧客户端时这是唯一正解）、「查看诊断」（T04 诊断页：两端版本号、日志位置、审计里的 `reason`）；同时指数退避重连（初始 200ms，上限 5s，不设总时长），每次重连仍然先 `judge_peer`，陌生对端一律不接受。不加任何信任宽限，不结束任何进程 |
| `ConnectError::ClosedBeforeWelcome` | 对端认不出我（它先关了）。同样分不出是我旧还是它旧 | 与上一行完全相同：同一句提示、同两个出口、同样退避重连。两种拒绝在客户端是同一个状态 |
| `ConnectError::VersionMismatch` | 主版本不同 | 显示「正在切换版本」（设计 4）；跨主版本时新后台会被数据库门拒绝启动（设计 5.5），只承诺回退旧程序原库可用，客户端这边没有别的事可做 |

两个真实身份组合都落在前两行里：新客户端 × 旧后台（后台自行重启后，退避重连会成功，提示自动消失）；旧客户端 × 新后台（重连永远被拒，用户点「重新打开 iWork」）。客户端不去猜是哪一种，所以不会在后者上无限等。

T03 自己的交付只有这三个错误变体与客户端契约里的提示语义；检测、重启、崩溃恢复、「继续」卡片都是 T04 的范围，T09 出提示与退避。

### 2.5 帧编解码与上限（设计 3.3；T01 3.2）

帧 = `u32 长度（小端，= 类型字节 + 载荷字节数）| u8 类型 | Protobuf 载荷`。

常量放 `iwork_proto::limits`（新模块，第 9 节）：

| 常量 | 值 | 用途 |
| --- | --- | --- |
| `MAX_FRAME_LEN` | 4 MiB | 长度字段的上限；超过立刻断开，不等载荷到齐 |
| `MAX_CHUNK_DATA` | 1 MiB | `Chunk.data` 上限；`ReadArtifact.limit` 的上限也读它 |
| `MAX_HELLO_LEN` | 64 KiB | 握手前唯一允许的帧的上限，身份还没完全确认时不为对端分配 4MB |

`frame.rs`：

```rust
pub enum Frame { Hello(Hello), Welcome(Welcome), Request(Request), Response(Response), Event(Event), Chunk(Chunk) }
pub enum FrameError { TooLarge { len: u32, max: u32 }, UnknownType(u8), Malformed { frame_type: FrameType, message: String }, Direction { frame_type: FrameType } }
/// 纯函数：从缓冲里切出一帧；不够一帧返回 Ok(None)。fuzz 目标就是它。
pub fn decode_frame(buf: &mut BytesMut, max_len: u32, direction: Direction) -> Result<Option<Frame>, FrameError>;
pub fn encode_frame(frame: &Frame, dst: &mut BytesMut);
```

- `Direction::ToServer` 只接受 Hello、Request、Chunk；`ToClient` 只接受 Welcome、Response、Event。方向不对按 `Direction` 错误处理（协议违规，断开）。
- `prost::Message::decode` 失败 → `Malformed`。帧内多余字节、未知字段按 Protobuf 规则忽略（兼容加字段）。
- `Encoder`/`Decoder` 实现用 `tokio_util::codec::{Framed, Decoder, Encoder}`，解码器内部调 `decode_frame`。不用 `LengthDelimitedCodec`：我们要在读到长度字段的那一刻就拒绝超长帧，并把类型字节单独处理，自己写比包一层清楚。
- 调试输出：`dev` feature 下 `Frame` 实现 `Display` 为 JSON（`prost-reflect` + `serde_json`，与 `iwork-proto` 的 dev-dependency 同一条链），给 `ipc-tool` 与 `RUST_LOG=iwork_ipc=trace` 用；线上始终二进制（设计 3.3）。

### 2.6 握手（设计 3.3；T01 3.7「握手门」）

连接建立后的顺序，一步都不能换：

1. 两端各自 `Connection::peer()` → `judge_peer`。服务端 `Rejected` → 审计（2.12）→ 关闭连接，**不发任何帧**；客户端 `Rejected` → 关闭连接，**不发 `Hello`**，返回 `PeerRejected`。不向没验明身份的进程透露任何信息；原因在各自的日志里。
2. 服务端启动 5 秒握手计时器。读第一帧，上限 `MAX_HELLO_LEN`：不是 `Hello`、超长、解不出 → 审计 → 关闭。
3. `check_hello(&hello, cfg.protocol_major)`：`Err(e)` → 发 `Response{request_id: 0, error: e}` → 关闭。此时还没有登记任何订阅、没有把任何帧交给 handler，满足「拒绝前不处理任何业务帧」。
4. 发 `Welcome{session_id: 新 ULID 文本, server_version: cfg.server_version, capabilities: [], head_seq: source.head_seq().await, protocol_major, protocol_minor}`。连接进入 `Established`。

`cfg.protocol_major` 默认 `iwork_proto::PROTOCOL_MAJOR`，可配置的原因只有一个：3a 的两方向测试要在同一个进程里扮演「旧后台」与「新后台」。

`Hello.resume_token` M1 不用：服务端忽略它（`debug` 日志一条），每次连接都发新的 `session_id`。重连靠订阅自带的 `from_seq`（2.8），设计 3.5 已经把这条路铺好了，不再加第二套会话恢复。`frame.proto` 里这个字段的注释改为「预留；M1 服务端忽略，重连靠 Subscribe.from_seq」（注释改动不影响契约）。

客户端这一侧：收到 `Welcome` 后比一次 `protocol_major == PROTOCOL_MAJOR`，不等就当 `PROTOCOL_VERSION_MISMATCH` 处理（防着没有握手门的假后台——虽然 2.4 已经把假后台挡在前面，两道门各守各的）；收到 `Response{request_id: 0, error}` 原样交给上层；连接在 `Welcome` 之前被对端关闭 → `ConnectError::ClosedBeforeWelcome`。`PeerRejected` 与 `ClosedBeforeWelcome` 只差在谁先关了连接，都只说明「两端版本不一致」，客户端对它们做同样的事；三种错误在升级窗口里的含义与动作见 2.4c 的表。

### 2.7 连接状态机与请求分流

```
Accepted ──peer 不过──▶ Closed(audit)
   │ peer 过
   ▼
AwaitHello ──超时 / 非 Hello / 主版本不符──▶ Closed
   │ Welcome 已发
   ▼
Established ──协议违规 / 对端关闭 / 服务停机──▶ Closed
```

`Established` 后每条入站帧的去向：

| 帧 | 处理 | 失败怎么回 |
| --- | --- | --- |
| `Request{command}` | 进本连接的**命令道**：一个接一个 `handler.handle(ctx, req).await`，响应按完成顺序（也就是到达顺序）发 | handler 返回的 `Response{error}` 原样发；handler panic 由 daemon 的监督器处理（设计 10.4），连接当作内部错误 `INTERNAL` 回给客户端 |
| `Request{query}`，`iwork_proto::routing::query_lane(&query) == ViewQuery` | 进**交接 FIFO**（与 `Subscribe` / `Unsubscribe` 同一条队列，一次一个，2.8「交接」）：流暂停为缓冲 → handler 在一个读事务里取结果与 `QueryResult.seq` → 结果按 seq 的位置插进事件流 → 回到 Live。响应因此与事件流**同序**，客户端不用比 seq | handler 返回的 `Response{error}` 立即发出（错误不参与排序），流回到 Live，游标不动；交接超时、缓冲溢出 → `fail_connection` |
| `Request{query}`，`query_lane(&query) == SideQuery` | 进**查询道**：`spawn` 一个任务，最多 4 个在飞（信号量），第 5 个等。只有不写视图的查询（`ReadArtifact`、`ListModels`）在这里，它们的结果与事件先后无关 | 同上 |
| `Request{subscribe}` / `{unsubscribe}` | 连接任务自己处理（2.8），不进 handler | 范围为空 → `INVALID_ARGUMENT`；`Unsubscribe` 的 id 不存在 → `NOT_FOUND`；一条连接同时存在的范围超过 256 个 → 协议违规（界面不会有这么多视图，超过是 bug） |
| `Chunk` | `data.len() > MAX_CHUNK_DATA` 或 `upload_id` 为空 → 协议违规；否则 `handler.chunk(ctx, chunk).await` | handler 的错误没有 `request_id` 可挂，所以 `chunk()` 只返回 `Result<(), ChunkRefused>`；`Refused` 时发 `Response{request_id: 0, error}` 并断开——上传缓冲超限这类事不该发生在守规矩的客户端上（T09 先检查 20MB） |
| `Request.request_id == 0` | 协议违规 | — |
| `Request.body` 为空 | `INVALID_ARGUMENT` | — |

协议违规（方向不对、类型未知、超长、解不出、`request_id` 0、握手前的非 `Hello`、`Chunk` 超限、同时范围数超上界）一律：发 `Response{request_id: 0, error{MALFORMED_FRAME, details{frame_type, reason}}}`（能发就发，队列满了就算了）→ 关闭 → 审计一条 `protocol_violation`。不重试、不宽容：对端是我们自己写的客户端，违规只会是 bug 或攻击。

为什么命令串行、查询并发：用户连发两条消息，第二条先落盘会颠倒对话顺序（命令道必须 FIFO）；而一次十万条历史里的 `GetConversation` 分页可能要几十毫秒，不能挡住 `DecideApproval`（唤醒 ≤ 1s）。

读循环的暂停：连接预算（2.9）用满时停止从 socket 读请求，直到回落到一半以下。客户端狂发查询又不收响应，最后是它自己被堵住，不是后台的内存涨。

### 2.8 每条连接一条事件流：范围、快照、补发、实时（设计 3.5；第 3 轮审查后按产品负责人选定的做法重写）

前两版分别用「跨订阅共享交付记录」和「订阅各自独立 + 客户端按实体版本合并」，各被审出一批交错反例。根源都是一条连接上存在多个游标。这一版只留**一个游标**：一条连接就是一条按 seq 排好的事件流，订阅范围只是这条流的过滤条件。

**ipc 看到的事件**（由 daemon 在提交后调 `Publisher::publish`）：

```rust
/// 路由键（iwork_proto::routing::StreamKey）：范围与事件之间唯一的匹配依据。
/// kind 是 StreamKind 的蛇形名（真值在 iwork-domain），ipc 当不透明字符串；id 为 None 表示整类。
pub struct StreamKey { pub kind: Cow<'static, str>, pub id: Option<String> }

/// 带路由的持久事件：实时推送与历史补发都是它，routes 由同一个 iwork_app::subscription::routes_for 算出。
pub struct RoutedEvent { pub event: pb::PersistedEvent, pub routes: Vec<StreamKey> }

pub enum Published {
    Persisted(Arc<RoutedEvent>),
    Transient { event: pb::TransientEvent, routes: Vec<StreamKey> },
}
```

范围匹配事件 := 范围的某个键 `k` 覆盖事件的某个路由键 `r`：`k.kind == r.kind` 且（`k.id == None` 或 `k.id == r.id`）。范围 → 键的映射是 `iwork-app::subscription::scope_streams(&SubscriptionScope) -> Vec<StreamKey>`（2.10）。回合、审批、亲手执行卡片事件带会话 ID（Q3 已决定），所以它们的 `routes` 同时有 `turn:<id>` / `approval:<id>` 与 `conversation:<id>`。

**连接的流**：

```
Stream {
  scopes: BTreeMap<u32 /* subscription_id */, (SubscriptionScope, Vec<StreamKey>)>,  // 活动范围
  filter: Vec<StreamKey>,      // scopes 里全部键的并集（去重）
  cursor: u64,                 // 已向客户端送出（或经快照覆盖）的最高 seq，只增
  state: Empty | Replaying { to: u64, buffer: VecDeque<Arc<RoutedEvent>> } | Live,
  fifo: VecDeque<StreamOp>,    // 待执行的 Subscribe / Unsubscribe / ViewQuery，一次只执行一个（2.8「交接」）
}
```

没有「落后」状态：流出任何异常（预算用满、交接超时、发布停滞）都走 2.9 的唯一入口 `fail_connection(cause)` 关闭这条连接，客户端用已有的断线重连续传。一条连接上只有「正常」与「已关闭」两种结局，不留第二套恢复。

```
```

流的三条保证（7.2 proptest 要检查的性质，对整条流说）：

1. **不漏**：匹配 `filter` 的、`seq > 起点` 的每一条持久事件都送出过一次（起点 = 快照 seq 或续传的 `from_seq`）。范围加入时它 ≤ 快照 seq 的部分由快照覆盖。
2. **不重**：送出的事件 seq 两两不同。
3. **严格递增**：送出的事件按 seq 严格递增。

连接上只有这一条流，所以不存在「跨订阅」这件事——客户端收到的就是一条有序、不重的事件序列，按实体 id 幂等应用即可。

**Subscribe{id, scope, from_seq} 的处理**（连接任务内，串行；它改的是范围集合，流随之整条重订阅或续传）：

0. **先进 FIFO**：`Subscribe`、`Unsubscribe`、`ViewQuery` 三种改流的操作都进同一个 `fifo`，一次只执行一个，执行中的不被后来的打断、不被取消（没有「立即取消 / 重启」这回事）。连接任务在取 FIFO 头之前先把当前已经读到的入站帧全部处理完（都入队），然后把**头部连续的、`from_seq` 相同的 `Subscribe`** 合并成一次操作（范围一起加、`filter` 一起算、一次续传或一次快照）——客户端重连时一次写出全部 `Subscribe`，正常情况下就是一次续传；若网络把它们拆到两次读里，后面的会因 `from_seq ≠ cursor` 走快照，正确但多做一次。这是确定的规则，不是竞态优化。
1. `keys = source.scope_streams(scope)`；为空 → `INVALID_ARGUMENT`（错误立即发出，不占 FIFO）。
2. 同 id 已存在 → 先移除旧范围再往下走（替换）。把 `(id, scope, keys)` 放进 `scopes`，重算 `filter`。
3. **先登记后读 head**：`state = Replaying{to: ?, buffer: 空}`（原来若是 Live，缓冲从空开始；原来不可能是 Replaying——FIFO 保证上一个操作已结束）。从这一刻起，匹配新 `filter` 的实时事件进缓冲。
4. `head = source.head_seq().await`，记为 `to`。
5. 走**续传**还是**快照**：
   - 续传条件：`from_seq > 0` 且 `from_seq == cursor` 且 `head - from_seq ≤ cfg.replay_limit`（默认 50 000）。含义：客户端声明「我对当前全部范围的视图都齐到 `from_seq`，流接着往下走」。`cursor` 为 0 的空流上第一次 `Subscribe` 带 `from_seq > 0`（重连）时，`cursor` 先置为 `from_seq`，于是条件成立。
   - 否则走快照（`from_seq == 0`、`from_seq ≠ cursor`、`from_seq > head`、落后超过 `replay_limit`，都算）。
6. 快照：`(snapshot, snapshot_seq) = source.snapshot(全部活动范围).await`——快照包含**每个活动范围**各自的部分（2.8「快照的组成」），在同一个读事务里取，所以只有一个 `snapshot_seq ≥ to`；`cursor = snapshot_seq`；发 `Response{Subscribed{id, snapshot, snapshot_seq}}`。客户端用它替换全部活动范围的视图。进入第 8 步。
7. 续传：发 `Response{Subscribed{id}}`（没有快照）；`spawn` 补发任务：循环 `page = source.replay(&filter, scan, to, cfg.replay_page).await`，对 `page.events` 每条 `deliver(e)`，`scan = page.next_from`；`next_from >= to` 时结束，`cursor = max(cursor, to)`。`next_from` 是**扫描到的位置**，不是最后一条匹配事件的 seq，所以「这一页过滤后不足一条」不会被误判为读完（Q3 的会话过滤靠它）。
8. **交接**（回到连接任务）：把缓冲按 seq 顺序逐条 `deliver(e)`——`seq ≤ cursor` 的被跳过（快照路径：已在快照里；续传路径：已补发），其余送出；`state = Live`。

**投递函数**（补发、排空缓冲、实时三处共用同一个 `deliver(e)`）：

- `e.seq ≤ cursor` → 不发。
- 否则发 `Event{subscription_ids: 匹配 e 的全部活动范围 id, body: e}`，`cursor = e.seq`。

**实时 publish(e)**（`Publisher` 由存储写线程在提交后按 seq 递增顺序调用；ipc 对每条连接）：

- 不匹配 `filter` → 忽略。匹配：`Replaying` → 推进缓冲（缓冲字节算进连接预算，2.9；放不下 → `fail_connection(ReplayBufferFull)`，见 2.9 第 3 条）；`Live` → `deliver(e)`；`Empty` → 忽略。
- 无论匹配与否，`Server.published_head = max(published_head, e.seq)`（交接第 4 步等它）。
- 瞬时事件：没有 seq，不进 `cursor`，不进缓冲（补发期间的流式文字不值得补），只在 `Live` 时投给匹配的范围。

**Unsubscribe{id}**：从 `scopes` 移除，重算 `filter`，流不变（游标、状态都不动）。缩小过滤不破坏三条保证；缓冲或队列里已经排着的、只属于被移除范围的事件照常发出，客户端收到后找不到对应视图就丢掉。`scopes` 空了 → `state = Empty`、`cursor` 保留（客户端再订阅时可续传）。

**重连**：客户端重连后把全部范围一次写出 `Subscribe`，每条都带 `from_seq = 上一条连接的流游标`。按第 0 步，连接任务先把已读到的入站帧全部入 FIFO，头部这几条 `from_seq` 相同的 `Subscribe` 合并成一次操作：范围一起加、`filter` 一起算、`cursor = from_seq`、一次续传。没有「补发重启」或「取消再 spawn」——FIFO 里的操作一个接一个，执行中的不被打断。若网络把这批 `Subscribe` 拆到两次读里，后到的那条在前一次续传结束后执行，`from_seq ≠ cursor` → 走快照，正确但多做一次。

**为什么第 3 轮的三类问题在单流下不再成立**：

- 3/F-1「增量事件被整实体版本挡掉」：没有实体版本了。流严格递增且不重，每条事件到客户端时都比它之前的所有事件新，`MessageDelta` 这类按 `(id, offset)` 追加的增量照常应用，不会被「实体版本不比本地新」拦下。
- 3/F-2「删除后复活」：复活需要「删除之后又收到更早的创建事件」。单流严格递增，创建一定在删除之前到达；快照只有一个 seq，不含已删除的实体，快照之后的流从 `snapshot_seq` 起，不会再送 ≤ `snapshot_seq` 的事件。多查询快照取最小 seq 的交错也不存在：快照在一个读事务里取（2.10 对 `EventSource::snapshot` 的要求）。
- 3/F-3「分页缺席误删」：快照与分页查询只改**视图**——某个范围当前显示哪些实体、这些实体的内容；它们从不删除全局实体表里的东西。会话视图的「最新一页」只决定成员列表，更早的消息留在实体表里等下一次翻页查询再进入视图。实体的生死只由事件流决定（`ConversationDeleted` 等）。写进 2.11 客户端契约。

**交接：会写视图的查询与订阅快照走同一条路**（第 6 轮，产品负责人「从根因上修」；第 5 轮让客户端比 `QueryResult.seq` 决定取舍的那套规则已删）

根因：会改视图的查询结果和事件流走两条道，客户端只能事后比 seq 猜新旧——超前的结果先应用、缓冲里的旧事件后到会把状态改回去、把未读数这类汇总字段重复计入（5/F-1）；按全局游标淘汰结果，在别处持续写入时又让没变化的页面反复加载失败（5/F-2）。修法不是再加规则，是让这类查询**走事件流**：结果在流里有一个确定的位置 S，S 之前的事件在它前面、之后的在它后面，客户端按到达顺序应用就是 S 时刻的状态。这正是 2.8 第 3–8 步订阅快照已经在做的事，所以两者合成一个机制：

```
Handover（交接）= 一次「暂停流 → 在一个读事务里取 (payload, S) → 把 payload 插到流里 seq = S 的位置 → 恢复流」
  触发者：Subscribe 的快照路径（payload = Subscribed{snapshot}）；lane == ViewQuery 的查询（payload = Response{QueryResult}）
  每条连接一个 FIFO，一次只做一个（理由见下）
```

步骤（连接任务内）：

1. 入队 FIFO（2.8「Subscribe」第 0 步的同一个队列）。前面有操作在执行 → 等它结束；没有 → 立即开始。整个交接（第 2–6 步）受一个计时器 `cfg.handover_timeout`（默认 10s）约束。
2. **暂停**：`state = Replaying{to: 待定, buffer}`；从这一刻起匹配 `filter` 的实时事件进缓冲（算预算，2.9）。
3. **取数**：订阅快照 → `source.snapshot(全部活动范围)`；查询 → `handler.handle(ctx, req)`。两者都在**一个读事务**里执行并返回那个事务看到的 head 作为 S（快照：`snapshot_seq`；查询：`QueryResult.seq`，T10 在读事务里填）。
4. **等 S 之前的事件都到齐**：写线程「提交后发布」是同步顺序的（设计 5.2），读事务看到 seq S 时，S 的 `publish` 可能还差几微秒没调；`Server` 记一个 `published_head`（`Publisher::publish` 每次推进，所有事件都经它，与 `filter` 无关；**启动基线**见 2.10——`serve` 开始接受连接之前先把库里已持久化的 head 设成它，否则非空库重启后第一次交接会永远等一个不会再发布的 S），交接等到 `published_head ≥ S` 再往下走。等待通常是零。
5. **插入**：先 `deliver` 缓冲里 `seq ≤ S` 的事件（按序，`≤ cursor` 的照旧跳过）；然后发 payload；`cursor = max(cursor, S)`。
6. **恢复**：`deliver` 缓冲里剩下的（都 `> S`）；`state = Live`；FIFO 取下一个。
7. **业务失败**：第 3 步返回 `Response{error}`（找不到对话、参数错）→ 立即发出错误响应（错误不参与排序），`cursor` 不动，缓冲按序全部 `deliver`，`state = Live`，FIFO 取下一个。这是唯一不断开的异常：它是请求本身的问题，流没有问题。
8. **其他任何异常 → 断开**：`handover_timeout` 到期（取数不返回、或 `published_head` 追不上 S——两者都说明后台自身出了问题：存储卡住、写线程提交了却没发布）、交接期间缓冲放不下（2.9）→ `fail_connection(cause)`，这条连接关闭，FIFO 连同在飞的操作一起丢弃；迟到的取数结果回来时连接已不在，直接丢弃，不改新连接的流。客户端走已有的断线重连：一次写出全部 `Subscribe` 带同一 `from_seq` 续传（2.11）。不回 `UNAVAILABLE`、不转 Live、不等重订阅——这些都是第二套恢复路径，删掉。

2.8 第 3–8 步的订阅快照路径就是这个流程的实例（第 5 步的 payload 是 `Subscribed{snapshot}`）；续传路径不同——它从存储补发 `(cursor, to]`，没有 payload，但同样独占 FIFO、同样受 `handover_timeout`（按页重置：每拿到一页就重新计时，补发 5 万条不会被 10s 误杀）。

**交接期间收到 `Subscribe` / `Unsubscribe`**：进 FIFO 排队，等当前操作结束后按到达顺序执行；不打断、不取消正在飞的操作。`Unsubscribe` 在执行时只缩 `filter`，不碰游标与状态；已经进了缓冲或队列的、只属于被移除范围的事件照常发出，客户端收到后找不到视图就丢掉（2.11）。这与 2.8「Subscribe」第 0 步是同一条规则，不存在第二套仲裁。

**为什么一次只做一个**：每个交接都给流定一个插入点 S，两个并发交接 S1 < S2 要把两个 payload 分别插进流的两个位置，还要各自等 `published_head`，正确性可以做到，但状态机多一维；而会写视图的查询由人触发（打开一个对话、滚一页），一秒钟不会有几个，串行的代价是「翻页时打开另一个对话要等上一页的查询返回」，毫秒级。选串行。命令道、并行查询道都不受交接影响：命令照常提交，它们产生的事件进缓冲，交接结束后按序送出。

**边界**：哪些查询走交接由一张登记表决定，真值在 `iwork_proto::routing::query_lane(&pb::Query) -> QueryLane`（穷举 `Query` 的 oneof，加一种查询编译器就逼着登记；放在 proto 而不是 app，是因为服务端的连接任务和客户端的 `Client` 都要读它，而 ipc、client-core 都不能依赖 app——它是协议层面的事实「这个结果会不会写视图」，与 `StreamKey` 同属 `routing`）。M1 的表：`GetConversation`、`ListConversations`、`ListProjects`、`ListAssistants`、`ListPendingItems`、`GetQuota`、`GetRuntimeStatus`、`ListRules`、`ListLocalConfig`、`ListSecurityLists`、`GetSettings` → `ViewQuery`（结果会成为某个视图的成员或内容，而事件也会改同一份东西）；`ReadArtifact`（字节，不进视图）、`ListModels`（运行时给的列表，事件不改它）→ `SideQuery`。

**对客户端的意义**：一条连接上收到的持久事件与 `ViewQuery` 响应是**一个全序**，按到达顺序应用即可；`QueryResult.seq` 只是信息，不用来判断取舍。第 5 轮那套「结果比游标旧就丢弃重查 3 次、失败提示」整体删除——没有新旧可比了。

**三类低 `from_seq`**（第 1 轮 F-4 的用例）：同 id 替换、退订后再订阅、断线重连，`from_seq` 只有两种结果——等于 `cursor` 就续传，不等就快照。没有「从更低的位置重发」这件事，流永远不回退。

**快照的组成**（真值在 `iwork-app::subscription`，T03 只写纯函数部分，查询执行接 T10 的受理）：

| 范围 | 路由键 | 快照 = 这些查询的结果 | 替换哪个视图 |
| --- | --- | --- | --- |
| `Sidebar` | `project:*`、`conversation:*`、`assistant:*` | `ListProjects`、`ListConversations{}`、`ListAssistants` | 侧栏：项目、对话摘要（含未读）、助手 |

### 2.9 连接预算、背压与断开（设计 3.5；第 7 轮：异常只有一个出口）

每条连接一个 `ConnectionBudget`（`budget.rs`，纯逻辑，有单测）：

```rust
pub struct ConnectionBudget {
    limit: usize,            // 默认 8 MiB
    replay_reserve: usize,   // 默认 1 MiB：只给补发用的保底，实时事件与缓冲用不了它（只是优化）
    queue: VecDeque<Outbound>, queue_bytes: usize,
    buffered_bytes: usize,   // Replaying 缓冲的字节
}
pub enum Outbound { Response(pb::Response), Event(pb::Event) }
pub enum Push { Queued, Overflow }
```

`used = queue_bytes + buffered_bytes`。规则：

1. 字节数按 `encoded_len()` 计，入队时算一次存着；编码在写任务里做。缓冲里的 `Arc<RoutedEvent>` 按它编码后的长度计。
2. `Response` 永远入队，不受上限限制——它对应客户端自己发的请求，数量由读循环的暂停（2.7）兜底。
3. **流的任何异常只有一个出口** `fail_connection(cause)`：① 审计 `connection_failed{connection_id, cause, cursor, used_bytes}`（`warn`；`cause` 属于「后台自身有问题」的——`PublishStalled`、`HandoverTimeout`——另记 `error`，让 T04 的监督器看到）；② 取消补发任务与在飞的交接，丢弃 FIFO；③ 停止读写，丢弃队列与缓冲（队列里排着的持久事件不再发——客户端重连后从游标续传，它们从存储里回来；没有「先发完再关」的尾巴，不然又是一条特殊路径）；④ 关闭 socket；⑤ `handler.connection_closed(ctx)`。原因清单：`QueueFull`（Live 时合并后仍放不下）、`ReplayBufferFull`（Replaying 时缓冲放不下）、`ReplayReserveTimeout`（补发等预算超过 `replay_reserve_timeout`）、`HandoverTimeout`（交接整体超时，含取数不返回）、`PublishStalled`（`published_head` 追不上 S，同样由交接计时器判出，审计单独标）、`ProtocolViolation`（2.7 的协议违规也走这同一个入口，只是前面多发一帧 `MALFORMED_FRAME`）。没有「落后」状态，没有 `SubscriptionLagging`（T01 的字段保留，M1 不发），没有 `UNAVAILABLE` 后转 Live，没有 `cancel_at`。
4. **为什么统一断开而不是「预算落后发通知、交接异常才断开」**：两条路径在客户端最终做的是同一件事——对全部范围一次写出 `Subscribe{from_seq = 游标}`。留两条只是多一套状态（`Lagging`）、多一种帧（落后通知）、多一处顺序要求（先清瞬时再入队通知，5/F-3 就是这里出的错），而断开 + 重连本来就必须有（进程崩溃、socket 错误）。断开多付的代价是一次重连握手与对端校验（毫秒级）和在飞命令的重发——命令带 `command_id` 幂等，重发返回上次结果（设计 5.2），不会重复执行。所以选断开。
   **同游标反复失败怎么处理**：服务端不记任何跨连接的东西（连接状态随连接消失）。客户端记：重连后若在**同一个游标**上连接再次被关（续传没送出任何事件就断），下一次重连用 `from_seq = 0`——全范围快照把游标一步推到当前，被卡住的那段历史由快照覆盖，不再续传那一段。这是客户端契约（2.11）的一条。它收得住「补发那一段太大或太慢」的卡住；收不住「本连接范围内持久事件的持续速率 × 快照取数时间 > 缓冲预算」——那种情况下 `from_seq = 0` 的快照在返回前缓冲同样会满，重连循环不收敛，登记为已知限制 L7，不再加恢复机制。
   **补发的保底只是优化**：实时事件与缓冲只能用到 `limit - replay_reserve`（7 MiB），补发往队列放事件时能用到 `limit`（8 MiB），多数情况下补发能发出至少一页，不至于一满就断。它不是正确性依据：接近 `MAX_FRAME_LEN`（4 MiB）的合法单事件比保底大，`reserve` 等不到就按第 3 条断开，客户端重连；再卡在同一游标就 `from_seq = 0` 走快照，那条大事件的效果在快照里。补发 `reserve(len)` 最多等 `cfg.replay_reserve_timeout`（默认 2s）。
5. 实时 `Event`：`used + len ≤ limit - replay_reserve` → 入队（Live）或进缓冲（Replaying）。放不下时：Replaying → `fail_connection(ReplayBufferFull)`；Live → 先**合并**：从队尾往前找到最近一个 `Event{transient: MessageDelta}`，若新事件也是 `MessageDelta`、`message_id` 相同、`offset == 前者.offset + 前者.text.len()`、`subscription_ids` 相同、合并后 ≤ `MAX_CHUNK_DATA` → 拼接文字，字节数重算；`ToolOutputDelta` 同理（`tool_call_id`）。合并后仍放不下 → `fail_connection(QueueFull)`。
6. 持久事件在任何路径上都不丢弃：要么在队列里等着发，要么在存储里等客户端重连后续传。瞬时事件（流式文字）在断开时随队列丢弃，是显示问题（S7）。

写任务：从队列取尽可能多的帧编码进一个 ≤ 64 KiB 的 `BytesMut` 再一次 `write_all`，减少每秒上千条小事件时的系统调用；队列空时 `await` 通知，不轮询（空闲 CPU）。写失败（对端关闭）→ `fail_connection(PeerClosed)`（同一个入口，审计级别 `debug`）。

慢消费者不影响别人：`publish` 对每条连接只是拿一次互斥锁、推一次队列或缓冲（入队、进缓冲或判溢出），永不等待 socket，也永不等待预算；每条连接有自己的写任务与补发任务；一条连接被 `fail_connection` 关掉不影响其他连接。这就是卡「验收 5」的全部依据。

T04 的组合顺序：`SelfIdentity::detect()` → `LocalEndpoint::for_current_user()` → 拿 `run/daemon.lock` → 打开存储、跑崩溃恢复（T04 第 4 条，会提交事件）→ `Server::new(..)`（拿到 `Publisher`，此后才允许任何提交把事件发布进来）→ `LocalListener::bind(&endpoint)` → `serve(listener, token)`。**`published_head` 的启动基线**：`serve` 在接受第一条连接之前先 `source.head_seq().await`，`published_head = max(published_head, head)`；之后由 `publish` 按 seq 推进（也取 max）。两处都取 max，所以「崩溃恢复的提交在 `Publisher` 存在之前还是之后」都不影响结果：之前的在基线里，之后的经 publish 进来。没有基线的话，非空库重启后第一次交接读到的 S 是库里已有的 head，而没有任何新事件会发布到那个 seq，交接会一直等到超时（6/F-3）。`ShutdownDaemon` 命令受理、升级自重启都是取消 token。`Publisher` 交给存储写线程（提交后调用）与发瞬时事件的地方（T05/T06 的适配层经 app）。

```rust
pub enum ConnectError {
    Io(io::Error),                              // 连不上：后台没起（T04 据此拉起）
    PeerRejected(RejectReason),                 // 我们拒绝了对端：版本不一致（2.4c：中性提示 + 退避重连）
    ClosedBeforeWelcome,                        // 对端拒绝了我们：同上
    VersionMismatch { client_major: u32, server_major: u32 },
    Timeout,
}
/// 客户端唯一的有序出口（6/F-1）：服务端在一条连接上排好的全序，原样交给状态库。
/// 持久事件、ViewQuery 结果、Subscribed 快照、服务端主动的错误都从这里按到达顺序出来，谁也不能从别的地方拿到会写视图的数据。
pub struct Incoming { .. }  // impl Stream<Item = IncomingItem>
pub enum IncomingItem {
    Event(pb::Event),
    ViewResult { request_id: u64, result: pb::QueryResult },
    Subscribed { request_id: u64, subscribed: pb::Subscribed },
    ServerError(pb::Error),                     // Response{request_id: 0}
    Closed(CloseReason),                        // 流结束：对端关闭、io 错误、我们自己 fail
}
```

`Client` 内部只有一个读任务：按帧到达顺序，`Event` → `Incoming`；`Response{request_id}` → 查这个 id 当初是哪类请求——命令 / `SideQuery` → 唤醒对应 future 并把 `Response` 交给它；`ViewQuery` / `Subscribe` → 载荷推进 `Incoming`，再唤醒 future（只带成功 / `Error`）。**`Incoming` 是有界的**（7/F-1）：容量按编码字节计，`ClientConfig.incoming_limit` 默认 4 MiB——服务端每连接预算 8 MiB 的一半，取字节不取条数是因为一条 `Event` 从几十字节到 1 MiB 都有；两边加起来一条连接最多占 12 MiB，有上界。满了读任务**停止读 socket**，不丢、不重排；socket 缓冲随即填满，服务端的写任务写不动，队列涨到预算上限，按 2.9 `fail_connection(QueueFull)` 关掉这条连接——客户端不需要自己的落后处理，复用服务端那一条。上层消费慢只是延迟，不是乱序，也不是内存增长。这样服务端的全序到了客户端还是一条序列：第 6 轮的问题是「E11 → R12 → E13 在客户端被 request future 与 `Incoming` 两个出口拆开，上层可能按 E11、E13、R12 应用」，现在 R12 就在 E11 与 E13 之间，想拆也拆不开。

**客户端契约**（写进 `Client` 的文档注释，T09 按它实现）：

- **只从 `Incoming` 这一个出口写状态库**：持久事件、会写视图的查询结果、快照、服务端错误按它给出的顺序逐个应用，不缓存、不重排、不从 `view_query` / `subscribe` 的 future 里取数据（它们只说完成或失败）。到达顺序就是服务端的全序，同一条事件在一条连接上不会到两次。应用方式是按实体 id 幂等写入状态库——不需要跨订阅合并，不需要实体版本，不比 seq。
- 快照（`Subscribed.snapshot`）替换**全部活动范围的视图**：每个部分对应一个范围，内容是「这个视图当前显示哪些实体 + 它们的内容」。快照只改视图成员与成员内容，**不删除**实体表里没出现在快照中的实体；实体的删除只由事件（`ConversationDeleted`、`ProjectRemoved` 等）触发。分页查询（`GetConversation{before_message_id}`）的结果同样只更新视图成员。
- 范围集合变化（打开一个对话、关掉它）就是一次 `Subscribe` / `Unsubscribe`；`Subscribe` 的响应若带快照，按上一条处理；不带快照（续传）则什么都不用做，事件会接着来。
- 客户端记一个数：流游标 = 最近一次**已应用**的持久事件 seq、`snapshot_seq` 或 `ViewResult.seq`（三者都在同一条序列里，取最后一个应用的）。游标在状态库应用完那一项时推进，不在读任务收到帧时推进——还排在 `Incoming` 里没应用的数据不算客户端持有，连接被关后重连用这个游标续传，它们会从存储里再来一遍。连接因任何原因结束（`Incoming` 给出 `Closed`）就走**同一条**恢复路：重连（2.4c 的退避）→ 把全部范围**一次写出** `Subscribe{id, scope, from_seq: 游标}` → 续传；在飞的命令按原 `command_id` 重发（幂等）。没有别的恢复路径——服务端不发落后通知，也不会在流出问题后继续用这条连接。
- 同游标第二次被关就改走快照：重连后若续传还没送出任何事件连接又被关（游标没动），下一次重连用 `from_seq = 0`（全范围快照）。这处理的是「补发那一段太大或太慢」；若快照本身也在返回前被关（持续高写入 + 快照取数慢，L7），客户端不再加别的办法，继续按同样的退避重连并累计同游标失败次数，连续 3 次就把「后台负载过高，稍后重试或重新打开 iWork」显示给用户。等待期间用户照常可以关闭、打开视图：客户端只更新本地期望的范围集合，下次重连按最新集合一次写出全部 Subscribe（关掉高流量对话本身就是降载办法；第 8 轮复审 8/F-1，supervisor 改）。服务端不记任何东西。自己丢掉了状态也用 `from_seq = 0`。
- 收到的事件若没有任何活动范围对应（退订后排队里剩下的），丢掉。
- 升级窗口：`PeerRejected` 与 `ClosedBeforeWelcome` 是同一个状态——显示中性的「后台服务与客户端版本不一致」，给「重新打开 iWork」「查看诊断」两个出口，指数退避重连（200ms 起、上限 5s），每次仍先 `judge_peer`；不从错误变体推断谁新谁旧。`VersionMismatch` → 显示「正在切换版本」。三种都不发 `Hello`、不接受陌生对端、不结束进程。
- 会写视图的查询（`GetConversation`、各列表等，表见 2.8「交接·边界」）用 `view_query` 发；结果以 `IncomingItem::ViewResult` 从 `Incoming` 出来，与持久事件是**一个全序**：按到达顺序应用，结果替换该视图的成员与内容，之后到达的事件都比它新。不比 `QueryResult.seq`，不丢弃，不重查。结果到达时视图已退订 → 丢掉（和退订后剩下的事件一样）。`ReadArtifact`、`ListModels` 用 `request` 发，结果从 future 回来，与事件先后无关。
- 查询在飞时连接被关：`view_query` 的 future 返回连接已关闭的错误，没有结果；重连续传后视图由快照或事件对齐，需要的话再发一次查询。

重连与退避、提示文案都在 `iwork-client-core`（T09）；T03 的 `Client` 只负责一条连接的生命周期，断了就结束，让上层决定怎么办。

## 3 数据流

```
客户端进程                                   后台服务进程
──────────                                   ──────────
iwork-client-core ─ Client::connect ──▶ Listener::accept
   │ Connection::peer() → judge_peer       │ Connection::peer() → judge_peer ──拒──▶ 审计 + 关闭（无帧）
   │  ──拒──▶ 关闭（不发 Hello），等待升级 │ 过
   │ 过                                    │
          Hello ─────────────────────────▶│ check_hello ──不符──▶ Response{0, VERSION_MISMATCH} + 关闭
                                          │ 符
          ◀───────────────────── Welcome ─┘
Request{command} ────────────────────────▶ 命令道（串行）──▶ RequestHandler::handle ──▶ iwork-app（T10）
Request{query} ──────────────────────────▶ 查询道（≤4 并发）──▶ RequestHandler::handle
          ◀─────────────── Response{id} ──┘
Request{subscribe} ──────────────────────▶ 范围集合 += scope → 登记(Replaying, to=head) → 续传(from==cursor) 或 快照(全部范围, 一个读事务)
          ◀──────── Subscribed{snapshot?} ─┘                      → 补发 (cursor, to] → 排空缓冲 → Live
                                          存储写线程 提交后 ──▶ Publisher::publish(Published{RoutedEvent})
          ◀──────────────── Event ────────   每条连接一条流：匹配 filter → deliver(e)：seq > cursor 才发
                                                             Replaying→缓冲(算预算)；published_head = max(·, seq)
Request{query, ViewQuery} ───────────────▶ 进同一个 FIFO → 暂停 → 读事务取 (结果, S) → 等 published_head ≥ S
          ◀─ ≤S 的事件, Response{result}, >S ─┘   → Live（客户端从 Incoming 按序拿到）
          ◀──────────── 连接被关 ───────────   预算满 / 补发等预算超时 / 交接超时 / 发布停滞：fail_connection，唯一出口
```

客户端内部（`iwork-client-core`，T09）：`Incoming` 的事件按 id 幂等写进状态库，快照替换视图，16ms 合并 `ViewPatch`。ipc 不参与。

## 4 每条规则的「目的 + 手段」

| 规则 | 目的（防什么） | 手段 |
| --- | --- | --- |
| 只走 UDS / 命名管道，任何构建不开 TCP | 本机其他用户、局域网里的机器连上后台服务；`localhost` 被当成可信 | `Endpoint` 只有 `Unix` / `Pipe` 两个变体；`scripts/check-no-tcp.sh` 对全部 iWork crate 源码查 TCP/UDP 类型与监听调用（含阳性对照）；`deps-policy.toml` 的 `io_and_framework` 传递禁用已经把 hyper、reqwest 挡在闭包外；运行时证据（起来后 `lsof -i` / `netstat` 无监听端口）归 T11 的故障矩阵（Q4 已决定） |
| socket 目录 0700、属主本人、不是符号链接；管道 DACL 只有本人 | 其他用户连接或替换 socket 文件 | `LocalEndpoint::for_current_user()` 创建并校验，不自动修权限；Windows 用 SDDL 只给当前 SID；验收 6 的测试 |
| **两端**都在发出任何帧之前判定对端 | 后台：未验身份的进程让后台分配内存、解析帧、触发 handler。客户端：同用户的假后台（抢占管道名、替换 socket）回合法 `Welcome`，拿走用户输入、附件、审批选择 | 2.6 第 1 步两端对称；客户端不过不发 `Hello`；握手前帧上限 64KiB；fuzz 目标 `connection_prehello` 断言 handler 调用计数为 0；`client_rejects_fake_server_with_valid_welcome` 断言假后台收到 0 字节 |
| 不通过不发帧、记审计 | 向陌生进程泄露版本、能力；排查时找不到被谁连过 | `judge_peer` 为 `Rejected` 时直接关闭；`peer_rejected` 审计一条，字段固定，两端都记 |
| 判定是纯函数，三平台同一份，两端同一份 | 三平台各写一套 `if`，某个平台漏了第 1 步或第 2 步；客户端另写一套比后台松 | 平台代码只负责装 `PeerIdentity`；`judge_peer` 的每个分支有单测，三平台都跑；客户端与服务端调同一个函数 |
| 核验运行中的映像，不是路径上的文件 | 先跑自己的程序、再把路径上的文件换回原版，骗过哈希或验签 | Linux 读 `/proc/<pid>/exe` 的 inode；macOS 用动态 `SecCode`；Windows 按句柄验、两次查名一致才算（2.4b），两个分支都过绑定；绑定未经实测证明的平台整体拒绝；N1–N3 的反例脚本 |
| 同签名判据由构建决定，不是运行时二选一 | 「证书不匹配就退到哈希」这样的 OR 让攻击者挑最弱的一条 | `own.signer` 是 `Certificate` 就只认自己的叶证书，是 `Image` 就只认启动时读的清单；两条分支互斥 |
| 信任根启动时固定，运行中不扩大 | 同用户进程不用私钥、不用换二进制，往清单 JSON 里加一行就被正在运行的后台当成可信客户端，或让真客户端信任假后台 | `SelfIdentity::detect()` 只在启动时跑；清单读进内存后不再碰磁盘；`judge_peer` 没有任何运行期输入；`manifest_change_after_start_is_ignored` 测试 |
| 升级窗口里客户端只等，不结束进程、不接受陌生对端 | 为了升级顺利而放宽校验，或让客户端去杀进程（同用户下杀错进程、权限边界模糊） | 2.4c：`PeerRejected` → 等待提示 + 指数退避 + 每次重连仍 `judge_peer`；检测与重启归后台（T04，设计 4） |
| 拿不到对端身份按拒绝 | 对端进程在判定前退出、`/proc` 读不了、映像绑定没过时被放行 | `SignerIdentity::Unavailable` → `Rejected`；与 hook「失败即关闭」同一原则 |
| `--dev-trust` 在发布构建里不存在，两端都一样 | 用户或攻击者在发布版上加一个开关就绕过签名校验 | `#[cfg(feature = "dev")]` 包住 `TrustPolicy::DevTrust`、参数解析、日志；`dev` 不是默认 feature；CI 三样证据：`cargo metadata` 的 feature 解析里没有工作区成员开 `iwork-ipc/dev`、`iwork-daemon/dev`、`iwork-client/dev`（S3）；对打包产物里的两个二进制 `grep -c dev-trust == 0`、对 dev 构建 `> 0` 作对照；发布构建的后台收到 `--dev-trust` 退出码非 0、不绑定 socket |
| `dev-trust` 只放宽第 2 步 | 开发期连同用户校验一起关掉，别的用户在开发机上也能连 | `judge_peer` 第 1 条在任何 policy 下都先执行 |
| 帧长度上限 4MiB，读到长度就判 | 一个长度字段让后台分配任意大内存 | `decode_frame` 看到 `len > max` 立即返回 `TooLarge`，不等载荷；fuzz 目标 `frame_decode` |
| 协议违规一律断开 | 畸形帧让状态机进入未定义状态；宽容处理掩盖客户端 bug | 2.7 的违规清单；统一的 `MALFORMED_FRAME` + 关闭 + 审计 |
| 主版本两方向都拦，拦在任何业务帧之前 | 旧客户端用新类型解出错值；新客户端把新命令发给旧后台 | 服务端 `check_hello`（T01 已交付）在 `Welcome` 之前；客户端再比一次 `Welcome.protocol_major`；3a 测试 |
| 命令串行 | 两条消息颠倒顺序落盘 | 命令道 FIFO，一个 `await` 完再取下一个 |
| 会写视图的查询走事件流的交接，一次一个 | 结果和事件走两条道，客户端只能事后比 seq 猜新旧：超前结果先到、旧事件后到把状态改回去、未读数重复计入（5/F-1）；按游标淘汰结果让没变化的页面在别处持续写入时反复加载失败（5/F-2） | 交接 FIFO：暂停流 → 读事务里取 `(结果, S)` → 等 `published_head ≥ S` → 先发 ≤ S 的事件、再发结果、再发 > S 的 → Live；`query_lane` 登记表穷举 `Query` oneof；客户端只按到达顺序应用 |
| 不写视图的查询并发但有上限 | 一个慢的制品读取挡住审批决定（唤醒 ≤ 1s）；无限并发吃光读连接 | 并行查询道信号量 4，只放 `ReadArtifact`、`ListModels` |
| 调用方不碰队列与缓冲 | 调用方各清各的、顺序不一（5/F-3 的落后通知被自己删掉就是这么来的） | `fail_connection` 五步固定顺序，审计 → 丢 FIFO → 丢队列与缓冲 → 关 socket → 通知 handler；预算判定只返回 `Overflow`，不动任何东西 |
| 一条连接一个游标 | 多个游标让范围之间互相牵连，每种交错都是一个新反例（三轮审查） | `Stream` 只有一个 `cursor`；范围只是 `filter`；`deliver(e)` 只比 `cursor` |
| 先登记再读 `head`，补发上界固定为登记时的 `head` | 补发读完存储到切实时之间提交的事件谁也没收到；持续有新提交时补发永远追不完 | 2.8 第 3 步先于第 4 步；`to = head`；交接时按 `cursor` 排空缓冲；proptest 随机在任意时刻提交事件 |
| 范围变化 = 整条重订阅或续传，流永不回退 | 新范围的历史事件从流的中间插进来，破坏递增；或把旧快照当成全部历史 | `from_seq == cursor` 才续传，否则对全部活动范围取一次快照并把 `cursor` 推到 `snapshot_seq`；没有「从更低位置重发」 |
| 快照在一个读事务里取、只有一个 seq | 多查询各自的 seq 不同，中间夹着提交，部分实体比快照 seq 新，事件再送一遍时把新状态盖旧 | `EventSource::snapshot` 的契约（2.10）；做不到返回错误而不是拼一个 min |
| 快照与分页只改视图，不删实体 | 用「这一页没出现」推断「实体被删了」，把翻页之外的消息、别的范围的实体删掉 | 2.11 客户端契约；实体生死只由事件决定；`snapshot_does_not_delete_entities_outside_view` 测试 |
| 流的任何异常只有一个出口：关闭连接 | 预算落后一套恢复（落后通知 + 重订阅）、交接异常另一套（`UNAVAILABLE` + 转 Live）、等重订阅再一套——每套都有自己的顺序要求与边角（5/F-3、6/F-2、6/F-4、6/F-5），客户端也得各接一套 | `fail_connection(cause)` 唯一入口（2.9 第 3 条）：审计 → 丢 FIFO 与在飞操作 → 关 socket → `connection_closed`；客户端只有「重连 + 一次写出全部 `Subscribe` 续传」一条恢复路；`SubscriptionLagging`、`Lagging`、`cancel_at` 全部删除 |
| 同游标第二次被关改走快照（客户端记） | 补发在同一位置反复卡住（缓冲占满、单事件大于保底）原地打转 | 客户端记上次重连的游标，续传没送出任何事件又被关 → 下一次 `from_seq = 0`；服务端不记连接之外的状态 |
| 交接整体有超时，超时断开 | 取数永不返回、提交了却永不发布，让流永远停在缓冲态 | `handover_timeout` 10s 覆盖取数 + 等 `published_head`（补发按页重置）；到期 `fail_connection(HandoverTimeout / PublishStalled)`，迟到的结果丢弃 |
| `published_head` 有启动基线 | 非空库重启、零新增提交时，第一次交接读到的 S 永远等不到发布 | `serve` 接受连接前 `published_head = max(·, head_seq())`；publish 也取 max；与 T04 启动顺序一起写在 2.10 |
| 补发等预算有上限 | 预算被自己的缓冲占满、缓冲只在补发结束后排空，没有新提交时补发永远等下去 | `reserve` 最多等 2s，超时 `fail_connection(ReplayReserveTimeout)` |
| 客户端只有一个有序出口 | 服务端排好的全序在客户端被 request future 与 `Incoming` 拆成两路，上层按 E11、E13、R12 应用（6/F-1） | `view_query` / `subscribe` 的 future 只带成功 / 失败；结果与快照以 `IncomingItem` 从 `Incoming` 按到达顺序出来；`client_single_outlet_preserves_order` 用真实 `Client` 刻意延迟消费 future 断言不回退 |
| `Incoming` 有界，满了停止读 socket | 状态库应用慢于收帧时，积压留在客户端内存无界增长（7/F-1） | `incoming_limit` 4 MiB 按编码字节；读任务停读 → 服务端队列涨满 → `fail_connection(QueueFull)`，复用服务端的那一条处理；客户端游标只在应用完一项时推进，重连续传不漏排在 `Incoming` 里没应用的 |
| 补发缓冲算进连接预算 | 一个慢补发的 `VecDeque` 无限长，把后台内存拖垮 | `ConnectionBudget` 三项共用 8 MiB；`replay_buffer_bounded_*` 测试 |
| 历史与实时走同一套路由 | 补发的事件没有路由，ipc 自己猜领域归属，或两条路径算出不同的范围集合 | `ReplayPage` 的每条都是 `RoutedEvent`，`routes` 来自同一个 `routes_for`；`routes_match_between_live_and_replay` 对拍 |
| 太旧、为零、不等于游标、超前都走快照 | 从 0 补发十万条；后台换库后客户端拿着不存在的 seq 补发；客户端的视图与流游标对不上 | 2.8 第 5 步；`replay_limit` 50 000 > 基准的 1 万 |
| 持久事件只延后不丢 | 断开时把业务事件丢了，客户端状态永久错 | 断开时队列与缓冲一起丢，但持久事件在存储里，客户端重连后按游标续传补回；瞬时事件才真丢 |
| 响应不受预算限制，但读循环会停 | 响应被丢导致请求永远挂起；或客户端用请求把队列撑爆 | 2.9 第 2 条 + 2.7 读循环暂停 |
| publish 永不等待 socket 或预算 | 一个不读的客户端让存储写线程卡住，全体变慢 | `publish` 只推队列、进缓冲或判溢出（溢出 → 关那一条连接）；写任务、补发任务独立；验收 5 |
| 审计不记内容 | 日志里出现消息正文、附件、命令参数 | `audit.rs` 的字段表是封闭的；T04 验收 6 的 grep |
| ipc 只依赖 proto；app 不依赖 ipc | ipc 长出业务判断，或把 domain 拖进客户端；app 为了一个类型反向依赖 ipc | `deps-policy.toml` 不变；`StreamKey` 放 `iwork_proto::routing`；范围 → 键、范围 → 快照、事件 → 路由三张表都在 app，经 `EventSource` 注入 |

## 5 出事场景

每条写：会出什么事 / 怎么止血和回退 / 由什么保证。

**S1 身份校验在用户机器上把自己人拒之门外**
- 会出什么事：客户端连不上后台（证书不一致、清单缺失或过期、`SecCode` 行为随系统版本变化），或客户端拒绝了真后台。用户看到「后台服务与客户端版本不一致」一直不消失。不是安全问题，是可用性事故，但影响所有用户；「查看诊断」出口是这时候的唯一线索。
- 止血和回退：两端的审计都写清 `reason`（`SignerMismatch{peer, own}` 带两个哈希前缀、`ImageNotTrusted{image}`、`NoManifest{expected_at}`、`OutsideInstallDir`、`Unavailable{reason}`），T04 诊断页给出日志位置与「后台服务版本」；等待提示上有「查看日志」入口（T09）。回退路径是装回上一个版本（后台发现程序换了会自行重启，设计 4）；不存在「临时关掉校验」的开关——发布版没有这个开关是有意的，所以这条紧急路径必须靠日志把原因说清。发布前的本机验证（Q4 已归 T04）每个平台跑一遍是预防。
- 由什么保证：`judge_peer` 全分支单测 + 审计字段测试（`reason` 一定非空、带哈希前缀）；三平台「本机验证步骤」写进实施报告；需实测 N1、N2、N3 跑过。

**S2 攻击者冒充客户端**
- 会出什么事：同用户下的恶意进程（或另一用户）连上后台，发 `SendMessage` 让助手干活、读 `ReadArtifact` 拿到工具输出、发 `ExecuteUserAction` 以用户身份跑命令。
- 止血和回退：另一用户：目录 0700 / DACL 连不到 socket，连到了也在第 1 步被拒。同用户、未签名或换了签名的进程：第 2 步拒；先跑自己的程序再把路径上的文件换回原版：核验的是运行中的映像（2.4b），换文件没用；运行中改清单：不读（2.4）。同用户、在后台启动前就能换二进制或清单、或拿到签名私钥的进程：挡不住，但这样的攻击者已经能直接替换后台二进制，不在 IPC 能防的范围（需求 11 的边界，L2）。发现被冒充：审计里有 `peer_rejected` 的 pid 与路径可追；已经放进来的没有补救，所以第 1、2 步都没有「宽限」。
- 由什么保证：验收 1（Linux CI 以另一用户连接被拒）、验收 2（改一字节的二进制被拒；连接期间替换文件仍按运行中映像判定；启动后改清单无效）、`judge_peer` 单测；已知限制 L1、L2 写明挡不住的情形。

**S3 发布构建里混进 `--dev-trust`**
- 会出什么事：有人在 `Cargo.toml` 的 `[features] default` 里加了 `dev`，或某个工作区 crate 依赖 `iwork-ipc` / `iwork-daemon` / `iwork-client` 时开了 `features = ["dev"]`，发布版带着开关出去；`AGENTS.md` 的安全不变量被破坏。
- 止血和回退：CI `check-no-dev-trust.sh` 红，合不进去。已经发出去的版本：撤版本、重新打包；用户机器上的后台没开这个参数就不受影响（它是启动参数，不是默认行为）。
- 由什么保证：脚本三步——① `cargo metadata --format-version 1` 的 `resolve.nodes` 里，`iwork-ipc`、`iwork-daemon`、`iwork-client` 三个节点在默认 feature 下的 `features` 列表不含 `dev`（这是 feature 依赖图，不是字符串）；② 对 `pnpm -C client tauri build` 产物（打包后的客户端与随包的后台二进制）与 `cargo build --release -p iwork-daemon` 产物 `grep -a -c 'dev-trust' == 0`，再对 `--features dev` 的产物 `> 0` 做阳性对照（证明 grep 真的能找到）；③ 行为证据：发布构建的后台以 `--dev-trust` 启动，断言退出码非 0、stderr 含「未知参数」、socket 文件不存在。字符串对照只是冒烟，①③才是证明。

**S4 补发与实时交接处漏事件或重复**
- 会出什么事：客户端重连后缺一条 `ApprovalRequested`，「待你处理」里少一张卡；或 `MessageAppended` 到两次，对话里出现两条一样的消息。
- 止血和回退：客户端用 `from_seq = 0` 重订阅拿快照，视图整体替换；或重新建连。修复在 `stream.rs` 一处。
- 由什么保证：7.2 的 proptest（随机事件、随机范围增减、随机时刻提交、随机断线重连、随机预算溢出与交接超时注入（都表现为连接被关），断言整条流不漏、不重、严格递增，并用按 id 幂等应用的客户端模型比对最终视图与实体）；`deliver` 是唯一发送入口（`grep` 不到第二处 `Outbound::Event` 的构造）。

**S5 范围变化时的交接：新范围的历史、多查询快照、`snapshot_seq` 与 `to` 的关系**
- 会出什么事：打开一个对话（加范围）时，这个对话的历史消息要进来，而侧栏范围的流已经走到很后面；若把新范围的历史从流中间插进来，流就不递增了。快照若由几个查询在不同时刻取，部分实体比快照 seq 新，事件再送一遍会把新状态盖旧。
- 止血和回退：同 S4。
- 由什么保证：范围变化不续传就整条快照（2.8 第 5、6 步），快照在一个读事务里取、只有一个 seq（2.10 契约，做不到返回错误）；`cursor = snapshot_seq ≥ to`，缓冲里 `≤ snapshot_seq` 的被跳过；测试 `add_scope_after_live_takes_snapshot_and_keeps_stream_monotonic`、`snapshot_is_single_read_transaction_or_error`（内存 `EventSource` 故意在两部分之间提交 → ipc 拒绝该快照并重试，客户端不会看到两个 seq 的拼接）、`snapshot_seq_above_to_skips_covered_buffer`、`conversation_snapshot_has_pending_items`。

**S5a 第 3 轮的三类客户端问题：版本挡增量、删除后复活、分页缺席误删**
- 会出什么事：见 2.8「为什么第 3 轮的三类问题在单流下不再成立」。
- 止血和回退：不适用——单流下这三类事没有发生的路径。
- 由什么保证：`increments_apply_in_order_without_version_gate`（`MessageDelta` 按 offset 连续到达、全部应用）；`deleted_entity_never_resurrects`（流里删除之后没有任何 ≤ 删除 seq 的事件；快照之后没有 ≤ `snapshot_seq` 的事件）；`snapshot_does_not_delete_entities_outside_view`、`pagination_updates_view_members_only`（翻页快照后，实体表里不在本页的消息仍在）。

**S5b 会写视图的查询结果与事件流错位（4/F-1、5/F-1、5/F-2）**
- 会出什么事：若查询结果与事件走两条道——翻页查询在 seq 10 读到消息「生成中」，seq 11 的「完成」事件先到，旧结果后到把消息改回「生成中」；或结果在 seq 12 先到（含未读数 3），缓冲里 seq 11 的 `MessageAppended` 后到，未读数被加成 4；或按游标淘汰结果，在别处每 20ms 提交一次时，一个内容没变的对话页反复「加载失败」。
- 止血和回退：这些路径在交接机制下不存在：结果就在流里 seq = S 的位置，之前的事件在前、之后的在后，客户端不比 seq、不淘汰。查询本身的业务错误（找不到对话、参数错）只得到一个错误响应，流照常；交接的任何其他异常走 2.9 的 `fail_connection`，客户端重连续传。
- 由什么保证：`view_query_result_sits_at_its_seq_in_stream`（内存服务端：查询在 S = 10 读到「生成中」并把结果扣住，期间提交 11「完成」；断言客户端收到的顺序是 …、10 之前的事件、结果、11；逐步断言每个可见状态：结果应用后是「生成中」，11 应用后是「完成」，之后不再回退）；`view_query_ahead_result_then_buffered_older_events_no_double_count`（5/F-1 反例：暂停后缓冲里有 seq 11 `MessageAppended`，查询在读事务里看到 S = 12、未读数 3；断言送出顺序是 11、结果、>12 的事件，客户端逐步状态：应用 11 后未读 N+1，应用结果后未读 = 3，不是 4；`published_head` 等待生效）；`view_query_succeeds_while_other_writes_continue`（5/F-2 反例：查询的数据不变，别的对话每 20ms 提交一次持续 2s；断言一次请求一次响应、有限步内视图加载成功、没有重查）；`deleted_conversation_query_result_comes_before_delete_event`（`ConversationDeleted` 在 S 之后提交 → 结果先到、删除事件后到，视图随删除事件消失；在 S 之前提交 → handler 在读事务里就看不到它，结果本身就是空）；`view_query_error_resumes_live_without_cursor_change`；`view_query_after_failure_arrives_on_new_connection_only`、`committed_but_never_published_fails_handover`、`read_never_returns_fails_handover_without_buffer_pressure`（三条交接异常，见 S6）；`side_query_runs_in_parallel_lane`（`ReadArtifact` 不暂停流）；`query_lane_table_is_exhaustive`（app：`Query` oneof 每个变体都在表里）。

**S6 慢客户端把后台拖慢或拖爆；补发等预算死锁；同游标反复卡住；交接永不结束**
- 会出什么事：一个客户端窗口被系统挂起不读 socket，后台的存储写线程卡在 `publish`；或这条连接的发送队列、补发缓冲无限增长；或补发在持续提交下永远追不完；或补发等预算而预算被自己的缓冲占满、缓冲又要等补发结束才排空，没有新提交时永远卡住；或每次重连都在同一个游标处卡住，原地打转；或交接的取数永不返回、或提交了却永不发布，流永远停在缓冲态（6/F-4、6/F-5）；或非空库重启后第一次交接等一个不会再发布的 S（6/F-3）。
- 止血和回退：只有一条：`fail_connection` 关闭这条连接，客户端重连续传。预算 8 MiB 封顶（队列 + 缓冲），满了关；补发等预算最多 2s，等不到关；交接整体最多 10s（补发按页重置），到期关；`publish` 永不等待；补发上界固定为登记时的 `head`；`published_head` 有启动基线。同游标第二次被关由客户端改走快照。**在 L7 的边界之内**（本连接范围内持久事件的持续速率 × 快照取数时间 < 缓冲预算）这些都是自动的，不用人干预；超出边界时重连循环不收敛，客户端累计到 3 次同游标失败后提示用户，恢复办法是降低写入（停掉正在跑的成员）后重新打开 iWork，或重启后台。真的出事（内存涨、后台自身停滞），`connection_failed` 审计里有 `cause`、`cursor`、`used_bytes`、`in_flight`，同游标连续失败能从连续几条 `connection_failed` 的 `cursor` 相同看出来；`HandoverTimeout` / `PublishStalled` 另记 `error` 给 T04 监督器；重启后台即恢复（崩溃恢复是 T04 的）。
- 由什么保证：验收 5 的集成测试（一个客户端停止读，另一个按时限收齐、有序，推送延迟 P95 只打印不断言；停止读的那个连接被服务端关闭，审计 `QueueFull`，它重连续传后收到的持久事件序列与另一个一致）；`replay_buffer_bounded_with_slow_source`、`replay_buffer_bounded_under_publish_storm`（`used ≤ limit` 恒成立，另一条连接照常收事件）、`replay_terminates_under_continuous_commits`（补发在 `to` 处结束，之后的事件经缓冲交接送达）、`replay_reserve_timeout_fails_connection_and_reconnect_recovers`（预算调小；有限发布突发把缓冲占满后完全停止提交，客户端持续读取：补发在 2s 内发出至少一页，或连接被关、重连续传成功，或同游标第二次被关后客户端用 `from_seq = 0` 得到快照；断言「有限步内客户端状态追平服务端、没有无限等待」）、`same_cursor_second_close_makes_client_snapshot`（客户端模型：两次重连都在同一游标被关 → 第三次 `from_seq = 0`、得到快照、游标跳到 `snapshot_seq`）、`buffer_overflow_before_first_page_fails_connection`（补发第一页还没返回，实时事件把缓冲撑满 → 连接被关、审计 `ReplayBufferFull`；重连续传成功）、`single_event_larger_than_reserve_recovers_via_snapshot`（一条接近 4 MiB 的合法事件，实时占用 7 MiB，补发 `reserve` 超时 → 关；重连同游标再关 → 客户端快照，该事件的效果在快照里，状态正确）；`queue_full_fails_connection_and_reconnect_resumes`（三个活动范围、客户端停止读、队列堆满 → 连接被关；客户端恢复后重连、一次写出三个 `Subscribe` 带同一游标 → 一次续传，序列与对照连接一致，没有重复）；交接异常三条（6/F-2、6/F-4、6/F-5）：`view_query_after_failure_arrives_on_new_connection_only`（Q 在连接被关后才到服务端——服务端此时已没有这条连接，Q 的帧随 socket 关闭丢弃；客户端重连后重发 Q，结果只出现在新流里）、`committed_but_never_published_fails_handover`（内存 `Publisher` 对 seq S 永不 publish：交接 10s 后 `fail_connection(PublishStalled)`，审计 `error`，客户端重连续传后状态正确，迟到的结果没有出现）、`read_never_returns_fails_handover_without_buffer_pressure`（取数 future 永不完成、缓冲不满：10s 后 `HandoverTimeout`，重连续传后状态正确；之后取数 future 完成，其结果被丢弃，新连接的流不受影响）；`published_head_baseline_from_store`（6/F-3：非空库重启、零新增提交，第一次交接立即成功，不等待）；`ConnectionBudget` 的单测（上限、保底、合并、溢出判定、缓冲计入、带超时的 reserve）；`fail_connection_is_the_only_close_path`（计数断言：除对端关闭与服务停机外，所有关闭都经它）。 **P95 < 5ms 这个数挪到基准**（supervisor 2026-11-13 定）：共享 CI 与高负载本机上墙钟 P95 不可信、反复误报，按 AGENTS.md「性能」节，阈值由 `iwork-bench` 的 ipc 基准量（加一组「另一条连接停止读」的慢消费者对照，看 P95 相对于全部连接都在读时的变化），超阈值记回归、不挡合入；集成测试只守隔离本身（另一条照常收齐有序、停止读的被关、重连续传一致）。

**S7 断开时丢了流式文字，界面显示不完整**
- 会出什么事：助手正在输出，这条连接因预算被关，队列里的 `MessageDelta` 随之丢弃；重连续传回来的是持久事件，没有中间的文字片段，界面上那条消息停在旧位置，直到下一片增量或 `MessageCompleted`。
- 止血和回退：`MessageCompleted` 带完整正文（设计 3.5），消息结束时一定会对齐；进行中的消息，T09 可以在重连后对可见对话发一次 `GetConversation`（T02 的 500ms 检查点让查询结果带上已收到的正文）。这是显示问题，不是业务事件丢失。
- 由什么保证：记为 T09 的接口事实（2.11 客户端契约 + 第 9 节「补充」）；T09 验收 2「断线重连界面状态一致」覆盖。

**S8 畸形帧或超长帧让后台崩溃**
- 会出什么事：一个长度字段 `0xFFFFFFFF` 让后台分配 4GB；一个 `Request` 里的 oneof 全空让 handler `unwrap` panic。
- 止血和回退：前者在 `decode_frame` 看到长度就拒；后者 ipc 在交给 handler 前校验 `body` 非空。真崩了由 T04 的拉起与崩溃恢复兜底，不丢已提交事件。
- 由什么保证：fuzz 目标 `frame_decode`、`connection_prehello`、`connection_established`（后者喂随机 `Request`，用计数 handler，断言不 panic、`body` 为空的从不到 handler）；验收 3 的集成测试（超长、垃圾、握手前请求 → 断开，下一条连接正常）。

**S9 macOS socket 路径超长 / Linux 目录权限不对**
- 会出什么事：用户名很长（macOS 路径 > 103 字节）或 `XDG_RUNTIME_DIR` 指向别人建的 0755 目录，后台拒绝启动。
- 止血和回退：`EndpointError` 带路径、上限、实测权限，T04 诊断页原样显示；用户改环境变量或清理目录。不自动修。
- 由什么保证：`endpoint.rs` 的单测用临时目录构造各种错误情形；验收 6。

**S10 同用户的进程抢占管道名或 socket 路径，冒充后台**
- 会出什么事：同用户下另一个进程先建了 `\\.\pipe\iwork-<SID>`，或在我们的后台没起来时把 socket 文件换成它自己的，然后回一个合法的 `Welcome`。客户端如果只看同用户，就会把消息、附件路径、审批选择都交给它。
- 止血和回退：客户端在发 `Hello` 之前对服务端跑完整的 `judge_peer`（2.4），抢占者没有我们的签名或不在清单里 → `PeerRejected`，客户端不发任何帧，按 2.4c 显示等待提示并退避重连（每次仍判定，抢占者永远进不来）；真后台这边 `first_pipe_instance(true)` 失败就退出，T04 当「已有实例」显示诊断（锁持有者 pid）。用户据诊断结束抢占进程。
- 由什么保证：`client_rejects_fake_server_with_valid_welcome`（假服务端：同用户、不同签名、建连即发合法 `Welcome`；断言客户端返回 `PeerRejected`，假服务端一个字节都没收到）、`client_rejects_server_of_other_user`、`client_keeps_rejecting_on_every_retry`；T04 验收 1（并发启动只有一个存活）。

**S11 `Publisher::publish` 被乱序调用**
- 会出什么事：存储写线程在两个线程里提交并发布，seq 10 先于 seq 9 到达 ipc；`cursor = 10` 后 9 被当成「已送出」跳过。
- 止血和回退：ipc `debug_assert!` 在测试里直接失败，发布构建 `error!` 日志一条并照常投递（不丢，可能重复）；修在调用方（单写者，设计 5.2）。
- 由什么保证：ipc 单测 `publish_out_of_order_is_reported`；T02 的单写者是前提。

**S12 升级窗口：新旧版本互不相认，旧后台有待审批的回合**
- 会出什么事：用户装了新版本，新客户端连旧后台在 `Hello` 之前互相拒绝（信任根固定）；旧后台还有待审批的回合。若旧后台要等回合结束才切换，用户批不了也取消不了——卡死（第 1 轮 F-6）。
- 止血和回退，**同协议主版本**（设计 4，`bf73ed9`）：旧后台发现安装目录里的程序换成了新版本，自行重启成新版本，不等回合结束；运行中的回合按中断处理（与崩溃恢复相同，出「继续」卡片，可续接），待审批保留、不作废（需求 12）。客户端在这个窗口里只显示中性的「后台服务与客户端版本不一致」，带「重新打开 iWork」「查看诊断」两个出口，并退避重连，不结束任何进程、不接受陌生对端、不猜谁新谁旧（2.4c）；新后台起来后重连成功，提示消失，用户在「继续」卡片上续接或放弃，待审批照常处理。旧客户端 × 新后台：同一句提示，重连一直被拒，用户点「重新打开 iWork」。回退对称：装回旧版，新后台发现程序换了同样自行重启成旧版。
- 止血和回退，**跨协议主版本**：新后台启动即被数据库门拒绝（备份后拒绝启动，库不动，设计 5.5），客户端看到的是连不上（`Io`）与 T04 诊断页的两个主版本号；没有经过验证的转换，**只承诺装回旧主版本的程序后原库原样可用**。
- 由什么保证：`judge_peer_rejects_other_version_image`（新映像不在旧清单 → 拒）、`manifest_change_after_start_is_ignored`、`client_waits_and_retries_on_peer_rejected`（内存传输：前 N 次连接对端身份是「旧后台」→ `PeerRejected` 且不发 `Hello`；之后对端换成合法身份 → 握手成功；断言退避间隔递增、每次都调了 `judge_peer`）；演练归 T04（Q4 已决定）：同主版本——旧后台有待审批 → 装新版 → 客户端显示等待提示 → 旧后台自行重启 → 新后台起来，回合 `interrupted`、「继续」卡片在、待审批在，批准或拒绝生效 → 回退：装回旧版 → 同样路径；跨主版本——装新版 → 新后台拒绝启动、备份存在、原库哈希不变 → 装回旧版 → 旧后台正常启动、`head_seq` 不变、待审批仍在（与 T01 附录 A 第 1–3 步合并）。

**已知限制（T03 登记）**

- **L1 Linux pid 复用窗口**：`SO_PEERCRED` 给出 pid 到打开 `/proc/<pid>/exe` 之间，对端进程退出、pid 被另一个进程复用，我们算的是复用者的哈希。窗口是微秒级，且攻击者必须是同用户（目录 0700）。macOS 用审计令牌、Windows 持进程句柄，没有这个窗口。不加 `pidfd` 之类的机制堵它。
- **L2 能在我们启动之前改安装目录的同用户攻击者**：双向校验能挡住「同用户下没签名 / 签名不同 / 不在清单里的进程」，不怕路径上的文件被换，也不怕**运行中**清单被改（信任根启动时固定）；挡不住在后台启动之前就换掉我们二进制或清单、或拿到签名私钥的进程。这是需求 11「端点鉴权」能达到的上限，不是 IPC 的缺陷。
- **L3 连接被关期间的流式文字不可补**（S7）。
- **L4 Windows、macOS 的「另一用户连接」在 CI 上测不了**，只测判定函数与 DACL / 目录权限；本机验证步骤写进实施报告（卡验收 1 允许）。
- **L5 映像绑定依赖平台事实**（2.4b）：Windows 的两个分支都依赖「进程映像名反映改名后的名字」，macOS 的两个分支都依赖动态 `SecCode` 的行为，Linux 依赖 `/proc/<pid>/exe` 的 inode 语义；实测证明不了的平台，该平台**全部分支**拒绝连接，M1 暂不支持该平台（Q1 已决定）。
- **L6 升级窗口里客户端分不出「后台旧」「客户端旧」「连到了别的东西」**：三者在客户端都是 `PeerRejected` 或 `ClosedBeforeWelcome`，取决于谁先关连接。提示因此写成中性的，并给「重新打开 iWork」「查看诊断」两个出口，哪一种原因都能走出去；具体是哪一种靠诊断页与审计日志里的 `reason`、路径分辨。不为区分它们再加协议或握手字段。
- **L7 持续高写入 + 快照取数慢时，重连循环不保证收敛**（7/F-2）：成立边界是「本连接过滤范围内**持久事件**的持续速率 × 全范围快照的取数时间 > 缓冲预算（7 MiB）」——此时无论续传还是 `from_seq = 0` 的快照，在结果返回前实时缓冲就满了，`fail_connection(ReplayBufferFull)`，重连后再来一遍。持久事件不含 `MessageDelta` 这类瞬时增量（它们在 Replaying 时不进缓冲），边界按持久事件的**编码字节**速率乘**实际**快照耗时算：`MessageCompleted` 带完整正文，大正文事件、慢磁盘或读池排队都会提高触发机会，实际发生频率待实测（T11 基准）。诊断：`connection_failed` 审计里连续多条 `cause = ReplayBufferFull`、`cursor` 相同、`in_flight` 是快照。用户可执行的恢复：停掉正在跑的成员（降低写入）后重新打开 iWork，或重启后台服务。用户也可以关掉高流量的对话来缩小本连接范围（2.11 契约）。不为此加新的恢复机制（比如快照分片、限流）：产品负责人 2026-11-10 已接受这条限制，每加一套机制就是一轮新的交错反例。

T0 没有任何 IPC 与签名实测。下面三项在实施第 3 步（2.4 的平台代码）之前跑，结果写进 `docs/design/t0-findings.md` 新一节「T03 本机通信实测」。每项都含「换文件」的反例：**证明不了平台会阻止替换或我们的绑定能识别替换，那个平台的全部分支就拒绝，M1 暂不支持该平台**（2.4b、L5；Q1 已决定）。

### 8.1 N1 macOS：审计令牌、动态 `SecCode`、自签证书、换文件

要验证：① `LOCAL_PEERTOKEN` 在当前 macOS 上可用，拿到的令牌能喂给 `SecCodeCopyGuestWithAttributes`；② ad-hoc 签名的二进制 `SecCodeCheckValidity` 通过、没有证书、`kSecCodeInfoUnique` 有值；③ 用临时钥匙串里的自签代码签名证书签的两个二进制，叶证书哈希一致，`SecCodeCheckValidity` 通过；④ 改一字节后 `SecCodeCheckValidity` 失败；⑤ 未签名二进制的行为；⑥ **反例**：对端进程连着时，(a) 把它的可执行文件 `mv` 走、放一个别的签名的文件在原路径——动态 `SecCode` 的证书与 cdhash 是否仍是原映像的；(b) 原地 `dd` 覆盖几个字节——`SecCodeCheckValidity` 是否立刻失败；(c) 在 `SecCodeCheckValidity` 与 `SecCodeCopySigningInformation` 之间换文件——两者是否都来自同一个运行中映像（预期是：都从动态对象读）。

脚本草案 `tools/t0/iwork-t03-macos-codesign.sh`（`tools/t0/` 风格，输出到 `tools/t0/out/`）：

```bash
#!/usr/bin/env bash
set -euo pipefail
OUT=tools/t0/out/t03-macos; mkdir -p "$OUT"; cd "$OUT"
# 1. 自签代码签名证书 + 临时钥匙串
cat > csr.cnf <<'EOF'
[req]
distinguished_name=dn
x509_extensions=v3
prompt=no
[dn]
CN=iWork Test Signer
OU=IWORKTEST01
[v3]
keyUsage=critical,digitalSignature
extendedKeyUsage=critical,codeSigning
EOF
openssl req -x509 -newkey rsa:2048 -nodes -days 2 -config csr.cnf -keyout key.pem -out cert.pem
openssl pkcs12 -export -inkey key.pem -in cert.pem -out signer.p12 -passout pass:t
security create-keychain -p t t03.keychain-db
security import signer.p12 -k t03.keychain-db -P t -T /usr/bin/codesign
security set-key-partition-list -S apple-tool:,apple: -s -k t t03.keychain-db
# 2. 最小二进制：unsigned、adhoc、signed、tampered、other（另一张自签证书）
printf 'int main(){return 0;}' > a.c; cc a.c -o unsigned; cp unsigned adhoc; cp unsigned signed; cp unsigned other
codesign -s - adhoc
codesign --keychain t03.keychain-db -s "iWork Test Signer" signed
cp signed tampered; printf '\x00' | dd of=tampered bs=1 seek=$(( $(stat -f%z tampered) - 1 )) conv=notrunc
codesign -s - other   # 另一个 ad-hoc 身份，用作「换上去的文件」
# 3. codesign 自验：证书、cdhash、完整性
for b in unsigned adhoc signed tampered other; do
  echo "== $b"; codesign -dvvv "$b" 2>&1 | grep -E 'TeamIdentifier|Signature|CDHash|Authority' || true
  codesign --verify --verbose=2 "$b" 2>&1 || echo "verify failed: $?"
done
LEAF=$(openssl x509 -in cert.pem -outform DER | openssl dgst -sha1 | awk '{print $2}')
codesign --verify -R="=certificate leaf = H\"$LEAF\"" signed && echo "leaf requirement OK"
codesign --verify -R="=certificate leaf = H\"$LEAF\"" adhoc || echo "adhoc rejected by leaf requirement (expected)"
# 4. 审计令牌 + 动态 SecCode + 换文件反例：dev example `peer-probe` 起一个 UDS 服务端，
#    用 `--hold` 让客户端连上后停住；期间按下面三种方式换文件，服务端每秒重新算一次 PeerIdentity 并打印。
cat > probe.cmd <<'EOF'
# (a) 改名替换：cp signed live && (./live --connect & sleep 1; mv live live.old; cp other live)   期望：证书、cdhash 仍是 signed 的
# (b) 原地覆盖：cp signed live && (./live --connect & sleep 1; printf '\x00' | dd of=live bs=1 seek=4096 conv=notrunc)   期望：SecCodeCheckValidity 失败 → Unavailable
# (c) 两步之间换文件：peer-probe --pause-between-validity-and-info 5，期间做 (a)   期望：两个结果一致
cargo run -p iwork-ipc --features dev --example peer-probe -- --server --hold 30 &
EOF
security delete-keychain t03.keychain-db
```

要记录的结论：五种二进制各自落到 `SignerIdentity` 的哪个变体；`LOCAL_PEERTOKEN` 的 `getsockopt` 返回值；(a)(b)(c) 三个反例的结果；`security-framework` crate 的哪个版本提供了审计令牌入口。

### 8.2 N2 Windows：自签 Authenticode、`WinVerifyTrust` 返回码、改名后的映像路径、管道两端 pid

要验证：① `New-SelfSignedCertificate -Type CodeSigningCert` + `Set-AuthenticodeSignature` 签的 exe，`WinVerifyTrust(WTD_UI_NONE, WTD_REVOKE_NONE)` 返回 `CERT_E_UNTRUSTEDROOT`（预期）而不是别的；② 改一字节后返回 `TRUST_E_BAD_DIGEST`；③ 未签名返回 `TRUST_E_NOSIGNATURE`；④ 从 `WTHelperGetProvSignerFromChain` 取到的叶证书 SHA-256 等于证书的 SHA-256；⑤ `GetNamedPipeClientProcessId` 与 `GetNamedPipeServerProcessId` 对 tokio 命名管道两端的句柄都可用；⑥ **反例**：对运行中的进程，(a) 原地写它的 exe → 预期 `ERROR_SHARING_VIOLATION`；(b) `Rename-Item` 它的 exe 再放一个别的文件到原路径 → `QueryFullProcessImageNameW(PROCESS_NAME_NATIVE)` 返回**新名**（绑定成立）还是旧名（绑定不成立，Windows 暂不支持）；(c) 在第一次查名与 `CreateFileW` 之间换文件 → 第二次查名与 `GetFinalPathNameByHandleW` 不一致，被 2.4b 第③步拦住。


### 8.3 N3 Linux：`/proc/<pid>/exe` 在二进制被替换后的行为

要验证：对端进程启动后把它的可执行文件 `mv` 走、原地覆盖、`rm`，服务端打开 `/proc/<pid>/exe` 读到的哈希仍是启动时那份（预期：是，魔法链接指向 inode）；`readlink` 带 `(deleted)` 后缀时去掉后缀的路径仍是原目录。

```bash
#!/usr/bin/env bash
set -euo pipefail
OUT=tools/t0/out/t03-linux; mkdir -p "$OUT"; cd "$OUT"
cp /bin/sleep ./peer; ./peer 300 & PID=$!
sha256sum ./peer > before.txt
sha256sum /proc/$PID/exe | sed 's#/proc.*#exe-before#' >> before.txt
mv ./peer ./peer.old; cp /bin/true ./peer                              # 改名替换
sha256sum /proc/$PID/exe | sed 's#/proc.*#exe-after-rename#' > after.txt  # 期望等于 exe-before
readlink /proc/$PID/exe >> after.txt                                     # 期望指向 peer.old
printf '\x00' | dd of=./peer.old bs=1 seek=100 conv=notrunc 2>/dev/null  # 原地覆盖（会报 Text file busy 或成功，都记下）
sha256sum /proc/$PID/exe | sed 's#/proc.*#exe-after-overwrite#' >> after.txt
rm ./peer.old; readlink /proc/$PID/exe >> after.txt                     # 期望带 (deleted)
sha256sum /proc/$PID/exe | sed 's#/proc.*#exe-after-rm#' >> after.txt   # 期望仍可读、仍等于 exe-before
kill $PID; cat before.txt after.txt
```

另外两件事不需要实测、实施时直接核对：tokio `UnixStream::peer_cred()` 在 macOS 上是否返回 pid（返回就省一次 `getsockopt`）；`security-framework` 的 `code_signing` 模块版本。

## 10 已决定（产品负责人 2026-11-10）

五个问题全部有了结论，方案正文按结论写；这里保留问题与选项供追溯。

**Q1 发布构建的签名身份、安装清单的产生、各平台支持范围——已决定：按默认 (a)**
- 问题：设计 3.2 第 2 步以「发布构建有代码签名证书」为前提；iWork 是非商用个人工具，文档没写有没有证书；没有证书时 macOS ad-hoc、Windows 未签名，第 2 步永远不过；Linux 的「安装清单」没人产生；每个平台的身份取法都依赖一条未实测的操作系统事实。
- 决定：判据由构建自己的身份决定——有证书只认同一张叶证书；没有证书只认启动时读一次的安装清单（Linux 永远如此；macOS、Windows 无证书时也如此）。清单由 `scripts/write-install-manifest.sh` 产生，打包流程调用，放在两个二进制旁边，只登记这一版；客户端与后台服务打包在同一目录。**映像绑定实测不过的平台 M1 暂不支持**，不走任何退路分支。
- 曾列的备选：(b) 只按设计字面实现，无证书构建在 macOS、Windows 不可用；(c) 无证书时跳过第 2 步（等于发布版自带 dev-trust，违反安全不变量）。
- 支持矩阵（「证据」列由实施者在第 0 步实测后填进 `t0-findings.md`；任一格不通过 → 该平台整体受阻）：

| 平台 | 构建 | 对端身份怎么取 | 绑定到运行中映像靠什么 | 证据 | 不通过时 |
| --- | --- | --- | --- | --- | --- |
| Linux | 无证书（唯一） | `SO_PEERCRED` uid/pid；`/proc/<pid>/exe` fd 读全文 SHA-256；安装清单 | `/proc/<pid>/exe` 是映像 inode 的魔法链接 | N3 待测（改名、覆盖、删除三种） | Linux 暂不支持 |
| macOS | 有证书 | `LOCAL_PEERTOKEN` → 动态 `SecCode` → 叶证书 SHA-256 | 动态 `SecCode` 由内核按进程跟踪 | N1 待测（含换文件反例 a/b/c） | macOS 暂不支持 |
| macOS | 无证书（ad-hoc） | 同上 → cdhash；安装清单 | 同上 | N1 待测 | macOS 暂不支持 |
| Windows | 有证书 | 管道两端 pid → 进程句柄 → 令牌 SID；映像文件按句柄 `WinVerifyTrust` → 叶证书 | 2.4b 两次查名 + 按句柄验（依赖「映像名反映改名后的名字」） | N2 待测（含改名、原地写、两步之间换文件） | Windows 暂不支持 |
| Windows | 无证书 | 同上 → 按同一句柄读全文 SHA-256；安装清单 | 同上 | N2 待测 | Windows 暂不支持 |

**Q2 macOS「同一签名者」比什么——已决定：叶证书 SHA-256**
- 问题：设计 3.2 写 Team ID；Team ID 来自叶证书 OU，要配 `anchor apple generic` 才防自签冒充，而带了锚 CI 就测不了通过分支；Windows 那条本来就是证书指纹。
- 决定：两个平台统一比叶证书 SHA-256（macOS 从动态 `SecCode` 的 `kSecCodeInfoCertificates[0]`，Windows 从同一次 `WinVerifyTrust` 的签名者证书）。换证书时新旧版本互不相认，走升级路径（2.4c），不设过渡清单。
- 曾列的备选：按设计用 `anchor apple generic and certificate leaf[subject.OU] = "<Team ID>"`，通过分支只能本机验证。

**Q3 会话范围的订阅拿不到回合、审批事件——已决定：事件带会话 ID（(a)）**
- 问题：`DomainEvent::stream()` 把回合事件放 `turn:<turn_id>`、审批放 `approval:<approval_id>`，`TurnStateChanged`、`ToolCallStarted`、`ApprovalDecided` 等载荷里没有 `conversation_id`，按流补发会漏。
- 决定：给缺 `conversation_id` 的回合、审批、亲手执行卡片事件加该字段（Protobuf 只增字段，`update-contract --additive`；domain 结构体与 `convert` 同步）；补发对会话范围用 `EventFilter::All` 从 `from` 读到 `to`，在 daemon 侧按载荷过滤（纯函数 `routes_for`，同一个函数也给实时 `publish` 算 `routes`）。配套三点：旧载荷（加字段前的开发期库）`conversation_id` 为空时 `routes_for` 只返回主键并 `warn` 一次，不回填；补发以 `to` 为固定上界、靠 `next_from` 判结束，不把「过滤后不足一页」当读完；会话范围的快照 = `GetConversation{最新一页}` + `ListPendingItems`，已决定的审批与已结束卡片靠 `GetConversationResult` 补 `approvals`、`user_actions`（只增字段，归 T10）。
- 曾列的备选：(b) T02 的 `events` 表加路由列；(c) 会话范围不补发、一律快照。

**Q4 发布前与升级期的本机验证归谁——已决定：真机互连与升级演练归 T04，无监听端口检查归 T11**
- ① 三平台「真实构建的客户端连真实构建的后台」；② 升级演练两段：同主版本——旧后台有待审批 → 装新版 → 客户端显示等待提示 → 旧后台自行重启 → 新后台起来，回合 `interrupted`、「继续」卡片在、待审批在，批准或拒绝生效 → 回退：装回旧版 → 同样路径；跨主版本——装新版 → 新后台拒绝启动、备份存在、原库哈希不变 → 装回旧版 → 旧后台正常启动、`head_seq` 不变、待审批仍在（与 T01 附录 A 第 1–3 步合并）；③ 运行时「无监听端口」检查（`lsof -i -P` / `netstat -ano` 对 iWork 全部进程无监听端口）。T03 只交脚本、步骤与断言。

**Q5 升级规则——已决定并已写进技术设计第 4 节（`bf73ed9`）**
- 原规则：有回合在跑就等它们结束再切换。问题：信任根固定后升级窗口里新旧版本互不相认，审批不超时，旧后台有待审批时既等不到回合结束、用户也批不了。
- 决定：后台发现安装的程序已换成新版本就自行重启切换，不热替换；有回合在跑时不等，按中断处理（与崩溃恢复相同，出「继续」卡片，可续接），待审批保留、不作废；客户端不负责结束旧后台进程。检测与自行重启的机制归 T04（2.4c）。
- 曾列的备选（第 2 轮方案）：客户端提示用户确认后结束旧后台——产品负责人否决，客户端不碰进程。

## 12 ADR（由 developer 随实现写入 `docs/adr/`，每条一个文件；合入时定为 ADR-0011 / 0012（原暂记 ADR-T03-a / b））

**ADR-0011 本机 IPC 的对端信任：两端互验，同用户 + 同签名者或同映像，核验运行中的映像，信任根启动时固定，升级靠后台自行重启，开发开关编译期剔除**
- 背景：需求 11 要求本机 IPC 端点鉴权、不把 localhost 当可信；设计 3.2 给出两步校验但只写了后台验客户端；iWork 可能在没有代码签名证书的情况下发布；升级期间新旧二进制同时存在且审批不超时；T0 没有实测。
- 决定：平台代码只负责把操作系统给的事实装进 `PeerIdentity`，并保证装的是运行中映像的身份（Linux `/proc/<pid>/exe` inode、macOS 动态 `SecCode`、Windows 按句柄 + 两次查名，有证书无证书都先过绑定）；判定是纯函数 `judge_peer`，三平台、两端同一份。第 1 步比 uid / SID，任何构建、任何开关都不跳过。第 2 步按自己的身份选判据：自己有证书 → 对端叶证书 SHA-256 必须等于自己的；自己没有 → 对端映像身份在**启动时读进内存**的安装清单里且在安装目录内。信任根此后不变：运行中没有任何输入能扩大它。取不到对端身份、映像绑定未被实测证明的平台，一律拒绝，该平台暂不支持。客户端在发 `Hello` 之前对服务端做同样的判定。拒绝不发帧、记审计。升级期间新旧版本互不相认是预期行为：后台发现安装的程序换了版本就自行重启（回合中断可续、待审批保留，设计 4），客户端只显示等待提示并退避重连，不结束任何进程、不接受陌生对端。`--dev-trust` 只跳过第 2 步，整段代码只在 `dev` feature 下存在，CI 查 feature 图、打包产物与运行行为。
- 备选：客户端只验同用户（同用户的假后台能拿走用户输入，否决）；按路径重新打开文件验签（验的可能不是运行中的映像，否决）；清单每次连接重读、带签名者列表与上一版条目以便升级期互认（同用户进程改一个 JSON 就能获得信任，否决）；客户端提示用户确认后结束旧后台（产品负责人否决，客户端不碰进程；由后台自行检测并重启）；macOS 比 Team ID 并锚定 Apple（CI 测不了通过分支，且与 Windows 判据不一致，否决）；无证书时跳过第 2 步（等于发布版自带 dev-trust，否决）；运行时「证书不匹配就退到清单」的 OR 逻辑（让攻击者挑最弱的一条，否决）；绑定实测失败的平台改走「有证书」分支当退路（证书解决不了「验的不是运行中的映像」，否决）；升级时临时关闭验签（否决）；用 `pidfd` 堵 Linux 的 pid 复用窗口（为一个微秒级、仅同用户可利用的窗口加机制，按安全设计原则不加，记已知限制）。
- 影响：发布流程必须产生安装清单并把两个二进制放在同一目录；升级一定伴随后台重启，正在跑的回合中断可续（设计 4 已改）；审计日志里能看到两端每次拒绝的 pid、路径、原因；在后台启动前就能改安装目录的同用户攻击者挡不住，这是需求 11 能达到的上限；某个平台的绑定实测不通过就是该平台暂不支持。

**ADR-0012 事件订阅的投递模型：一条连接一条按 seq 排好的流，范围只是过滤条件，范围变化整条重订阅，快照只替换视图，补发有固定上界、保底预算与有界等待，落后只丢瞬时事件**
- 背景：设计 3.5 要求「先补发再无缝切实时」「太旧返回快照」「持久事件在任何情况下不丢」；多个订阅范围会重叠（侧栏与某对话）且视图粒度不同（摘要 vs 全文）；ipc 不能依赖 domain，不知道事件属于谁；补发期间的缓冲与补发终止条件要有界。前两版（跨订阅共享交付记录；订阅各自独立 + 客户端按实体版本合并）在三轮审查里各被审出一批交错反例，根源都是一条连接上有多个游标。
- 决定：上层随事件给出路由键集合（`RoutedEvent`，实时与历史都由 `iwork_app::subscription::routes_for` 算），ipc 只做键的覆盖匹配。**一条连接一条流**：范围集合的键取并集作过滤，一个游标。范围变化时：`from_seq == cursor` 则续传（从 `cursor` 按页补发到登记时的 `head`，`ReplayPage.next_from` 是扫描位置），否则对全部活动范围在一个读事务里取一次快照、游标推到 `snapshot_seq`；然后按游标排空缓冲、切实时。投递只比游标：`seq ≤ cursor` 不发。保证：整条流不漏、不重、严格递增。客户端按实体 id 幂等应用事件；快照与分页只替换视图成员与内容，不删实体，实体生死只由事件决定。发送队列与补发缓冲共用 8 MiB 预算，其中 1 MiB 只给补发：队列满先合并相邻文字增量；流的任何异常（预算用满、补发等预算超时、交接超时、发布停滞）只有一个出口 `fail_connection`：关闭连接，客户端走已有的断线重连——一次写出全部 `Subscribe` 带同一游标续传；同游标第二次被关由客户端改用 `from_seq = 0` 拿快照。不实现「落后」状态与落后通知。`published_head` 在接受连接前以库里的 head 为基线。客户端只有一个有序出口 `Incoming`：会写视图的查询结果与快照和事件一起按到达顺序出来，future 只带成功 / 失败。会写视图的查询不走独立查询道，而是与订阅快照共用「交接」：暂停流、读事务里取结果与 S、等 `published_head ≥ S`、把结果插到流里 S 的位置、恢复；一条连接上的持久事件与这类响应因此是一个全序，客户端按到达顺序应用、不比 seq。
- 备选：ipc 在内存里保留最近 N 条事件做补发（内存随事件增长，与「补发走存储」冲突）；跨订阅共享交付记录做连接级去重（每种交错都是一个反例，否决）；订阅各自独立并要求客户端按实体版本合并（增量事件被整实体版本挡掉、删除后复活、分页缺席误删，否决）；范围变化只快照新范围、流不重启（新范围的历史从流中间插入，破坏递增，否决）；多查询快照各自取 seq 再取最小值（部分实体比快照新，事件再送一遍把新状态盖旧，否决——改为要求一个读事务）；补发无限等预算（死锁，否决）；无保底预算（同游标反复取消，否决）；会话恢复用 `resume_token` 在服务端保留订阅（多一套状态，重连靠 `from_seq` 已足够）；落后时把持久事件也丢掉（违反设计 3.5）。
- 影响：所有发事件的地方必须给出路由键，且 `publish` 按 seq 递增调用（单写者）；`EventSource` 实现方要返回扫描游标，快照要在一个读事务里取（T02 提供读事务，T10 的查询受理在其中执行）；打开一个对话 = 一次全范围快照；T09 的状态库按 id 幂等应用、快照只改视图、重连时一次写出全部 `Subscribe`；落后期间的流式文字不可补，界面靠 `MessageCompleted` 或重新查询对齐（T09）；加一种订阅范围 = `frame.proto` 一个字段 + `iwork-app::subscription` 两行。
