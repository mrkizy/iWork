# ADR-0012 事件订阅的投递模型：一条连接一条按 seq 排好的流，异常只有一个出口——关连接

- 状态：提议（2026-11-10，T03；编号由 supervisor 合入时统一）
- 依据：技术设计 3.4、3.5、3.6；T03 方案 2.7–2.11、第 13 节（九轮方案审查的反例与收口）

## 背景

技术设计 3.5 要求「先补发再无缝切实时」「太旧返回快照」「持久事件在任何情况下不丢」。多个订阅范围会重叠（侧栏与某对话）；ipc 不能依赖 domain，不知道事件属于谁；补发期间的缓冲与终止条件要有界。前几版（跨订阅共享交付记录；订阅各自独立 + 客户端按实体版本合并；「落后」状态 + 落后通知）在审查里各被审出一批交错反例，根源是一条连接上有多个游标、多条恢复路径。

## 决定

1. **路由由上层给出**：事件随 `RoutedEvent.routes` 带路由键（`iwork_proto::routing::StreamKey`），实时与补发由同一个 `iwork_app::subscription::routes_for` 算；ipc 只做键的覆盖匹配。
2. **一条连接一条流、一个游标**：全部范围的键取并集作过滤。唯一的发送入口 `deliver` 只比游标（`seq ≤ cursor` 不发），保证整条流不漏、不重、严格递增。
3. **范围变化 = 续传或整条快照**：`from_seq == cursor`（空流上第一次订阅把游标置为 `from_seq`）且落后不超过 `replay_limit` 就续传——从存储按页补发到登记时的 `head`，`ReplayPage.next_from` 是扫描位置；否则对全部活动范围取一次快照（必须一个读事务、各部分 seq 相同，不同就丢弃重取）。先登记后读 head，期间实时事件进缓冲，交接时按游标排空。
4. **会写视图的查询走同一条「交接」**：暂停流 → 读事务里取 `(结果, S)` → 等发布水位 `≥ S` → 把结果插在流里 S 的位置 → 恢复。订阅、退订、会写视图的查询进同一个 FIFO，一次一个；头部连续同 `from_seq` 的订阅合并成一次。不写视图的查询（`ReadArtifact`、`ListModels`）并行（≤ 4）；命令串行。哪些查询算「会写视图」由 `iwork_proto::routing::query_lane` 穷举登记。
5. **发布水位有启动基线**：`serve` 接受连接前以存储 head 为基线。
6. **背压与一切流异常只有一个出口 `fail_connection`**：每连接 8MiB 预算（发送队列 + 补发缓冲，其中 1MiB 只给补发）；实时事件放不下先合并同一条消息的相邻文字增量，仍放不下、补发等预算超过 2s、交接超过 10s、发布停滞、存储出错、协议违规，一律审计后关闭连接。持久事件不丢：它们在存储里，客户端重连按游标续传。不实现「落后」状态，`SubscriptionLagging` 字段保留不发。
7. **客户端只有一个有序出口 `Incoming`**，按字节有界（默认 4MiB），满了停读 socket，由服务端预算接手。会写视图的查询结果与快照和事件一起按到达顺序出来；future 只说成败。

## 备选

- ipc 在内存里保留最近 N 条做补发：与「补发走存储」冲突，内存随事件增长。
- 跨订阅共享交付记录 / 订阅各自独立 + 实体版本：每种交错都是新反例。否决。
- 范围变化只快照新范围、流不重启：新范围的历史从流中间插入，破坏递增。否决。
- 多查询快照各取 seq 再取最小值：部分实体比快照新，事件再送一遍把新状态盖旧。否决。
- 「落后」通知 + 客户端重订阅，与断线重连并存：两套恢复路径在交界处反复出反例；断开重连本来就必须有。否决（产品负责人第 7 轮批准）。

## 影响

- 所有发事件的地方必须给出路由键，且 `Publisher::publish` 按 seq 递增调用（单写者）。
- `EventSource` 实现方（daemon）要返回扫描游标，快照在一个读事务里取；会写视图的查询受理（T10）在一个读事务里执行并把那个事务看到的 head 填进 `QueryResult.seq`。
- 客户端（T09）按 id 幂等应用、快照与查询结果只替换视图、游标在应用时推进；连接结束就重连并一次写出全部 `Subscribe`；有范围的视图还没对齐（它的 `Subscribed` 没到）时重连用 `from_seq = 0`；同游标第二次被关也改用 0。
- 持续高写入 + 快照取数慢时重连不保证收敛（方案已知限制 L7，产品负责人已接受）。
