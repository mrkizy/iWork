# ADR-T10a-a 回合的派发、取消、续接、删除都由一个回合宿主从已提交的状态推出来

- 状态：提议（2026-11-13，T10a 步 3–5；编号合入时由 supervisor 统一）
- 依据：`docs/plans/T10a.md` 0a.1 第 1、2、7、9 条，0a.3 的 A、D、E 组，2.5、2.6、2.8，第 13 节；ADR-T10a-b

## 背景

回合编排（T05、T06）、审批引擎（T07）、存储（T02、T04）各自都对，缺中间一层决定「谁来做下一步」：谁派发排着的回合、谁给在跑的回合发取消、谁续接已中断的回合、编排出错后谁补账、退出时谁收尾。ipc 在客户端断开时会在任何一个等待点中止受理函数；用户的操作可能在进程没了之后才轮到。T10e 的卡片一侧为同一类问题审了五轮。

## 决定

1. 受理函数只做「校验 + 一笔提交」，落盘才算受理（`handler/dispatch.rs`）：同一个 `command_id` 一次只进一份，轮到自己先查回执（排在写队列里），没查到才进受理函数。提交之后要做的事一律不放在它的返回路径上。
2. 一个致命的常驻任务（回合宿主，`host/`）每轮读已提交的状态，决定派发、发取消、续接、补账；每个对话一条会话线，一个会话线任务拥有那条 `SessionLine`。宿主做什么只看已提交的状态和自己的关闭状态，内存里另外只留进程句柄与每趟编排的结局。决定「一个对话这一轮做什么」是纯函数（`host/plan.rs`）。
3. 用户的「取消」「继续」落成事件（回合意图），不是内存信号；意图只管它落盘时的那一段，不跨后台重启。
4. 会话线表与关闭状态在一把锁里：交活即占用、交活的依据不比上一趟的结束更旧（趟数）、发取消在锁里同步调用、记结束与交下一趟同一把锁。
5. 封口闸放在存储端口的入队点上（`gate.rs`），全后台拿到的都是带闸的那一个；封口之后没有新入队的提交。
6. 宿主或会话线 panic 时整个后台退出，交崩溃恢复，不在进程内补事实。

## 放弃的做法

1. 受理函数直接调编排：提交后的事挂在一个会被中止的任务上。
2. 每条命令一个后台任务：要给每个任务定监督与恢复。
3. 取消、继续用内存信号：重放去不了重，进程没了就丢（方案第 1 轮的 1/F-2、F-4、F-5）。
4. 宿主 panic 后只重启这一条线：要靠内存里的东西补事实（T10e 第 3 轮被否过）。
5. 在各个提交调用点上检查封口：经引擎的提交在追平、拿令牌之后才入队，调用点上看不到（方案 5/F-1）。

## 影响

- 多一种事件（回合意图）与几列投影（步 1）；每条命令多一次排在写队列里的查回执。
- 一个对话的缺陷会连带打断所有在跑的回合（P3 a，M1 单人使用）。
- `ShutdownDaemon` 的受理变成异步（读 N 限时 2 秒，再在宿主的锁里一口气判）；`RunningWork` 接缝从「同步数内存」改成 `quit_counts` + `try_quit`。
- ipc 的 `Server` 要先拿到请求入口才给出发布方，而受理与宿主要用发布方：请求入口与停机流程看到的「在跑的东西」都先交一个空的、`bind` 之前填好（`handler::Late`、`work::LateWork`）。
