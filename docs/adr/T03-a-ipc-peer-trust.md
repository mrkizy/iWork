# ADR-T03-a 本机 IPC 的对端信任：两端互验，同用户 + 同签名者或同安装映像，核验运行中的映像，信任根启动时固定

- 状态：提议（2026-11-10，T03；编号由 supervisor 合入时统一）
- 依据：需求第 11 章（本机 IPC 端点鉴权、不把 localhost 当可信）；技术设计 3.1、3.2、第 4 节「升级」；T03 方案 2.2–2.4c、第 10 节 Q1/Q2/Q5

## 背景

需求要求本机 IPC 端点鉴权。技术设计 3.2 给出两步校验（同用户、同签名），但只写了后台验客户端；iWork 可能没有代码签名证书就发布；升级期间新旧二进制同时存在、审批不超时；T0 没有任何 IPC 与签名的实测。

## 决定

1. **平台代码只装事实，判定是一个纯函数**。`peer::{linux, macos, windows}` 把操作系统给的事实装进 `PeerIdentity`；`judge_peer(own, peer, policy)` 三平台、两端同一份，每个分支有单测。
2. **第 1 步比 uid / SID，任何构建、任何开关都不跳过**（`--dev-trust` 也不跳过）。
3. **第 2 步按自己的身份选判据，两条分支互斥**：自己有证书 → 对端叶证书 SHA-256 必须等于自己的，不看清单；自己没有证书 → 对端映像身份必须在**启动时读进内存**的安装清单 `iwork-manifest.json` 里，且可执行文件在安装目录内。不存在「证书不符就退到清单」的 OR。
4. **核验运行中的映像，不是路径上的文件**：Linux 读 `/proc/<pid>/exe` 的 fd；macOS 用审计令牌拿动态 `SecCode`；Windows 按句柄验、开句柄前后两次查名一致才算。**映像绑定没有被实测证明的平台，两条分支一律返回 `Unavailable`，按拒绝处理，该平台暂不支持**（实测结论见 `docs/design/t0-findings.md`「T03 本机通信实测」）。
5. **信任根启动时固定**：`SelfIdentity::detect()` 只在启动时跑一次，之后不读磁盘上的清单。
6. **客户端在发 `Hello` 之前对服务端做同样的判定**；任何一端拒绝都不发帧，记审计 `peer_rejected`（`iwork.ipc.audit`，不记内容）。
7. **升级期间新旧版本互不相认是预期行为**：后台发现安装的程序换了版本就自行重启（T04）；客户端把 `PeerRejected` 与 `ClosedBeforeWelcome` 当同一个状态，显示中性的「后台服务与客户端版本不一致」，给「重新打开 iWork」「查看诊断」两个出口，退避重连（200ms 起、上限 5s），每次仍判定，不结束任何进程。
8. **`--dev-trust` 整段代码只在 `dev` feature 下存在**：`TrustPolicy::DevTrust`、参数解析、审计字样都 `#[cfg(feature = "dev")]`；`scripts/check-no-dev-trust.sh` 在 CI 查 feature 图、产物字符串（含阳性对照）与「发布进程收到该参数拒绝启动」。

## 备选

- 客户端只验同用户：同用户的假后台能拿走用户输入、附件、审批选择。否决。
- 按路径重新打开文件验签：验的可能不是运行中的映像。否决。
- 清单每次连接重读、带上一版条目以便升级期互认：同用户进程改一个 JSON 就获得信任。否决。
- 客户端提示后结束旧后台：产品负责人否决，客户端不碰进程。
- macOS 比 Team ID 并锚定 Apple：CI 测不了通过分支，与 Windows 判据不一致。否决。
- 无证书时跳过第 2 步：等于发布版自带 dev-trust。否决。
- 用 `pidfd` 堵 Linux pid 复用窗口：为微秒级、仅同用户可利用的窗口加机制，按安全设计原则不加，记已知限制 L1。

## 影响

- 发布流程必须产生安装清单（`scripts/write-install-manifest.sh`）并把客户端与后台放在同一目录。
- 升级一定伴随后台重启（技术设计第 4 节）。
- 在后台启动前就能改安装目录、或拿到签名私钥的同用户攻击者挡不住（L2），这是需求 11 能达到的上限。
- 某平台映像绑定实测不通过，就是该平台暂不支持；改为支持要先补实测并另出方案。
