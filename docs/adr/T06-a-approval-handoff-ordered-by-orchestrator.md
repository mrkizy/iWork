# ADR-T06-a 审批的提交、交付、等待上限由回合编排的提交顺序裁决；请求交接是一把锁护着的一张表

- 状态：已采纳（2026-11-11，T06 S2；编号合入时由 supervisor 统一）
- 依据：`docs/plans/T06.md` 2.6 第 3–5、8 条，2.7，4.2，4.2a，15.3；`docs/plans/T07.md` 6.10.8
- 实现：`crates/iwork-core/src/turn/{permission,runner,scheduler,binding,resume_note}.rs`、`crates/iwork-agent-acp/src/client.rs`

## 背景

Claude Code 的 hook 超时即放行（t0-findings 2.1），所以要在到时前主动拒绝并停下回合，且审批不作废、批准后可续接。方案第 1 版把计时放在 ACP 客户端、到时就丢掉处理中的 future：一个 `select!` 只裁决哪个 future 先返回，撤不回已经落盘的批准和已经发出的答复。后面几版把「停止受理」做在信号信箱上（只撤票；关信箱加排空；回绝调度器暂存的那一个），每轮审查都还剩一个入口：信箱的发送分两步（先加计数、后入队），和「关」不是一个原子动作，编排读到「空了」时处理方可能正送到一半，两边互相等满 `GRACE_PERIOD`。

## 决定

1. **三件事都是编排循环的输入**，一次处理一个、各自提交事件，事件在日志里的先后就是裁决：用户的决定由判定方提交 `ApprovalDecided`；采纳一条结论时编排提交 `ApprovalDelivered`（经审批的）再回执；等待上限到时编排先采纳表里已有的结论，还有超期的票就提交 `Interrupted{ApprovalWaitLimit}`，然后停止受理、请运行时停下。判定方只按已提交事件推进（R1–R3）：中断时已批准而没有交付记录的审批留作一次性授权。
2. **编排的回执是结论去运行时路上唯一的交接点。** 适配器的权限任务只转发处理方的返回值，自己不选「已取消」；挂起的请求只有一种停法：编排停止受理。
3. **请求交接是 `TurnSlot` 那把 `std::sync::Mutex` 护着的一张表（`Handoff`）**，不是信箱。每个在途请求占一格，格子里放的正是处理方此刻在等的那个 oneshot 的发送端（等受理 / 等判定方时的撤销信号 / 等回执）。临界区写成 `Handoff` 上拿 `&mut self` 的方法：「看还受不受理」与「写表」在同一个函数体里，`&mut Handoff` 只能从锁守卫借出，所以「同一段锁」由类型保证。`stop_accepting()` 在锁里关标志、取走整张表，放锁后逐格回绝；之后 `register`、`submit` 在锁里当场拒绝。一张票的结局只有三种：采纳、被停止取走、停止之后才来。
4. **停止的次序**：用户取消是「提交（带作废）→ 停止受理 → `session.cancel()` → 提醒判定方」；等待上限是「采纳已到的结论 → 提交中断（不作废）→ 停止受理 → `session.cancel()` → 提醒」。ACP 客户端的 `cancel()` 先等这条会话上的权限任务都把答复写出去，再发 `session/cancel`；因为编排已停止受理，这些任务都已有结论，正常路径用不到上限。
5. **业务状态与清树分开立约**：中断可以先提交；丢掉一条会话只走 `SessionLine::retire()`，确认整棵进程树清空才放掉。清不掉就把会话留着、记下原因，下一次开会话前先再清一次，仍不行就不开；因等待上限中断的回合清不掉时改记 `Failed`（转换表加 `(Interrupted, Failed) → Failed`），不能续接。
6. **续接入口由回合状态决定**：`TurnPlan.turn` 在 `Interrupted` 时第一步用 `Resume`，另起一条助手消息；不另设入口字段，「入口与状态对不上」写不出来。
7. **会话线与快照同寿命**：下一回合的 `SessionSpec` 与打开会话时的比，模型、系统提示变了就带 `resume` 重开；别的绑定项变了是调用方的错，回合以「会话约束与快照不一致：<字段>」失败。比较时逐字段解构 `SessionSpec`，加字段时编译不过，逼着加的人归类。

## 备选与放弃原因

- 桥接计时并通知后台：裁决分在两个进程。
- ACP 客户端计时并丢弃 future：撤不回已提交的副作用。
- 让判定方靠「回答通道还在不在」判断交付：不是已提交的事实，崩溃后重建不出来。
- 适配器里把 `select!` 改成偏向处理方的那一路：能过测试，但正确性靠轮询次序，下一个改这段的人看不出来。
- 请求交接留在信箱里、停止时关信箱再排空：信箱做不到「看还受不受理」与「登记」同一步（方案第 3–5 版三轮各补一个入口）。
- 在产品代码临界区里放 `#[cfg(test)]` 停靠点：`&mut self` 的写法让那个点不存在；屏障测试自己拿着锁扮「发送方在临界区里」。
- 续接用 `TurnPlan.entry` 字段（方案原写法）：入口完全由状态决定，多一个字段就多一种不合法组合（supervisor 2026-11-11 同意改）。

## 影响

- `PermissionHandler` 多一条约定：回合停下时让挂起的请求返回拒绝。`PermissionGate` 撤票、被拒都答 `TURN_GONE_MESSAGE`（一个常量；supervisor 2026-11-11 定）。
- 每个权限请求多两次拿锁（登记、交结论）；编排原来轮询信箱的那一处换成拿一次锁看表头，频率不变。
- 丢掉会话要等 `terminate()` 确认清空；树已空时立刻返回。
- 屏障测试（15.3 的十六条）对参照判定方与真实引擎各跑一遍；`iwork-fake-agent` 多一种 `parallel_permissions` 步骤与到达记录，供连着测比线上先后。
