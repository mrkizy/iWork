# ADR-T07-c 拒绝记忆与一次性放行是对话内状态，在每对话决策锁下更新与复查、由事件重放重建；引擎经 PermissionDecider 接回合编排

- 状态：已采纳（2026-11-10，T07；编号合入时由 supervisor 统一）
- 依据：`docs/plans/T07.md` 6.1–6.8、第 16 节；需求 AC05；ADR-0006（T05 回合编排）

## 背景

AC05 的拒绝记忆与等待上限中断后的一次性放行都是「某些动作指纹在本对话里的临时状态」；非用户的放行路径（AI 审查、切档、一次性放行）与用户的拒绝之间有竞态。方案写于 T05 合入之前，按「引擎实现 `PermissionHandler` 并写回合状态」设计；T05 已合入的回合编排定了另一个接缝。

## 决定

1. 两者都在引擎内存里，键是对话，与待审批、审查任务同在一把决策锁下。锁是 core 自写的无运行时异步互斥（`engine::lock::AsyncLock`，无 `unsafe`），锁内可以 `await` 一次提交，保证「判定 → 计算转换计划 → 提交事件 → 更新状态 → 答复」对同一对话串行。
2. 拒绝记忆记被拒调用的**全部**子动作指纹；`Approval.call` 持久化恢复所需的最小调用记录（Q8）。一次性放行绑定回合与这份记录（两个摘要都要相等），七步跑完只豁免询问，命中即消费。AI 审查通过、切档放行、一次性放行答复前都用当前状态重判资格（`still_eligible`）；AI 审查结果先在克隆上判 Stale、再复查、只施加一次。
3. 两者是审批流与对话流事件的确定性函数：`DenialMemory::apply` 在线与重放共用；`ApprovalEngine::recover` 启动时按事件重建待审批（全部 detached）、拒绝记忆与活规则，进行中的审查按失去执行者放弃（Q9），放弃计划也在恢复事务确认后才应用。恢复查询 `keys_for(conversation_id, turn_id)` 按原回合定位助手、私聊项目和快照，不能只按对话取一个键。亲手执行卡片独立保存助手归属并重放全部卡片状态事件，恢复后的回答通道为 detached。
4. **与回合编排的接缝**（**已被 ADR-T07-e 取代**，2026-11-10 引擎重做；下面保留原文作为历史。「记全部指纹」「放行前用当前状态重判资格」「只 `apply` 一次」见第 2 条，仍有效）（supervisor 2026-11-10 确认，偏离方案 2.4 / 6.1 / 6.2 / 6.7 的写法，判定逻辑不变）：
   - 引擎为每条会话给出 `decider_for(keys) -> SessionDecider`，实现 T05 的 `turn::PermissionDecider`，交给 `SessionLine::new`；方案里的 `handler_for` 都读作 `decider_for`。
   - 回合状态（`PermissionAsked` / `PermissionDecided`）只由编排写；引擎只提交审批流与审计流事件。
   - 回合级作废（取消、放弃、回合失败）走 `void_pending`，返回的 `ApprovalVoided` / 卡片作废事件由编排与回合状态同一次提交；对话、助手删除走 `ApprovalEngine::void_for_event`，事件由 T10 提交。
   - 第 1 轮返工给 T05 `PermissionDecider` 加默认空实现的 `committed(events)` 回调：`void_pending` / `void_for_event` 只返回计划，不提前改等待表；runner 的提交接缝只在存储确认成功后调用回调。T10 提交删除事务后同样调用 `ApprovalEngine::committed`。回合状态仍只由编排写。
   - 第 2 轮返工（2/F-1）：交出作废计划时在决策锁下**预留**挑中的审批、卡片与回合：确认前 `decide`、切档放行、审查生效都跳过它们，这些回合也不再登记新的等待项。确认（`committed` 或订阅重投 `ApprovalVoided`）时清掉预留；外部事务明确失败时调 `void_aborted`（T05 接缝加默认空实现的 `aborted(events)`，runner 提交失败时调用）撤销预留，计划可以重算重试。
   - 已提交事件只有一个应用入口 `apply_committed`，幂等（2/F-2）：发起方拿到回执后调它，订阅把同一批事件投给 `on_event` 时也调它（审批决定、审查更新、作废、档位变化、卡片状态、回合结束）。**等回执时请求被取消不等于回滚**：事件多半已落盘，本地没来得及应用的由订阅重投补上，拒绝记忆、放行、档位都不会丢。所以 daemon 必须把每条已提交事件（含引擎自己提交的）按序投给 `on_event`。提交明确失败（`Err`）时内存保持原样。`on_permission` 先登记等待项与卡片再提交，提交明确失败才撤回；等回执时取消，登记留着，回答通道成 detached（等同等待上限中断）。
   - 活规则缓存与审计的 `live_rules_seq` 描述同一段完整有序前缀（2/F-3）：订阅按序投递，序号不比缓存新的跳过；本地提交了记住规则时先从日志读 `(缓存游标, 回执序号]` 的全部事件补齐再推进，不会越过还没消费的撤销。读日志失败就不推进，等订阅。
   - 一次性放行命中只是计划消费，审计提交成功后才移除（2/F-4）；资格已不成立的当场作废。
   - 等待上限中断：编排丢掉等审批的请求（回答通道接收端随之丢弃），审批保持 `Pending`；用户允许时 `decide` 返回 `resume_turn`，续接后重新 `decide` 时由一次性放行命中。
   - AI 审查在等用户答复的同一个 future 里与答复并行跑；用户先决定、作废或切档放行时审查作废。`SessionKeys` 由调用方给出审查端口的 `runtime_id` 与 `assistant_version`，引擎用真实 `Turn{SystemAiReview}` 记录排队、状态、用量、额度、实际模型及收尾；这些系统回合仍由引擎这一个写者拥有。
   - 同一个截止时间覆盖建连、prompt、更新流与关闭；到期先写超时、转问用户，取消与关闭最多再等三秒。离开自动档时，切档命令与私聊项目切换共用放弃计划，未被自动放行的审查统一放弃；领域触发与原因改名 `ModeChangedFromAuto`，旧事件的无理由 Abandoned 仍能读取。事件消费 `on_event` 与恢复 `recover` 返回 Result；项目切换引起的放弃提交失败时保留旧内存并把错误交回调用方重试。
   - 通过和不通过都保存理由；通过理由复用 proto 的 `reason`，旧 Passed 事件缺少理由时读为空串。审查上下文按 `(conversation, context_project_id)` 保存任务目标与最多 2000 字符的助手输出尾部，在线与恢复共用消息事件更新函数。正文落成制品（`MessageBody::Artifact`）的消息不进审查上下文，跳过后保留已有摘要；T10 接制品消息时要给引擎供给有界摘要，本轮不增加 `ArtifactStore` 泛型（supervisor 2026-11-10 确认）。

## 备选及放弃原因

只记代表动作（拆开重发可绕过）；只按指纹集合放行（调序、改连接符、重复、改重定向归属都能命中）；只查 AutoDeny（放不过用户新消息后的强制询问）；先施加通过再复查（回不到 Pending）；无锁（迟到的审查通过放行刚被拒的动作）；生成临时规则条目（要精确指纹集合匹配器，且会出现在规则列表里）；加投影表（多一份真值）；引擎自己写回合状态（与 T05「单写者」冲突）。

## 影响

引擎启动要重放审批与对话事件；没有调用记录的旧审批批准后不发一次性放行、也不续接（被 ADR-T07-e 与方案 6.2 E1 的改定取代，原写「只续接」）。审查在等待期间被编排丢弃（hook 等待上限早于审查超时）时审查随之中止、审批停在「审查中」，下次启动恢复时按失去执行者放弃——hook 等待上限应长于审查超时（默认 60 秒），交 T06 核对。
