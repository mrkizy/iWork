# ADR-T04-a 后台服务的生命周期：被拉起是唯一的重启方式，启动恢复是唯一的中断方式

- 状态：提议（2026-11-12，T04；编号由 supervisor 合入时统一）
- 依据：技术设计第 4 节、10.3、10.4；需求第 12 章；T04 方案（`docs/plans/T04.md`）第 2 节、第 12 节；实测见 `docs/design/t0-findings.md` 第 7 节（N1–N5）

## 背景

设计 4 要求后台由客户端拉起、单实例、可选自启、崩溃后不丢状态、升级时自行重启。后台会因为五种原因消失（崩溃、存储故障、升级、系统关机、用户退出），每种都要回答「谁把它带回来」「在跑的回合怎么办」。存储的拒绝启动每次都会做全量备份；对端校验让新旧版本互不相认；审批不超时。

## 决定

1. **后台从不守护自己，只会被拉起。** 拉起方有两个：客户端连不上就拉（`iwork_client_core::launcher`）；登录自启开着时加上服务管理器，它只认「退出状态非零或被信号结束就再拉」。「再拉有没有用」只有一个判据：纯函数 `rendezvous::relaunchable(状态文件里的 Phase)`，答案三种（有用 / 用户回来之前别拉 / 这一版起不来）；托管实例报零还是非零（`exit::process_status`）、等锁的托管实例接不接班（`instance::standby_action`）、客户端自动拉不拉（`launcher::should_launch`），都调它并照同一张角色表做。停机一开始就把原因写进状态文件，之后卡住或被 15s 硬上限强退都不改变答案。服务管理器起的实例撞锁时等锁，所以自启开着时它名下总有一个进程。
2. **回合的中断只有一条路**：启动时的恢复把持有进程的回合标「已中断」；升级、关机、故障在退出前只关会话，不写回合状态；只有用户明确退出才走取消流程。
3. **恢复是纯函数算出的一次提交**（`iwork_core::recovery::plan`），只写「停了」的事实，不重放任何动作，不动审批。之前有一步只读的兼容检查（启动表 5a）：库里有本版本不认识的事件种类就在任何写入之前拒绝启动（逻辑码 12）。
4. **单实例靠每样资源旁边的操作系统锁**：数据目录 `run/` 与 socket 目录各一把，相同就一把；锁文件从不删除。
5. **持久事件的发布顺序取自存储写线程的提交回调**（`set_commit_observer`）；观察者在写线程上只做内存操作与非阻塞唤醒。
6. **存储给出结构化的失效信号**（`failed()`），监督器据此整体退出（逻辑码 20，停机跳过关存储）；辅助任务各自退避重启，60s 内失败 5 次升级为整体退出。
7. **升级的判据是两问**。第一问：磁盘上的后台文件是不是我正在运行的这一份——参照物是启动表第 1 步从运行映像取的身份，不设基线；用和包的形态无关的身份比（Linux 全文 SHA-256，macOS cdhash）。第二问（只在第一问答「不是」期间问，按 2/4/8/16s、之后每 30s 的有界间隔完整重查）：磁盘上有没有装齐的包——带清单的看清单与文件逐个对得上，整包签名的看整包验签通过，两行都试。一次判定 `evaluate()` 把两问放在一起答、动手之前再答一次第一问；每个进程启动后 30s 内不做升级重启。重启 = 走完停机后原地 `exec`。
8. **客户端与后台在 socket 目录用两个文件互通**（`daemon.lock`：pid 与版本；`daemon.status.json`：启动到哪一步、为什么拒绝）；程序读它们只允许得出「少做一次」的结论。
9. **对系统有副作用的设置（登录自启）**：受理只提交事件；全进程只有对齐任务调 `AutostartPort::set`，每次读最新的已提交设置；托管实例运行中不注销自己，留到下次启动、`bind` 之前（启动表 9a）。macOS 只用 LaunchAgent plist（`Program` 绝对路径）+ `launchctl`，不用 `SMAppService`（N1）；Linux 用 systemd 用户单元，不加 `RestartForceExitStatus`（N4）。
10. **可重启的任务每次启动都从真值重建自己的状态**：投递任务每次启动先对账不确定的投递（`outbox_requeue_dispatched(redeliver, fail)`：不认识的去向原样留在 `Dispatched`，交给认识它的版本）；没有去向认领的 `queued` 条目原样留着、只报不动（产品负责人 2026-11-11 定）。

## 备选

- 服务管理器对所有非零退出码都重启而后台不做映射：拒绝启动时反复备份。否决。
- 服务管理器只在被信号结束时重启：存储失效这类退出没人拉。否决。
- 服务管理器起的实例撞锁就退出：自启开着却没有进程归它管。否决。
- 受理自启命令时先改系统再提交：重发的旧命令会撤销新设置、注销会结束自己。否决。
- 退出状态映射、等锁接班、客户端防重拉各写各的判断：三处分叉。否决。
- 用「两次哈希相同」判装齐；拿启动时磁盘上的清单当基线；所有包都带登记全文哈希的清单：分别证明不了装齐、在安装中途起来时基线是错的、签了名的 macOS 包里清单与签名互为前提。否决。
- 停机没清空进程组时改用另一个退出码：拦不住任何拉起方，不是门。否决。
- 后台自带看门狗进程；升级时先把回合标中断再退出；升级只退出不 `exec`；在存储外包一层发布；按 pid 核对旧进程是否还在；监听操作系统的唤醒通知：多一个要管的进程 / 多一条并行的中断路 / 没有客户端时后台不回来 / 并发提交时乱序 / 要记进程身份 / 两套平台代码而没有消费者。否决。
- 没人认领的 outbox 条目标 `Failed`：装回旧版本会把新版本写下的待投条目永久作废。否决（第 1 轮审查 1/F-4）。

## 影响

- 打包要把后台与客户端放在同一目录；无证书的包不做整包签名、带安装清单，有证书的包整包签名、不放清单；带上「非零就重启」且参数含 `--service` 的 plist / 单元文件。
- 任何退出原因之后用户看到的都是同一套「已中断 / 继续」界面。
- T10 的回合宿主必须能「封口、只关会话、不写状态、报告清没清空」（`RunningWork`）；审批引擎的恢复接在启动表第 9 步（`StartupParticipant`）。
- 存储写线程多一个回调点：单事件提交装真观察者前后约 +1.5%（`cargo bench -p iwork-daemon --features dev --bench lifecycle`，本机负载高时只看相对值）。
- 没开自启且客户端没开时，运行期故障后后台停到用户下次打开（已知限制 L5）；新后台起来时旧成员进程树可能还没清完、核对不了（L6）；带迁移或新事件种类的版本运行过之后不能退回旧版（Q4、PD6）。
- Windows 恢复支持时要补脱离方式、自行重启、会合点位置与睡眠修正四处。
