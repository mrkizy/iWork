# M1 任务卡

M1 的目标、范围与验收见 `docs/design/m1-tech-design.md` 第 1 节。T0（厂商实测）已完成，结论在 `docs/design/t0-findings.md`。本目录是 T01–T11 的任务卡，每张卡就是一次派活的完整说明。

## 依赖与并行

```
T01 骨架
 ├─ T02 存储 ─┐
 ├─ T03 通信 ─┴─ T04 生命周期 ─ T09 客户端 ─┐
 ├─ T05 接入与假运行时 ─ T06 Claude 适配器 ──┤
 ├─ T07 审批引擎 ────────────────────────────┼─ T10a 接线 ─┬─ T10b～T10g ─┬─ T11 基准与故障测试进 CI
 └─ T08 版本控制 ────────────────────────────┘             └─ T10e ─ T10h ─┘
```

- T01 完成后，T02、T03、T05、T07、T08 五条线可并行（各用独立 worktree）。
- T04 需要 T02、T03；T06 需要 T05（审批通道可先接 T07 的桩，T07 完成后换真实引擎）；T09 需要 T03、T04。
- T10 汇合 T06–T09，拆成 T10a～T10g 七张小卡（2026-11-10）：T10a 接线先做，其余六张在它之后；依赖见 T10.md；T11 的基准框架可在 T05 完成后先搭，T10 完成后补全。
- T10h（补丁卡片）2026-11-12 从 T10e 再拆出（产品负责人定，需求附录 B）：排在 T10e 之后，仍在 M1 内，T11 等它。T10h 合入之前，Edit 命中系统底线只拒绝、提示改用命令卡片。
- 关键路径：T01 → T05 → T06 → T10a → T10b～T10g（T10e 之后还有 T10h）→ T11。

## 每张卡的约定

- “验收标准”每一条都必须有自动化测试或可复现的检查命令；实现报告逐条给出命令与结果。
- “不做”里的内容不要顺手做；发现必须做才能完成本卡的，先报 supervisor。
- 卡片末尾“完成记录”由 supervisor 填写。

## 评审意见的处理结果

开工前的文档评审（2026-11-08）提出的 11 项问题已全部决定：凭据目录读写都禁、关键路径清单、`.git/` 写入的范围、私聊目录位置、配置隔离与本机导入（实测采用参数屏蔽）、联网不受控、拒绝的作用范围、模式与规则叠加、审批作废、审批三档与沙箱分层（需求 v1.34–v1.46）；hook 通道鉴权（M1 技术设计 6.3）；受保护分支在 M1 作为已知缺口（M1 技术设计第 1 节）；M1 做最小助手管理（9.1a）；计划卡片移到 M2，M1 提供“待你处理”列表。

## 固定版本

M1 的兼容测试基准跟着实测时本机能装到的 Claude Code 版本走（T0 实测时是 2.1.319，T06 方案阶段本机已自动升到 2.1.322；具体版本以 `docs/design/t0-findings.md` 的记录为准），T0 的关键结论由 `tools/t0/iwork-t0g.py` 复核（产品负责人 2026-11-10 定，T06 方案 P1）。CLI 升级后重跑 `tools/t0/` 的相关脚本与 T06 的兼容测试；未验证版本第一次使用前在本机自动跑硬前提验证，通过才放行（T06 方案 P2 选 c）。
