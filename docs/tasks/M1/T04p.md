> 从 T04 组 3 拆出（supervisor 2026-11-12，按 T04 组 3 审查 1/F-7 的建议「拆到打包任务，先明确方案与验收归属」）。T04 组 3 的代码（完成形态判定、身份互认、自启对齐）已合入；它要的「真实发布包上的证据」要有真实的包才验得了，现在 `pnpm -C client tauri build` 的产物里没有后台程序和安装清单。

- **风险**：中（先出方案）
- **依赖**：T03（`scripts/write-install-manifest.sh`、对端校验）、T04 组 3
- **依据**：T04 方案 2.9（完成依据与两种包形态）、2.12（自启 plist 的 `Program` 是包内后台程序的绝对路径）；T03 方案 2.4a；AGENTS.md「本机通信」安全不变量

## 目标

`tauri build` 打出的 macOS 包（无证书、自签证书两种）里带着后台程序 `iwork-daemon` 和安装清单，装上之后客户端能拉起后台、双方身份互认、升级检查不卡在 Installing。

## 范围

1. 选定后台程序进包的办法，二选一，方案里写理由：
   - a. Tauri 配置的 `bundle.externalBin`（sidecar）带进包；
   - b. `tauri build` 之后由打包脚本把后台程序放进包、写清单。
   要说清：清单里的哈希是不是最终产物（签名之后）的；证书包整包签名会不会被后放进去的文件破坏；包内路径和 T04 2.12 的 plist `Program`、T03 对端校验用的路径是否一致。
2. 打包命令仍只经 `pnpm -C client tauri build` 一个入口（AGENTS.md 客户端配置三层的约定），不新增裸调 tauri 的路径。
3. CI 的发布构建检查（`scripts/check-no-dev-trust.sh --artifacts`）覆盖新产物。

## 验收（照 T04 组 3 审查 1/F-7）

1. 真实产物上，T04 2.9 的完成形态**恰好一种**成立：无证书包是 `self_listed`（清单列着自己、哈希对得上），证书包整包验签通过。
2. 装上后客户端经 Launcher 拉起后台，握手互认成功（不是 `--dev-trust`）。
3. 升级检查不停在 Installing：装新版后旧后台交接、新后台起来。
4. 以上三条有可复现的步骤和结果记录（本机 macOS；Linux 包 M1 只要求构建通过）。
