# T04p 发布包：后台程序与安装清单进包

> 从 T04 组 3 拆出（supervisor 2026-11-12，按 T04 组 3 审查 1/F-7 的建议「拆到打包任务，先明确方案与验收归属」）。T04 组 3 的代码（完成形态判定、身份互认、自启对齐）已合入；它要的「真实发布包上的证据」要有真实的包才验得了，现在 `pnpm -C client tauri build` 的产物里没有后台程序和安装清单。

- **风险**：中（先出方案）
- **依赖**：T03（`scripts/write-install-manifest.sh`、对端校验）、T04 组 3
- **依据**：T04 方案 2.9（完成依据与两种包形态）、2.12（自启 plist 的 `Program` 是包内后台程序的绝对路径）；T03 方案 2.4a；AGENTS.md「本机通信」安全不变量

## 目标

`tauri build` 打出的 macOS 包（无证书、自签证书两种）里带着后台程序 `iwork-daemon` 和安装清单，装上之后客户端能拉起后台、双方身份互认、升级检查不卡在 Installing。

## 范围

1. 选定后台程序进包的办法，二选一，方案里写理由：
   - a. Tauri 配置的 `bundle.externalBin`（sidecar）带进包；
   - b. `tauri build` 之后由打包脚本把后台程序放进包、写清单。
   要说清：清单里的哈希是不是最终产物（签名之后）的；证书包整包签名会不会被后放进去的文件破坏；包内路径和 T04 2.12 的 plist `Program`、T03 对端校验用的路径是否一致。
2. 打包命令仍只经 `pnpm -C client tauri build` 一个入口（AGENTS.md 客户端配置三层的约定），不新增裸调 tauri 的路径。
3. CI 的发布构建检查（`scripts/check-no-dev-trust.sh --artifacts`）覆盖新产物。

## 验收（照 T04 组 3 审查 1/F-7）

1. 真实产物上，T04 2.9 的完成形态**恰好一种**成立：无证书包是 `self_listed`（清单列着自己、哈希对得上），证书包整包验签通过。
2. 装上后客户端经 Launcher 拉起后台，握手互认成功（不是 `--dev-trust`）。
3. 升级检查不停在 Installing：装新版后旧后台交接、新后台起来。
4. 以上三条有可复现的步骤和结果记录（本机 macOS；Linux 包 M1 只要求构建通过）。

## 完成记录

### 验收 1：真包上恰好一种形态成立、能互认（方案 9.5；2026-11-13，本机）

环境：macOS 27.2 arm64，main 308430c（T04p 已合入，e06677b）；打包时 loadavg 66–120（同机多张卡在跑重测试）。经唯一入口打包，套重测试锁、`CARGO_INCREMENTAL=0`，从空的 `target/release` 开始：

```sh
lockf /tmp/iwork-heavy-test.lock pnpm -C client tauri build                       # 形态 A
IWORK_SIGN_IDENTITY="iWork Drill Signer" IWORK_SIGN_KEYCHAIN=<临时钥匙串> \
  lockf /tmp/iwork-heavy-test.lock pnpm -C client tauri build                     # 形态 B（自签证书）
```

证书由 `scripts/test-signing-identity.sh` 建在临时目录里的钥匙串中（不改用户的钥匙串搜索列表），叶证书 SHA-256 `d7cd929aba9d1d41633858b870b7afaa98e1d9b2198e78cc18003a9330cb3d29`；用完已删钥匙串。

| 查的 | 结果 |
| --- | --- |
| 形态 A `check-install <A>/Contents/MacOS` | 退出 0：形态 `manifest=Complete signed-bundle=NotThisForm`；互认双向 `Accepted { signature_checked: true }`（daemon `cdhash:35aaf886…`，client `cdhash:a2fe7b1a…`） |
| 形态 B `check-install <B>/Contents/MacOS --expect-leaf <叶证书>` | 退出 0：形态 `manifest=NotThisForm signed-bundle=Complete`；互认双向接受（两端都是 `certificate:d7cd929a…`）；证书一件过 |
| `codesign --verify --deep --strict --verbose=2 <B>` | `valid on disk`、`satisfies its Designated Requirement` |
| `ls <B>/Contents/MacOS` | 只有 `iwork-client`、`iwork-daemon`，没有清单 |
| `<A>/Contents/MacOS/iwork-manifest.json` | `app_version` 0.1.0；两个程序各有 `sha256:` 与 `cdhash:`，cdhash 与核对打出的一致 |
| `codesign --verify --deep --strict <A>` | `code has no resources but signature indicates they must be present`（形态 A 的正常样子，方案 L5、N5 A4） |
| `scripts/check-no-dev-trust.sh --artifacts`（两种形态的四个程序） | 三步全部通过；发布后台对 `--dev-trust` 报「未知参数」并拒绝启动 |

### P1、P2（方案 8.1；同一次打包）

- **P1**：形态 A、B 都经新的打包命令退出 0，核对三件事都过（上表）。用时（含排锁，负载很高）：形态 A 冷编 714 秒，形态 B 1142 秒。
- **P2**：仓库默认的 `target/` 里留着上面打出的 0.1.0 成品；把根 `Cargo.toml` 的 `[workspace.package] version` 临时改成 0.1.1（`cargo update --workspace --offline` 同步锁文件；`git diff` 只有这两个文件里的 version 行），设 `CARGO_TARGET_DIR=<scratchpad 里的新目录>` 再打两种形态，打完 `git checkout` 还原、工作区干净。结果 **PASS**：
  - 成品出在新目录的 `release/dist/{unsigned,signed}/iWork.app`；
  - 老 `target/` 里比打 B 版之前（时间戳文件）新的文件：0 个；老 `dist/` 全部文件的摘要前后相同，老 `iwork-daemon`、`iwork-client`、`check-install` 的 SHA-256 前后相同；
  - 新清单 `app_version` 0.1.1（老的 0.1.0），两个 cdhash 是新的（daemon `244d155e…`、client `b06d321d…`，老的 `35aaf886…`、`a2fe7b1a…`）；新的两个包核对都过（形态 B 带 `--expect-leaf`）。
  - 用时：形态 A 1259 秒，形态 B 5036 秒（大部分是排重测试锁）。
