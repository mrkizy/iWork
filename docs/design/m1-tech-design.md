| Linux 上没有系统级提醒：系统通知只记日志，也没有 Dock 角标（产品负责人 2026-11-11 定，T09 方案 N3） | 有新的待处理项时用户要自己回窗口看「待你处理」的计数；审批不超时，不会丢 | 接入 Linux 通知实现时换一个 `Notifier` 实现，规则与客户端都不用动 |

**验收方式**：每项能力有自动化测试；性能项以第 10 节基准为准；作者连续一周用 M1 完成日常开发任务且无数据丢失，视为 M1 完成。

## 2 进程与分层

iWork 在本机是三类进程：客户端、后台服务（daemon）、每个运行中成员一个 ACP 桥接进程（其下是厂商 CLI）。需求文档 7.2 的六层中，只有客户端层在客户端进程，其余五层都在后台服务内；编排核心是后台服务里的一层，不是一个进程。

| 进程 | 内容 | 生命周期 | 内存预算 |
| --- | --- | --- | --- |
| 客户端（Tauri） | Rust 侧：连接、解码、界面状态；网页侧：只渲染 | 用户开关 | 空闲 ≤ 250MB |
| 后台服务（daemon） | 应用服务、编排核心、端口、适配层、基础设施 | 常驻，单实例 | 运行中 ≤ 200MB |
| ACP 桥接（每成员一个） | Claude Code 自写适配器（M1）；各厂商适配器均按此形态 | 随成员会话 | ≤ 60MB |
| 厂商 CLI | Claude Code 等，不受 iWork 控制 | 由桥接拉起 | 不计入预算 |

桥接独立成进程的理由：崩溃隔离（一个 CLI 异常不拖垮后台服务）、可独立升级、后台服务对所有运行时只讲 ACP。

**Rust 工作区（crate）划分**

| crate | 层 | 职责 | 可依赖 |
| --- | --- | --- | --- |
| `iwork-proto` | 协议 | Protobuf 定义与生成的 Rust 类型；同时生成 TypeScript 类型 | 无 |
| `iwork-domain` | 领域 | 实体、值对象、状态机、领域事件；不做 I/O | 无 |
| `iwork-ports` | 端口 | AgentPort、VcsProvider、StoragePort、ExecutionBackend、SecretStore、Notifier 等 trait | domain |
| `iwork-core` | 编排核心 | 调度、等待与唤醒、消息路由、审批引擎、防失控底线 | domain、ports |
| `iwork-app` | 应用服务 | 命令与查询处理、权限校验、配置快照 | core、ports、proto |
| `iwork-store` | 基础设施 | SQLite 事件日志与投影、制品存储 | ports |
| `iwork-agent-acp` | 适配层 | ACP 客户端端，实现 AgentPort | ports |
| `iwork-vcs-git` | 基础设施 | VcsProvider 的 git 实现 | ports |
| `iwork-host` | 基础设施 | 本机能力：ExecutionBackend 的用户执行（亲手执行卡片，7.2a）、SecretStore 的系统钥匙串实现（M1 存 MCP 密钥）、Notifier 的系统通知实现与「把桌面客户端叫到前台」（7.3） | ports |
| `iwork-ipc` | 基础设施 | 本地传输、对端身份校验、分帧、订阅 | proto |
| `iwork-daemon` | 组合入口 | 二进制；在这里把实现注入端口 | 全部 |
| `iwork-bridge-claude` | 适配层 | M1 接法：独立二进制，ACP agent 端 ↔ Claude Code CLI（-p + hook）；把随会话下发的抽象约束与会话工具集翻译为 Claude Code 启动参数与 `sandbox` 设置（7.0、7.2b） | proto（ACP 消息，以及抽象约束、会话工具集等随会话下发的类型；不依赖 domain 与 core） |
| `iwork-client-core` | 客户端 | Tauri Rust 侧：连接、状态、帧合并 | ipc、proto |

依赖只向下：`domain` 与 `ports` 不依赖任何框架与 I/O（包括 tokio；`ports` 的异步接口用语言原生的 async trait）；`core` 不知道 SQLite、git、ACP 的存在；只有 `iwork-daemon` 同时知道所有实现。CI 用 `cargo-deny` 与自定义检查强制这条规则。异步运行时统一为 tokio。

## 3 客户端与后台服务通信

本机专线 + 操作系统级身份校验 + Protobuf 二进制帧 + 按序号可续传的事件流；网页层只接收每帧合并后的视图增量。

### 3.1 传输

| 平台 | 通道 | 位置与权限 |
| --- | --- | --- |
| macOS | Unix domain socket | `~/Library/Application Support/iWork/run/d.sock`，目录 0700（路径须短于 104 字节，启动时校验） |
| Linux | Unix domain socket | `$XDG_RUNTIME_DIR/iwork/d.sock`，目录 0700；未设置 `XDG_RUNTIME_DIR` 时退到数据目录下的 `run/d.sock`（目录 0700，启动时校验属主为当前用户、权限不宽于 0700，路径须短于 108 字节，不满足则拒绝启动并提示） |
| Windows | 命名管道 | `\\.\pipe\iwork-<用户 SID>`，DACL 只允许当前用户，`FILE_FLAG_FIRST_PIPE_INSTANCE` 防抢占 |

### 3.2 对端身份校验

建连后、任何消息处理之前，后台服务向操作系统询问对端是谁：

1. 同一用户：Linux `SO_PEERCRED`，macOS `getpeereid` + `LOCAL_PEERPID`，Windows `GetNamedPipeClientProcessId` + 进程令牌。
2. 同一签名：按 pid 取可执行文件，校验代码签名与后台服务自身同一签名者（macOS Team ID，Windows Authenticode 证书指纹；Linux 无系统签名，改为校验可执行文件路径属于安装目录且哈希与安装清单一致）。
3. 不通过即断开并记审计。开发版本用显式的 `--dev-trust` 开关放宽第 2 步，发布版本编译时去掉该开关。

### 3.3 帧与握手

帧 = `u32 长度（小端）| u8 类型 | Protobuf 载荷`，单帧上限 4MB。类型：`Hello`、`Request`、`Response`、`Event`、`Chunk`（大数据分片，每片 ≤ 1MB）。调试模式下同一结构以 JSON 输出到日志，线上始终是二进制。

握手：客户端发 `Hello{protocol_major, protocol_minor, client_kind, client_version, resume_token?}`，后台服务回 `Welcome{session_id, server_version, capabilities, head_seq}`。主版本不同即拒绝并提示升级，两个方向都拦（旧客户端 × 新后台、新客户端 × 旧后台），拒绝时带上双方的主版本号，拒绝前不处理任何业务帧。主版本就是协议身份：破坏性变更（改号、改类型、删字段）一律升主版本（包名 `iwork.vN`），不在同一主版本内重置；数据库门见 5.5（T01 方案 3.7，产品负责人 2026-11-09 决定）。次版本只做加法（Protobuf 字段只增不改号）。

### 3.4 三类消息

| 类 | 方向 | 语义 | 例子 |
| --- | --- | --- | --- |
| 命令 | 客户端 → 后台 | 改变状态；带客户端生成的 `command_id`，重发幂等 | SendMessage、DecideApproval、CancelTask、AddProject、UploadAttachment |
| 查询 | 客户端 → 后台 | 只读，返回快照与快照对应的 `seq` | GetConversation、ListProjects、GetQuota |
| 事件 | 后台 → 客户端 | 按订阅范围推送 | MessageAppended、ApprovalRequested、TaskStateChanged |

命令不返回最新状态，只返回受理结果和产生的事件 `seq`；状态变化一律经事件到达，客户端只有一条更新路径。少数命令只改连接级或进程级状态、不产生事件：`ShutdownDaemon`、`ReportPresence`（3.6 第 5 条），它们的受理结果里两个 `seq` 都是 0。

### 3.5 事件流：序号、续传、背压

- **两种事件**：持久事件先写入 SQLite 再推送，带全局单调 `seq`；流式增量（模型输出的文字片段）不逐条落盘，带 `(message_id, offset)`，客户端按 offset 去重。消息结束时写入完整内容；运行中每 500ms 写一次检查点，崩溃后最多丢失 500ms 的显示文字，不丢业务事件。
- **订阅**：`Subscribe{scope, from_seq}`，scope 为侧栏摘要、某个对话、待处理、额度等。后台服务先从存储补发 `from_seq` 之后的事件，再无缝切到实时推送；`from_seq` 太旧时返回快照 + 快照 `seq`。
- **背压**：每个连接一个有界发送队列（默认 8MB）。满时先合并同一条消息的相邻文字增量；仍满则后台服务关闭这条连接（审计记原因），客户端按断线处理，重连后从自己已应用到的最后 `seq` 续传。客户端接收也有界，处理不过来时停止读取，由后台服务按同样方式关闭连接。持久事件在任何情况下都不丢弃，只会延后。（产品负责人 2026-11-10 同意，见 T03 方案 2.9）

### 3.6 客户端内部：Rust 侧做重活，网页只渲染

1. `iwork-client-core` 持有连接，把事件应用到一个按 id 索引的本地状态库。
2. 网页层声明当前可见的视图（侧栏、某对话的可见窗口、待处理…）。Rust 侧只为这些视图计算增量。
3. 每 16ms 最多刷新一次：把本帧内的所有增量合并成一个 `ViewPatch`（也由 Protobuf 定义），由网页层用一次 invoke 长等待来取（同一时刻最多一个在等），以原始字节返回，不经 JSON；不用 Tauri `Channel` 推，因为它对大于 1 KiB 的载荷有不受限、刷新不清的暂存（产品负责人 2026-11-10 同意，见 T09 方案 2.4）。
4. 网页层只解 `ViewPatch` 并更新组件；不接触协议全集、不做业务判断。用户操作经 Tauri `invoke` 交给 Rust 侧，由 Rust 侧转成命令。
5. 客户端自己不发系统通知。它向后台报「窗口是否在前台、正在看哪个对话或『待你处理』页」（`ReportPresence`）：值变了就报，离开立刻报、到来延后 500ms 报，连接断开即视为没人在看；这只供后台决定要不要发系统通知，不产生事件。被系统通知叫到前台时，用 `GetOpenTarget` 问后台要打开哪一项（产品负责人 2026-11-11 定，T09 方案 2.8）。
6. macOS 上客户端设 Dock 角标并在出现新的待处理项时让图标跳动：角标数字与侧栏「待你处理」计数由 Rust 侧同一个函数算出，网页不参与，窗口关着、进程还在时照常有效。

### 3.7 大数据与附件

两端同机同用户：本机文件直接传路径，由后台服务自己读取、校验、复制进制品存储；粘贴的图片等内存数据用 `Chunk` 帧分片上传。大文本（长日志、大 Diff）不随事件推送，事件只带制品引用，客户端按可见范围分段读取。

### 3.8 远程预留

传输是一个 trait（连接、对端身份、收发帧）。本机实现如上；远程实现（D05）将用 QUIC + TLS 1.3 + 设备密钥认证，协议、事件序号与续传语义不变。M1 不实现远程。

## 4 后台服务生命周期

后台服务由客户端按需拉起、可选登录自启，全机每用户只有一个实例；崩溃后重启不丢业务状态，运行中的成员变为“已中断”并可续上。

**拉起**

1. 客户端启动即尝试连接。连不上则以脱离方式启动后台服务（macOS/Linux 新会话 `setsid`；Windows `DETACHED_PROCESS`），确保客户端退出不带走它。
2. 后台服务先拿独占锁 `run/daemon.lock`（`flock` / `LockFileEx`），拿到才清理旧 socket 并绑定；拿不到说明已有实例，直接退出。
3. 客户端以指数退避重连，总时长预算 1s；超时则显示诊断信息（日志位置、锁持有者 pid）。

**登录自启（设置里开启）**：macOS 用 `SMAppService` 注册 LaunchAgent；Linux 写 systemd 用户单元；Windows 用登录触发的计划任务。三者都配置为异常退出后自动重启。

**成员进程与后台服务的关系**：桥接进程是后台服务的子进程，各自独立进程组。后台服务意外退出时，桥接从 stdin 读到结束，先记录 CLI 会话 id，再结束 CLI 进程树。不让成员在无人监管时继续写文件，审批底线始终有效。

**崩溃恢复**：启动时比对存储里“运行中”的回合与实际进程：进程不在的标为 `interrupted` 并在对话里出一张“继续”卡片，用 CLI 的会话恢复能力续上；待审批项保留；未发送的待发消息按事务记录重投。

**退出**：Linux 上关窗即退出客户端；macOS 上关窗只关窗口，客户端进程留在 Dock（角标与跳动靠它，3.6 第 6 条），点 Dock 图标重新开窗，退出客户端要用应用菜单或 Cmd+Q（产品负责人 2026-11-11 确认；菜单怎么摆见 T09 方案 Q16）。两种情况后台服务都继续运行。菜单“完全退出 iWork”才停后台服务；有成员在运行时先确认，确认后按取消流程结束各回合再退出。

**升级**：新版本安装后，后台服务发现安装的程序已换成新版本，就自行重启切换到新版本，不热替换。有回合在跑时不再等它们结束：这些回合按中断处理（与崩溃恢复相同，出「继续」卡片，可续接），待审批保留、不作废；客户端不负责结束旧后台进程（产品负责人 2026-11-10 决定，T03 方案 Q5）。客户端与后台服务协议主版本不一致时，客户端只显示“正在切换版本”。数据库迁移见第 5 节。

**睡眠唤醒**：监听系统唤醒事件，重新计算所有计时器（如提问 10 分钟上报），用单调时钟加墙钟修正，不把睡眠时间误算成超时。

## 5 数据与存储

一个 SQLite 数据库同时保存事件日志与查询用的投影表，事件与投影在同一事务里写入；大文件进按内容哈希寻址的制品存储，数据库只存引用。

### 5.1 位置

| 平台 | 数据目录 |
| --- | --- |
| macOS | `~/Library/Application Support/iWork/` |
| Linux | `$XDG_DATA_HOME/iwork/` |
| Windows | `%LOCALAPPDATA%\iWork\` |

目录下：`iwork.db`（及 WAL）、`artifacts/`（制品存储：长日志、大 Diff 等，Agent 不可读）、`attachments/`（附件区，只读区）、`imports/`（只读区）、`private/`（凭据附件存档）、`run/`、`logs/`。Agent 只能读两个只读区，其余读写都禁（需求 v1.64）。助手私聊的工作目录不在数据目录内，见 9.1。项目内的 `.iwork/` 放随仓库共享的内容（记忆等），唯一例外是 `project.toml`（项目 ID）：它只属于本机这份工作副本，不进 git，见 8.2。

### 5.2 写入模型

- **单写者**：一个专用写线程持有唯一的写连接，所有命令经队列串行写入；读走只读连接池，WAL 模式下读写不互相阻塞。
- **组提交**：`synchronous=FULL` 保证断电不丢已确认的事件；写线程把 2ms 内到达的多个命令合并为一次提交，把 fsync 成本摊薄。
- **事务内容**：一次命令 = 追加事件 + 更新投影 + 写待发消息（outbox）+ 记录 `command_id`。提交后才推送事件、执行对外动作；重发同一 `command_id` 直接返回上次结果。
- **事件不可改**：只追加；载荷是带版本的 Protobuf。投影可从事件重建，重建只更新视图、不重做对外动作。
- **回合收尾的事件约定**：回合状态只由 `TurnStateChanged` 改写；回合进入终态时，进入终态的 `TurnStateChanged` 与 `TurnFinished` 在同一次提交里、前者在先，`TurnFinished` 只带用量、结局摘要等附加信息，投影不靠它改回合状态（T05 编排已这样发，T02 投影按此实现）。

### 5.3 M1 表

| 表 | 用途 | 主要字段 |
| --- | --- | --- |
| `events` | 事件日志 | `seq` 主键自增、`stream_kind`、`stream_id`、`type`、`payload`、`command_id`、`actor`、`at` |
| `commands` | 命令幂等 | `command_id`、`result`、`at` |
| `outbox` | 待发消息 | `id`、`target`、`payload`、`state`、`attempts` |
| `projects` | 项目 | `id`（与 `.iwork/project.toml` 一致）、`root_path`、`vcs_kind`、`name`、`pinned`、`last_active_at`、`path_status` |
| `assistants` | 助手（含内置 iWork） | `id`、`name`、`role_label`、`avatar`、`builtin`、`current_version`（版本内含运行时、模型、思考强度） |
| `assistant_versions` | 助手配置版本 | `assistant_id`、`version`、`config`、`created_at` |
| `project_members` | 助手加入的项目（**M2 再建**：M1 没有团队，也没有写入它的事件，见 9.1） | `project_id`、`assistant_id`、`in_default_team`、`joined_at` |
| `conversations` | 对话 | `id`、`kind`（项目对话 / 助手私聊）、`project_id?`、`assistant_id?`、`last_read_seq`、`unread`、`model_override?`、`effort_override?`、`updated_at` |
| `messages` | 消息 | `id`、`conversation_id`、`author`、`context_project_id?`、`status`、`body`、`checkpoint_offset`、`created_at` |
| `turns` | 一次成员运行 | `id`、`conversation_id`、`assistant_version`、`runtime_id`、`model`、`effort`、`cli_session_id`、`state`、`started_at`、`ended_at` |
| `approvals` | 审批请求与决定 | `id`、`turn_id`、`kind`、`request`、`matched_rule`、`state`、`decided_at` |
| `approval_rules` | 审批规则 | `id`、`scope`（全局 / 项目 / 助手）、`matcher`、`effect`、`priority`、`source` |
| `attachments` | 附件 | `id`、`sha256`、`size`、`mime`、`name`、`origin`（仓库路径 / 复制 / 粘贴） |
| `runtimes` | 运行时登记 | `id`、`kind`、`cli_path`、`cli_version`、`adapter_version`、`status` |
| `quota_snapshots` | 额度 | `runtime_id`、`window`、`used_pct`、`resets_at`、`observed_at` |

索引按读取路径建：`messages(conversation_id, created_at)` 支持十万条历史的键集分页；`events(stream_id, seq)` 支持按范围补发。多成员、审查、记忆相关表在后续里程碑以迁移加入。

### 5.4 制品存储

`artifacts/sha256/<前 2 位>/<其余>`，写入先到临时文件、校验哈希再原子改名；相同内容只存一份。引用计数在数据库里，定期回收无引用对象。仓库外附件用同样的结构单独存在 `attachments/sha256/…`，与其他制品分开，因为附件区对 Agent 只读可见，而长日志、Diff 不可见（需求 v1.68）。

### 5.5 迁移

迁移脚本编译进后台服务，只向前。执行前用 `VACUUM INTO` 生成备份；失败则保持旧库不动并拒绝启动新版本，提示回退。

**协议主版本门**（T01 方案 3.7，产品负责人 2026-11-09 决定）：迁移只处理同一协议主版本内的表结构变化，不处理事件编码的破坏性变化。数据库 `meta` 表记 `protocol_major`；启动时与程序的主版本不符，先 `VACUUM INTO backups/` 备份，再拒绝启动，不迁移、不删除、不写库，客户端诊断页显示两个主版本号和备份路径。回退办法是装回旧主版本的程序，旧库原样可用。要带着数据升主版本，必须在升级前为这两个主版本写显式转换（覆盖事件信封 seq / at / actor / command_id、`commands` 幂等表、outbox、制品引用），并做无损演练（旧库 → 转换 → 新库 → 重建投影 → 与旧程序逐表比对），通过后才允许合入；没做到就只承诺「旧库保留、可回退旧程序」。

## 6 Agent 接入

后台服务只通过 AgentPort 说 ACP；接入选择规则（需求 8.2）：原生 ACP 优先；无原生 ACP 的由 iWork 自写适配器驱动用户本机 CLI；第三方翻译适配器只作可选。据此 M1 的 Claude Code 用 6.3 的自写适配器（已由 T0 实测确定，见 `t0-findings.md`）；6.2 的 claude-agent-acp 只作可选接法。

### 6.1 AgentPort

| 方法 | 作用 |
| --- | --- |
| `capabilities()` | 运行时能力：图片、文件引用、会话恢复、额度上报等（来自 ACP 初始化协商） |
| `open_session(spec)` | 按配置快照开会话：工作目录、模型、提示词、MCP、可恢复的旧会话 id |
| `prompt(session, blocks)` | 发送文字、图片、资源链接；返回更新流 |
| `cancel(session)` | 取消当前回合 |
| 回调 `on_permission(req)` | 运行时请求权限时调用，由审批引擎给出结果 |

实现用官方 ACP Rust SDK（`agent-client-protocol` crate）。厂商原始事件在适配层标准化为领域事件后才进入核心；原始事件只用于诊断，脱敏、限量。

### 6.2 可选接法：claude-agent-acp（不用于 M1）

1. 后台服务启动 `claude-agent-acp`（npm 包 `@agentclientprotocol/claude-agent-acp`，版本固定并写入运行时登记），经 stdio 说 ACP。
2. 登录：用户经 Claude Code 自己的登录流程登录本人订阅；iWork 不提供登录、不接触凭据。
3. 审批：适配器发出 ACP `session/request_permission`，由审批引擎判定。须补测确认用户的 auto 模式与放行规则不会让工具调用绕过该请求（Q7）。
4. 命令执行：客户端声明 `terminal` 与 `fs` 能力。若适配器把命令交给客户端终端执行，iWork 即可直接把命令放进沙箱；否则启用 Claude Code 自带的 Bash 沙箱（Q8）。
5. 任一项不满足且无法通过配置解决时，M1 改用 6.3 的自建桥接。

### 6.3 M1 接法：Claude Code 桥接（`iwork-bridge-claude`）

1. 后台服务启动桥接，经 stdin/stdout 说 ACP。
2. 桥接以非交互流式模式启动 CLI：`claude -p --input-format stream-json --output-format stream-json --verbose`，加上模型与思考强度（9.6）、追加系统提示、MCP 配置、`--resume <session_id>` 等参数。不修改 CLI、不读写其登录凭据。
3. 转换：ACP 的用户消息→CLI 输入流；CLI 的 `system/init`、`assistant`、工具结果、`result`→ACP `session/update`；`result` 里的用量上报为额度与用量事件。
4. 权限：桥接通过 `--settings` 注入一个 PreToolUse hook，每次工具调用前都会执行它；hook 经本机 socket 问桥接，桥接发 ACP `session/request_permission` 给后台服务。hook 在放行规则之前执行，所以用户在 Claude Code 里配过的放行规则不会跳过 iWork。hook 连不上桥接时一律拒绝（失败即关闭）。
   hook 与桥接之间的通道（防止伪造“允许”）：
   - 桥接先创建并绑定 socket，再启动 CLI；socket 路径已存在则中止，不复用、不删除他人的文件。
   - socket 放在数据目录 `run/` 下（目录权限 0700），每个会话随机文件名；Windows 用以 `FILE_FLAG_FIRST_PIPE_INSTANCE` 创建的命名管道，DACL 只允许当前用户。
   - 桥接为每个会话生成一次性令牌，与 socket 路径一起经环境变量交给 CLI，hook 继承后使用；令牌不落盘、不进日志。
   - 双向校验：hook 校验对端是同一用户、且进程号等于环境变量中给出的桥接进程号（macOS `LOCAL_PEERPID`，Linux `SO_PEERCRED`，Windows `GetNamedPipeServerProcessId`）；桥接校验令牌，并校验对端为同一用户。任一校验失败，hook 返回拒绝。
5. 取消：ACP `session/cancel` → 向 CLI 发中断；超过 3s 未结束则结束进程树。hook 超时防护（已实测 hook 超时即放行）：hook 的 timeout 设为允许的最大值，桥接在到时前主动中断回合并以拒绝返回，用户批准后用 --resume 续接。命令改写（已实测可用）：hook 返回 updatedInput，把 Bash 命令包进 iWork 沙箱执行器。

以上 CLI 参数与事件字段以实施时固定的 Claude Code 版本为准，写成兼容性测试；版本变化导致测试失败时，按 FR17 阻断该版本组合。

### 6.4 会话映射

- 项目对话：一个对话对应一条 CLI 会话线，跨回合用 `--resume` 续接。
- 助手私聊：界面上是一条连续长对话，底层按「助手 × 项目」（含“私聊”）各有一条 CLI 会话线。切换项目就切到该项目的会话线，工作目录、AGENTS.md 与审批规则随之切换。其他项目段的对话内容不带入新会话，避免跨项目串味。
- 回合（turn）= 一次 prompt 到结束；状态 `queued → running → (waiting_approval ↔ running) → completed | cancelled | failed | interrupted`。

### 6.5 进程监管

- 进程树管控：macOS/Linux 用进程组与 `killpg`；Windows 用 Job Object（关闭即结束全部子进程）。不会留下孤儿进程。
- 每 2s 采样各进程树的内存与 CPU，用于显示和性能基准；不用于业务判断。
- 运行时发现：在 PATH 与已知安装位置查找 `claude`，读取版本。登录状态用 `claude auth status`（JSON），只取 `loggedIn`、`authMethod`、`subscriptionType`、`loginExpiresAt`；未登录时打开 Claude Code 自己的登录流程。

## 7 审批引擎

每次工具调用先归一为一个“动作”，再按规则求值。结果固定为五种（需求第 9 章“安全规则的组织”，v1.52）：放行、询问、拒绝、亲手执行、沙箱外执行（询问的一种，批准后命令在沙箱外运行）；询问永不超时。

规则是数据：系统底线、必问清单、各档默认值、需凭据命令清单、会被自动执行的配置清单、敏感目录清单、可写缓存区、用户记住的规则，都是同一种规则条目（`id`、层级、匹配条件、结果、来源、范围）。内置规则集带版本号，随代码发布；新增规则只加条目或动作分类器，不改求值流程。审计记录命中的规则 `id` 与规则集版本（7.4）。

### 7.0 两道闸与沙箱固定配置

| 闸 | 管什么 | 和档位的关系 |
| --- | --- | --- |
| 沙箱（Claude Code 自带，配置由适配器生成，经 `--settings` 注入） | Bash 命令及其子进程 | **底线部分三档相同**；只写白名单在手动、自动档生效，全开档放开（v1.65） |
| 审批（本章） | 文件工具、命令文字、MCP 调用 | 档位只决定默认问不问 |

编排核心只产出抽象约束，适配器翻译为 Claude Code 设置项（需求第 9 章，v1.52）：

| 抽象约束 | Claude Code 设置项 |
| --- | --- |

Bash 命令用 shell 语法解析器拆成管道、子命令、重定向、变量展开位置，每个子命令单独归类，取最严的结果；解析不了的命令（如 `eval`、动态拼接）一律询问。需凭据命令清单按命令文字匹配，规则与 `excludedCommands` 一致：连起来的命令每一段都要匹配；带重定向、`cd`、`$(...)` 的不算清单内，仍在沙箱内运行。hook 的判定与写入 `excludedCommands` 的条目必须出自同一份清单、用同一套匹配规则（O1 第 ④ 项实测 Claude Code 的实际匹配行为）；两边结果可能不一致时（如匹配规则的边界情况），一律按“沙箱外执行”求值，宁可多问，不能让审批以为命令在沙箱内而直接放行。

### 7.2 求值顺序

1. **系统底线**（三档相同，命中即拒绝，不询问、不可提权；与需求第 9 章一致）：
   - 读写用户凭据目录：Agent 直接访问（工具读写、命令或重定向的目标路径落在凭据目录内）由审批拒绝；命令及其子进程的实际访问由沙箱挡住。需要凭据的程序走“沙箱外执行”。
   - 读写 iWork 数据目录：同上，两道闸都禁。只读区 `attachments/`、`imports/` 例外：可读、不可写（需求 v1.64、v1.68），供 Agent 读取仓库外附件与导入技能的参考文件和脚本。
   - 写入 `.git/` 内部：只能由审批拦 Agent 直接写文件（工具写入、重定向、rm / mv / cp 等目标落在 `.git/` 内）；git 命令本身照常执行。脚本直接写 `.git/` 为已知限制。
   - 删除关键路径：删除目标是需求第 9 章所列关键路径之一或其上级目录。
   - 非流程产生的受保护分支变更：**M1 已知缺口**，不实现监控；M2 起由 `watch_protected()` 事后发现，且成员改在独立工作区工作。
   - **亲手执行卡片**（需求第 9 章、AC36）：命中底线、且整条命令是单个简单命令（或单个文件补丁）时，拒绝的同时生成卡片；组合命令只拒绝。卡片不可记住，全开档也照样出现；不得提供任何让 Agent 自己确认的路径。实现见 7.2a。
2. **拒绝记忆**（需求 AC05，v1.58）：已被用户拒绝的同一动作（按“动作类型 + 目标”识别，与所用工具无关）在本对话内、直到用户发出下一条消息之前自动拒绝，跨回合与 `--resume` 续接都算；不生成亲手执行卡片。用户发出下一条消息后，该动作下一次被请求时**强制询问一次**：三档都适用，不受记住的放行规则影响，卡片与普通询问相同（不额外标注）。用户允许则执行并清除这条记忆，之后按正常规则求值；再次拒绝则重新进入自动拒绝。换一种写法达到同一效果为已知限制。
3. **工具配置与统一边界**：被助手工具配置禁用的工具一律拒绝，审批卡片上也不提供临时启用（需求 FR05）；写非本人工作区、读敏感目录清单的动作标记为越界。联网不构成越界。
4. **拒绝规则**：用户设的拒绝规则与项目拒绝规则，命中 → 拒绝。排在必问之前，保证“拒绝 > 询问 > 放行”（v1.58 修正）。
5. **必问**：命中必问清单 → 询问；不经 AI 审查，不受放行规则影响。全开档下只对 git push 生效（发布、写会被自动执行的配置、删除、丢弃改动在全开档放行）。
6. **放行规则**：用户记住的规则与项目放行规则，命中 → 放行。越界动作可被记住的放行规则放行；清单外的沙箱外执行不能记住，不受放行规则影响。
7. **默认**：7.1 表中当前档位那一列。越界与沙箱外执行在手动档询问、自动档先 AI 审查、全开档放行。

求值是纯函数，输入动作、规则快照与档位，可全量单元测试。档位只改变第 5 步的必问范围与第 7 步的默认值，记住的规则在各档下都生效；档位按「成员单独设置 > 主管对话设置 > 项目默认（手动，只能是手动或自动）」取值；全开只在当前对话生效，新对话回到默认；助手私聊不跟随 iWork 对话，按所选项目的默认档位，切换项目时全开失效，未选项目时为手动（需求 FR11）。自动档下结果为“询问”且原因是越界或沙箱外执行时，先交 AI 审查：一次独立的系统回合，**不开任何工具**，输入为动作、任务目标与最近上下文摘要，输出通过 / 不通过与理由；不通过、审查失败或超过 60 秒未给出结果，都转为询问用户（超时值可在项目设置中调整）。“必问”动作不经 AI 审查。由哪个运行时与模型承担 AI 审查，默认与 iWork 相同，可配置。

### 7.2a 亲手执行卡片的实现

分层（需求 7.2，v1.48 确认）：判定在编排核心，用户确认在应用服务，执行在基础设施，适配层只转发，客户端只展示与发命令。

1. **判定**（`iwork-core`）：hook 照常把工具调用交给后台服务。第 1 步底线命中、且整条命令是单个简单命令（或单个文件补丁）时，求值结果为“拒绝 + 亲手执行提议”；组合命令与拒绝记忆命中的动作只拒绝。提议包含：
   - 动作类型；
   - 精确内容，取自被拒的调用：Bash 取 `command` 与工作目录；Write / Edit 取目标路径与新旧内容，生成补丁；
   - 理由：取调用自带的说明（如 Bash 的 `description`），没有时写“Agent 未说明”；
   - 提议哈希。
   这是纯函数，进 T07 单元测试。
2. **等待**：卡片与审批共用等待登记（hook 保持等待、超时防护同 6.3），进“待你处理”计数，作废规则同 7.3 第 5 条。
3. **受理**（`iwork-app`）：
   - `ExecuteUserAction{card_id, proposal_hash}` 与 `DismissUserAction{card_id}` 只接受来自客户端连接的请求；桥接与 hook 的连接发来即拒绝，并记审计。
   - 执行前校验哈希与卡片一致、卡片未作废；审计主体为用户本人。
   - 两个命令都没有“记住”字段，核心里也不存在能放行底线动作的规则。
4. **执行**（`iwork-host`，ExecutionBackend）：
   - 由后台服务直接起进程，不经厂商 CLI、不带 hook、不进沙箱。
   - 工作目录为提议中的目录，环境为用户登录 shell 的环境，stdin 关闭；运行中可在卡片上停止。
   - 补丁由后台服务自己写文件（原子替换）。
5. **结果**：
   - 输出与退出码只进卡片，发给客户端，不写进运行时上下文。
   - 回给 Agent 的只有一句“用户已执行，退出码 N”，作为该次调用的拒绝原因返回，Agent 不会重试。
   - “忽略”时回给 Agent“用户未在 iWork 中执行”。
   - “复制命令”只是客户端剪贴板操作，卡片仍待处理。
   - **后台服务崩溃后的收尾**（做法 A，产品负责人 2026-11-09 决定，T01 方案 4.3）：崩溃时停在启动中、执行中、停止中的卡片，重启后一律转为「结果未知」。iWork 不判断进程是否还活着，也不从卡片停止崩溃前起的进程，绝不自动重跑，也不自动判为结束；Agent 收到「用户已执行，结果未知」。唯一出口是用户自己核对后点「我已核对」（`ConfirmUserActionEnded`）。删除对话碰上这种卡片时停在「删除中」，期间只受理收尾命令，用户确认后删除自动完成。**已知限制**：崩溃后 iWork 停不了那条命令，也不知道它跑完没有，由用户自己处理；没崩溃时经句柄停止与等待不受影响。
6. **M3 预留**：密钥注入的包装程序在厂商沙箱内运行，需要连后台服务的本地连接。届时由适配器在生成沙箱配置时放行（Claude 为 `allowUnixSockets`），M1 不做。

### 7.2b 会话工具集与系统回合（需求 FR05、FR11，v1.57）

每次启动 CLI 前，编排核心按会话类型算出本次可用的工具，适配器用 `--tools`（白名单）或 `--disallowedTools` 传入（以固定版本支持的参数为准，T06 实测），hook 对工具集之外的调用兜底拒绝：

| 会话类型 | 工具集 |
| --- | --- |
| 助手会话（项目对话、私聊） | 全部内置工具 − 7.1 永久禁用的工具 − 助手配置里关掉的分组（9.1a） |
| AGENTS.md 草稿（系统回合） | 只开“读文件与搜索” |
| AI 审查（系统回合） | 不开任何工具 |

系统回合是 iWork 自己发起的回合。规则：其中的工具调用不经 AI 审查、不询问用户；超出工具集的、以及在助手会话中本该询问的动作（如读敏感目录），一律拒绝（失败即关闭）。AI 审查不开工具，所以不会触发 hook，也就不会递归。以后新增的系统回合按同一规则定义自己的工具集。

### 7.2c 安全清单（需求 FR11、AC41，v1.65–1.66；能力 M1 完整实现，桌面界面待定）

三张清单都是规则条目，各由内置条目（随规则集版本发布，不可删除）与用户条目组成；用户条目带范围（全局 / 某个项目）。

| 清单 | 作用 | 用户条目的写法与校验 |
| --- | --- | --- |
| 需凭据的命令 | 写入 `excludedCommands`，命中的命令在沙箱外运行，按“沙箱外执行”审批 | 只能写“程序名 + 子命令”（如 `terraform apply`、`gh`），匹配规则同 7.1；程序名命中“拒收名单”（`bash`、`sh`、`zsh`、`python`、`python3`、`node`、`ruby`、`perl`、`env`、`xargs`、`make` 等，本身也是规则条目）时拒收并返回原因 |
| 敏感目录 | 读取判越界（7.1） | 绝对路径或 `~` 开头的路径；不能是当前项目的工作区或其上级 |
| 可写目录 | 写入 `allowWrite`（手动、自动档的白名单） | 绝对路径或 `~` 开头的路径；不能落在底线目录（凭据目录、iWork 数据目录）内，也不能是用户主目录本身或系统目录 |

- 命令：`AddSecurityListEntry{list, value, scope}`、`RemoveSecurityListEntry{id}`；查询：`ListSecurityLists`。校验在 `iwork-core`（纯函数），失败返回可读原因。
- 生效：对新启动的会话生效；正在进行的回合不变。增删写审计。
- 能力与界面分离（需求 7.2，v1.66）：命令、查询、校验与持久化在 M1 完整实现，经命令端到端验收；桌面客户端的界面待定，以后其他界面复用同一组命令。

### 7.3 询问流程

1. 回合进入 `waiting_approval`，对话里出现审批卡片，“待你处理”计数加一，并提醒用户：
   - macOS 上客户端的 Dock 角标随计数更新，出现新项时图标跳动（3.6 第 6 条）。
   - 系统通知由后台服务发（`Notifier` 端口，`iwork-host` 实现），客户端不发。发不发由后台按规则定：桌面客户端报了窗口在前台，并且正看着这个对话或“待你处理”页时不发；同一项只发一次；已经处理或作废的不发。拿不到系统的通知权限时只记日志（M1 在 macOS 上就是这种情况，Linux 上只记日志，见第 1 节已知缺口）。用户点通知后，后台记下是哪一项并把客户端叫到前台，客户端来问要打开什么；拿不到点的是哪一项时只提醒、不跳转。
   - 亲手执行卡片、AGENTS.md 草稿、继续卡片进“待你处理”时同样处理。
2. 选项：允许（可选记住范围：一次 / 本对话 / 本项目 / 永久，永久记在助手上；记住即生成规则，可在设置里查看与撤销，三档都生效）/ 拒绝。记住的匹配范围（需求 FR11，v1.61）：执行命令按程序名加子命令（`npm test` 带任何参数都算，`npm publish` 不算），写文件与读敏感目录按目标所在目录，MCP 与未归类工具按工具名；卡片的记住下拉里写明范围，如“本项目内 `npm test …` 不再问”。“必问”动作与清单外的沙箱外执行只有“允许一次”，不显示记住范围。沙箱外执行的卡片标明“将在沙箱外运行，命令带起的脚本也不受沙箱约束”。
3. 拒绝时，运行时收到“用户已拒绝，不要换方式重试”的说明；同一动作指纹在本对话内、直到用户发出下一条消息之前自动拒绝。
4. 没有超时；客户端不在线时请求保留，重新打开即可处理。运行时一侧有等待上限的（Claude Code hook），由适配器在到时前中断回合并以拒绝返回，用户批准后续接（见 6.3）。
5. 作废：所属回合或任务被取消、所属回合失败（需求 v1.70）、对话被删除、回合中断后用户选择不再继续时，待审批转为“已作废”（需求第 12 章）：卡片置灰、移出“待你处理”，运行时侧不再等待。hook 超时防护引起的中断不作废，审批继续等待，批准后经 `--resume` 续接；用户拒绝时回合保持「已中断」，对话里出「继续 / 放弃」卡片，点继续则把拒绝结果随续接告诉模型，点放弃则回合结束、其余待审批作废（产品负责人 2026-11-09 决定）。
6. 档位切换即时生效：切到更宽松的档位时，已弹出且在新档位下可直接放行的待审批自动放行，其余保留（例：手动切自动只放行边界内的；切到全开放行除 git push 以外的全部（亲手执行卡片不受档位切换影响，始终等你本人处理））。切到全开每次都弹确认；在 iWork 对话中切到全开时，确认框列出受影响的成员。

**已知限制**：以需求第 9 章“已知限制”清单为准，新增规则时同步登记。不支持沙箱的平台上沙箱不可用，界面须常驻提示“隔离不可用”。审批卡片对“执行脚本”类动作标注“审批看不到脚本内部”。

### 7.4 审计

每次求值写一条事件：动作、命中的规则与层、结果、决定人、耗时。放行也记录，便于事后查“它到底做了什么”。

## 8 工作区与版本控制

核心只依赖 VcsProvider；M1 只实现 git，读操作用进程内的 gitoxide（`gix`）求快，写操作调用本机 `git` 命令求正确（沿用用户的 hooks、凭据助手与配置）。

### 8.1 接口（M1 实现加粗）

| 方法 | 作用 | git 实现 |
| --- | --- | --- |
| **`detect(path)`** | 判断是否受版本控制，返回仓库根与共享目录 | gix；链接的工作树按 common dir 归到同一仓库 |
| **`init(path)`** | 初始化并首次提交 | `git init` + `git add -A` + `git commit` |
| **`clone(url, dest)`** | 克隆，带进度 | `git clone --progress`，解析进度输出 |
| **`baseline()`** | 当前基线版本 | gix 读 HEAD |
| **`status()` / `diff(range)`** | 显示改动 | gix |
| `create_workspace(base)` | 隔离工作区 | `git worktree add`（M2） |
| `snapshot()` | 提交或快照 | `git commit`（M2） |
| `merge(into)` / `conflicts()` | 合入与冲突检测 | `git merge`（M2） |
| `watch_protected()` | 受保护线变更监控 | 监听 refs（M2） |

接口以“能力”描述差异：不支持廉价隔离工作区的工具（如将来的 Perforce）在能力上声明，核心据此限制并行度，而不是在核心里写 git 特例。

`status()` / `diff()` 不执行仓库配置的外部过滤程序（需求 v1.71 已知限制）。需要外部过滤的文件不比内容，按暂存区记录的时间戳与大小判断：变了，或条目是 racy 的（文件修改时间不早于索引文件自身的时间戳；gix 默认按整秒比较），都列为「可能有改动，内容比较不支持」。所以这类文件和索引在同一秒内写入、之后索引没被重写时，提交干净后仍会显示「可能有改动」，直到下一次有 git 命令重写索引为止（产品负责人 2026-11-10 批准宁可多报，T08 第 5 轮）。

### 8.2 项目身份

- 首次添加时在仓库写 `.iwork/project.toml`（含项目 ID，ULID 文本，与其他实体 ID 同一格式；产品负责人 2026-11-09 决定）。此后以它识别项目，而不是路径。项目 ID 只属于本机这份工作副本：iWork 写 `project.toml` 时，同时在 `.iwork/.gitignore` 里忽略它（文件不存在就创建，已有就追加一行），不进 git。原因：它要是被提交，同一仓库的另一个克隆会带着重复的项目 ID，主键冲突，重新定位也会把历史串到别的克隆上（产品负责人 2026-11-09 决定）。万一仍碰到已登记的 ID 出现在另一个共享目录（比如用户强制提交了这个文件），添加时报 `PROJECT_ID_CONFLICT` 并写明冲突的 ID 与已登记项目的路径，不覆盖、不当成重新定位。
- 去重：按仓库共享目录的真实路径（解析符号链接、大小写规范化）判断；重复添加直接跳转到已有项目。
- 重新定位：启动与打开项目时检查路径；不存在则标为“找不到路径”。用户选择新位置后读取其 `project.toml`，项目 ID 一致才重新关联。

### 8.3 M1 的写入位置

已确认（Q1）：M1 成员直接在用户的工作副本里改文件，与直接用 Claude Code 一致，不由 iWork 提交或合入；独立工作区在 M2 多成员时启用。两种都经 VcsProvider，切换不影响其他设计。

## 9 M1 功能实现

四项功能都不引入新机制，只是前面各节的组合；唯一的不确定项是额度的数据来源。

### 9.0 删除对话（需求 FR18，v1.60）

- 只限项目对话；助手私聊 M1 不提供删除。
- 入口：侧栏对话右键 → 删除，弹确认框。
- 后台服务受理 `DeleteConversation`：
  1. 先按取消流程结束该对话正在运行的回合；
  2. 该对话的待审批、亲手执行卡片转为已作废；
  3. 删除对话、消息、附件引用与本对话记住的规则，写一条审计（审计本身保留）。
- 不改动任何代码文件。附件副本按附件区的引用计数清理。

### 9.0a 对话标题与重命名（需求 FR18，v1.75）

- 对话记录 `title` 与 `title_source`（`auto` / `user` / `fixed`）。
- 项目对话（`auto`）：发出首条消息前标题为空，界面显示“新对话”。首条用户消息落库时同一事务写入标题：取消息文本，换行与连续空白折叠为一个空格，按字符（字素簇）截取前 20 个，超出加“…”；文本为空（只有附件）时取第一个附件的文件名。之后不再自动变化。不调用 AI 生成标题。
- 重命名：后台服务受理 `RenameConversation{conversation_id, title}`，去掉首尾空白后长度 1–50 个字符，空标题拒绝；写入后 `title_source=user`，发 `ConversationRenamed` 事件，侧栏摘要随之更新。只限项目对话。
- 固定标题（`fixed`）：助手私聊取助手名（助手改名时随之变），成员子对话取成员角色名；`RenameConversation` 对它们返回“不可重命名”。
- 入口：侧栏项目对话右键菜单“打开 / 重命名 / 删除”；重命名为就地编辑，回车确认、Esc 取消。

### 9.1 助手私聊

- 对话类型 `assistant_dm`，每个助手一条。M1 没有团队，标题栏项目选择器列出全部项目 + “私聊”（M2 起只列助手加入的项目）。项目选择器的值记在对话上，每条消息记录发送时的 `context_project_id`，切换时生成“切换到 X”分隔事件。
- 选“私聊”时，工作目录为 `~/iWork/assistants/<助手名>/`（Windows `%USERPROFILE%\iWork\assistants\<助手名>\`），与项目默认目录 `~/iWork/projects/` 同属用户可见的 iWork 根目录，不在数据目录内（数据目录受系统底线保护，不可写）。目录在新建助手时按当时的名字创建并记入数据库，之后改名不移动；名字含路径不允许的字符时做替换，重名加序号。审批中的“工作区”即指它，任何仓库都算工作区外。
- 未读数：对话上记 `last_read_seq`；只有“发给用户的消息”与“待处理卡片”两类事件计数；客户端打开对话即发 `MarkRead`。

### 9.1a 助手管理（最小）

- 工具开关分组（与画布第 13 页一致）：

  | 分组 | 包含的工具 |

  | 读文件与搜索 | Read、Grep、Glob |
  | 编辑文件 | Edit、Write、NotebookEdit |
  | 执行命令 | Bash、读取后台命令输出、停止后台命令 |

- 删除（需求 FR05、AC40，v1.61；不提供停用）：入口在侧栏助手的右键菜单（打开对话 / 配置 / 删除；iWork 的菜单不含删除）。确认框写明不可撤销与私聊工作目录路径。`DeleteAssistant` 依次：取消该助手正在运行的回合，待审批与亲手执行卡片转为已作废；删除助手配置、私聊对话与记在它身上的永久规则；项目对话中它的消息保留，发送者显示名字加“（已删除）”（消息上保存发送时的名字快照）；私聊工作目录 `~/iWork/assistants/<名字>` 不删除；写一条审计。

### 9.2 附件

1. 客户端：拖入或选择的本机文件只传路径；粘贴的图片用 `Chunk` 上传。发送前已在客户端检查 20MB，后台服务再检查一次。
2. 后台服务：计算 sha256；位于当前项目仓库内的文件只记路径引用，其余复制进附件区 `attachments/`（只读区，Agent 可读、不可写；与存长日志、Diff 的 `artifacts/` 分开）。
3. 送达：图片 → ACP image 内容块（运行时声明不支持时只提示）；其他文件 → ACP resource\_link（绝对路径）。
3a. 凭据附件（需求 FR03、AC36，v1.47）：文件路径落在需求第 9 章凭据目录清单内时，后台服务返回“需确认”，客户端提示“文件内容将发送给模型厂商”，用户确认后附加：内容直接嵌入消息（文本内容块）发给运行时，存档副本放在数据目录的 `private/` 下（不在只读区，Agent 读不到）（v1.64）；私钥（文件名如 `id_rsa`、`id_ed25519`、`*.pem`、`*.key`，或内容含 `PRIVATE KEY` 头）一律拒绝附加，提示原因。凭据目录清单与系统底线共用同一份定义。
4. 审批联动：无需特殊处理。仓库内附件在工作区里；仓库外附件在只读区，读取放行（原“本回合只读许可”规则 v1.64 删除）。

### 9.3 添加项目

1. 入口：侧栏“项目 +”、拖入文件夹、首次引导。方式：打开本机文件夹、从 Git 克隆、新建项目（FR19）。
   - 新建与克隆的默认父目录为 `~/iWork/projects/`（Windows 为 `%USERPROFILE%\iWork\projects\`），存在全局设置里，可修改；每次添加时也可更换。目标目录已存在且非空时拒绝并提示。
   - 新建项目：创建目录 → `init`（git init + 首次提交，空仓库用 `--allow-empty`）→ 进入第 5 步；不生成 AGENTS.md 草稿（没有代码可读）。
2. `detect`：已是已知项目 → 跳转；不受版本控制 → 显示初始化提示，初始化前“添加”不可用。
3. 克隆：由后台服务执行，进度以事件推送；失败保留错误输出与重试。
4. AGENTS.md 草稿：由 iWork 跑一个系统回合，会话工具集只开“读文件与搜索”（7.2b），产出以卡片展示。用户确认后由后台服务写入文件，成员自己不写。
5. 写 `.iwork/project.toml`、登记项目、进入该项目新对话。

### 9.4 本机额度

- M1 只接 Claude Code；Codex 与 agy 显示“—”（M2 接入后，Codex 额度取自 app-server 的 account/rateLimits/read）。
- 确定可得的数据：每回合结束时 CLI 上报的用量（token 等），用于“本对话用量”。
- 费用：CLI 上报的 `costUSD` 是它按官方标价估算的（`costBasis: "list"`），订阅账号并不按它扣费。存储照原样记（`turns.cost_usd`），界面只在“本对话用量”的悬停里标“按官方标价估算”显示，标签本身只显示 token（`ui-m1.md` 2a 第 15 条）。为此本对话用量的视图数据要带上该运行时的登录方式（订阅 / API Key / 未知，取自探测时 `claude auth status` 的 `authMethod`、`subscriptionType`，只取这两个字段），以及“有回合缺少费用”的标记。
- 额度窗口：取自 CLI 输出的 rate\_limit\_event（窗口类型、使用率、重置时间，见第 12 节 Q3），写入 quota\_snapshots；上报了哪些窗口就显示哪些。只用 CLI 公开输出的数据，不读凭据、不自行调用厂商接口；拿不到就显示“—”。

### 9.5 配置隔离与本机导入

1. 隔离方式（需求 8.4）：已由 `tools/t0/iwork-t0f.py` 实测确定，**M1 采用参数屏蔽**（结果见 `t0-findings.md` 2.2a）：
   - **参数屏蔽**（优先）：`--setting-sources` 排除 user、project、local 三类（需求 8.4，v1.63；具体写法如传空值，O1 实测）、`--strict-mcp-config` + `--mcp-config <iWork 生成>`、`--settings <iWork 生成>`；导入的插件与技能经 `--plugin-dir` 按会话加载。沿用用户已有的登录。
   - ~~专用配置目录~~（不采用：实测需要用户重新登录）：每家厂商一个 iWork 专用目录（Claude 为 `CLAUDE_CONFIG_DIR`），放在 iWork 数据目录下，所有成员共用；用户在 iWork 里经厂商流程登录一次；导入的技能与插件写入该目录。
   - 照常加载：Claude Code 自带的内置技能与插件；仓库内的 `CLAUDE.md`、技能与子代理定义（只是说明，动作照常经审批）。
   - **不加载**（需求 8.4，v1.63，推翻 v1.44 的项目级设置部分）：仓库内的 `.claude/settings.json`、`.claude/settings.local.json`（及其中的 hook、权限、沙箱配置）。理由：仓库自带的 hook 会在会话启动时不经审批、不在沙箱内执行；项目设置可能放宽沙箱，或用“关闭全部 hook”把 iWork 注入的审批 hook 一起关掉。仓库里有意提交的 hook（如自动格式化）在 iWork 中不生效。若 O1 实测发现参数无法完全排除项目级设置，停下交产品负责人决定。
   - 选择标准：用户 hook、用户权限模式、未导入的 MCP / 技能 / 插件、全局 CLAUDE.md 都不进入会话；iWork 注入的 hook 与 MCP 生效；导入的技能与插件能按会话加载。参数屏蔽全部满足则用它，否则用专用配置目录。
2. 发现：读取用户本机该 CLI 的配置，列出 MCP 服务器（名称、启动方式，不读取其中的密钥值）、技能（名称、描述、来源目录）、插件（只取其中的技能与 MCP）。用户自己的 hook 与权限模式不列出、不导入。
3. 时机：每家运行时首次接入时提示一次（M1 只有 Claude Code）；记录“已提示”，之后不再提示。设置 › 运行时 › “从本机导入” 可随时再次打开，不弹窗、不显示红点。
4. 导入：用户勾选后，后台服务把技能与插件复制进 iWork 管理的目录（数据目录下 `imports/<厂商>/`，只读区：Agent 可读与执行其中的参考文件和脚本，不能修改），MCP 配置写入数据库；MCP 需要的密钥由用户在 iWork 里重新填写，存系统钥匙串，数据库只存引用。M1 导入的内容对全部助手与项目生效，M3 起按助手与项目控制。
5. 启动会话时，按上面选定的隔离方式把导入的 MCP、技能、插件与 iWork 自己的 hook、协作 MCP 一起显式提供给 CLI。

### 9.6 模型与思考强度（需求 FR03、FR05、FR17、AC37，v1.49）

1. 三级：运行时 → 模型 → 思考强度。助手配置里是默认值（记在助手版本里）；对话可以临时改选模型与思考强度，存在 `conversations` 的覆盖字段上，只对本对话有效，新对话回到助手默认。iWork 的默认值取项目默认（FR04）。
2. 对话开始后运行时固定。客户端菜单里运行时一节在对话开始后置灰，悬停提示“要换运行时请开新对话”；后台服务也拒绝对已开始对话更换运行时的命令。
3. 改选模型或思考强度：下一轮生效，正在进行的一轮不受影响；对话中插入一条系统记录“已切换为 X”。不额外提示用量变化（产品负责人决定）。
4. 每一轮在 `turns` 上记下实际使用的模型与思考强度：取 CLI `system/init` 里报告的模型，与请求的不一致时以 CLI 报告为准，并记一条警告日志。
5. 模型列表：优先从 CLI 取可用模型；取不到时用适配器内置的别名表（Claude Code：opus、sonnet、haiku），另可手填模型 ID。思考强度的可选值也由适配器提供，运行时不支持时界面不显示这一项。
6. 每次启动或续接会话都显式传模型参数。配置隔离之后，用户在 Claude Code 里自设的默认模型不会生效，所以不传就等于用 CLI 内置默认，不允许出现这种“不知道在用哪个”的状态。
7. 模型不可用（无权限、已下线、过载）：该轮以错误结束，错误码区分这三种原因，界面提示改选；不设备用模型，不自动换用其他模型（产品负责人决定）。
8. AI 审查：项目设置里可选承担 AI 审查的运行时与模型，默认与 iWork 相同（需求 FR11）。
9. 接法（CLI 参数、中途换模型的方式、思考强度参数）在 T06 实测确定，见任务说明 O10。

### 9.7 轻松元素（需求 FR22，v1.56）

1. 头像表情由成员状态决定，后台服务随 `ViewPatch` 下发：空闲、工作中（回合进行中）、等你（有待审批或亲手执行卡片）、完成（回合正常结束后保持数秒，再回到空闲）、出错（最近一个回合失败且没有等你处理的事，新回合开始后换回；2026-11-11 加，素材 `*-sorry.svg`，见 `ui-m1.md` 2a 第 13 条）；2026-11-12 加：疑惑（有待回答卡片）、没电（该助手所用运行时的额度耗尽且没有进行中的回合）、瞌睡（空闲超过 30 分钟）。冲突时按 等你 > 疑惑 > 工作中 > 没电 > 出错 > 完成 > 瞌睡 > 空闲 只下发一个（见 `ui-m1.md` 2a 第 14 条）。彩蛋表情（思考、惊讶、喜欢、得意、害羞）M1 不下发。网页层只按状态切换图形与动画。
2. “搞定”印章：编排核心在回合结束时判断，条件是回合正常结束（不是出错、取消或作废），而且本回合产生了改动（Diff 非空）。满足时在该回合的改动摘要事件上带 `celebrate: true`，网页层据此盖章。不解析测试输出，不判断“测试全过”。
3. 设置项 `playful_ui`（默认开）：关闭后不盖章、头像不浮动、不弹“嗨”气泡、侧栏眼睛不跟随，表情仍随状态变化。系统开启“减少动态效果”时，动画一律停用。
4. 审批、越界、拒绝、亲手执行卡片与确认框上，不出现任何轻松元素。
5. 经验条、成就卡、小队小结暂不做（产品负责人 2026-11-09 决定）。画布上的“LV 7”与成就卡只作远期参考，M1 侧栏不渲染。

## 10 性能、测试、可观测性与错误处理

性能与正确性都靠一个可控的“假运行时”来测：它说 ACP，按脚本产生文字、工具调用与权限请求，让 CI 不依赖任何厂商就能跑完全部基准与故障测试。

### 10.1 M1 进入 CI 的基准（阈值见需求文档第 14 章）

| 基准 | 场景 | 量什么 |
| --- | --- | --- |
| 流式输出延迟 | 4 / 16 个假成员各以 100 片段/秒输出 | 后台收到 → 客户端 Rust 侧收到的 P50/P95/P99 |
| 唤醒延迟 | 审批通过 → 成员恢复运行 | 不含假运行时自身耗时 |
| 启动与恢复 | 冷启动；客户端重连并补发 1 万条事件 | 时长 |
| 写入 | 组提交下每秒命令数；单命令延迟 | P95 |
| 内存与 CPU | 空闲 10 分钟；4 成员连续 8 小时（夜间任务） | RSS 峰值与增长率、空闲 CPU |

超阈值记为回归并在审查页标出，不阻止合入（与需求文档一致）。界面帧时与输入延迟基准在 M2 加入。

### 10.2 正确性测试

- **纯逻辑**：状态机与审批求值无 I/O，用属性测试（proptest）生成大量动作与规则组合，验证“结果不会比任何一层更宽”。
- **故障注入**：在写入、推送、审批等待的任意点杀掉桥接或后台服务，重启后验证：无重复执行、无丢失事件、待审批仍在、回合正确标为中断。
- **协议兼容**：旧版客户端 × 新版后台服务的握手与字段兼容测试。
- **Claude Code 兼容**：对固定版本的真实 CLI 跑一组录制的会话，版本变化时重跑。

### 10.3 可观测性

用 `tracing` 输出结构化日志到 `logs/`，按大小滚动；每个命令、回合、审批一个 span，带 `command_id` / `turn_id` 串联。只存本机、不上报。设置里可导出脱敏诊断包。

### 10.4 错误处理

- 协议错误统一为 `{code, message, retryable, details}`，错误码定义在 Protobuf 里，客户端按码显示与重试。
- 后台服务内每个长期任务在监督器下运行，单个任务 panic 只重启该任务并记录；存储层不可恢复错误时整体退出，由拉起方重启并走崩溃恢复。
