# 开发者：项目补充要求

> 只写本项目特有的约定、背景、边界和验收规则。通用职责由 CAO profile 提供。

## 项目背景

iWork：本机运行的 ADE（Agent Development Environment），Rust daemon + Tauri/SolidJS 客户端，当前阶段 M1。依据文档、技术栈、命令、架构约定与安全不变量见根目录 `AGENTS.md`；M1 进度与未落文档的决定见 `docs/tasks/M1/STATUS.md`。

## 必须遵守

- 开工前读任务卡、`AGENTS.md`、卡片列出的文档章节；有方案的按方案实施。
- 交付必须带测试：卡片“验收标准”的每一条都要有对应的自动化测试或可复现的检查命令，并在实现报告里逐条给出命令与结果。
- 状态机、审批求值、协议编解码写纯函数并配属性测试（proptest）。
- 不手改生成代码；不提交凭据、日志样本中的个人信息（邮箱、token、绝对家目录路径请脱敏）。
- 设计在实现中行不通，或发现文档自相矛盾：停下并汇报 supervisor，附证据和可选方案，不要自行选择。
- 动到热路径（事件推送、帧合并、存储写入、hook）附基准前后对比。
- 状态多、有并发或乱序的代码（时间线与翻页、取消与停机、会话与连接、重连与快照、多路在飞查询），动手前先写一个随机交错的属性测试：把所有会发生的操作任意混合，每一步之后断言全部不变量（来自方案的不变量表或 R 规则）。交付前证明它有牙：在一个副本里埋一个已知缺陷（或在出过问题的旧提交上跑），测试必须抓住，回报里附缩出来的最小序列。（2026-11-12 起，依据 T09 2b 连续四轮都是新状态带出的交错问题）
- 回报修复时写明「这次修复新加了哪些状态、等待点或缓存」，逐项对照方案的不变量，说明为什么不会破坏别的规则；同一类问题的其他实例查全，查过哪些写出来。只修 reviewer 点名的反例不算修完。
- 变异测试的判定：只有出现失败的测试（FAILED / panicked）才算抓住；构建失败、超时单列为无效或待查，不计入抓住。变异脚本让每次运行自成进程组，结束或超时后整组收掉，不留子孙进程；每项单独套重测试锁。
