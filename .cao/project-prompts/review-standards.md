# 项目审查标准

只报告有证据、可能影响正确性、安全、数据完整性、验收结果或后续修改的问题。

## 严重度

每条 finding 标两样：**严重度**，说有多严重；**出处**，说是不是本次改动引入的（记账字段 `introduced_by_change`，`true` / `false`，必填）。两样互不影响：改动前就有的问题照样标真实严重度。

- `blocking`：会造成错误行为、安全问题、数据损坏，或验收条件不通过。未处理前不能汇报通过。
- `important`：不一定马上出错，但必须修，除非用户明确接受风险。哪些情况算这一级见下文。
- `nit`：建议项，不改也不影响正确性和后续修改。

拿不准时：会让用户或数据出错的是 `blocking`；会让下次修改出问题、或违反写明规则的是 `important`。

本次引入的 `blocking` / `important` 进修复循环，没处理完不能汇报通过。改动前就有的 `blocking` / `important` 不挡本次通过，但也不能就这么放着：supervisor 会单独列给用户决定这次修、另开任务还是不改。所以严重度要照实标，影响要按「finding 怎么写」追到最坏的那处。`nit` 不用关。

## 分级细则

以下两类按 `important` 报：本次改动用 `as any`、`@ts-ignore`、`# type: ignore`、`eslint-disable` 之类压掉报错，且项目规范没有允许；本次新增的测试在被测函数都返回空值时仍能通过，等于没验证行为。

代码质量按「有没有明文规则、有没有具体后果」分级：

- 按 `important` 报：本次改动违反了项目写明的规则（`AGENTS.md`、`.cao/project-prompts/`、`.cao/agent-store/developer.md` 里的「通用编码要求」），并且能指出具体后果。例如把已有的事实或规则另抄一份、以后两份会对不上；依赖方向反了；错误被静默吞掉；再加一种同类东西要改好几处；关键逻辑没有任何验证。
- 只报 `nit`：命名、注释、格式、不影响后续修改的写法差异，以及本次没要求的顺手清理。
- 每条质量类 finding 都写明违反的是哪条规则、不改会让下次修改出什么问题；说不出后果的按 `nit` 报。

## finding 怎么写

- 结果开头先写共几条 finding；没有需要修改的问题就直接说没有，写 `findings: []`。
- 每条写明：ID（记账后用账本给的完整 ID，见下文「记账」）、严重度、把握程度、文件行号或复现步骤、出错场景、证据、影响、是否由本次改动引入、最小修复建议。各审查角色还会要求补充自己的字段。
- 出错场景写清什么输入或状态、得到什么错误结果；说不出场景的不按 bug 报。
- 影响按最坏的那处写：出错的值或规则会流到哪些地方，在哪里造成的后果最大，就写哪里。问题被另一道检查挡着（CI 规则、校验、权限、发布流程），不能拿「会被挡住」当影响，要写清漏过这道门会怎样，再写这道门靠不靠得住。例如版本清单接受了预发布版本号，版本匹配又不排除预发布版，所有项目自动选版时都会选中它；只写「会被 CI 的 tag 规则挡住」，就看不出这个影响是全量的。
- 把握程度二选一，写成 `confirmed` 或 `plausible`：`confirmed`（确认）是能说出触发条件和错误结果，并引用代码行或截图；`plausible`（可能）是机制成立、触发条件不确定，写明怎样能确认。
- 写明这是哪一类问题，并列出找到的其他同类位置，方便 developer 一次改全。

## 记账

每次审查都记进项目的审查账本（`.cao/metrics/`）。supervisor 靠它关 finding，指标也从它算。

- 任务 ID 和轮次写在 supervisor 的派活消息里。没给就先用 `send_message` 问 supervisor，不要自己编。
- 审方案和审 diff 分开记账：审方案的任务 ID 是原任务 ID 加 `-plan` 后缀（如 `2026-11-03-login-hint-plan`），轮次单独从 1 起。任务 ID 最长 64 个字符，所以要先审方案的任务，起原任务 ID 时不超过 59 个字符，给 `-plan` 留位置。
- 给 supervisor 发汇报之前，先运行 `agent-scaffold findings add --task <任务> --round <轮次> --role <你的角色>`，从 stdin 喂一个 JSON 数组，一项一条 finding。键名对应上面写 finding 的字段：`ref`（你自己的编号）、`severity`、`confidence`（`confirmed` / `plausible`）、`category`（问题类别）、`location`（文件:行）、`title`、`failure_scenario`、`introduced_by_change`（`true` / `false`）、`evidence`、`impact`、`suggestion`。`severity` 到 `introduced_by_change` 这七个必填，多出别的键会报错。例如：

  ```sh
  echo '[{"ref":"CR-1","severity":"important","confidence":"confirmed","category":"边界条件","location":"src/cart.js:40",
    "title":"空购物车时越界","failure_scenario":"传入 [] 时读 items[0] 得到 undefined 并抛错","evidence":"cart.js:40 没有判空","introduced_by_change":true}]' \
    | agent-scaffold findings add --task feature/cart --round 1 --role code_reviewer
  ```

- 没有 finding 也要跑一次，数组写 `[]`。
- 命令给每条打印完整 ID `<任务>/<轮次>/F-<n>`。把这些 ID 写进汇报，supervisor 关 finding 时用的就是它们。
- 复审时新发现的问题算新一轮：`--round` 加 1。这一轮记完后又发现新问题，加 `--append` 补记；同一轮重跑别加。
- 命令报错就按报错改了再跑。只通过这条命令写账本，不要直接编辑 `.cao/metrics/` 下的文件。

supervisor 给每条 `blocking` / `important` 定一个结局：

| 结局 | 含义 |
|---|---|
| `fixed` | 成立，已经修了 |
| `refuted` | 不成立：看错了，代码不是这么写的，或者别处已经处理 |
| `intentional` | 代码这么写是需求或开发方的决定。报出来没有错，不算判错，也不算噪音 |
| `not_worth` | 成立，但永远不值得改；这次不管、以后要管的记 `pre_existing` |
| `pre_existing` | 成立、改动前就有，用户决定另开任务处理。不算噪音。supervisor 照用户的决定记，理由引用用户的话 |

精确率只看 `fixed` 和 `refuted`，噪音只看 `refuted` 和 `not_worth`，漏报另外记。改动前就有的 `blocking` / `important` 同样进指标。宁可多报，不能漏报：有证据但拿不准的照样报，标 `plausible`。

## 方案

这三类任务要先出方案、审过再实施：跨模块的；会成为后续范例的；发布、运维这类一出事就影响所有人的。写方案的人（architect，或者没有 architect 时的 developer）照这一节写，审方案的人照这一节审。

方案写成文件，审方案的人才拿得到：交互派活时写进 `docs/plans/`（项目另有约定就按约定），汇报里给出路径。在 CAO workflow 步骤里不写这个文件，方案只写进 workflow 指定的结果文件。

### 方案要写什么

现状与约束、做法、涉及的文件和接口、分步计划之外，再写两样：

- **每条规则（约束）写成「目的 + 手段」**：先说它要防什么，再说怎么做到。例如「不让用户装到没测过的包（目的）：只有跑完集成测试的构建能发布（手段）」。只写手段，后来的人分不清能不能改它，审的人也看不出它和别的规则叠在一起还守不守得住目的。
- **出事场景**：上线后可能出的每一种事，都写清三件事：
  - 会出什么事：什么输入、状态或操作下出错，谁受影响。
  - 怎么止血和回退：发现后第一步做什么，怎么退回到上一个好的状态。撤回、回退、降级这些紧急路径要真的走得通，不能被方案里别的规则挡住。
  - 由什么保证：哪条测试或哪次演练证明止血和回退走得通。还没有的写「待补」，排进分步计划。

### 怎么审方案

方案本身也是审查对象，不只是审代码时拿来对照的标准。只问「跟现有规则一致吗」，查不出规则本身的错。

1. 推演出事场景：方案列出的每一种走一遍，再补上它没列的，尤其是几条规则叠在一起才会出现的。
2. 拿每条规则的目的检查它的手段：这个手段在所有场景下都守得住目的吗？会不会妨碍别的规则的目的？只有手段、说不出目的的规则，先要求写出目的。
3. 专门走一遍紧急路径：假设刚发出去的东西有问题，要回退、撤回或降级，按方案的规则一步步做，看会不会被哪条规则卡住。例如「开关只能由发布流程改」会不会让线上出事时没法手动关掉它。
4. 看每个出事场景有没有测试或演练兜底；写了「待补」却没排进计划的，按 finding 报。

问题照上文写成 finding，照「记账」一节记账。照方案实施会让用户或数据出错的报 `blocking`；缺目的、缺出事场景、出事后没有走得通的止血和回退办法，报 `important`。审代码时发现问题出在方案的规则上，同样报，写明要先改方案。

## 复审

只检查新 diff 和仍开放的 finding，不重复已关闭的问题。

UI 审查按主管给的依据、项目规范和定稿、现有页面、设计原则判断，优先级依次降低。功能审查只按验收条件检查行为、数据和边界。证据不足时说明不确定点，不要推测。

## 跑命令和测试

所有角色跑命令和测试都照这一节，developer 也一样。下面分原工作区和临时验证副本两处说。

### 原工作区

- 为了查看或验证跑的命令，不改原工作区的任何文件。被 Git 忽略、但会影响之后行为的本地状态也算：锁文件、依赖目录、本地配置。有些命令看着只是检查，实际上会重写它们，例如 `bundle check` 会重写被忽略的锁文件。测试顺带写出的缓存不在此列。developer 改本任务要改的文件不受这条限制。
- 拿不准一条命令会不会写这些，或者验证要解包、打补丁、装依赖，都到临时验证副本里做。
- 工作区里有别人没提交的改动（`git status` 里有不属于本任务的文件）时，不在原工作区跑测试，到临时验证副本里跑。汇报写上原工作区跑前跑后的 `git status`，证明跑测试没往里面写东西。

### 临时验证副本

副本用 `mktemp -d` 建在 TMPDIR 指的临时目录里（没设就是 `/tmp`；TMPDIR 指到自己的 scratchpad 时就在 scratchpad 里），不放在仓库目录里，用 `git archive` 导出（不碰原仓库的 `.git`）。副本里可以解包、打补丁、装依赖、跑测试、写测试产物，用完删掉。CAO workflow 步骤里不往原仓库新增文件的限制照旧。照下面的步骤在原工作区的根目录里敲，用 bash 运行；路径带空格时在数组里分别加引号。整段的退出码就是结果：核对不一致、装依赖失败都会中途停下并返回非零，测试失败时照样打出跑后的 `git status`，再返回测试的退出码；副本不管成败都会删掉。

```bash
set -euo pipefail
git status --short                      # 跑前，写进汇报
# 本任务的文件清单：改的、新增的、删掉的都算，重命名的新旧两个路径都算
FILES=(<本任务的文件…>)
NEW_UNTRACKED=(<清单里还没被 Git 跟踪的新文件…>)
C=$(mktemp -d "${TMPDIR:-/tmp}/verify.XXXXXX")
trap 'rm -rf "$C"' EXIT
git archive HEAD | tar -x -C "$C"
# 已暂存和未暂存的改动按路径打进去；--binary 才带得上二进制文件，删除和重命名也在这份补丁里
# 清单里只有还没被跟踪的新文件时补丁是空的，git apply 会报错，所以先判断有没有改动
git diff --quiet HEAD -- "${FILES[@]}" || git diff HEAD --binary -- "${FILES[@]}" | (cd "$C" && git apply)
# 数组可能为空，这样写 macOS 自带的 bash 3.2 在 set -u 下也不报错
for f in ${NEW_UNTRACKED[@]+"${NEW_UNTRACKED[@]}"}; do mkdir -p "$C/$(dirname "$f")" && cp -p "$f" "$C/$f"; done
# 核对：工作区里有的文件逐个 cmp，工作区里已经删掉的，副本里也不能有；有一处不对就停
bad=0
for f in "${FILES[@]}"; do
  if [ -e "$f" ]; then
    cmp -s "$f" "$C/$f" || { echo "不一致：$f"; bad=1; }
  elif [ -e "$C/$f" ]; then
    echo "副本里多了：$f"; bad=1
  fi
done
[ "$bad" -eq 0 ] || exit 1
# 先建受控环境，再在同一个环境里装依赖、跑测试
mkdir -p "$C/.verify-home"
run() { (cd "$C" && env -i HOME="$C/.verify-home" PATH="<要用的工具所在目录>:/usr/bin:/bin" "$@"); }
run <项目声明的安装命令，例如 npm ci>
result=0
run <项目声明的测试命令，例如 npm test> || result=$?
git status --short                      # 跑后，写进汇报，和跑前一致
exit "$result"
```

- 文件清单只放本任务的文件。不加路径的 `git diff` 会把别人改了一半的文件一起带进去。核对时有任何一行输出，就先查清再跑。
- 本任务的改动和别人的改动在同一个文件里分不开时，不硬跑：停下来请 supervisor 安排先后，supervisor 自己碰到时让这两件事串行。
- 运行环境一定要在装依赖之前就隔离好。只换目录，子进程照样继承父进程注入的环境变量和工具搜索路径：在 `bundle exec` 下起的进程会把 `BUNDLER_SETUP` 传下去，带着 `BUNDLE_GEMFILE` 时，在副本里跑 `bundle install` 照样会写回原项目的锁文件。`env -i` 把这些都清掉，HOME 指进副本后，包管理器的缓存也落在副本里。安装目录也要在副本里：npm 的 `node_modules` 本来就在项目里，默认装到全局的（例如 Bundler）在 `run` 里加上装进副本的变量，如 `BUNDLE_PATH=vendor/bundle`。
- 做不到这样隔离（离线装不上依赖、工具只能从全局找），就不装、不跑，汇报里写明「没验证本机状态依赖」，不能拿「换了目录」当证据。
- 汇报里写明这次是在副本里跑的，附上跑前跑后的 `git status --short` 和核对结果。
